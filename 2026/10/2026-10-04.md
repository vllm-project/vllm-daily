  - `tests/v1/worker/test_gpu_worker.py`
  - `vllm/v1/worker/gpu_worker.py`

### Summary

**What changed and why**  
The PR wraps both GPU memory-profiling profile_run() call sites in Worker.determine_available_memory with set_current_vllm_config(self.vllm_config), so the active vLLM config is available during profiling. This fixes a ROCm sparse-MLA indexer regression where, without config context, the decode-logits workspace sizing fell back to max_num_batched_tokens (32768) instead of max_num_seqs*(1+num_speculative_tokens), causing a 128 GiB allocation failure at 1M context. A parametrized regression test verifies the config context is set and torn down correctly and that randomize_inputs still propagates.

**Technical impact**  
Behavioral change in the V1 GPU worker startup path: profile_run now executes inside a config context manager, allowing downstream components (e.g., ROCm sparse-MLA indexer) to read scheduler_config and speculative_config during memory profiling. The kv_cache_memory_bytes branch and the general profiling branch both gain the context, and the existing _scoped_allocator_max_split context is preserved. The test asserts the context is None before and after, confirming proper scoping without leakage.

**Potential risks**  
The change alters global/thread-local config state during profiling; if profile_run or its callees spawn threads or rely on a different config, behavior could shift subtly. The regression test uses SimpleNamespace mocks and monkeypatches, so it validates the context wiring rather than real ROCm kernel behavior, and the author notes no AMD GPU run was performed on the rebased PR. There is also a minor risk of interaction with the upstream randomize_inputs argument if future refactors change the call signature.

**Key insights**  
The root cause is a missing config context during memory profiling, not the profiling logic itself, and the fix is a minimal, well-scoped context-manager wrap at both call sites. The test cleverly asserts both the corrected row count (16*6=96 vs 32768) and context cleanup, guarding against regressions. Validation is limited to CPU tests and historical MI300X results for an equivalent local patch, so AMD CI confirmation remains outstanding.

## 2. [[Bugfix][Attention] Support int4_per_token_head on non-power-of-two head sizes](https://github.com/vllm-project/vllm/pull/56198)


### Base Information

- **PR Number:** #56198
- **Author:** [LiRunGuo](https://github.com/LiRunGuo)
- **Merged By:** [mgoin](https://github.com/mgoin)
- **Merged time:** 2026-10-04 21:52:39
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/56198/files) (2):**
  - `tests/kernels/attention/test_attention_selector.py`
  - `vllm/v1/attention/ops/int4_per_token_head.py`

### Summary

**What changed and why**  
The PR fixes a bug where --kv-cache-dtype int4_per_token_head was accepted for any head size but the Hadamard rotation in the write path asserted power-of-two dimensions, causing engine initialization to abort for models like Phi-3-mini (head_size=96). It changes single_rht to apply the transform block-diagonally using the largest power-of-two divisor b of the head size, and updates unified_attention_int4 to scale softmax_scale and the inverse output by b instead of head_size. A parametrized unit test verifies backend selection for several head sizes including non-power-of-two ones.

**Technical impact**  
Enables int4_per_token_head KV cache for models with non-power-of-two head sizes without changing cache layout or adding padding, while preserving the exact previous code path for power-of-two head sizes (b == d). The math is adjusted so the forward/inverse RHT norm sqrt(b) is correctly compensated, keeping numerics consistent with the existing power-of-two case. The change is localized to the INT4-specific wrapper and attention kernel, leaving fast_hadamard_transform's power-of-two contract intact for other callers.

**Potential risks**  
The block-diagonal transform changes the effective rotation for non-power-of-two head sizes, which could subtly affect quantization accuracy; the PR reports gsm8k results showing a small int4 degradation comparable to int8, but broader model coverage is not demonstrated. The scaling change from head_size to b must be correct for all paths, and any other caller relying on the old norm assumption could be affected. The new test only checks backend selection, not numerical correctness of the transform, and the reported test run had 13 unrelated errors from missing MLA-sparse backends.

**Key insights**  
The fix is mathematically sound: for d = b * n, applying H_b block-diagonally yields an orthogonal transform with H @ H.T = b * I, so the norm is sqrt(b) and the existing 1/head_size factors must become 1/b. The PR is well-scoped, includes reproduction and benchmark evidence, and explicitly notes the int4 throughput trade-off rather than claiming a win. The main residual risk is limited numerical validation across diverse models, though the unchanged 128 path shows comparable error magnitude.

## 4. [[Bugfix][KV Offload] Reset SimpleCPU eager-store placement state on MRV2 resume](https://github.com/vllm-project/vllm/pull/57816)


### Base Information

- **PR Number:** #57816
- **Author:** [kamb-code](https://github.com/kamb-code)
- **Merged By:** [ivanium](https://github.com/ivanium)
- **Merged time:** 2026-10-04 19:00:08
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/57816/files) (2):**
  - `tests/v1/simple_kv_offload/test_scheduler.py`
  - `vllm/v1/simple_kv_offload/manager.py`

### Summary

**What changed and why**  
Fixes a bug in SimpleCPU eager KV offload where, under MRV2, a preempted and resumed request kept its stale accumulated GPU block table and per-group store cursors, causing the resumed tail block to be missed during offload scheduling. The fix resets the retained block table and cursors directly from the scheduler's authoritative preempted_req_ids set before consuming resumed placement data, unifying the MRV1 and MRV2 reset paths. A parametrized regression test covers MRV1/MRV2 and delayed/same-output preemption scenarios.

**Technical impact**  
Changes eager-store bookkeeping in vllm/v1/simple_kv_offload/manager.py so preemption resets occur from preempted_req_ids rather than the per-request yield_req_data preempted flag. This restores correct offload scheduling for MRV2 NewRequestData resumes and MRV1 resumed-cached requests through the same reset site. Lazy mode, cache lookup, and eviction policy are explicitly untouched.

**Potential risks**  
The reset now relies on preempted_req_ids being populated correctly by the scheduler; if a runner reports preemption through a different channel, the reset could be missed. Resetting state for any preempted req_id present in _reqs_to_store could also clear state for requests that are not actually being resumed in the same output, though the subsequent yield_req_data loop only repopulates resumed entries. Test coverage is limited to CPU runs and the specific SimpleCPU scheduler path.

**Key insights**  
The root cause is a representation mismatch: MRV2 reports preemption via SchedulerOutput.preempted_req_ids while the resumed request arrives as complete NewRequestData without a preempted flag, so the old per-yield-entry reset never fired. Moving the reset to the authoritative preempted_req_ids set before processing placement data makes both MRV1 and MRV2 resume paths consistent. The PR description is unusually thorough, including negative test results on upstream main and a duplicate-PR search.

## 6. [[Bugfix][DSv4.1] Keep the compressor ring out of the null block](https://github.com/vllm-project/vllm/pull/58560)


### Base Information

- **PR Number:** #58560
- **Author:** [bluemelov1](https://github.com/bluemelov1)
- **Merged By:** [ivanium](https://github.com/ivanium)
- **Merged time:** 2026-10-04 18:49:42
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/58560/files) (2):**
  - `tests/kernels/test_compressor_kv_cache.py`
  - `vllm/models/deepseek_v41/compressor.py`

### Summary

**What changed and why**  
The PR fixes a bug in vllm/models/deepseek_v41/compressor.py where _ring_slot_mapping_kernel mapped dummy/warmup tokens (whose block tables are zeroed) into block 0, the shared null block. Because every KV-cache group shares block 0, fp32 compressor state bytes were written into other layers' pages, and non-finite values there caused NaN propagation (0 x NaN) in sparse MLA decode, leading to wrong outputs and cudaErrorIllegalAddress/Xid 31 MMU faults on sm_120 with DSpark and FULL CUDA graphs. The fix maps tokens whose ring block is 0 to PAD (-1), which ring consumers already skip, and a test was updated/added to cover the null-block case.

**Technical impact**  
Behavior changes only for requests whose ring block is 0 (dummy/warmup/padding rows), which now map to PAD instead of writing into the null block; real requests never own block 0 so their slot mapping is unchanged. This prevents compressor state from corrupting shared block-0 pages across KV-cache groups, eliminating the latent NaN contamination that survived into serving after the gpu_worker.py ordering change (warmup_kernels before capture_model). The change is small (+5/-1 in the kernel) and localized to the ring slot mapping path.

**Potential risks**  
The fix assumes block 0 is always the null block and never a legitimate ring block for real requests; if any code path legitimately assigns block 0 to a real request, its compressor state would now be silently dropped. End-to-end validation was only performed on sm_120 (RTX PRO 6000) with a patched page-geometry setup and not on current main or other GPU architectures, so cross-platform behavior is unverified. The test file imports modules newer than the nightly image used, so the full test suite was not run verbatim.

**Key insights**  
The root cause is a latent ordering dependency: warmup_kernels previously ran after capture_model and re-zeroed block 0, masking the bug, but reordering in gpu_worker.py exposed it. The fix is minimal and targeted, relying on the existing PAD-skipping semantics of ring consumers. The PR also notes a related robustness concern for FlashInfer's SM120 DSv4 sparse decode, which is only correct while slot 0 is finite because masked candidates still contribute 0 x V.

  - `vllm/lora/ops/triton_ops/lora_shrink_op.py`

### Summary

**What changed and why**  
Adds a deterministic split-K=8 LoRA shrink path for VLLM_BATCH_INVARIANT=1. Instead of SPLIT_K=1 (used because split-K normally relies on float atomics), the kernel now stores unscaled FP32 partials for 8 fixed K splits (BLOCK_K=256) and a new reducer sums them in a fixed order and applies scaling once. This preserves K parallelism while keeping batch-invariant outputs bitwise-stable across batch composition, at the cost of changing results relative to the previous SPLIT_K=1 path due to different reduction order.

**Technical impact**  
Touches the core Triton LoRA shrink kernel (kernel_utils.py, lora_shrink_op.py) with a new STORE_PARTIALS branch, a new _lora_shrink_reduce_kernel, and per-call torch.empty FP32 partials allocation so each CUDA graph keeps scratch in its own pool. Non-batch-invariant path is unchanged, PDL is disabled on the split-K path, and an early return is added for empty inputs. Adds a new determinism test, CI wiring in misc.yaml, and a docs note.

**Potential risks**  
The batch-invariant LoRA numerical output changes versus the prior SPLIT_K=1 path, which could shift downstream results for users relying on exact prior values. Per-call torch.empty of shape (slices, 8, tokens, rank) adds memory and allocation overhead, potentially significant for large token counts or many slices. The reducer assumes grid[0] is divisible by SPLIT_K and that partial strides/layout match the producer; any mismatch in grid formulation or stride handling (note the switch to first_out.stride(-2)/stride(-1)) could cause incorrect indexing. The new path is only exercised under VLLM_BATCH_INVARIANT=1, so coverage outside the added tests may be limited.

**Key insights**  
The design cleanly separates the atomic-free partial store from the fixed-order reduction, keeping the non-BI path untouched and avoiding a new env var. The test suite is strong: FP64 reference checks over K tails, empty splits, multiple slices, and no-LoRA rows, plus a bitwise-equality check across M=31..129 and a monkeypatched assertion that the reducer launches exactly 7 times. The main review focus should be on partials memory footprint, stride correctness in the STORE_PARTIALS branch, and confirming the intentional numerical change is acceptable and documented.

## 11. [[CI][Docs] Fix decode/prefill consistency test prefix construction; add GLM-4-9B and Phi-4 to batch-invariant tested models](https://github.com/vllm-project/vllm/pull/53692)


### Base Information

- **PR Number:** #53692
- **Author:** [LioEinaudi](https://github.com/LioEinaudi)
- **Merged By:** [yewentao256](https://github.com/yewentao256)
- **Merged time:** 2026-10-04 08:55:19
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/53692/files) (2):**
  - `docs/features/batch_invariance.md`
  - `tests/v1/determinism/test_batch_invariance.py`

### Summary

**What changed and why**  
The determinism test test_decode_logprobs_match_prefill_logprobs was rebuilding prefill prefixes by re-encoding decoded text, which is lossless-unsafe for BPE tokenizers and could evaluate a different token sequence than decode, producing false mismatches (e.g. GLM-4-9B emitting '.' + 'Here' that re-encodes to a single merged token). The fix constructs prefixes directly from token ids via TokensPrompt(prompt_token_ids=prompt_token_ids + token_ids[:i]), eliminating the re-encode round-trip and the extra O(N^2) llm.generate calls. Docs were also updated to list zai-org/glm-4-9b-chat and microsoft/phi-4 as validated batch-invariant models.

**Technical impact**  
Removes a soundness bug in the test harness so decode/prefill logprob comparisons are performed on identical token sequences, and cuts per-token prefix generation from an extra full generate call to a direct token-id prompt, reducing test runtime from O(N^2) to O(N) generations. Failure diagnostics now report prefix_token_ids instead of prefix_text. The change is confined to a test file and documentation, so no production inference behavior is altered.

**Potential risks**  
The test now depends on TokensPrompt and prompt_token_ids being populated by the LLM output; if prompt_token_ids is None or empty the prefix construction silently degrades to only decode tokens, which could mask issues. Token-id prefixes bypass tokenizer detokenize/re-encode paths, so any real tokenizer-related divergence in the engine would no longer be exercised by this test. The added model entries in docs are only as trustworthy as the reported validation runs, and GLM-4-9B still OOMs on 24 GB GPUs per the test results.

**Key insights**  
The root cause was a classic BPE non-round-trip issue: encode(decode(ids)) != ids at merge boundaries, which made the test unsound for any model whose greedy output hits a merge point. Building prefixes from token ids is both more correct and more efficient, and the GLM A/B (59/64 text re-encode vs 64/64 token ids) provides direct evidence. The PR also carries forward the fix from stale PR #43317 with original authorship, and reports first-ever determinism suite runs on sm120 hardware.
