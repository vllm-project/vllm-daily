**Key insights**  
The core fix is aligning runtime admission with profiling assumptions, closing a gap where dummy-input sizing did not constrain real inputs. ## 6. [[Security] Fix ReDoS in validation error path sanitizer](https://github.com/vllm-project/vllm/pull/52120)


### Base Information

- **PR Number:** #52120
- **Author:** [jperezdealgaba](https://github.com/jperezdealgaba)
- **Merged By:** [DarkLight1337](https://github.com/DarkLight1337)
- **Merged time:** 2026-10-27 22:46:43
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/52120/files) (2):**
  - `tests/entrypoints/serve/exception_handling/test_error_sanitization.py`
  - `vllm/entrypoints/serve/exception_handling/utils.py`

### Summary

**What changed and why**  
Fixes a CWE-1333 ReDoS in sanitize_message() where a slash-delimited input without a filename extension (e.g. '/a' * 50000) caused catastrophic backtracking in the generic path regex, hanging an API worker for 3+ seconds per rejected request (GHSA-f2g9-pmwr-xwc7). The fix adds a dot pre-check to skip the regex when no extension is possible and wraps the repeated slash-segment in an atomic group (?>...) to prevent backtracking. Four regression tests were added covering adversarial input, alphanumeric input, linear scaling, and continued path redaction.

**Technical impact**  
Behavior for legitimate path redaction is preserved while adversarial inputs now complete in sub-millisecond time. The dot pre-check is a cheap short-circuit that avoids regex execution entirely for the common no-extension case, and the atomic group bounds work to near-linear for messages that do contain dots. This is a security-relevant hot-path change in the exception-handling layer that affects every rejected API request.

**Potential risks**  
The atomic group changes matching semantics: patterns that previously relied on backtracking within repeated slash-segments may now fail to match some edge-case paths, potentially leaving some paths unredacted. The dot pre-check assumes any redactable path must contain a dot, which is true for the extension-bearing pattern but should be confirmed against all intended path shapes. Timing-based tests (elapsed < 0.1s, ratio < 100x) can be flaky on slow or loaded CI runners, and the PR notes GPU/RDMA and full CI were not run during rebase.

**Key insights**  
The fix is minimal and targeted, correctly addressing the root cause (backtracking) rather than just the symptom. The regression tests are valuable but rely on wall-clock thresholds that may be brittle; a more robust approach would assert on input-size scaling or use a timeout harness. The rebase note indicates the change was relocated into current exception-handling modules, so reviewers should confirm the sanitizer is still invoked on all relevant error paths and that no duplicate or conflicting sanitizer remains.

  - `tests/v1/core/test_kv_cache_utils.py`
  - `vllm/v1/attention/backends/utils.py`

### Summary

**What changed and why**  
The PR fixes a startup failure under pipeline parallelism where resolve_kv_cache_layout asserted that all workers report identical supported KV cache layout lists. Because PP stages hold different layers and thus different attention backends, their lists legitimately differ. The fix extracts the existing merge logic from get_supported_kv_cache_layouts into a new _merge_supported_layouts helper and applies it to worker reports, treating workers that report the default preference as non-voting, and adds a unit test covering the PP scenario.

**Technical impact**  
Behavior changes only when worker lists differ: the engine now intersects the reported layout sets and picks the layout most workers rank first, instead of aborting. When all workers agree, the result is unchanged, and an empty intersection still raises ValueError. This unblocks PP serving for models mixing backends across stages (e.g. FlashInfer dense layers plus sparse layers) while preserving the single-worker and TP-only paths.

**Potential risks**  
The removed assertion also guarded against TP ranks within one stage reporting divergent lists (e.g. a rank accidentally selecting a different backend); such divergence is now silently merged rather than flagged. The default-preference non-voting rule is a heuristic that could mask a stage genuinely preferring a layout, and the chosen layout is only guaranteed to be supported by every worker, not necessarily optimal. Validation was on B200 with FLASHINFER and V2 model runner, not the reported GB200, and no accuracy eval was run.

**Key insights**  
The root cause is that per-worker layout reporting reflects only the layers that worker holds, so PP stages naturally diverge; the fix correctly reuses the intra-worker merge semantics at the inter-worker level. The non-voting rule for default-preference workers is important to keep PP layout selection consistent with PP=1. The tradeoff of dropping the cross-rank equality assertion is reasonable but could warrant a future per-stage consistency check if the engine core gains stage awareness.

  - `vllm/v1/executor/cuda_checkpoint_executor.py`

### Summary

**What changed and why**  
Adds a new opt-in CUDACheckpointExecutor (default-off) that, after ordinary level-1 sleep, checkpoints CUDA worker processes via NVIDIA driver checkpoint APIs (cuCheckpointProcessLock/Checkpoint/Restore/Unlock) and restores them before waking allocator tags, preserving captured graph executables without recapture. It introduces a helper module (vllm/utils/cuda_process_checkpoint.py) that runs driver calls in a separate interpreter with concurrent per-rank stages and deadlines, plus extensive experimental documentation and three new test files. The feature is extracted from #58183 and deliberately excludes follow-up client cleanup/resume-guard changes.

**Technical impact**  
Adds ~1457 lines across 6 files: a new executor subclassing MultiprocExecutor with strict config validation (Linux/CUDA, V2 model runner, cumem sleep backend, single-node TP, no EP/PP/DP/CP, no external transfer, NCCL suspend and transport env restrictions), serialized sleep/wake/shutdown via an RLock, RPC gating while checkpointed, and forced worker termination on failure. The helper isolates potentially blocking driver calls in a subprocess with stage deadlines (30s stage, 10s lock, 120s sleep/wake hooks) and validates complete per-rank stage responses. Behavior is unchanged for all existing users since the executor is opt-in and default-off.

**Potential risks**  
The feature is experimental and depends on specific NVIDIA driver versions, NCCL 2.29.7+ with comm suspend, and FlashInfer workspace hooks; unsupported combinations are rejected but the surface is large and fragile. Real-GPU validation (5 opt-in tests) was not rerun for this split and TP8/full native rebuilds are unestablished. A checkpoint failure terminates workers and requires engine restart, and the docs note an EngineCore exit during a management call can leave clients waiting without an external timeout. Partial-wake restores the whole CUDA process, so callers must serialize control calls and fully wake before resuming.

**Key insights**  
The design cleanly separates the risky driver interaction into a subprocess helper so blocked CUDA calls can be killed by deadline, and enforces all-ranks-locked-before-checkpoint / all-ranks-restored-before-unlock ordering with concurrent per-stage execution. Validation is thorough on CPU-side lifecycle and failure cleanup (57 passed) but GPU-path evidence is historical from the combined PR, so reviewers should treat GPU correctness and performance claims as provisional. The PR is well-scoped as a default-off opt-in feature with explicit documented restrictions, which limits blast radius to users who deliberately select the executor.
