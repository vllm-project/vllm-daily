## 1. [[Bugfix][MiniMax-M3] Scope prompt reasoning-end checks to the last message](https://github.com/vllm-project/vllm/pull/63492)

  - `tests/reasoning/test_minimax_m3_reasoning_parser.py`
  - `vllm/reasoning/minimax_m3_reasoning_parser.py`

### Summary

**What changed and why**  
Fixes MiniMax-M3 streaming reasoning parsing where the M3.1 chat template's system message and prefixed assistant turns contain literal <mm:think>/</mm:think> markers, causing is_reasoning_end to return True before generation and bypassing the reasoning parser. The fix adds a _last_message_ids helper that scopes reasoning-end checks to tokens after the last message-begin token ]~b], applied in both is_reasoning_end and is_reasoning_end_streaming, plus two new unit tests.

**Technical impact**  
Changes behavior of the M3 reasoning parser's end-detection for both streaming and non-streaming paths (and structured-output grammar start via resolve_reasoning_ended). Output-only token ids without a ]~b] token are scanned whole as before, and tokenizers lacking ]~b] in vocab are unaffected, limiting blast radius to MiniMax-M3. The backward scan adds minor cost proportional to input length, comparable to existing token-sequence scans.

**Potential risks**  
Correctness depends on the ]~b] message-begin token being present in the tokenizer vocab and consistently emitted by the template; a template or tokenizer change could silently break scoping. The fix is narrower than the broader #50594 approach and may not cover other serving paths or models with similar prompt-marker issues. Only unit tests and manual E2E validation are provided; no CI integration coverage is shown.

**Key insights**  
Root cause is prompt-side reasoning markers leaking into the end-of-reasoning check, which non-streaming parsing avoided by not consulting the prompt. Scoping to the last message via the message-begin token is a targeted, low-blast-radius fix confined to the M3 parser, trading generality for safe landing on the model branch. The added tests directly reproduce the M3.1 template shape and fail without the change, giving good regression protection.

## 6. [[Bugfix][ROCm] Wait on per-slot events in packed NCCL consumer](https://github.com/vllm-project/vllm/pull/63833)


### Base Information

- **PR Number:** #63833
- **Author:** [dharak-cohere](https://github.com/dharak-cohere)
- **Merged By:** [aoshen02](https://github.com/aoshen02)
- **Merged time:** 2026-10-26 20:01:03
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/63833/files) (1):**
  - `vllm/distributed/weight_transfer/packed_tensor.py`

### Summary

**What changed and why**  
The packed NCCL consumer previously called streams[buffer_idx].synchronize() before reusing a slot. On ROCm, HIP multiplexes streams onto a small pool of hardware queues, so synchronizing one stream can also wait for work queued later on another stream sharing that queue (e.g. a layerwise reload replay), stalling the host and breaking multi-buffer overlap. The fix records a per-slot torch.Event after post_unpack_func and waits on that event instead, skipping the wait on a slot's first use.

**Technical impact**  
Behavioral change in the consumer's slot-reuse synchronization path in vllm/distributed/weight_transfer/packed_tensor.py. It narrows the wait to exactly the work on that slot's stream (receive, unpack, post_unpack_func) rather than any later work on a shared queue, restoring overlap on ROCm and fixing the MI300X test failure when GPU_MAX_HW_QUEUES=1. Adds one event record per pack and removes num_buffers waits per call; the final drain loop is unchanged.

**Potential risks**  
The fix relies on the event correctly covering all work that must complete before slot reuse; any future work queued on the slot stream outside the recorded region would no longer be waited on. There is a small per-pack event-record overhead (0.4-1.6% slower in some no-queue-sharing MI300X microbenchmarks) and up to 3.1 GB higher peak reserved memory on MI300X at one queue due to restored overlap. No new test is added, so regression detection depends on the CI runner's queue assignment; forcing GPU_MAX_HW_QUEUES=1 is needed to reliably reproduce.

**Key insights**  
The root cause is a ROCm-specific stream-to-hardware-queue multiplexing behavior that makes stream-level synchronization over-broad; CUDA does not serialize host synchronization this way. The PR is well validated with a targeted reproducer, bit-for-bit correctness checks, and benchmarks on both H100 and MI300X showing no H100 regression. The main gap is test coverage: the existing test only catches the bug under specific queue configurations, so a deterministic test forcing one queue would strengthen CI.

### Summary

**What changed and why**  
Fixes a correctness bug in copy_kv_cache_blocks_inplace where the CoW dedup key was only (device, data_ptr). For hybrid models, a narrow Mamba state view and a wider attention view can share a base address but cover different bytes per block, so the second view was skipped and only a partial block was copied, corrupting KV cache data. **Technical impact**  
Changes the dedup behavior of the partial-prefix-hit CoW copy path in vllm/v1/worker/utils.py. **Potential risks**  
The extra copies for overlaid views add minor overhead on the CoW path, though the PR argues it is redundant but harmless. The fix is validated by a targeted unit test and E2E GSM8K results, but broader hybrid-model configurations are not exhaustively covered.

**Key insights**  
The root cause is a subtle aliasing assumption: same data_ptr does not imply same copy coverage when views have different geometry. The fix correctly generalizes the dedup key to describe both starting location and layout. The regression test is well-constructed, deliberately using two tensor regions in one storage to disable the whole-storage fast path that would otherwise mask the bug.   - `tests/kernels/attention/test_triton_prefill_attention.py`

### Summary

**What changed and why**  
Fixes a Triton OutOfResources crash in context_attention_fwd on GPUs with 99 KiB shared memory (RTX 30/40/50, L4) by halving the tile size on CUDA until the Q, K and P tiles fit the device's opt-in shared memory limit. Previously the tile was chosen only from dtype and compute capability, so bf16 head size 256 and fp32 head size 512 exceeded the limit and broke engine warmup for google/embeddinggemma-2. The test parametrization adds D=256 and D=512 to cover the failing paths.

**Technical impact**  
Adds a cached helper _fit_block_to_shared_memory that computes the tile from element size, head dim (next_power_of_2(Lk)) and get_max_shared_memory_bytes(), gated to CUDA only. Tiles that already fit are unchanged, so existing configurations remain bitwise identical, while oversized tiles shrink (e.g. bf16 D=256 goes 128 to 64). The cache keyed on (block, head_dim, element_size) keeps per-call overhead to a lookup, and the floor of 16 preserves tl.dot validity.

**Potential risks**  
The shared-memory formula was measured on sm_120 and is not proven to be an upper bound on all GPUs; the PR itself notes it under-counts fp16 use on sm_75, though chosen tiles still fit there. ROCm is excluded, so head-size-256 encoder attention on 64 KiB ROCm GPUs may retain the same bug. The cache omits the memory limit, so tests mocking a different limit in-process can get stale tiles, and get_max_shared_memory_bytes reads only GPU 0 on mixed-GPU hosts. fp32 head sizes above 512 still fail since 16 is the minimum tile.

**Key insights**  
The fix is narrowly scoped and well-validated: it preserves existing tile choices rather than over-shrinking like the alternative PRs, and the added D=256/D=512 test cases fail on old code on sub-160 KiB GPUs, giving real regression coverage. The main residual concerns are the unverified formula generality across architectures and the ROCm gap, both explicitly documented. Overall a reasonable, low-blast-radius bugfix with clear evidence.
