No validation details are provided in the PR description, so runtime correctness on real hardware is unconfirmed.

**Key insights**  
This is a clean, low-risk refactor that converts a hard-to-patch kernel entry point into a standard vLLM pluggable layer, aligning with existing OOT extension patterns. The main review focus should be confirming that the wrapper and the vision tower both resolve OOT overrides consistently, and that the added test is robust to plugin registry state across the test session.

### Summary

**What changed and why**  
Replaces the O(N) any(...) scan in EncoderCacheManager.free_encoder_input with a per-request mm_hash reference count (request_hash_refs), making freeing a request with N multimodal items O(N) instead of O(N^2). A new helper _add_cached_input_id keeps request_cached_ids and request_hash_refs in sync, and reset() clears the new structure. A test verifies each hash is released exactly at its last occurrence.

**Technical impact**  
Scheduler-thread bookkeeping only; no change to model outputs or cache release semantics. The duplicate-hash retention behavior from #54284 is preserved via a dict lookup instead of a linear scan, yielding large speedups for prompts with hundreds of items (e.g., 235 ms to 1.2 ms at 4,096 items). Adds one small dict per active request.

**Potential risks**  
Out-of-tree subclasses that mutate request_cached_ids directly would desynchronize request_hash_refs and could cause incorrect eviction or KeyError on hash_refs[mm_hash]. The free path assumes request_hash_refs[req_id] exists whenever input_id is in cached_ids, so any inconsistent state could raise. Validation is CPU-only with no GPU end-to-end run, though the change is confined to scheduler bookkeeping.

**Key insights**  
The fix trades a small per-request dict for eliminating quadratic behavior on the engine-core thread, which matters because the whole batch waits on the scheduler. The new test meaningfully covers the repeated-hash last-occurrence invariant and cleanup of both dicts. The main review concern is the implicit coupling between request_cached_ids and request_hash_refs, which is worth documenting or encapsulating.

**What changed and why**  
Adds CuTe DSL (SM10x tcgen05) verify and commit kernels for Kimi-K3 KDA RecoverSSM, with automatic fallback to the existing Triton path, and moves the per-step verify records (FP32 corrections, keys, raw gates) out of the Mamba KV cache pages into a per-layer buffer indexed by speculative batch row. This shrinks the Mamba page/attention block (1024 -> 896 tokens at TP8), lets KV connectors (P/D disaggregation, offloading) work with RecoverSSM, and removes the record-shape helpers from mamba_utils.py. It also tightens config validation (requires Model Runner V2, rejects --enable-dbo) and rebuilds the commit context when the KV cache is re-bound.

**Technical impact**  
Large behavioral change across config validation, KV cache layout, layer state management, and two new hand-written CuTe kernels (verify, warp-specialized verify, commit) plus host wrappers with compile-time caching and alignment checks. Records are now indexed by request row rather than state slot, which decouples scratch memory from KV cache sizing and enables connector compatibility. Reported microbenchmark gains are 1.4x-5x over Triton and 1.2x-3.1x over stock speculative decoding, with end-to-end throughput +1.9% and decode KV capacity +7.1%.

**Potential risks**  
The CuTe kernels are low-level, architecture-specific (SM10x only) and rely on alignment assumptions; misaligned inputs fall back to Triton, but the fallback path and the warp-specialized variant (which had a betas-at-window-8 bug) are subtle and correctness-critical. Record buffers sized by max_num_seqs add memory proportional to concurrency and must stay in sync with batch row indexing, especially under CUDA graphs, preemption, and DBO (now rejected). The P90 TTFT regression is unconfirmed as noise. New hard requirements (Model Runner V2, no DBO) may break existing deployments, and the large diff (+2957/-212) with AI assistance warrants careful review of the kernel math and edge cases.

**Key insights**  
Moving transient verify records out of the KV cache is the key architectural win: it restores stock Mamba page sizing, unblocks KV connectors, and improves cache capacity. The CuTe kernels deliver substantial per-step speedups but are gated behind strict capability checks with a Triton fallback, which limits blast radius. Test coverage is extensive (kernel parity, preemption, metadata, config, accuracy and perf), though the P90 TTFT delta and some alignment/fallback paths deserve follow-up validation.
