## 1. [[Bugfix][Multimodal] Normalize single-channel audio to 1D](https://github.com/vllm-project/vllm/pull/56691)


### Base Information

  - `tests/multimodal/test_audio.py`
  - `vllm/multimodal/audio.py`

### Summary

**What changed and why**  
The fix in vllm/multimodal/audio.py changes normalize_audio so that when the input already has the target channel count and that count is 1, it returns audio[0] (a 1D waveform) instead of the original 2D array. This addresses a bug where mono audio shaped (1, N) failed Whisper preprocessing and caused AudioProcessorItems.get_audio_length() to report 1 instead of N. Tests in tests/multimodal/test_audio.py were extended to parametrize over (N,), (1, N), (N, 1), and (1, 1) layouts for NumPy, Torch, and parser paths.

**Technical impact**  
Mono audio with an explicit channel axis is now consistently normalized to a 1D array, matching the behavior of already-1D input and fixing downstream Whisper feature extraction and length reporting. The change is localized to the early-return branch and preserves existing behavior for multi-channel inputs and for cases requiring reduction or expansion. The added tests cover both channel layouts and the single-sample edge case, improving regression coverage for the audio normalization path.

**Potential risks**  
The fix assumes that a single-channel array can always be safely indexed with audio[0] to drop the channel dimension, which holds for NumPy and Torch tensors but could be problematic for other array-like types that do not support indexing or have different semantics. There is also a subtle risk that callers relying on the previous 2D shape for mono input (even if incorrect) may observe changed downstream behavior, though the PR's Whisper validation suggests this is the intended fix. The test environment lacks torchaudio and CUDA, so some audio and parser tests were skipped or filtered, leaving those paths unverified in this run.

**Key insights**  
The root cause was an early return that skipped normalization when the channel count already matched the target, leaving mono input as 2D and breaking Whisper preprocessing and length reporting. The fix is minimal and targeted, and the expanded parametrized tests directly encode the expected 1D output for all mono layouts. The PR description notes related work in #47693, #56023, and #51022 that does not address this early return, indicating this is a distinct bug fix rather than a duplicate.

## 2. [[Bugfix][KV Offload] Release pending CPU lookup pins on cache reset](https://github.com/vllm-project/vllm/pull/59862)


### Base Information

- **PR Number:** #59862
- **Author:** [zupengwang](https://github.com/zupengwang)
- **Merged By:** [ivanium](https://github.com/ivanium)
- **Merged time:** 2026-10-03 21:30:18
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/59862/files) (2):**
  - `tests/v1/simple_kv_offload/test_scheduler.py`
  - `vllm/v1/simple_kv_offload/manager.py`

### Summary

**What changed and why**  
The PR fixes a bug in the KV offload manager where CPU lookup pins held by get_num_new_matched_tokens() were not released during reset_prefix_cache(reset_connector=True). A request waiting for GPU allocation could keep these pre-allocation references in _pending_cpu_hits, causing reset() to return False even after GPU blocks and in-flight transfers drained. The fix iterates over _pending_cpu_hits, calls _free_pending_cpu_hit() on each, and clears the map before the existing transfer-abandonment logic runs.

**Technical impact**  
Reset now releases temporary CPU lookup pins and invalidates their saved lookup state, allowing reset to succeed when only pending lookups remain. In-flight DMA references are unaffected because submitted transfers retain separate pins and existing completion-based cleanup. A waiting request performs a fresh lookup when scheduling resumes, so no API, storage format, or normal scheduling policy changes are introduced.

**Potential risks**  
The change assumes pending CPU hits have no associated worker DMA, which the description asserts but is not independently verified in this review. If any pending lookup were later found to share state with an in-flight transfer, freeing it early could cause premature release. Validation was performed by AI (Codex) with no confirmed independent human reruns, and multi-node, disk/GDS, and other GPU backends were not tested, so broader backend behavior remains unverified.

**Key insights**  
The fix is small and targeted, reusing the existing _free_pending_cpu_hit() helper rather than adding new logic. The regression test is well-parameterized across eager/lazy modes and one/two cache groups, and asserts both ref-count release and that a subsequent lookup returns no stale hit. The main open concern is the reliance on the claim that pending lookups have no worker DMA, plus the lack of independent human validation.

### Summary

**What changed and why**  
Fixes a bug in the harmony (gpt-oss) streaming path of /v1/responses where response.completed rebuilt output items with freshly minted ids and call_ids that did not match those previously sent in response.output_item.added/done events, causing strict clients to abort. The fix records the items emitted per completed harmony message in HarmonyContext.streamed_items_by_message, matches each message by object identity in responses_full_generator, and copies the streamed id/call_id onto the rebuilt items via a new reuse_streamed_item_ids helper. It also changes streamed harmony reasoning item ids from the msg_ prefix to rs_, aligning with the non-streaming and non-harmony paths.

**Technical impact**  
Adds a new field to HarmonyContext and a new utility function in utils.py, and modifies the streaming event processing loop to collect ResponseOutputItemDoneEvent items per message. The rebuild loop in responses_full_generator now iterates with index to preserve the incomplete flag on the last message while reusing streamed ids. Behavior of generated content is unchanged; only item identifiers in the final response are affected, improving client compatibility with the Responses API streaming contract.

**Potential risks**  
The pairing logic in reuse_streamed_item_ids matches items by type in order, so if a message rebuilds multiple items of the same type in a different order than they were streamed, ids could be assigned incorrectly; the per-message identity matching mitigates cross-message mismatches but not intra-message reordering. The assert on ResponseFunctionToolCall types could raise if a streamed item type and rebuilt item type diverge unexpectedly. The rs_ prefix change alters id format for streamed reasoning items, which could affect any client that pattern-matched on msg_, though this aligns with existing non-streaming behavior.

**Key insights**  
The core insight is that streamed messages form an ordered subsequence of the final harmony messages, so matching by object identity per message is necessary to avoid assigning a streamed id to the wrong rebuilt item, especially when a built-in python call streams as code_interpreter_call but rebuilds as reasoning. The fix is well-scoped, includes targeted regression tests that fail on main, and was validated with manual curl checks across forced tool calls, reasoning plus text, and truncated incomplete responses with 0/9 mismatches versus 9/9 on main.

Previously, abort outputs (token_ids=[], finish_reason='abort') were skipped in token mode, so clients saw [DONE] with no finish_reason. **Technical impact**

Clients that assumed the last data chunk before [DONE] always contained tokens may need to handle empty token_ids chunks, though this aligns with text mode and the Rust frontend. The change relies on sampling_params.n being correct and stable for the request; if n is mutated or differs from the engine's actual choice count, counter sizing could still mismatch. The test skip reason was changed to reflect that the Rust frontend does not serve /inference/v1/abort_requests, so Rust-frontend coverage for this path is absent. No changes to non-streaming or text-mode behavior are expected, but the broader emit condition could surface previously suppressed outputs in edge cases.

**Key insights**  
The core bug was an emit filter that dropped terminal outputs lacking new token IDs, which is exactly the shape of an abort output. Unifying the emit condition around finish_reason (plus text-mode held-back text) is a clean fix that removes mode-specific branching. Separately, deriving the token counter length from the first output was fragile for n > 1; sizing it from sampling_params.n is the correct invariant. The added parametrized tests for stop/length/abort and the n=2 partial-first-output case give good regression coverage for both fixes.

**Key insights**  
The design deliberately separates mechanism (CuMemAllocator.cudagraph_pool tagging and pool lifetime) from policy (CuMemBackend.suspend offload tags), and centralizes the predicate in one helper so capture sites, CudaCommunicator and the NCCL default stay consistent. Memory profiling is intentionally excluded via capture_outside_cumem_pool so throwaway profiling graphs free normally, and elastic EP must drop the pool before recapture because stream-local block reuse would otherwise grow it unboundedly. The PR is well-tested across models, TP/EP topologies, wake orders and elastic EP, but reviewers should focus on the release/refusal logic, the custom-allreduce copy path, and the dependency ordering with #59228.

## 9. [[ROCm][RDNA3] Fix W4A16 split-K accuracy and determinism](https://github.com/vllm-project/vllm/pull/54706)


### Base Information

- **PR Number:** #54706
- **Author:** [AIwork4me](https://github.com/AIwork4me)
- **Merged By:** [tjtanaa](https://github.com/tjtanaa)
- **Merged time:** 2026-10-03 08:44:18
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/54706/files) (5):**
  - `csrc/rocm/moe_q_gemm_rdna3.cu`
  - `csrc/rocm/q_gemm_rdna3.cu`
  - `csrc/rocm/q_gemm_rdna3_wmma.cu`
  - `csrc/rocm/qdq_4_rdna3.cuh`
  - `tests/kernels/quantization/test_rdna3_w4a16_determinism.py`

### Summary

**What changed and why**  
This PR replaces the nondeterministic split-K epilogues of the RDNA3 (gfx11) W4A16 GPTQ kernels. Previously, per-split partials were narrowed to bf16/fp16 and accumulated via CAS-atomic loops, so the execution-dependent CAS completion order changed the rounded result for identical inputs. The fix stores FP32 per-split partials to scratch and reduces them in a fixed ascending-z order with a single final cast, making outputs bit-reproducible. It also ports an exact factored fp16 dequant (fp32 y/z pairs instead of baked fp16 constants), moves the WMMA dispatch crossover to M>=12 for both dtypes, and fuses the fp16 split-K reduction into the GEMM kernel using per-call ticket counters.

**Technical impact**  
Touches five files across the dense scalar kernel, WMMA kernel, MoE kernel, the shared qdq header, and a new test module (+1524/-266). Accuracy improves substantially (bf16 scalar 4-6x, WMMA ~2x, scalar fp16 94-201x after the exact dequant), and determinism is achieved (20/20 benchmark shapes repeatable, 1 unique result per 100 calls on real weights). Performance is at parity or better for prefill and most decode shapes, with a residual ~4-10% cost at M=1 decode from the scratch round-trip. The legacy CAS epilogues are retained but never selected by the shipped dispatch.

**Potential risks**  
The deterministic epilogue relies on an at::empty scratch whose correctness depends on a total-coverage invariant (every reducer-visible slot has exactly one writer); a violation would produce repeatable-but-wrong results, which the tests attempt to catch via FP32-reference tolerances. The fused fp16 reduce introduces per-call ticket state and a last-block-wins reduction, which is a concurrency-sensitive pattern; the PR argues per-call allocation avoids cross-launch hazards but this is a subtle area. The MoE kernel gets the exact dequant but keeps its existing epilogue, so MoE split-K remains nondeterministic (acknowledged follow-up). The new host-side TORCH_CHECK that groupsize % 32 == 0 could reject previously-accepted (but silently wrong) configs, a behavior change for some users. The large diff and multiple interacting changes (dequant, dispatch, epilogue, fused reduce) increase review and regression surface.

**Key insights**
