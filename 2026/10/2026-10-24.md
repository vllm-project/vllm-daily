  - `vllm/v1/attention/backends/triton_attn.py`
  - `vllm/v1/attention/backends/utils.py`

### Summary

**What changed and why**  
Adds a set_triton_ptr_range helper that assigns a ptr_range() bound to KV cache views, and calls it on ROCm in TritonAttentionImpl.forward and do_kv_cache_update. This restores Triton's AMD 32-bit buffer addressing for views into the single large KV allocation introduced by #51718, recovering a ~16-18% throughput regression on RDNA3.

**Technical impact**  
Python-only change affecting Triton code generation on ROCm: key/value cache pointers regain tt.pointer_range=32, reducing VGPRs (256 to 205) and improving occupancy. Non-ROCm platforms, allocation, layouts, and KV connectors are untouched; the bound is recomputed per forward from host-side metadata with no GPU sync.

**Potential risks**  
Correctness depends on kernels never addressing past the view's real extent; the bound is the distance from data_ptr to region end, so any out-of-view access would become a silent miscompile rather than a crash. Layers above 2 GiB or block-outermost layouts fall back to 64-bit addressing, so gains are not universal. No new tests were added and CI lacks RDNA runners, so regressions would rely on manual validation.

**Key insights**  
The fix is a targeted, well-documented workaround for a Triton AMD backend heuristic rather than a vLLM logic change, and the PR provides strong evidence (bisect, kernel trace, codegen inspection, token-identical accuracy). The main review focus should be the safety assumption that both kernels only address within the view and that ptr_range is correctly recomputed for all layouts.

## 2. [[Bugfix][KV Connector] Serve and store OffloadingConnector partial tails with EAGLE/MTP groups](https://github.com/vllm-project/vllm/pull/61019)


### Base Information

- **PR Number:** #61019
- **Author:** [kimseunghyun-kr](https://github.com/kimseunghyun-kr)
- **Merged By:** [orozery](https://github.com/orozery)
- **Merged time:** 2026-10-24 23:03:53
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/61019/files) (2):**
  - `tests/v1/kv_connector/unit/offloading_connector/test_scheduler.py`
  - `vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py`

### Summary

**What changed and why**  
Fixes a bug in the native CPU OffloadingConnector where, with an EAGLE/MTP draft model and mamba_cache_mode=align, partial tails were never served or stored, so CPU-tier hits stopped at scheduler-block boundaries and tokens were recomputed. The change removes the EAGLE exclusion from supports_partial_tail, keys EAGLE non-recurrent groups at boundary + eagle_proof_margin (matching core's proof position), fixes the store gate that always skipped the proof step, widens the partial search by one block with bridge keys for the popped chunk, and adds a store policy that only stores an EAGLE tail for requests that loaded from the CPU tier. Tests are added for proof keying, store gating, lookup behavior, and the store policy.

**Technical impact**  
Touches only offloading/scheduler.py (+161/-32) plus tests; no core files change. Behavior is unchanged without an EAGLE group or where partial tails are unsupported (DCP > 1, blocks_per_chunk > 1, mixed block sizes, sliding-window groups), and no new config option is introduced. The store policy (part 3) is essential: without it, parts 1+2 roughly double GPU-to-CPU store traffic and measurably regress serving latency, so the three parts are coupled and should land together.

**Potential risks**  
The store policy is a heuristic validated on a single workload: a request served only from the GPU prefix cache stores no EAGLE tail, so after GPU eviction the next turn's CPU hit ends at a complete chunk. The proof-step store relies on the CPU transfer stream waiting on the compute stream, which is an implicit ordering assumption. The hand-off step can stop before T+h, losing the tail in multi-module MTP (0.2-0.45%) or when block > max_num_batched_tokens (up to 1.7%). The widened two-block search applies only with EAGLE groups but adds lookup cost. Serving A/B gains are within repeat spread, so the claim is no-regression rather than speedup.

**Key insights**  
The root cause was two independent bugs: supports_partial_tail was disabled for EAGLE groups, and the store gate compared boundary+margin against num_computed_tokens, which at metadata-build time equals T, making the condition always true and the store always skipped. The author's diagnostic (external_prefix_cache_hits_total being an exact multiple of the block size) is a clean way to localize the store-gate bug. The decision to keep part 3 in the same PR is well justified by the A/B showing parts 1+2 alone regress SLO pass from 91.7% to 86.6%; splitting would land a regression. The proof-margin rule mirrors core's coordinator, keeping keying consistent with GPU prefix-cache hits.

### Summary

**What changed and why**  
In MRV2 UBatchRunner.finish(), the reported failing microbatch is changed from min(errors) to next(iter(errors)) so the first recorded failure is surfaced instead of the lowest-index one. This addresses a case where microbatch 1 fails first but microbatch 0's follow-on AttributeError (from registering a recv hook on the exited peer) was reported, hiding the root cause. **Technical impact**  
Behavioral change is limited to error reporting when multiple microbatches fail: the first-inserted error key is now reported rather than the minimum index. **Potential risks**  
The 'first recorded' failure is the first Python-level exception, which may not correspond to the actual GPU fault since CUDA errors are asynchronous, so the reported microbatch could still differ from the true root cause in some scenarios. The change does not address the hang when a peer exits mid-handoff or the HiSparse + DBO issues in #61487. Correctness depends on the invariant that errors is written once per thread and read only post-join; any future change to that invariant could break the ordering assumption.

**Key insights**  
The fix is a one-line selection change with a targeted regression test that reproduces the hidden-error scenario from #61487. The test's new [1] case deliberately triggers the follow-on recv-hook error to verify the original failure is reported. The PR is transparent about limitations (async CUDA timing, mid-handoff hang) and confirms no duplicate open PR exists.

## 7. [[Bugfix][KV Offload] Reject misaligned chunked-local CPU suffix hits](https://github.com/vllm-project/vllm/pull/63266)


### Base Information

- **Author:** [charxwu](https://github.com/charxwu)

  - `tests/v1/simple_kv_offload/test_integration.py`
  - `tests/v1/simple_kv_offload/test_scheduler.py`
  - `vllm/v1/simple_kv_offload/manager.py`

### Summary

**What changed and why**  
Fixes a correctness bug in SimpleCPUOffloadConnector where a GPU-local prefix ending inside a chunked-local attention chunk caused CPU suffix lookup to misinterpret absolute chunk boundaries, loading wrong/null blocks and producing incorrect output. The fix adds an alignment guard in manager.py that declines CPU suffix lookup when the local prefix is not aligned to every chunked-local attention group's chunk size, preserving the GPU prefix and recomputing the suffix. Tests (scheduler unit tests and a real-LLM integration regression) and documentation were added.

**Technical impact**  
Behavior changes only for misaligned mixed GPU/CPU hits in chunked-local attention: those now return (0, False) and recompute the suffix instead of reusing CPU KV. Requests with no GPU prefix or chunk-aligned prefixes retain CPU reuse, so the common paths are unaffected. The guard iterates prefix_cacheable_group_ids and inspects specs, adding a small per-lookup cost.

**Potential risks**  
The tradeoff is extra prefill work for misaligned mixed hits, which could reduce performance in workloads that frequently produce short GPU prefixes. The guard relies on num_computed_tokens and attention_chunk_size semantics matching absolute token positions; if chunking semantics change or multiple chunked-local groups with differing chunk sizes exist, the check may need revisiting. Validation was limited to a single AMD MI350X, TP1, eager mode, and random weights, so CUDA Graphs, multi-GPU, and trained-model quality were not evaluated.

**Key insights**  
The root cause is that CPU lookup passes a suffix-relative token budget to a coordinator that interprets it with absolute chunk positions, so a prefix ending mid-chunk shifts which blocks are treated as null padding. The minimal, targeted fix is a conservative alignment guard rather than implementing joint GPU/CPU lookup (deferred to #57325). Tests cover local prefixes of 0, 16, and 64 tokens with CPU-tail presence/absence, and the integration test verifies logprob parity against cold inference, confirming the fix restores correctness.

The Triton _apply_write_kernel in buffer_utils.py previously looped over 1024-element chunks inside a single program per staged write, serializing long writes on one SM. This PR adds a second grid dimension (cdiv(max_write_len, 1024)) so each chunk runs as its own program, tracks the longest staged write per StagedWriteTensor (and max across tensors in FusedStagedWriter) to size the grid with O(1) host work, and adds a test for a fused write spanning multiple chunks. It also removes per-block ref_cnt checks in BlockPool.get_new_blocks when neither prefix caching nor metrics is enabled.

**Technical impact**  
Long staged writes (e.g. admitting a 128K-token prompt into all_token_ids) now parallelize across SMs, with claimed 31x-120x speedups and reduced rank skew in DEP decode. Short writes (decode steps, block tables) are unaffected or slightly faster. The BlockPool fast path sets ref_cnt=1 directly, relying on the invariant that blocks popped from the free queue have ref_cnt==0. Bytes written and synchronization behavior are unchanged; grid dim 1 is at least 1 so empty/short writes still launch correctly with fully masked programs.

**Potential risks**  
The BlockPool optimization depends on the invariant that free-queue blocks always have ref_cnt==0; if any code path frees a block without resetting ref_cnt, this could silently corrupt refcounts. The grid sizing relies on _staged_write_max_len being correctly maintained across stage_write, stage_write_elem, and clear_staged_writes; a missed reset or update could under-launch programs and truncate writes. In mixed batches with one long write and many short ones, short writes launch programs that exit immediately, adding minor overhead (still far below the old cost). The kernel change is validated by microbenchmarks and existing tests, but the serving-context numbers come from an internal branch rather than this exact PR.

**Key insights**  
The core insight is that the per-program chunk loop was the bottleneck for long writes, and moving chunking into the grid dimension is a clean, low-risk parallelization that preserves semantics via masking. Tracking max write length at stage time avoids a costly host-side reduction at apply time. The BlockPool change is a separate, smaller optimization that trades a redundant check for a documented invariant, which should be clearly asserted or commented to prevent future regressions. The PR is well-validated with microbenchmarks, serving measurements, and targeted tests, though the refcount invariant deserves extra scrutiny.
