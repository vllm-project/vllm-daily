### Summary

**What changed and why**  
Adds an opt-in int4_per_group_32 MoE weight quantization key that requantizes Kimi-K3 MXFP4 expert weights to packed int4 once at load time on gfx942, where native scaled FP4 conversion instructions are unavailable. The path is gated behind an explicit --quantization-config.moe.weight int4_per_group_32 override plus SiTU activation, AITER fused MoE, and gfx942 checks, leaving the default MXFP4 path unchanged.

**Technical impact**  
Mxfp4MoEMethod now selects AITER_MXFP4_BF16 and its kernel class when the K3 SiTU int4 override is active, converts experts in chunks of 8 to bound transient memory, and serves through AITER's replacement BF16 x packed-int4 FlyDSL kernels. The new key is registered in the quantization name map and deliberately excluded from the online MoE table so load-time conversion is owned by Mxfp4MoEMethod. It also forces AITER_BF16_FP8_MOE_BOUND=0 to avoid leftover a8w4 config keeping bf16 activations.

**Potential risks**  
The conversion is lossy and irreversible, so correctness depends on the explicit opt-in and the warning being surfaced. It fails closed if the AITER build lacks the act parameter on flydsl_a16w4_gemm1, but otherwise relies on a specific AITER version (v0.1.21.post2) and the replacement pipeline from ROCm/aiter#4646. Memory behavior is sensitive: holding both MXFP4 and packed int4 doubles footprint, which the PR notes fits under expert parallelism but not pure tensor parallelism. The os.environ mutation is a global side effect with a TODO to remove once AITER accepts it as a kernel argument.

**Key insights**  
The change is well-scoped as an explicit opt-in that does not alter default checkpoint behavior, and it is backed by substantial validation including strict production-shape comparison, full GSM8K, long-context NIAH, DSpark, and graph capture. Chunked conversion with preallocated output and per-chunk cache release is a deliberate memory-safety measure. The main residual concerns are the lossy nature of the requant, the tight coupling to a specific AITER release, and the global environment variable workaround; a follow-up Mxfp4MoeBackend.AITER_INT4_BF16 is already anticipated.

### Summary

**What changed and why**  
This PR fixes a race between allocator zeroing and asynchronous KV cache loads by replacing the scheduler's token-range-based `_skip_zero_block_ids` mechanism with a connector-declared contract. A new `get_loaded_kv_cache_group_ids(request)` API is added to the base connector and overridden by NIXL, Mooncake, and MultiConnector to report exactly which KV cache groups an async load will restore. The scheduler passes these group IDs down through `allocate_slots` to `allocate_external_computed_blocks`, which now accepts a `record_for_zeroing` flag to selectively skip zeroing for those groups.

**Technical impact**  
The change moves zeroing-skip decisions from token-range slicing (which could not identify non-prefix-cacheable sliding-window blocks or circular-buffer blocks at index 0) to explicit group-level declarations by the connector. This correctly exempts all blocks an async load writes, including sliding-window blocks below a local prefix hit and circular-buffer ring blocks, while preserving zeroing for groups the connector does not load. The `get_zeroing_block_ids_in_range` method and `_skip_zero_block_ids` set are removed, and `allocate_external_computed_blocks` signatures are extended across all manager subclasses.

**Potential risks**  
The new contract requires every connector to correctly declare its loaded groups; a connector that returns an incomplete set could leave blocks unzeroed and cause data corruption, while an over-broad set could zero blocks that an async load is writing. The MultiConnector delegation relies on `_requests_to_connector` being populated before `get_loaded_kv_cache_group_ids` is called, which is an ordering assumption. The PR notes that model evaluations were not rerun after the API refactor, so end-to-end correctness on real workloads is not fully re-validated. The default implementation returns `prefix_cacheable_group_ids`, which may be incorrect for connectors that load non-prefix-cacheable groups but do not override the method.

**Key insights**  
The core insight is that allocation already knows the physical blocks being allocated, so the connector should declare which groups it restores rather than the scheduler trying to infer transferred blocks from token ranges. This shared contract is also consumed by #59197 for replay decisions, making it a foundational API change. The test coverage is thorough, including async/sync loads with and without sliding windows, circular-buffer zeroing, KpoolTail allocation, MultiConnector routing, and failure recovery, but the lack of rerun model evaluations is a notable validation gap.
