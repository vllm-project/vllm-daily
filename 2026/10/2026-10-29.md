**What changed and why**  
The four dispatch tests in test_lmhead_skinny_gemm_guard.py previously inferred which GEMM branch ran by reading kernel names from torch.profiler. On the daily Full CI run, an external ROCProfiler SDK tool registered via ROCP_TOOL_LIBRARIES prevents Kineto from registering, so torch.profiler captures nothing and the tests fail with kernels=[]. The change replaces profiler-based detection with a monkeypatch spy on ops.wvSplitK, which directly observes whether rocm_unquantized_gemm_impl took the skinny path, and drops the retry loop and kernel-name matchers. **Technical impact**  
Test-only change with no production code impact. The spy counts calls to ops.wvSplitK and asserts exactly one call for the skinny path, which is a more direct check of the guard's contract. **Potential risks**  
The spy assumes rocm_unquantized_gemm_impl resolves ops.wvSplitK through the module attribute at call time; if the implementation binds the symbol directly or calls it more than once per invocation, the calls == 1 assertion could break. The change also removes the explicit assertion that the fall-through reaches the hipBLASLt GEMM (Cijk), so a regression where the guard redirects to some other non-skinny path would no longer be caught. Validation was done on MI355X, not MI300 where CI runs, so MI300 behavior is inferred rather than directly verified.

**Key insights**  
Root cause is environmental: an external ROCProfiler SDK tool suppresses Kineto registration, making profiler-based dispatch assertions unreliable in the daily CI. Spying at the op boundary is the correct abstraction for testing which branch runs, since the guard's contract is dispatch, not kernel identity. The mutation checks (removing the guard, removing the n=1 carve-out) confirm the new assertions still detect the intended regressions.

## 7. [[ROCm][Bugfix] Skip AITER tuned GEMM when M*N >= 2^31 on gfx950](https://github.com/vllm-project/vllm/pull/64567)

  - `vllm/model_executor/layers/utils.py`

### Summary

**What changed and why**  
Adds a guard in rocm_unquantized_gemm_impl that skips AITER's tuned GEMM (tgemm.mm) and falls back to F.linear when the output element count n*m >= 2^31 or when A or B spans >= 4 GiB, working around an int32 output-offset overflow and 4 GiB buffer descriptor limit in AITER's gfx950 FlyDSL A16W16 kernel (ROCm/aiter#6853). This fixes a startup memory access fault for MiniMax-M3-MXFP4 with --mm-encoder-tp-mode data on MI355X.

**Technical impact**  
Behavior change limited to the single vLLM call site of tgemm.mm: oversized GEMMs are rerouted to hipBLASLt instead of AITER's tuned dispatch, while all other shapes retain AITER tuning. The guard is not gated on gfx950 in the code despite the PR description claiming it is, so it applies on any ROCm platform where tgemm is enabled, though the condition only triggers at very large shapes.

**Potential risks**  
The guard is applied unconditionally rather than being restricted to gfx950 as described, so non-gfx950 platforms with tgemm enabled would also skip AITER tuning for large GEMMs, potentially losing tuned performance there. The 4 GiB check uses max(n, m) * k * element_size() as a proxy for A/B buffer size, which may not exactly match actual tensor byte sizes (e.g., if A and B have differing dimensions or non-contiguous layouts). No unit test is added, so regression coverage relies on manual hardware validation.

**Key insights**  
The fix is a targeted, minimal workaround at the only call site of tgemm.mm and is intended to be removed once vLLM's minimum AITER includes ROCm/aiter#6853. The PR provides solid kernel-level and end-to-end validation evidence, but the implementation diverges slightly from the stated gfx950-only scope, which reviewers should confirm is intentional.

The /dev/shm fallback path is also hardened: unlink-before-register to avoid orphaned tables, an available-host-memory check to avoid OOM kills, and mbind(MPOL_LOCAL) to escape --numa-bind confinement. get_available_memory is moved from weight_utils to cpu_resource_utils and reused.

**Technical impact**

Reported prefill gains of 3.7-10.3% on GB200 and large lookup latency reductions, with decode unchanged and GSM8K accuracy within noise. Adds a new dependency on cuda.bindings driver APIs and raw syscalls (mbind) for the NVIDIA path.

**Potential risks**  
The cuMem path relies on driver/kernel behavior (FABRIC handle support, __GFP_RETRY_MAYFAIL semantics, NVreg_EnableSystemMemoryPools) that varies across driver versions and hardware, and the support probe is cached once per process. The mbind syscall numbers are hardcoded per architecture and silently degrade with only a warning on failure. The new available-memory pre-check makes /dev/shm sharing stricter and could disable sharing in memory-constrained or cgroup-limited deployments where it previously worked. The GPU view is built from a hand-rolled __cuda_array_interface__ with a weakref finalizer, which is subtle lifetime/ownership code that could leak or unmap prematurely if torch's retention assumptions change. Fallback correctness depends on every rank releasing and agreeing via gather_errors, so partial-failure paths are the main area to scrutinize.

**Key insights**  
The PR is well-scoped and defensively designed: allocation never OOMs, every failure path falls back to /dev/shm on all ranks, and the fallback path itself is made safer (orphan prevention, OOM avoidance, NUMA spill). The performance data is thorough and the sort-threshold change is justified by microbenchmarks. Reviewers should focus on the cuMem handle lifetime/finalizer logic, the hardcoded mbind syscall table, the stricter host-memory gate's effect on existing deployments, and whether the fabric support probe and chunked reserve logic behave correctly under concurrent multi-process memory pressure.
