  - `vllm/models/hy_v4/nvidia/attention.py`
  - `vllm/models/hy_v4/nvidia/model.py`
  - `vllm/models/minimax_m3/amd/model.py`

### Summary

**What changed and why**  
Fixes a GSM8K accuracy regression under pipeline parallelism for GLM-5.x/DeepSeek-V3.2-style models that reuse a previous layer's indexer top-k. When a PP stage begins on a top-k-reusing layer, that stage previously read a stale top-k buffer from the prior step/batch. The PR adds shared helpers in model_executor/models/utils.py (compute_skip_topk_layers, pp_splits_layer_sharing, pp_topk_buffers, copy_pp_buffers) and threads the top-k buffer through IntermediateTensors across stage boundaries for DSA (NVIDIA/AMD/dots3) and HY-V4 (NVIDIA/AMD), while rejecting the unsupported MiniMax-M3 AMD use_index_cache PP case.

**Technical impact**  
Adds cross-stage state transfer of a TP-replicated, token-major int32 top-k buffer alongside hidden_states/residual in IntermediateTensors, with empty-tensor allocation and copy-in on receive. Refactors compute_skip_topk_layers out of HY-V4 attention into shared utils and replaces the duplicated logic in DSA attention init, plus introduces sparse_layer_ids for HY-V4. Behavior is unchanged for models/partitions that don't split a top-k sharing group, but PP splits that do now incur an extra per-step tensor send.

**Potential risks**  
The buffer is sliced by positions.shape[0] (or full_num_tokens) on send and copied by received tensor shape on receive, so mismatches in token counts or buffer sizing could cause silent truncation or shape errors. The new NotImplementedError for MiniMax-M3 AMD use_index_cache is a behavior change that could break existing configs relying on PP there. Refactoring compute_skip_topk_layers into shared utils touches HY-V4 weight-skipping logic, so any subtle semantic drift could affect indexer weight loading. Test coverage is unit-level plus external GSM8K runs; ROCm PP results show ~1.3 point run-to-run variance, so the accuracy gain there is not cleanly separated.

**Key insights**  
Root cause is well-isolated: aligning the PP partition to a top-k group boundary restored accuracy, confirming stale top-k reads. The fix is a reasonable generalization of existing PP intermediate-tensor plumbing to carry cross-layer state. The shared helpers reduce duplication and the added test covers stage-boundary detection, empty tensor allocation, and middle-stage receive/forward. Main residual concerns are token-count edge cases in buffer slicing and the new hard failure for MiniMax-M3 AMD PP.

  - `tests/v1/core/test_kv_cache_utils.py`
  - `tests/v1/core/test_prompt_block_hash_vectors.py`
  - `vllm/v1/core/kv_cache_utils.py`
  - `vllm/v1/engine/__init__.py`
  - `vllm/v1/engine/core.py`
  - `vllm/v1/request.py`

### Summary

**What changed and why**  
This PR moves prompt block hashing from the engine's input thread into the Rust frontend to avoid holding the GIL while hashing long prompts, which stalls the engine loop. It adds a PrefixHashConfig to the engine ready response, a block_hashes field on EngineCoreRequest, a Rust PromptBlockHasher that reproduces the engine's sha256 and sha256_cbor encodings (pickle protocol 5 and canonical CBOR) including LoRA, cache-salt and lookahead extra keys, and engine-side logic to accept frontend hashes after a count check. It also adds cross-language hash vectors and tests to keep the two implementations byte-identical.

**Technical impact**  
The engine now advertises its prefix hash config and accepts precomputed block hashes, seeding Request.block_hashes so the existing hasher continues from there for output-completed blocks. The Rust client builds a hasher only when all engines report the same supported config, and falls back to engine-side hashing for unsupported cases (multimodal, prompt embeds, xxhash, oversized pickle frames, memoization-prone strings). The Python frontend does not send hashes yet, so behavior is unchanged for it; the Rust frontend gains the optimization with reported decode throughput gains of 9.6% (sha256) and 39% (sha256_cbor).

**Potential risks**  
The core risk is hash divergence between the Rust encoder and the engine's Python pickler/CBOR encoder, which would silently break prefix-cache hits, KV connector matching, or KV events across instances. The PR mitigates this with known-answer vectors, a Python test pinning the engine to those vectors, and conservative fallbacks, but the pickle encoder deliberately does not reproduce 64 KiB framing or memoization and relies on heuristics (may_share_pickled_objects) to bail out. The count-only validation in frontend_block_hashes means a frontend bug producing the right number of wrong hashes would not be caught at runtime. The new Dockerfile.cpu and Buildkite changes add a cross-tree test dependency that could break if the vectors file moves.

**Key insights**  
The design cleanly separates concerns: the engine remains the source of truth for hash semantics, the frontend only computes when it can prove byte-identical output, and unsupported requests fall back transparently.
