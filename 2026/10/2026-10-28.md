### Summary

**What changed and why**  
The PR converts GPU<->CPU KV transfer faults in OffloadingConnector from fatal engine errors into reported failures, matching the connector's declared best-effort cache semantics. It catches RuntimeError in transfer_async (clearing the pending device error so the next kernel launch does not die), downgrades poll/wait faults to TransferResult(success=False), propagates failures through OffloadingWorkerMetadata.failed_jobs, and makes the scheduler drop failed stores and route failed loads through failed_recving with kv_load_failure_policy handling (fail vs recompute, with load_failed suppressing retries).

**Technical impact**  
Changes span the offloading worker, scheduler, metadata aggregation, and connector API (new get_transfer_results override and take_failed_recving). Failed jobs still complete and fence stream ordering via end_event, but their stream/event/buffer resources are intentionally not returned to pools. Failed stores call complete_store(success=False) so chunks are never published; failed loads mark the request load_failed and either error out or recompute. Only RuntimeError is downgraded; other exceptions still propagate. Scope is limited to the batch-copy path (ROCm 7.1+, CUDA 12.8+); the per-copy fallback is unchanged.

**Potential risks**  
Resource leak risk: failed transfers never return stream/event/buffer pool entries, so repeated faults could exhaust pools. The load_failed flag permanently disables offloaded-cache reads for that request, which is intended but could mask recoverable transient faults. The sync-load failure path still raises RuntimeError, so sync loads can still take down the engine. The per-copy fallback path ignores cudaMemcpyAsync return codes, leaving a gap on older drivers. Correctness depends on end_event being recordable after a fault; if recording fails, the error propagates. Test coverage is strong (unit, real-weights, and ROCm fault injection), but the engine-level fault injection is ROCm-specific and not part of CI.

**Key insights**  
The core insight is that a caught copy fault leaves a pending device error that would kill the next kernel launch, so _clear_pending_device_error is essential on ROCm. Deferring failure reporting until end_event completes is necessary because earlier copies in the same batch may still be in flight. The PR correctly reuses the existing failed_recving design from Mooncake (#50984, #56855) rather than inventing a new channel, and the load_failed flag prevents infinite reload loops on persistent faults. The test suite is well-structured, including a success-path test to prevent vacuous guards and per-fix revert validation.

### Summary

**What changed and why**  
Adds two ROCm decode-time fastpaths for DeepSeek-V4.x block32 MXFP8 linears on MI355X: a fused tiny-M (M<=8) activation quant inside the block32 packed GEMM kernel (replacing a separate quant launch), and a weight-size guard that diverts the lm_head skinny-GEMM (wvSplitK) dispatch to the generic hipBLASLt GEMM when weights exceed an L3-derived byte cap at 1 < n <= 5. Includes new env vars (VLLM_SKINNY_GEMM_MAX_WEIGHT_BYTES, debug kill switches), hardware L3 detection via amdsmi, and ~28 new tests. Motivation is a measured ~2% decode ITL improvement.

**Technical impact**  
Changes the serving hot path for MXFP8 block32 linears and lm_head GEMM dispatch. The fused kernel is claimed bit-exact against the stock two-launch path at eligible shapes with bit-identical fallbacks for ineligible inputs (non-contiguous, fp32, M>8). The skinny-GEMM guard is explicitly NOT bit-exact (different GEMM kernel/accumulation order), so lm_head numerics shift within bf16 tolerance. Adds a per-process cached hardware query (amdsmi) and a per-decode-step predicate, plus one-shot census warnings. Kill switches allow reverting each lever independently.

**Potential risks**  
The skinny-GEMM guard changes numerics on large lm_head shards and relies on an amdsmi L3 read with a 256 MiB fallback; on parts where L3 is smaller (e.g. MI300X 128 MiB) the auto cap differs, and amdsmi availability/failure paths affect dispatch. The fused kernel duplicates quant arithmetic in Triton, so any divergence from _mxfp8_quant_triton_kernel would silently break bit-exactness; correctness depends on the shape-table hit and K-alignment assumptions. New env vars conflict textually with sibling PRs at the same envs.py anchor. Fused-quant tests are CDNA4-gated and skip on MI300 CI pools, so CI coverage is limited to local MI355X validation. The profiler-flake hardening in tests suggests some test fragility.

**Key insights**  
Well-scoped, independently revertible optimizations with strong empirical validation (12-cycle A/B, nightly re-verification, rebase re-check, gsm8k accuracy within noise band) and explicit bit-exactness contracts plus a QDQ fp32 reference to catch GEMM regressions. The guard's mechanism (weight re-reads vs L2/L3 bandwidth) is clearly distinguished from orthogonal VGPR-spill fixes. Main review focus should be on the fused kernel's arithmetic fidelity, the amdsmi L3 detection robustness, and the non-bit-exact lm_head swap's numerical tolerance.

## 4. [[Bugfix][KV Offload][P2P] Fail a timed-out load at once, defer releasing its slots](https://github.com/vllm-project/vllm/pull/64256)


### Base Information

- **PR Number:** #64256
- **Author:** [liranschour](https://github.com/liranschour)
- **Merged By:** [orozery](https://github.com/orozery)
- **Merged time:** 2026-10-28 22:23:14
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/64256/files) (5):**
  - `tests/v1/kv_offload/tiering/p2p/test_manager.py`
  - `tests/v1/kv_offload/tiering/p2p/test_sessions.py`
  - `vllm/v1/kv_offload/tiering/p2p/manager.py`
  - `vllm/v1/kv_offload/tiering/p2p/session/client.py`
  - `vllm/v1/kv_offload/tiering/p2p/session/session.py`

### Summary

**What changed and why**  
This PR changes P2P KV offload load-failure semantics so a timed-out load (or finish() of an in-flight load) is reported failed immediately with a deferred_release Event, instead of waiting for AbortAck or the abort-ack timeout. The destination chunks are held out of the free pool until the peer confirms its WRITEs ended (AbortAck/late TransferDone) or the session closes. It builds on the merged deferred-release API (#63779) and folds in #63715's disconnect-on-missed-AbortAck, replacing the earlier quarantine approach. The goal is faster fallback (10s/30s instead of 15s/35s) without risking early slot reuse while a peer WRITE may still land.

**Technical impact**  
LoadResult gains an optional deferred_release Event, propagated through the P2P manager into JobResult so the TieringManager holds chunks until the event is set. ClientRole now emits exactly one result per job: _abort_load sends AbortFetch and reports failure with a release event; on_abort_ack and late on_transfer_done only set the event; a missed AbortAck records expired_abort_ack, which P2PSession escalates into a peer disconnect (new _abort_ack_fault surfaced via data_plane_fault), and close() sets all held events. drain_jobs() keeps polling while held loads remain, bounded by the abort-ack timeout plus disconnect.

**Potential risks**  
The correctness of holding chunks depends on every hold being bounded: if a peer neither acks nor is disconnected, or if NIXL teardown does not fence a stalled WRITE, chunks could be held or reused unsafely (the PR explicitly leaves the stalled-WRITE-at-teardown case open on #63602). The new assert load.release is not None in on_abort_ack assumes every abort path sets a release; any path that aborts without going through _abort_load would trip it. Disconnecting on a missed AbortAck is a behavior change that could reduce availability against slow-but-alive peers. GPU e2e validation is still pending, so real transport behavior is unverified.

**Key insights**  
The core design insight is separating a job's outcome from its memory release, giving each job exactly one result and letting the release carry no outcome, which avoids the parallel quarantine tables and reset_cache rejection of #61667. Folding the disconnect-on-missed-AbortAck into this PR makes every hold bounded and satisfies the deferred-release contract that all events are set before drain_jobs() returns. Tests are meaningful, driving a real TieringOffloadingManager and P2PSession and asserting the chunk is held (num_deferred_release_chunks) and freed only after AbortAck, but the remaining stalled-WRITE teardown gap and pending GPU e2e are the main open validation concerns.
