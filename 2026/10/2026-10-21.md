### Summary

**What changed and why**  
Fixes a bug where JinaVL-based rerankers (jina-reranker-m0) lost their appended score token (id 100) when truncate_prompt_tokens was binding, causing /score and /rerank to silently score an ordinary token. The fix reserves room for tokens appended by post_process_tokens by shrinking max_total_tokens, truncate_prompt_tokens and pad_prompt_tokens via a new reserve_tokens helper, then appends the tokens after truncation/padding. A unit test verifies the score token survives truncation for both explicit and -1 truncation limits.

**Technical impact**  
Changes CrossEncoderIOProcessor.render ordering: post_process_tokens now runs after apply_post_tokenization instead of inside get_score_prompt, and length limits are reduced by the number of appended tokens (derived once via a cached_property probing post_process_tokens on an empty prompt). **Potential risks**  
The cached_property probe calls model.post_process_tokens on an empty TokensPrompt, which assumes the method is side-effect free and safe on empty input; a model implementation that mutates state or errors on empty prompts could break. Moving post_process_tokens out of get_score_prompt could affect any other code path that relied on it being applied there. The shrink helper clamps to 0, so very small limits combined with appended tokens could yield degenerate prompts. Validation is limited to one model and manual server runs; broader cross-encoder regression coverage is thin.

**Key insights**  
The root cause is an ordering regression from #28631 where truncation moved after get_score_prompt and thus over the appended score token. Reserving room rather than appending after truncation avoids exceeding limits, matching the reference compute_score behavior. The fix is well-scoped to CrossEncoderIOProcessor plus a small utility, and the before/after score tables convincingly show the bug and fix, though the empty-prompt probe is the main design assumption worth scrutinizing.

  - `vllm/model_executor/layers/fused_moe/runner/moe_runner.py`

### Summary

**What changed and why**  
Changes the custom op tags on vllm.moe_forward and vllm.moe_forward_shared from needs_fixed_stride_order to needs_exact_strides, and adds a CUDA-only unit test that compiles a mocked MoE block with Inductor and asserts the shared-experts input arrives packed. This fixes a correctness bug where Inductor passed a strided alias of the padded routed buffer to the shared expert, whose NVFP4 quant kernel assumes packed rows, producing garbage output under torch.compile for Nemotron-3-Nano NVFP4 TRTLLM MoE.

**Technical impact**  
Restores the torch 2.8+ default stride semantics for these two ops, aligning them with other MoE custom ops that already dropped the torch 2.6 workaround. Inductor may now insert one (tokens, hidden) copy per MoE layer when the hidden dim is padded, but no copy occurs when no padding happens and no host sync is added. The change is limited to two tag lines plus a test, with no other code paths touched.

**Potential risks**  
The added per-layer copy when hidden dim is padded could slightly reduce performance for affected models, though the PR reports eager-parity accuracy and no measured regression. The new test relies on Inductor internals, mocked MoERunnerInterface, and CUDA availability, so it may be brittle across torch versions or CI environments. The PR also notes that compile caches are not invalidated by tag changes, so dev installs may silently keep the old broken graph until caches are cleared, and no GSM8K CI config currently covers this path.

**Key insights**  
The root cause is a stride-order vs exact-stride mismatch: needs_fixed_stride_order only pins stride order, allowing Inductor to alias the padded buffer with a non-packed stride that the NVFP4 quant kernel misreads. The fix is minimal and well-justified, with strong before/after GSM8K evidence and a targeted regression test, but the PR explicitly leaves other needs_fixed_stride_order call sites unanalyzed and defers CI eval coverage to a follow-up.

### Summary

**What changed and why**  
The Rust DeepSeek DSML tool parsers (V3.2, V4, V4.1) now match DSML markers by token identity rather than by decoded text spelling. Each marker is built as Marker::text(...).then_special(｜DSML｜).then_text(...), so a marker only counts when its inner ｜DSML｜ came from the dedicated added token; ordinary-token spellings (e.g. the model quoting the format) stay as text. The parser buffer changed from String to DecodedText and now uses parse_buffered_event_attributed and take_until_marker for the invoke closer. A spelling fallback is kept for tokenizers lacking the ｜DSML｜ token (DeepSeek V3.2-Exp).

**Technical impact**  
Changes the core DSML parsing path: the buffer is now attributed DecodedText, markers are resolved against the tokenizer at construction, and the invoke closer is found via streaming marker scan so ordinary closers inside string values no longer terminate the invoke early. Constructors now take a tokenizer, and test/bench utilities were updated to feed attributed chunks through the real incremental decoder. Behavior with the dedicated token is intended to be unchanged; only ordinary-token spellings differ. Benchmarks show a measurable cost (~2-3x on the fixtures) attributed to carrying one attribution per token, not the guard itself.
