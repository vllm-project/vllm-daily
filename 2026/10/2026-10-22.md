### Summary

**What changed and why**  
The PR fixes encoder-cache identity collisions in DeepSeek-VL2 (and applies the same pattern to H2OVL and Unlimited-OCR) where the same raw image processed under different cropping modes produced different encoder outputs but shared the same cache hash. It overrides _get_mm_hashes() in each model processor to fold the effective cropping/MSAC flag into the raw-image hash, while leaving precomputed image embeddings untouched. Tests were added for processing and generation paths covering cropping boundaries, UUIDs, embeddings, and request ordering.

**Technical impact**  
Cache keys for raw images in these three models now incorporate a cropping-mode discriminator, so encoder outputs for cropped vs. uncropped variants are stored separately and cannot be incorrectly reused. Precomputed embedding identities and within-mode identities are preserved, so existing cache hits for consistent requests remain. Unlimited-OCR also now derives the effective crop_mode from merged mm kwargs rather than the module constant, aligning prompt replacement with the processor's actual behavior.

**Potential risks**  
The fix is model-specific and relies on duplicating the cropping-decision logic (len(images) <= 2 for DeepSeek-VL2, len==1 for H2OVL/Unlimited-OCR) in the hashing path; if the underlying processor's cropping rule changes, the hash logic could silently drift and reintroduce collisions. The hash_kwargs approach changes hash values for all raw images in these models, which invalidates previously cached entries (acceptable but worth noting). Coverage is limited to three models, so other processors with count-dependent preprocessing may still have the same latent bug.

**Key insights**  
The root cause is a mismatch between preprocessing cache bypass and encoder cache identity: the processor skipped its own cache for larger requests but still emitted identical image hashes for different encoder outputs. Folding the effective preprocessing mode into the hash is a clean, minimal fix that preserves embedding identities. The added tests are well-targeted, including the generation test that fails before the fix, and the real-weights validation on H800 provides good confidence that caching still works and outputs match unpatched behavior.

## 3. [[MM][Mistral] Use real-valued RoPE in the compiled Pixtral ViT](https://github.com/vllm-project/vllm/pull/63145)


### Base Information

- **PR Number:** #63145

- **Merged time:** 2026-10-22 23:08:54
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/63145/files) (2):**
  - `tests/models/multimodal/generation/test_pixtral.py`
  - `vllm/model_executor/models/pixtral.py`

### Summary

**What changed and why**  
The Pixtral ViT RoPE is reworked so that under torch.compile it uses a real-valued rotation (cos/sin) instead of a complex multiply, because Inductor does not generate code for complex operators and falls back to eager, losing most compile gains. The freqs_cis cache now stores torch.view_as_real of the complex frequencies, and apply_rotary_emb_vit dispatches on torch.compiler.is_compiling() to keep the complex path in eager mode. A new test verifies the real path matches the complex one numerically.

**Technical impact**  
Compiled Pixtral ViT encoder latency improves (claimed 8-25% on H100), and the complex-operator fallback warning disappears. Eager numerics are preserved since the complex multiply is retained there. The change is scoped to the Mistral-format Pixtral path and alters the freqs_cis tensor layout/dtype, which affects downstream consumers such as the CUDA-graph capture inputs in #56277 that must now supply a real (capacity, head_dim/2, 2) tensor.

**Potential risks**  
The compile/eager dispatch relies on torch.compiler.is_compiling(), so behavior can differ between compiled and eager execution and any future callers passing complex freqs_cis will hit the new float32 assertion. The real path uses torch.stack and multiple elementwise ops, which may be slower if compilation is partial or graph breaks occur. The interaction with #56277 CUDA-graph capture is a coordination risk: if that PR's complex64 ones are not updated, capture will fail the dtype assertion. Benchmark gains are measured on a single H100 configuration and may not generalize.

**Key insights**  
The core insight is that complex ops block Inductor codegen, so expressing RoPE as real arithmetic unlocks the compile speedup while keeping eager on the faster single-kernel complex path. The added unit test comparing real vs complex outputs is a good guard for numerical equivalence. Reviewers should confirm the #56277 dependency is handled and that the new freqs_cis dtype/shape contract is documented for other call sites.
