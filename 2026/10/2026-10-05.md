**What changed and why**

**Key insights**  
This is a targeted packaging fix addressing a real installability failure caused by custom-index-only dependencies.   - `vllm/model_executor/layers/fused_moe/oracle/mxfp4.py`
  - `vllm/model_executor/layers/quantization/utils/mxfp4_utils.py`

### Summary

**What changed and why**  
This PR enables the OAI Triton MXFP4 MoE kernels on SM12x (consumer Blackwell, e.g. RTX 5090) as a follow-up to #41028, which previously restricted Triton to SM90/SM100. It widens the device support window to cap < (13,0), adds SM12x-specific opt-flag constraints (is_persistent, epilogue_subtile=1), and introduces a block_m cap of 32 via _sm12x_block_m/_constrain_sm12x_block_m to fit the 99KB shared memory budget. Because Triton prefills ~10% slower than Marlin on SM12x, the backend priority list is reordered so MARLIN remains the default while TRITON stays opt-in via --moe-backend triton.

**Technical impact**  
SM12x devices can now run the Triton MXFP4 MoE path, gaining roughly +8% kvcache pool versus Marlin due to reduced alignment overhead, at equal decode speed but ~10% slower prefill. The change touches kernel dispatch (gpt_oss_triton_kernels_moe.py), backend selection (oracle/mxfp4.py), and quantization swizzling (mxfp4_utils.py), plus adds unit tests for the block_m heuristic and backend priority ordering. Default behavior on SM12x is unchanged (Marlin), so the impact is opt-in for users who want the kvcache benefit.

**Potential risks**  
The block_m cap of 32 is a hardcoded heuristic tied to the 99KB smem budget and triton_kernels 3.5.1 behavior, so it may become suboptimal or incorrect on future hardware or library versions. The epilogue_subtile=1 constraint is described as a workaround for a triton_kernels codegen bug (SWAP_XW with subtiled epilogue), which could mask a deeper issue or break if upstream fixes it differently. Widening the device window to < (13,0) also implicitly enables SM121 and any future SM12x variants without explicit validation, and the monkeypatched tests rely on platform mocking that may not fully reflect real device behavior.

**Key insights**  
The PR makes a deliberate performance tradeoff: Triton on SM12x is slower for prefill but yields a larger kvcache pool, so the authors keep Marlin as default and expose Triton as an explicit opt-in rather than silently switching backends. The core technical challenge is shared-memory pressure on consumer Blackwell, addressed by pinning block_m and forcing persistent/subtiled epilogue flags. Test coverage is reasonable for the new heuristic and priority logic, though end-to-end validation on actual SM12x hardware is only described in the PR text rather than automated.

### Base Information

- **Author:** [aoshen02](https://github.com/aoshen02)

- **Merged time:** 2026-10-05 22:20:10
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/60064/files) (5):**
  - `tests/kernels/test_dsv41_mega_attn_layouts.py`
  - `vllm/models/deepseek_v41/common/ops/fused_layout.py`
  - `vllm/models/deepseek_v41/nvidia/dspark.py`
  - `vllm/models/deepseek_v41/nvidia/flash_mla_mega_attn.py`
  - `vllm/models/deepseek_v41/nvidia/model.py`

### Summary

**What changed and why**  
DeepSeek-V4.1 mega attention previously permuted wq_b rows and wo_a columns into the FlashMLA kernel layout in a post-load step (finalize_loaded_weights), which only worked if it ran before the linear quant hooks and was skipped on dummy loads and layerwise reloads. This PR moves the permutation into the weight loaders via a new permute_on_load helper that wraps each parameter's weight_loader with composed_weight_loader, and removes the now-unnecessary finalize_loaded_weights, _fused_layouts_ready, finalize_mega_attn_weights, and DSpark's _finalize_attn.

**Technical impact**  
Each loaded shard of wq_b.weight, wq_b.weight_scale, wo_a.weight, and wo_a.weight_scale is now gathered into the fused layout immediately after being written, so the quant hooks see already-permuted tensors exactly as a real load did on main. Permutations are computed from the module's own n_local_heads/head_dim rather than tensor shapes, fixing the root cause where the CuteDSL hook transposed wq_b to [K, N] and made head_dim derivation wrong. This fixes the SM100 dummy-load startup crash and restores accuracy after reload_weights, while real-load checksums reportedly match main on all ranks.

**Potential risks**  
The change relies on each of these tensors being loaded by a single weight_loader call with no stacked mapping, so the whole local shard is present when the permutation runs; any future stacked or sharded loading path could silently produce incorrect layouts. Wrapping weight_loader mutates parameter attributes at init time, which could interact with other code that inspects or replaces weight_loader. The PR notes that with MegaMoE, reload_weights still collapses for a separate reason until #57733 lands, so this fix is a prerequisite rather than a complete solution, and the DP4 reload path remains unmeasurable due to a pre-existing OOM.

**Key insights**  
Moving the permutation from a post-load finalize step into the weight loader removes an ordering dependency on quant hooks and makes the behavior correct for dummy loads and layerwise reloads, which is a cleaner design than the idempotency-guarded finalize approach. The net deletion of ~46 lines plus a focused kernel test that validates permuted GEMMs against a permuted-activation reference is good evidence. The main residual concern is the implicit assumption of single-call, non-stacked loading for these four tensors, which is not enforced by an assertion.

### Summary

**What changed and why**  
This PR adds a new DecoderReplayCudaGraphManager that captures the DeepSeek-V4.1 decoder-side SWA bounded replay layers in their own breakable PIECEWISE CUDA graphs, keyed by the replay batch's padded token count, and makes PIECEWISE model graphs at or above a new decoder_replay_trim_threshold (default 768) break out to those replay layers. It also introduces a ReplayBatch dataclass, a ModelState.capture_inner_cudagraphs hook called by the runner, new CompilationConfig options (cudagraph_decoder_replay, decoder_replay_cudagraph_capture_sizes, decoder_replay_trim_threshold), and updates _prepare_replay_batch to pad the replay batch to the graph fitting the largest DP rank. The motivation is that eager replay-layer launches are launch-bound and leave the GPU idle, so running them in graphs removes that idle time.

**Technical impact**  
Behavior changes for DeepSeek-V4.1 with breakable PIECEWISE graphs: replay layers now run in dedicated CUDA graphs with static input buffers, attention runs in eager breaks, and PIECEWISE graphs above the threshold break out to the replay batch. It adds a new capture hook to the ModelState interface (no-op default), new config validation, and DP coordination that pads all ranks to one replay graph size. Reported prefill TTFT gains are 1.1x-1.6x over the parent and up to 1.7x over the off baseline, with the largest gains on TP4 long prompts.

**Potential risks**  
The feature is on by default for DeepSeek-V4.1 with breakable piecewise graphs, so regressions would affect default paths; it is disabled under LoRA, prompt embeddings, and non-first PP ranks, but those combinations are less exercised. Static input buffers and fixed break-output buffers sized by the first (largest) capture could break if shapes or dtypes vary, and the dummy-batch capture path reuses runtime logic, so subtle mismatches between capture and real steps are possible. DP padding to the largest rank's replay graph may increase work on smaller ranks, and the new config fields and validation add surface area. The PR notes DEP2 gains are limited to short steps, so benefits are topology-dependent.

**Key insights**  
The core idea is to treat the replay layers as a separate graph-capturable unit rather than nesting them in the model graph, which avoids the uniform-batch limitation of the SWA and sparse MLA builders by running attention in eager breaks. Capturing on a dummy batch that reuses the runtime path keeps the graph reading the same buffers a real step fills, and keying graphs by padded token count with DP-wide padding keeps all ranks in lockstep. The benchmark analysis correctly attributes TP4 gains to removing launch-bound idle time in layers 21-39, while DEP2 already hides those launches behind layers 0-20.
