### Summary

**What changed and why**  
Adds an opt-in specialized decode path for Kimi-K3 on MI355X (gfx950) at TP8, enabled via additional_config={"decode_backend": "latency_specialized"}. It introduces a new vllm/models/kimi_k3/amd/specialized_decode/ package (~6.3k lines) containing FlyDSL MonoKernels (K1 KDA layer, K2 o_proj+MoE layer), a runtime executor with plan/step routing, startup refusals, fail-stop health words, peer-memory TP all-reduces, and a new Buildkite step plus CPU/GPU/engine tests. The existing Kimi-K3 files only gain thin hooks (config check in __init__, plan in forward, step.layer(i) in the layer loop, after_step in compute_logits, skip_o_proj in MLA, get_model_state_cls).

**Technical impact**  
Default behavior is unchanged (decode_backend=auto returns None and nothing is checked). When enabled, pure spec-verify steps of up to 8 rows run persistent kernels that read vLLM's loaded weights and KDA states in place, with in-kernel TP all-reduces over peer memory, while all other steps (prefill, mixed, wider, PIECEWISE) fall back to vLLM's layers. Reported gains are ~20% TPOT reduction and ~23% throughput at c1/k7, with GSM8K/GPQA/AIME/NIAH accuracy statistically unchanged. The design is default-deny with staged refusals (config, weights, KV caches) agreed across TP ranks, and a fail-stop mechanism that stops all ranks together after a stalled in-kernel wait.

**Potential risks**  
The change is large and low-level (raw MFMA intrinsics, DPP shuffles, peer IPC, mailbox tagging), so correctness depends on many invariants (256 resident CTAs, uniform TP paths, epoch parity double-buffering, tag uniqueness). Fail-stop detection can take up to ~16 steps, so tokens from failed steps may reach clients before the engine stops. CUDA-graph replays with fewer requests than the captured graph rely on padding whole requests with a null state slot, which is subtle. The kernels read weights in place and refuse weight reloads, sleep mode, offload, and many parallelism modes, so any future feature touching those paths must keep the refusals accurate. The test suite depends on gfx950 hardware and a dummy model, so CI coverage outside MI355X is limited.

**Key insights**  
The PR is well-scoped: all new logic lives in one folder and the model files only call in, mirroring the NVIDIA (#61867) and GLM-5.2 (#60889) precedents. The refusal design (collect every reason, agree across TP ranks before any collective) and the fail-stop (sticky health words, non-blocking D2H copy, periodic TP agreement) directly address the deadlock risk inherent in in-kernel peer waits. The ISA byte-identical check across revisions and the 300 bit-identical graph replays are strong evidence of numerical stability. The main review focus should be the fail-stop latency window, the padded-replay semantics, and the correctness of the peer-memory handshake and tag scheme under graph capture.

### Summary

**What changed and why**  
Fixes a race where the async output handler invalidated sender-cache entries on the asyncio thread while the single-worker multimodal executor was mid-lookup/merge, causing 'Expected a cached item' assertions. The handler now records missed hashes via a new queue_mm_cache_invalidations helper before publishing outputs, and the renderer drains pending invalidations at the start of each _process_multimodal call on its own executor. Coalescing into a lock-protected set also bounds notification growth for uncached hashes.

**Technical impact**  
Moves cache invalidation from the asyncio thread to the renderer's single-worker executor, serializing it with lookups and merges. Adds a pending-set plus Lock to the renderer base, filters to currently-cached hashes, coalesces duplicates, and restores pending hashes on invalidation failure. Sync LLM path keeps direct invalidation; behavior is otherwise preserved with new tests covering queued renders, coalescing, and failure recovery.

**Potential risks**  
Pending records can briefly outlive the referenced cache entry, so counts may not equal live cache size; stale notifications become no-ops at the next render boundary. The membership check and invalidation run outside the lock, so a hash could be evicted between check and drain (benign no-op). Failure path re-raises after restoring pending state, which could surface errors on the executor. Validation is mostly CPU plus historical A800 HTTP stress on an earlier commit; the current cleanup lacks a rerun of that stress workload, and the pre-existing pooling/embedding cross-executor race is explicitly out of scope.

**Key insights**  
The fix correctly aligns invalidation ordering with the executor that performs cache lookups, and enqueue-before-publish ordering ensures already-queued renders see pending invalidations. Coalescing plus filtering to live hashes addresses unbounded growth on pre-rendered features traffic. Test coverage is strong for the race, coalescing, and failure paths, but reviewers should note the gap between the historical serving evidence and the final commit.

The PR is well-scoped with targeted regressions, but the hardcoded CPU-primary assumption and pending live validation are the main review concerns.

CMakeLists.txt lists the new sources and adds a configure-time guard that fails if a TU's ATTN_ENTRY is not dispatched.

**Technical impact**  
Behavior is intended to be identical: same template instantiations, same dispatch order, unchanged paged_attention signature and op registration, with only the head-size switch moved into attention_dispatch.cu and the block-size switch kept in the header. The build gains parallelism at the cost of a larger _rocm_C.abi3.so (196.3 MB to 219.2 MB, +11.6%, mostly duplicated device DWARF in .hip_fatbin) and ~30% more aggregate CPU work. Adding a new head size, dtype, or kv-cache combination now requires a new .cu file plus a CMakeLists.txt entry, and the CMake guard enforces dispatch reachability.

**Potential risks**  
The NAVI/gfx11/gfx12 #if regions are now evaluated once per TU and were only validated on MI350 (gfx950), so RDNA builds are untested here. The fp8_fp8 TUs are only exercised with VLLM_ROCM_FP8_MFMA_PAGE_ATTN=1 and no CI job sets it, and fp8_out_scale, the fp8_e4m3 alias, and the block-size default branch remain untested. The CMake guard relies on regex parsing of ATTN_ENTRY and ATTN_HEAD_SWITCH text, which is brittle if the macro formatting changes. The .so size increase and debug-info duplication are accepted tradeoffs deferred to a follow-up.

**Key insights**  
The root cause is that a HIP TU compiles on a single clang process with no thread-parallel equivalent, so MAX_JOBS cannot help the serial 9-minute tail; splitting instantiations across TUs is the effective lever, and -g0 would only recover ~18%. The rename to a .cuh preserves git blame, and hipify follows quoted includes so no special build handling is needed.
