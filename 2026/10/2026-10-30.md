### Summary

**What changed and why**  
Adds a new opt-in direct weight reload mode (VLLM_RELOAD_MODE=direct, default remains layerwise) that writes checkpoint tensors into the live model instead of rebuilding layers from meta. Cold start records each tensor's checkpoint layout and loader metadata; begin_direct_reload views re-laid-out tensors back to checkpoint layout on the same storage, and finish_direct_reload clears quant-method one-shot guards and reruns process_weights_after_loading. Supporting changes include a lifecycle dispatch module, config validation refusing incompatible setups (online quantization, torchao, offloading, LoRA, draft_lm_head_quantization, sharded_rdt), a module scan refusing online/humming methods, whole_storage growth in replace_parameter, Marlin bias written in place, and worker session handling for failed direct finishes.

**Technical impact**  
Introduces a second reload path across the NCCL, IPC and M2N weight-transfer engines and reload_weights, with env-driven dispatch fixed per process. It changes replace_parameter semantics under direct mode (can write into the existing storage beyond the old tensor's range) and alters Marlin bias handling to preserve addresses for captured CUDA graphs. Adds startup validation and runtime refusals that can reject previously valid configurations when direct mode is enabled, plus a new env var excluded from compile_factors.

**Potential risks**  
The delivery contract (every checkpoint tensor of modules whose PWAL changes layout or is non-idempotent must be resent) is not enforced until follow-up F2, so violations silently produce wrong outputs. A failed update leaves the model holding checkpoint-layout bytes with no rollback and no guard preventing serving, unlike layerwise mode which fails loudly on meta tensors. PWAL code that rebinds .data or reads stale aliases can move addresses or corrupt data; known remaining sites are platform-specific. The whole-storage views assume nothing else shares the storage, with no overlap check. E2E validation has not been rerun on the final code.

**Key insights**  
The design trades layerwise meta-materialization and per-layer bookkeeping for in-place writes plus a single PWAL rerun, relying on address stability for CUDA graphs. Correctness hinges on cold-start layout recording, guard clearing, and refusing configurations where PWAL is non-idempotent, replaces parameters, or shares storage across models. The PR is well-tested with a hazard-modeling toy test and explicit refusals, but the unenforced delivery contract and silent-corruption failure mode are the main concerns to resolve before enabling by default.

  - `vllm/distributed/kv_transfer/kv_connector/v1/nixl/push_worker.py`

### Summary

**What changed and why**  
Replaces all prior NIXL region-pairing strategies (index, PP window, layer-name routing, packed-row splitting) with a single layer-based pairing rule. Every worker now advertises region_members and layer_group_ids; a new _pair_regions builds a _RegionPairs record (remote, local, group, remote_regions, partner, groups_match, SSM/PLE regions) at handshake, and _compute_desc_ids takes a pairs=(regions, keys) argument instead of the old region_group_ids/uses_region_group_mapping modes. NIXL_CONNECTOR_VERSION bumps 15 to 16, and several helpers (_remote_region_offset, _align_remote_regions_by_layer, _split_remote_packed_rows, _transfer_layer_* tuples, _check_mamba_pairs, etc.) are removed.

**Technical impact**  
This is a deep refactor of the NIXL connector's core transfer path affecting pull and push, PP, HMA, packed MLA, and Mamba/SSM hybrids. Descriptor computation is unified: each pair reads/writes one region at its cache group's blocks, so regions shared by multiple groups transfer once per group from a single descriptor list. Handshake validation becomes stricter (missing layers, split-layer count mismatch, PP=1 peer holding extra layers, hybrid peers with differing cache groups are refused), and the version bump makes old peers incompatible via the hash. Tests are substantially rewritten to exercise _pair_regions and the new pairs argument.

**Potential risks**  
The change is large and touches every transfer topology, so regressions in edge cases (shared regions across groups, K/V-split layers, packed rows spanning multiple groups, SSM sub-regions) are plausible despite extensive simulation. The version bump breaks mixed-version P/D deployments. The PR notes that different cache-group plans on P and D are only covered by unit tests, and that pull from PP stages under HMA remains refused. Mamba PP is still unsupported and not validated. The author also flags a pre-existing BLHNC layout bug for Mamba models that is out of scope but could interact with the new pairing. Real-model evals for most topologies were not run, relying on byte-level simulation.

**Key insights**  
The central insight is that layer identity is a more robust pairing key than region index or layer-name routing, since it tolerates differing region groupings between P and D and between PP stages and the decoder. Comparing cache groups per layer catches mismatches even inside shared (-1) regions that a per-region check cannot see, guarding against divergent KV plans (e.g. sliding-window fallback when page sizes unify at one TP size but not the other). The simulation harness comparing every D page byte-for-byte against tagged P data, including TP/PP rank simulation and descriptor-swap negative tests, provides strong evidence of correctness for the covered layouts.

## 4. [[Bugfix][gRPC] Drain in-flight RPCs and engine work within --shutdown-timeout](https://github.com/vllm-project/vllm/pull/62967)


### Base Information

- **PR Number:** #62967
- **Author:** [mrn3088](https://github.com/mrn3088)
- **Merged By:** [njhill](https://github.com/njhill)
- **Merged time:** 2026-10-30 22:41:55
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/62967/files) (2):**
  - `tests/entrypoints/launchers/test_grpc_shutdown.py`
  - `vllm/entrypoints/launchers/grpc_server.py`

### Summary

**What changed and why**  
The gRPC launcher previously ignored --shutdown-timeout: it hardcoded a 5 s grace on server.stop() and called AsyncLLM.shutdown() without a timeout, so EngineCore was SIGKILLed ~5 s after SIGTERM. This PR introduces _drain_and_stop(), an _InflightRpcs server interceptor that counts non-subscription VllmEngine RPCs, and a polling wait that keeps EngineCore serving until in-flight RPCs and unfinished requests are done, then gives EngineCore the remaining budget plus a 5 s teardown floor. It also adds a second-signal fast path and moves AsyncLLM.shutdown() off the event loop.

**Technical impact**  
Shutdown sequencing for `vllm serve --grpc` now honors --shutdown-timeout: new RPCs are refused immediately, in-flight RPCs get max(N, 5 s), and EngineCore drains connector work (e.g. unread NIXL prefill blocks) before teardown. Default behavior with --shutdown-timeout 0 is preserved except that AsyncLLM.shutdown() now runs in an executor. The interceptor adds ~10 µs per RPC and negligible per-message overhead. A new unit test file exercises the drain logic against a real grpc.aio server with a fake AsyncLLM.

**Potential risks**  
The 0.1 s idle-poll heuristic can miss an RPC that gRPC accepted but has not yet dispatched, causing EngineCore to reject it (documented limitation). Supervisors must allow more than max(N, 5 s) + 5 s or pods will be killed mid-drain; Kubernetes terminationGracePeriodSeconds defaults may be too short. A prefill holding blocks no decode will read waits for the KV lease to expire. The interceptor relies on grpc.aio running interceptors in the RPC's serving task and on asyncio.current_task() being non-None, which is an implementation detail that could change across grpcio versions. Second-signal handling does not cut connector work short.

**Key insights**  
The root cause is that EngineCore's drain mode is never reached because the frontend kills it before the decode side reads NIXL blocks; the fix keeps EngineCore running normally rather than signalling it early, which avoids the _reject_add_in_shutdown aborts seen in the overlapped variant. Counting RPCs from dispatch (not from request receipt) is what makes requests still being preprocessed or queued at SIGTERM survive. The 5 s floor on both RPC grace and engine teardown ensures setting a timeout is never less graceful than the default. Validation is thorough across NIXL handoff, long streams, subscriptions, in-flight prefills, and second-signal cases, though each scenario ran only once.

**What changed and why**  
The AiterMLAMetadataBuilder previously sized its persistent decode metadata buffers with a single get_mla_metadata_info_v1 call at reorder_batch_threshold, but it actually builds metadata for every query length up to that threshold and aiter's buffer needs are non-monotonic in qlen (gfx950 tiles bf16 blocks of fewer than 128 packed rows by 64 instead of 128). **Technical impact**  
Behavior changes only in buffer sizing: configurations with speculative decoding can now allocate larger metadata buffers (e.g. ~55 KB extra int32 at 1024 requests for the reported case), while threshold-1 and the 16-head fp8 up-to-8 cases are unchanged. **Potential risks**  
The fix relies on the per-dimension max of independently computed shapes being a valid superset for all qlens, which holds only if aiter's buffer layout is dimension-wise compatible across qlens; this is plausible but not formally guaranteed by aiter. The new test uses a synthetic mock of get_mla_metadata_info_v1 rather than real aiter, so it validates the merge logic but not actual aiter behavior. CI does not run a DSpark draft on MI355X and validation used dummy weights, so real-weight Kimi-K3 behavior is unverified. Slightly increased memory footprint for some configs.

**Key insights**  
The root cause is a non-monotonic sizing function combined with a single sizing call at the maximum threshold, a subtle mismatch between what the builder sizes for and what it actually builds. Taking the elementwise max over all served qlens is a simple, low-risk fix that preserves existing behavior for the common cases. The PR is well-documented with concrete validation tables, but the lack of real-weight and CI coverage for the DSpark path is the main residual gap.

Level-1 sleep previously allocated a fresh pinned host buffer per offload via torch.empty(pin_memory=True), which torch's CachingHostAllocator rounds up to a power of two, inflating host memory up to ~2x offloaded bytes (85 GiB/GPU to ~578 GiB/node on Mistral Large TP8). The PR introduces an exact-size, reusable per-allocation CPU backup: cumem.py now creates an anonymous mmap wrapped with torch.frombuffer and pins it via cudaHostRegister, reuses it across sleep cycles, and releases it on free/discard; a shared _put_to_sleep helper centralizes the asleep transition. xpumem.py gets the same reuse/release semantics with its existing pinned tensor, and tests are strengthened with deterministic backup-size, pinning, reuse, and release assertions.

**Technical impact**  
Changes the lifetime and ownership model of AllocationData.cpu_backup_tensor: buffers now persist across wake-ups and are only released on allocation free or discard, with validity derived from is_asleep plus buffer presence rather than stored state. Host memory for level-1 sleep drops to exactly the offloaded size (23.00 to 16.92 GiB in the reported GB200 run) with unchanged sleep/wake latency and identical outputs. The cudaHostRegister failure path degrades gracefully to pageable memory with a one-time warning, and release_cpu_backup is non-raising so it is safe from the allocator free callback. No config, env var, API, or protocol changes.

**Potential risks**  
The XPU path is untested on hardware, and its _put_to_sleep drops the backup reference without an explicit unregister, relying on torch's allocator behavior. The invariant that an asleep allocation with a buffer holds current-sleep data depends on every asleep transition routing through _put_to_sleep; any future code path that sets is_asleep directly could restore stale data. Pinned buffers now live for the allocation's lifetime, so host memory stays reserved while awake (intended, matching prior behavior but worth noting for host-constrained deployments). The mmap-based buffer bypasses torch's host allocator, so any code assuming torch-managed pinned memory could be surprised.

**Key insights**  
The root cause was allocator rounding, not caching: the old code already retained backups across sleeps via torch's host cache, so the fix is to request exact-size memory and manage its lifetime explicitly. Centralizing the asleep transition in _put_to_sleep is the key correctness lever, making the 'asleep + buffer implies valid data' invariant enforceable. The test suite is notably strong, using deterministic checks (exact size, pinning, buffer pointer reuse, host allocator stats unchanged) instead of RSS thresholds, and the register-fails variant validates the fallback path that a prior revision got wrong.

### Summary

**What changed and why**  
Fixes a runtime OOM (#50699) in the DiffusionGemma sampler by moving logits projection from a single full-batch pass into per-tile projection inside the sampler loop, so peak memory scales with tile size rather than batch concurrency. Adds a profile_run hook (via new model_state methods compute_sample_logits and dummy_sampler_run) so the transient tiled-logits memory is reserved during profiling, and updates the model runner to route sampling through these hooks. The sampler now receives hidden states instead of precomputed logits and calls compute_logits per tile, with top_k/top_p and allowed-set masking applied per tile rather than to a full-batch logits tensor. The memory budget divisor increases from 3x to 5x to account for the extra projected-logits copies. The model runner's sample path and dummy sampler run are generalized through interface hooks, and profiling now reserves the tiled transient, which the PR reports increases max stable KV cache by ~36% at the cost of ~55k tokens at low utilization.

The new interface methods default to prior behavior, but any model_state subclass overriding custom_sampler must be checked for consistency with the new hidden-states contract.

**Key insights**  
The fix correctly targets the default sampler path rather than an opt-in env var, addressing the root cause of concurrency-scaled logits. The test suite is well-designed: it forces tiling via monkeypatched free-memory and asserts output equivalence plus a concrete peak-memory ratio. The main residual concern is the remaining prompt-logprobs OOM at high utilization and the loss of bit-identical outputs, both explicitly acknowledged and evaluated.

Behavior for unexpected non-mapped exceptions during handler execution is not explicitly covered by the new tests.

**Key insights**  
The root cause was overly broad exception handling conflating request preparation errors with handler execution errors, a common pattern that masks downstream error semantics. Separating the two concerns is a clean, low-complexity fix that reuses existing error mapping rather than introducing new logic. The parameterized test across both operations and three error classes provides good regression coverage for the specific bug.
