### Summary

**What changed and why**  
Implements lookahead block hashes for EAGLE/EAGLE3/MTP speculative decoding so the local prefix cache no longer drops the last matched block. Block hashes now incorporate the L tokens following each block (L=1, or k for multi-module MTP), gated by a new VllmConfig.num_hash_lookahead_tokens property and a SpeculativeConfig.disable_lookahead_block_hashes escape hatch; KV connectors keep legacy hashes. The change threads num_hash_lookahead_tokens through the block pool, coordinators, managers, scheduler, mamba checkpoint logic, and KV events (new BlockStored.lookahead_token_ids field), and removes the async scheduler's duplicate _update_request_with_output override in favor of shared logic in the base scheduler.

**Technical impact**  
Touches core prefix-caching, scheduler, KV cache manager/coordinator, mamba checkpoint, and KV event wire format. Hash format changes for EAGLE-family runs (new (E, token) tuple shape), so hashes are incompatible with legacy ones and with other engines unless the same setting is used. BlockStored gains a field that widens the msgpack map header (fixmap to map16) but preserves decoded contents. Scheduler now caches blocks at finish for spec/placeholder cases and clears block hashes for resumable streaming requests, which changes caching timing and correctness paths. Adds measurable hashing CPU cost (roughly +5% at B=128, +12.6% at B=16 on 32K prompts).

**Potential risks**  
Correctness depends on subtle invariants: the hash must only be emitted once the lookahead token is in all_token_ids, and the drafter's KV at the block's last position must be written by then; multi-module MTP and HiSparse paths are unit-tested only, not GPU-validated. Streaming-input sessions are explicitly unsupported and can leave unreachable cached blocks. Hybrid models can lose a hit when prompts diverge at the producer's last retained Mamba boundary. External KV-event consumers that index one hash per position must now key on lookahead tokens. The async scheduler override removal and new finish-time caching logic are behavior changes that could affect preemption/placeholder accounting. E2E and benchmark results cited are from the combined PR, not re-run on this split, and several GPU tests are still TODO.

**Key insights**  
The design is well-reasoned: including the successor token in the hash makes a cache hit provably equivalent to a cold run for draft KV, recovering floor((N-1)/B)*B hits instead of one unit less. The (E, token) tuple shape deliberately avoids colliding with legacy hashes of block size B+L, and the single E call per block keeps overhead moderate. The gating via num_hash_lookahead_tokens (0 = legacy) is a clean rollout mechanism, and the KV event field enables hash reconstruction. Main review focus should be on the scheduler caching/placeholder changes, the streaming-session limitation, and completing the pending GPU validation before part 2 extends connector support.

  - `vllm/models/deepseek_v41/common/engram.py`
  - `vllm/models/deepseek_v41/nvidia/model.py`

### Summary

**What changed and why**  
Replaces DP collectives (all_gather of hash ids plus all_to_all of rows) for GPU-resident Engram tables with a peer-read scheme: tables are row-sharded across the Engram DP group in symmetric memory, and each rank reads rows directly from the owning peer's HBM via a per-rank pointer table in the Triton lookup kernel (new PEER_ROWS constexpr). This is motivated by a real hang in FULL CUDA graph decode on GB200 DEP, where captured NCCL collectives deadlock next to MegaMoE kernels. It also touches parallel_state group creation (reusing _DP when ranks match, honoring embedding_across_dp for cross-node NVLink domains) and model.py to skip the hash gather.

**Technical impact**  
Adds a new execution path for Engram lookups that avoids collectives, barriers, and graph breaks, enabling GPU tables to work in full decode CUDA graphs. Changes group lifecycle (ENGRAM_DP may alias _DP, destroy logic updated) and adds symmetric-memory allocation with rendezvous and a registered peer_ptrs buffer. Behavior is gated on cpu_offload=false, TP=1, and NVLink P2P connectivity, falling back to existing collective path otherwise. Tests are extended to cover the peer path, group reuse, and P2P gating.

**Potential risks**  
The peer path relies on symmetric memory and NVLink P2P being available and correctly detected; misdetection could cause incorrect reads or crashes. Cross-node mode requires a single NVLink domain (GB200 NVL72), and the PR notes the exact NCCL/MegaMoE hang root cause was not pinned down, so the fix is a workaround rather than a diagnosed fix. The _ENGRAM_DP aliasing of _DP changes destroy ordering and could affect other code assuming distinct groups. Peer mode stages BF16 rows rather than packed MXFP8, so wkv quantizes its own input, a potential perf/accuracy difference. Accuracy shows a small drop (92.57% vs 92.87%) that may be within noise but is not fully explained.

**Key insights**  
The change is well-scoped with clear gating and fallbacks, and benchmarks show meaningful speedups (19.8us vs 46.7us microbenchmark, modest end-to-end gains) plus large memory savings. The main open concerns are the undiagnosed hang root cause, the reliance on NVLink domain assumptions, and the slight accuracy delta. Reviewers should scrutinize the symmetric-memory lifetime/cleanup, the _DP aliasing in destroy_model_parallel, and the P2P detection logic (in_the_same_node_as plus is_fully_connected).

  - `vllm/model_executor/model_loader/weight_cache/ipc_loader.py`
  - `vllm/model_executor/model_loader/weight_cache/protocol.py`

### Summary

**What changed and why**  
Adds moe_backend, linear_backend, and linear_backend_per_quant to WeightCacheKey so that IPC weight caches are invalidated when the engine's kernel backend differs from the daemon's. Previously, weights processed into one backend's layout (e.g. CUTLASS) could be silently mapped by an engine using a different backend (e.g. auto resolving to TRTLLM), producing garbage output with a healthy /health. The daemon and IPC loader now build the key from vllm_config.kernel_config, and a new parametrized test covers matching and mismatched backends on both initial load and standalone reload.

**Technical impact**  
Changes the cache key schema, so existing on-disk/daemon caches built without these fields will be treated as mismatches and fall back to disk loading (safe but a one-time cache miss). The key uses configured rather than resolved backends, which is conservative: a daemon on auto and an engine on the resolved backend counts as a miss, and two auto configs resolving differently (e.g. via env vars) are not caught. linear_backend_per_quant is normalized to a sorted tuple for hashability and stable comparison. The new kernel_config parameter is threaded through daemon, ipc_loader._fetch_entries, and load_weights, with a None default falling back to a fresh KernelConfig for backward compatibility.

**Potential risks**  
The unresolved-backend gap means the exact failure mode described (daemon auto vs engine auto resolving differently) remains possible and is only partially closed; the PR explicitly defers resolved-backend keying. Any code path constructing WeightCacheKey without kernel_config silently defaults to auto, which could mask mismatches if a caller forgets to pass it. The new test relies on monkeypatching several ipc_loader internals and SimpleNamespace configs, so it may be brittle to refactors. Cache invalidation on upgrade could cause unexpected cold-start latency for users relying on persistent caches.

**Key insights**  
This is a correctness fix for a silent data-corruption class of bug where wrong-layout weights are mapped without error. The conservative configured-backend approach trades some cache hit rate for safety and is a reasonable incremental step, but the follow-up to key on resolved backends is important to fully close the gap. The test design covering both initial load and standalone reload is good, since the reload path keys on current engine config rather than a recorded key.

After recovery, up to a scheduler step's worth of stores may be admitted before the next failure is observed, bounded by cooldown. The fix depends on external eviction to free space; if no evictor acts, the tier stays under pressure with only periodic probes. Interaction with in-flight admission-policy consolidation PRs (#53485/#51240/#51576) may require porting the signal to a different hook.

**Key insights**  
The root cause was that back-pressure only observed successful completions, so a tier failing fast produced no latency samples and never left the healthy fast-path. Feeding failures into the existing admission mechanism is a minimal, well-scoped fix that respects the established ownership split where eviction stays external to vLLM. The PR is well validated with a real tmpfs reproducer, unit tests, and independent E2E serving validation, and the p2p exclusion is a sound design choice since p2p store failures reflect per-request consumer behavior rather than tier health.

### Base Information

  - `vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py`
  - `vllm/v1/simple_kv_offload/manager.py`

### Summary

**What changed and why**  
Fixes a KV cache corruption bug in OffloadingConnector and SimpleCPUOffloadConnector for streaming-input sessions. A resumed streaming session arrives as a NewRequestData carrying its full block table, but yield_req_data previously flagged it as a delta, causing the connector to append the full table to the one it already held and store earlier chunks' KV under later chunks' keys. The fix renames the yield flag from 'preempted' to 'is_full_table' (True for new requests) and resets the accumulated block table on it, plus adds sync/async tests and a SimpleCPUOffload test.

**Technical impact**  
Changes the contract of yield_req_data: the third tuple element now signals a full block table rather than preemption. OffloadingConnector and SimpleCPUOffloadConnector reset their per-request block_ids when the flag is set, which is a no-op for non-streaming requests (table already empty) but corrects the duplicated-table case for resumed streaming sessions. NIXL and other consumers ignore the flag, so their behavior is unchanged. Test helpers gain req_id and resumable parameters to construct streaming sessions.

**Potential risks**  
Any out-of-tree or unlisted consumer of yield_req_data that relied on the old 'preempted' semantics could misinterpret the flag, since the meaning broadened from preemption-only to any full-table arrival. The SimpleCPUOffload fix only resets the table but the PR notes it still skips offloading the session's new blocks, so that connector remains partially incorrect pending a follow-up. Validation relies on unit tests plus a manual E2E comparison rather than a committed E2E test.

**Key insights**  
The root cause is a semantic mismatch: NewRequestData for a resumed streaming session is a full table, not a delta, and the connector's append logic assumed deltas. Renaming the flag to is_full_table makes the contract explicit and self-documenting. The added tests assert exact stored block tuples (0,1,2) vs (2,3,4), which directly pins the regression, and the E2E evidence (32/32 token match vs looping output on main) strongly supports the fix.
