### Summary

**What changed and why**  
This PR enables Mamba prefill checkpointing for the Kimi-K3 KDA path on ROCm, building on existing Mamba checkpoint infrastructure and the fused KDA prefill kernel that exposes intermediate states. It adds a new ROCm KDA checkpoint exporter, wires checkpoint metadata through the Kimi-K3 metadata builder and attention layer, and adds extensive unit tests plus fixes for non-contiguous block-table columns and padded zero-length sequences. The goal is to avoid an extra forward pass when context lengths are not multiples of the block size, improving TTFT by roughly 20% in agentic workloads on MI355X.

**Technical impact**  
Behavior changes in the Kimi-K3 ROCm prefill path: checkpoint metadata is now built and passed to the fused chunk kernel, the conv window is exported separately from the recurrent state, and NULL_BLOCK_ID is translated to -1 for the HIP kernel. The metadata builder overrides build() to re-key checkpoint rows by prefill_query_start_loc, and the layer now always uses the fused chunk path when available rather than disabling it for spec batches. New tests cover checkpoint offsets, state indices, conv window saving, strided block-table columns, and inert padded sequences.

**Potential risks**  
The change relies on the fused KDA chunk kernel being present and on the fixes from PR #59175 for scheduler/kv-cache-manager block boundary agreement; without those, checkpointing could waste allocation or drop cache. The new build() override and request-row reindexing are subtle and could misalign checkpoint rows for mixed spec/non-spec batches if assumptions about prefill_query_start_loc or num_decode_draft_tokens_cpu change. The non-contiguous output buffer fallback in kda_prefill adds an allocation on that path, and the checkpoint feature is gated by a config flag defaulting to True, so regressions would surface broadly on ROCm gfx950.

**Key insights**  
The core insight is that in align mamba cache mode the last prefill chunk can be done in one step if KDA states are recorded at block boundaries, eliminating a redundant forward pass. Correctness hinges on two invariants: checkpoint metadata must name a position the chunk kernel actually writes, and the saved conv window must match what a resumed prefill would have left. The PR also fixes real bugs around strided block-table columns and padded zero-length sequences, and the benchmark results show consistent TTFT reductions (15-47%) with neutral or slightly improved throughput and accuracy.

  - `vllm/v1/hisparse/runtime.py`

### Summary

**What changed and why**  
Fixes MTP acceptance collapse with HiSparse + speculative decoding under FULL CUDA graphs when the GPU pool saturates. Two root causes: (1) finish_forward mirrored all layers including draft layers before the drafter wrote them, so stale host rows were read after block reuse; (2) the residency resolver on the copy stream could read stale request ids because #59235 writes masked ids later on the compute stream. The PR tags draft attention layers, mirrors only target layers in finish_forward, defers draft-layer mirroring to the next start_step, and builds masked request ids on the copy stream into index-group-owned buffers.

**Technical impact**  
Introduces AttentionLayerBase.is_draft_layer, HiSparseCacheHandle.draft_layer, and a new _finish_previous_step path in the connector worker that mirrors prior-step draft rows and submits page transfers behind them on the same DMA stream. swap_in now requires num_valid_rows, and row_indices/request_ids move from SparseMLAIndexGroup to HiSparseRuntime. This changes ordering of host mirrors, page-clean reporting, and resolver input construction, affecting correctness of speculative decoding under FULL graphs and P/D transfers.

**Potential risks**  
The known limitation is that a host block freed after step N can be reallocated to a P/D import before step N's deferred copies land, since NIXL writes are not ordered against the copy stream; an imported request could rarely receive stale draft-layer rows (or stale rows for all layers in lazy mirror mode). The new ordering relies on host write events and DMA stream sequencing, so any future change to start_step/finish_forward ordering could reintroduce races. The added copy-stream build has a small measured cost (~1.2% per resolving layer) and the new num_valid_rows parameter is a breaking API change for swap_in callers.

**Key insights**  
The fix correctly separates target and draft mirror timing because the drafter writes after the target forward and re-prepares draft handles with decode-shaped metadata outside FULL graphs, making a combined end-of-step mirror fail metadata consistency checks. Deferring draft mirroring to the next start_step keeps pages from being reported clean before draft rows are queued, and building request ids on the copy stream after its wait closes the stale-id race. E2E results show acceptance length improving from 1.37 to 2.68 and throughput from 113-138 to 295 tok/s on B300, with unit and e2e tests covering both causes.

### Summary

**What changed and why**  
Fixes a HiSparse startup-check bug where the KV cache was sized from the model's grouped specs instead of the groups HiSparse actually allocates, so a GPU pool too small for one max_model_len request passed startup and requests hung forever. The grouping hook now returns the groups it allocates (host source, indexer, resident, hot, regular), workers report the derived resident/hot caches, and the standard startup check, override conversion, and cross-rank sync work unchanged. It also removes the HiSparse-specific memory estimate and the cross-worker min(available_memory) workaround, and sizes resident groups by their admission window.

**Technical impact**  
Touches core KV cache sizing (kv_cache_utils), layout resolution (attention/backends/utils), HiSparse layout/binding, kv_cache_interface.max_memory_usage_bytes, and worker attn_utils. Behavior changes: too-small pools now fail the standard max seq len check at startup before allocation; auto-fit uses the same criterion so it cannot pick a rejected length; KV cache layout resolution skips specs without per-layer views; projection preserves group flags when all layers are on the worker. **Potential risks**  
The fix depends on #59494 enforcing max_admission_blocks_per_request at runtime; without it the 4000-block case livelocks, so merging order matters. Removing the min(available_memory) workaround and the HiSparse-specific estimate shifts sizing logic onto shared paths, which could affect non-HiSparse configs if the host_resident filtering or has_layer_views skip is too broad. The new resident/hot derived specs must be consistently reported by all workers or cross-rank sync and projection could diverge, especially with unequal per-rank memory. Boundary correctness relies on exact block accounting (null block, COW tail, async scheduling doubling the in-flight window).

**Key insights**  
The root cause was a mismatch between the specs used for sizing and the groups actually allocated, causing silent under-provisioning and hangs rather than a clear error. The fix unifies HiSparse with the standard startup check by making the grouping hook authoritative and having workers report derived caches, eliminating special-case memory estimation. The exact 656/657 boundary test and the layout-invariance test are strong regression guards; the main residual risk is the runtime dependency on #59494 for admission-window enforcement.

### Summary

**What changed and why**  
This PR fixes a deadlock where VLLM_BATCH_INVARIANT=1 pins NCCL_ALGO, NCCL_PROTO, and channel counts in the worker environment, but NCCL never reconciles these across ranks, causing an external trainer without the same pins to hang in the warm-up all_reduce of the weight-transfer group. It introduces pin_nccl_env and unpinned_nccl_env in vllm/utils/nccl.py to record and temporarily restore launch values around the creation of trainer-facing communicators, and lists pins in NCCL_NO_CACHE so NCCL re-reads them per communicator.

**Technical impact**  
The change touches the batch-invariance determinism path, the NCCL weight-transfer engine, and the shared NCCL utility module. stateless_init_process_group and uid_init_process_group now wrap communicator creation in unpinned_nccl_env, so the transfer group uses the launch environment shared with the trainer, while vLLM's own collectives keep the pins. A new test case exercises the batch-invariant worker scenario, and the mechanism depends on CUDA NCCL >= 2.29.7 for NCCL_NO_CACHE.

**Potential risks**  
On ROCm, older NCCL, or when the NCCL library cannot be loaded, no pins are lifted and a warning is logged once; in that case a shared communicator can still hang if the peer does not set the same NCCL_* variables. The mechanism relies on NCCL_NO_CACHE being parsed before the first NCCL call, so ordering matters. If NCCL_ALGO, NCCL_PROTO, or channel limits are set only in nccl.conf rather than exported, the worker cannot restore launch values correctly. The test uses a 300-second timeout and max_calls=1 to avoid pin leakage between Ray tasks.

**Key insights**  
The core insight is that NCCL environment pins are process-wide and never reconciled across ranks, so they must be scoped to vLLM's own communicators and excluded from any communicator shared with an external trainer. NCCL_NO_CACHE is the enabling primitive that lets NCCL re-read variables per communicator instead of caching the first value. The fix is asymmetric and backward-compatible: the trainer needs no change, and copying vLLM's pins into the trainer would now cause a mismatch.

### Summary

**What changed and why**  
WorkspaceManager previously allocated its scratch buffer with a plain torch.empty outside the sleep-mode memory pool, so /sleep never released it (1.3 GiB/GPU at TP4, up to 4.5 GiB at DP8). This PR adds an optional alloc_context factory to WorkspaceManager (defaulting to nullcontext) and wires the shared Worker._init_workspace_and_model_runner() to pass _maybe_get_memory_pool_context("workspace"), so scratch is allocated under a new workspace tag that sleep discards and wake remaps at the same virtual address, keeping captured CUDA graphs valid. The re-entered-tag fix depends on subtle PyTorch pluggable-allocator behavior (pytorch/pytorch#146431): a tensor still alive in a dropped pool would be freed with cudaFree instead of my_free, and the new test_reentered_tag[x-alive] reproduces this on main. _trim's correctness relies on the Python-level unmap keeping the virtual address reserved, which the PR verifies on ROCm but is a platform-sensitive assumption. The PR is large and touches memory lifecycle, sleep/wake, and CUDA graph replay, so regressions may only surface under long-running or unusual sleep/wake sequences despite extensive testing.

**Key insights**  
The core insight is that workspace scratch holds no state between forward passes, so it can live in the sleep-mode pool and be discarded on sleep and remapped at the same virtual address on wake, preserving CUDA graph validity without any copy. The PR also fixes a latent allocator bug: re-entering a tag previously overwrote the only reference to the prior MemPool, and this PR (workspace) plus #59158 (runtime) are the first to trigger it. ## 62. [[Bugfix][ROCm] Fix race on AITER MLA FP8 prefill scheduling metadata under async scheduling](https://github.com/vllm-project/vllm/pull/58887)

### Summary

**What changed and why**  
Fixes a race condition in the ROCm AITER MLA FP8 prefill path where aiter.get_ps_metadata_v1 wrote scheduling metadata into persistent device buffers using a blocking hipMemcpy not ordered on the current stream, allowing async scheduling step N+1 to overwrite metadata still being read by step N's prefill kernels. The fix introduces two pinned host staging buffers, builds the plan into host memory, copies to device on the current stream, and uses per-slot CUDA events to gate buffer reuse.

**Technical impact**  
Changes the metadata build path in vllm/v1/attention/backends/mla/rocm_aiter_mla.py to stage host-side outputs and perform non-blocking H2D copies on the current stream, with double-buffering and event-based synchronization. It also removes a device-side sync previously used to read num_partial_tiles, now read directly from the host plan, which reduces synchronization overhead. Behavior is otherwise unchanged for non-affected configurations.

**Potential risks**  
The double-buffered staging scheme assumes at most two in-flight metadata builds; if more overlap occurs, an event may not yet be recorded and synchronize() returns immediately, potentially allowing reuse before the copy completes. Pinned host memory adds allocation overhead and the event-based synchronization must be correct across CUDA graph capture boundaries. The change is limited to the ROCm AITER MLA FP8 prefill path, so other backends are unaffected.

**Key insights**  
The root cause is a stream-ordering bug in an external AITER call that writes device buffers with an unordered copy, which is especially dangerous under async scheduling. The fix is a targeted double-buffered host staging approach with event synchronization, and the PR includes thorough before/after performance and accuracy validation on Kimi-K3 and DeepSeek-V3 showing crash elimination and no regression. The removal of the device sync for num_partial_tiles is a secondary improvement that avoids a per-build synchronization.
