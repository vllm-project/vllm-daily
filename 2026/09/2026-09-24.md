  - `vllm/models/deepseek_v4/nvidia/flashinfer_sparse.py`
  - `vllm/models/deepseek_v4/nvidia/ops/o_proj.py`

### Summary

**What changed and why**  
Wires FlashInfer 0.7.0's TRTLLM-GEN DSv4 sparse-MLA RopeQuant epilogue into FLASHINFER_MLA_SPARSE_DSV4 so the kernel applies inverse RoPE and casts attention output to FP8 (packed UE8M0 scales) in the layout DeepGEMM fp8_einsum consumes, eliminating a separate bf16 [T,128,512] write plus fused_inv_rope_fp8_quant pass. Adds an _alloc_attn_out hook on DeepseekV4Attention (default bf16 buffer unchanged) and a QuantizedActivation path in DeepseekV4FlashInferMLAAttention and deep_gemm_fp8_o_proj. Also fixes a DSpark non-causal decode index-layout bug where -1 padding was attended as keys and the causal window cut off later block tokens.

**Technical impact**  
Fused path activates automatically only when local heads == 128, KV cache is per-tensor FP8, and wo_a is FP8; other configs keep the existing path. Because the launcher requires the output group stride to equal sum_q, both decode and prefill calls span the full CUDA-graph-padded buffer and select tokens via cum_seq_lens_q, with build_flashinfer_mixed_sparse_indices gaining num_rows to size outputs. Reported gains: +6.5-16% throughput and 6-9% TPOT at c16+, +15.9-19.5% speculative acceptance length with DSpark, at the cost of ~2-2.5% slower single-request decode.

**Potential risks**  
The fused path relies on the kernel never reading rows outside cum_seq_lens_q and on RopeQuant's derived positions matching `positions`; the acknowledged inexact case is a DSpark draft block running past max_model_len, where the position clamp is not reproduced. The non-causal index-layout rewrite is intricate (window/spill arithmetic, pad-row handling) and correctness depends on the kernel treating every active-range entry as a key. The fused path is gated on exact head count 128, so it silently falls back elsewhere, and the new QuantizedActivation plumbing touches shared attention/o_proj interfaces.

**Key insights**  
The change is a meaningful perf win concentrated in prefill and high-concurrency serving, plus a real correctness fix for DSpark non-causal decode that also benefits the unfused path. It is well covered by new unit tests (fused-vs-unfused projection equivalence, DSpark block visibility across contexts, index-layout assertions) and existing suites, with E2E accuracy within noise. The main review focus should be the non-causal index arithmetic and the padded-buffer/cum_seq_lens_q contract, since those are the subtle correctness-critical parts.

  - `vllm/v1/core/kv_cache_utils.py`
  - `vllm/v1/kv_cache_interface.py`

### Summary

**What changed and why**  
This PR fixes a bug in V3.2 sparse MLA KV cache allocation where the physical block-stride alignment required by the selected kernel was not being published by the producer. It lifts block_stride_alignment from MLAAttentionSpec up to the base KVCacheSpec, sets it in MLAAttention.get_kv_cache_spec based on backend/cache format (including SM100 FlashMLA paged FP8/NVFP4 TMA alignment of 656/352 bytes), and updates the allocator to consume it generically without an MLA type check. HiSparse hot-page and stride constraints are now combined in a single LCM to avoid sequential rounding invalidating the first constraint.

**Technical impact**  
The allocator's _get_kv_cache_bytes_per_block now computes a single LCM over hot-page sizes and all per-layer block_stride_alignment values, replacing the previous two-step rounding that could invalidate the first constraint. The field is promoted to KVCacheSpec with validation (must be positive) and propagated through merge() for FullAttentionSpec, RSWASpec, and MLAAttentionSpec, with a new assertion that all layers in a group share the same alignment. MLAAttention.bind_kv_cache now uses a shared _uses_flat_kv_cache() predicate so warmup and allocation agree on addressing mode, and SM100 FlashMLA paged FP8/NVFP4 paths get independent native TMA alignment without flattened-row warmup.

**Potential risks**  
The merge() assertion that all specs in a group share block_stride_alignment could break existing configurations if any layer produces a different value, though this is intended to catch misconfiguration. The change from MLAAttentionSpec-specific handling to a generic KVCacheSpec field means any spec type could now set alignment, which is broader than before. The PR description notes that production MTP/DFlash2 correctness, acceptance, and long-context behavior still require retesting, and no new GPU run was performed on current main; CUDA cases were skipped on the CPU host, so GPU-specific behavior is validated only by historical B200 results on a prior revision.

**Key insights**  
The core insight is that alignment requirements must be published by the producer (the attention layer's get_kv_cache_spec) rather than inferred by the allocator via type checks, and that multiple alignment constraints must be combined in one LCM to avoid order-dependent rounding bugs. The _uses_flat_kv_cache() predicate centralizes the backend/cache-format logic so warmup and allocation cannot diverge. The test-only fix to test_mla_kv_cache_spec_uses_layer_cache_dtype (adding attn_backend and binding the real helper) addresses an incomplete SimpleNamespace fixture exposed by CI, with no production code change.

### Summary

**What changed and why**  
This PR replaces the existing FusedInputNorm module (previously in vllm/model_executor/models/vision.py) with a new FusedMMInputNorm CustomOp in vllm/model_executor/layers/fusion/mm_input_norm.py, adding a Triton kernel (fused_mm_input_norm_triton) that performs the per-channel affine normalisation in a single pass. The goal is to eliminate the fp32 intermediate DRAM round-trip of the eager path, since mm_input_norm is memory-bandwidth-bound. It also refactors parameter resolution into NormParams/_load_norm_params, adds an IdentityInputNorm stand-in, updates qwen2_vl/qwen2_5_vl to use build_mm_input_norm, and hardens merge_mm_processor_kwargs against per-request do_normalize/do_rescale overrides.

**Technical impact**  
The new kernel reads input in its native dtype (uint8/fp16/bf16/fp32), computes in fp32 in registers, and writes directly to visual_dtype, avoiding a global fp32 intermediate. It supports preallocated output buffers (only the leading N rows written) and uses int32 flat indexing with an explicit numel < 2**31 guard. Platform dispatch is via CustomOp (forward_native/forward_cuda/forward_xpu/forward_oot), with the CPU path serving as the semantic reference. The config change prevents silent double-normalisation when mm_device_do_normalize is enabled and per-request kwargs try to re-enable do_normalize/do_rescale.

**Potential risks**  
The int32 index guard means very large tensors (numel >= 2**31) will assert rather than fall back, which could surface as a hard failure on extreme image batches. The kernel requires outputs to be contiguous and exactly shaped (N, C, L), so callers relying on padded or non-contiguous output buffers must adapt. The channel index recovery via (offs // L) % C assumes a strict (N, C, L) layout; any layout change would silently produce wrong results. The removal of FusedInputNorm from vision.py is a breaking API change for any external code importing it, and the XPU path now depends on the new CustomOp dispatch rather than the previous explicit torch.ops.vllm.xpu_fused_input_norm call. The merge_mm_processor_kwargs change alters precedence so that mm_device_do_normalize now overrides per-request kwargs, which is a behavior change for users who previously passed do_normalize explicitly.

**Key insights**  
The PR is a well-scoped performance refactor that consolidates normalisation logic into a dedicated fusion layer with a Triton fast path, backed by a substantial new test suite covering dtypes, channel variants, block boundaries, non-contiguous inputs, and shape validation. The documentation update accurately reflects the new single-pass, fp32-compute, preallocated-output semantics. The main review focus should be on the int32 numel limit, the strict contiguity/shape contract for outputs, and the backward-compatibility impact of removing FusedInputNorm from vision.py.

The mutates_args=["output"] declaration is the critical detail that keeps the large embedding weight out of the compiled graph and prevents Inductor autotuning OOMs. The refactor into common/ngram_embedding.py is a sensible deduplication that makes the UVA offload reusable across CUDA-alike platforms, and the added tests specifically cover compile and cudagraph-capture safety of the pinned lookup op.
