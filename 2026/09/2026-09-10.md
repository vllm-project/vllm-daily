## 3. [[Bugfix] Fix FlashInfer KV sharing with omitted K/V](https://github.com/vllm-project/vllm/pull/55864)


### Base Information

- **Author:** [lzzzzzc](https://github.com/lzzzzzc)

  - `vllm/model_executor/models/gemma4_mtp.py`
  - `vllm/v1/attention/backends/flashinfer.py`

### Summary

**What changed and why**  
Fixes a FlashInfer regression where KV-sharing layers (e.g. Gemma4) pass key=None/value=None, but FlashInfer unconditionally sliced those tensors during CUDA Graph padding removal, raising TypeError: 'NoneType' object is not subscriptable. The fix makes key/value optional in the FlashInfer forward signature, removes the unconditional slicing, and only slices K/V at the DCP prefill call site where they are actually consumed. It also removes uninitialized placeholder K/V tensors from gemma4_mtp, passing None instead to match the attention-layer contract and avoid per-forward allocation.

**Technical impact**  
Restores FlashInfer startup and CUDA Graph capture for KV-sharing models like Gemma4 while preserving the optimization from #54917 that skips K/V projections. The common non-DCP path avoids extra Python branches and tensor slices, and the DCP prefill path now explicitly rejects KV-sharing layers with a clear NotImplementedError instead of silently consuming uninitialized tensors. The gemma4_mtp change removes a per-draft-forward allocation and aligns MTP KV-sharing behavior with the target model.

**Potential risks**  
The DCP prefill path for KV-sharing layers is now explicitly unsupported, so any configuration relying on it will fail fast rather than work; this is intentional but is a behavior change. The slice bounds changed from key[num_decode_tokens:] to key[num_decode_tokens:num_actual_tokens], which is correct given prior truncation but relies on num_actual_tokens being properly set. Test coverage is limited to Gemma4 E2B on a single RTX 3090 with mixed FlashAttention 2 / FlashInfer backends, so other KV-sharing models or backend combinations may not be exercised.

**Key insights**  
The root cause was an implicit assumption in FlashInfer that key/value are always non-None, which conflicted with the KV-sharing contract introduced by #54917. Deferring the K/V slice to the DCP call site is a clean way to keep the hot path branch-free while making the None case explicit. The gemma4_mtp placeholder removal is a good cleanup that also prevents DCP prefill from silently reading uninitialized memory, and the PR thoughtfully documents that it supersedes the closed alternatives #55871 and #55789.
