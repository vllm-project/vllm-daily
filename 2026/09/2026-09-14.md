  - `vllm/forward_context.py`
  - `vllm/v1/attention/backends/mla/index_group.py`
  - `vllm/v1/hisparse/runtime.py`

### Summary

**What changed and why**  
Fixes an engine-startup crash in sparse-MLA models using piecewise cudagraphs (e.g. GLM-5.3-Flash). The logical_topk_ready CUDA event was recorded inside a captured graph segment but waited on eagerly in the following eager break, which is illegal (cudaErrorInvalidValue). The fix adds in_piecewise_cudagraph() to forward_context.py and, in that mode, skips the event record in set_logical_topk_ready and falls back to wait_stream(compute_stream) in both index_group.py and hisparse/runtime.py, matching the existing has_indexer=False path.

**Technical impact**  
Behavior is unchanged for FULL cudagraph and eager modes, which retain the fine-grained event-based overlap. In piecewise mode the side stream is now ordered via wait_stream on the compute stream, which is correct because the convert is always invoked after the indexer on the same compute stream. A new regression test exercises record-inside-capture plus convert-in-eager-break under BreakableCUDAGraphCapture, and the PR reports 47 sparse-MLA tests passing plus a successful E2E run on 4x GB300 with 91.8% GSM8K accuracy.

**Potential risks**  
The fallback wait_stream is coarser than the event, so it may serialize slightly more work in piecewise mode, though correctness is preserved. The guard relies on cudagraph_runtime_mode being correctly set in the forward context at both capture and replay time; if that context is missing or stale, the event path could be taken incorrectly. The change touches two call sites (index_group and hisparse) that must stay consistent, and the fix is validated mainly on one hybrid model, so other piecewise sparse-MLA configurations are less covered.

**Key insights**  
The root cause is a subtle interaction between graph-captured event recording and eager event waiting, which only manifests for hybrid models that capture decode batches piecewise rather than fully. The bisect pointing to PR #53781 (which introduced the side-stream event) confirms the regression origin. The fix is minimal and mirrors an existing code path, and the added regression test reproduces the exact production failure, which is strong evidence of correctness.

  - `vllm/model_executor/layers/hpc/rope_norm.py`
  - `vllm/model_executor/model_loader/utils.py`
  - `vllm/model_executor/models/hy_v3.py`

### Summary

**What changed and why**  
Fixes a silent correctness bug where HpcRopeNorm kept float32 mirror Parameters (qnorm_weight/knorm_weight) of the q_norm/k_norm weights that were only refreshed by process_weights_after_loading, a hook dispatched solely by the cold-start HpcModule loop in model_loader/utils.py. Since no reload path (layerwise reload, NCCL/IPC weight transfer, sleep/wake_up) reaches that loop, RL weight refits left the fused kernel consuming pre-refit QK-norm weights with no error or warning. The fix removes the derived copies entirely: hy_v3.py now builds q_norm/k_norm in float32 when the HPC path is active, and the kernel reads those Parameters directly, so there is nothing to refresh on any load path. Bundled cleanup removes the now-unnecessary HpcIHCPre/HpcIHCHead weight aliases (which survive refits because they are pointers, not duplicates), the HpcModule.process_weights_after_loading no-op, and the loader loop.

**Technical impact**  
Eliminates a class of stale-weight bugs for HPC models under RL refit by removing the derived-copy indirection rather than adding another refresh hook. The kernel now reads live float32 Parameters whose storage is preserved across layerwise reload (in-place copy_ plus re-registration of original Parameter objects), so CUDA graph tensor pointers remain stable. Adds an explicit ValueError in HpcRopeNorm.__init__ when QK-Norm is enabled without fallback norm modules, replacing a latent None-attribute crash that mypy flagged. Removes one process_weights_after_loading mounting point (4 to 3) and deletes the HpcModule base hook, simplifying the loader. A new unit test drives the production _forward_impl with a recording stub and asserts the kernel receives refit Q and K weights in float32 with unchanged storage.

**Potential risks**  
Known limitation: sharded-state artifacts saved by an older build contain the retired hpc_rope_norm.qnorm_weight/knorm_weight keys, and ShardedStateLoader indexes state_dict by checkpoint key, so loading them now raises KeyError; artifacts must be regenerated. The author notes this swaps the direction of an existing incompatibility rather than introducing a new one, and deliberately did not touch the shared loader. The actual fix (HpcRopeNorm, hy_v3.py) could not be exercised end-to-end because HpcAttentionBackend.supports_compute_capability is sm90-only and the test cluster is GB200/sm100; only the iHC cleanup and mounting-point removal were validated end-to-end, so sm90 + HY3 + HPC_ATTN refit consistency remains unverified and needs an H100/H800 run that fails on main. The fp32 contract now lives with the caller (hy_v3.py) with no check for future models wiring up HPC_ATTN, and HpcModule is arguably dead after this change.

**Key insights**  
The core insight is the distinction between an alias and a duplicate: HpcIHCPre/HpcIHCHead cached pointers to owner Parameters, which survive refits because layerwise reload copies in place and re-registers the original Parameter objects, whereas HpcRopeNorm cached an independent copy_().float() duplicate that nothing refreshed. Removing the duplicate is more robust than adding another refresh path, since it makes staleness structurally impossible on every load path. The test plan is unusually rigorous: a positive control (perturbing the changed line) shows the 8/8 token-identical comparison has discriminating power, a same-code base2 arm establishes the run-to-run noise floor and reveals that apparent eager throughput gains track arm ordering rather than the change, and the full 78-layer GSM8K run (0.5660 vs 0.5660, invalid_rate 0.012) confirms no accuracy regression. The author also correctly flags that the 4-layer slice had no discriminating power (invalid_rate 0.985) and that the sm90 fix path is genuinely untested on the available hardware.

## 10. [[Model Runner V2] Tolerate lack of pinned memory support](https://github.com/vllm-project/vllm/pull/56908)


### Base Information

- **PR Number:** #56908
- **Author:** [njhill](https://github.com/njhill)
- **Merged By:** [WoosukKwon](https://github.com/WoosukKwon)
- **Merged time:** 2026-09-14 21:28:33
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/56908/files) (2):**
  - `vllm/v1/worker/cpu/buffer_utils.py`
  - `vllm/v1/worker/gpu/buffer_utils.py`

### Summary

**What changed and why**  
Model Runner V2 relied on UVA with static pointers, which requires pinned memory and fails on platforms like WSL where pinned memory is unsupported or disabled. This PR introduces a NonUvaBuffer fallback that uses explicit device-memory copies, gates pin_memory() usage behind the PIN_MEMORY flag, and converts the uva attribute into a uva(n) method so callers can request a sliced view or a copied tensor depending on the buffer implementation.

**Technical impact**  
UvaBufferPool now selects UvaBuffer or NonUvaBuffer based on is_uva_available(), and the CPU-side UvaBuffer no longer raises when UVA is unavailable, instead returning plain CPU slices. The GPU-side UvaBuffer keeps its accelerator view but exposes it via a method, and NonUvaBuffer performs explicit copy_ operations into device memory, adding synchronization and copy overhead on non-UVA platforms. The uva_instead_of_gpu optimization is now disabled when UVA is unavailable, so large cold tensors fall back to GPU allocation.

**Potential risks**  
The NonUvaBuffer path introduces per-access copy_ calls that may break assumptions about zero-copy semantics or asynchronous behavior in downstream code, and the returned tensor from uva(n) is a fresh copy rather than a stable view, which could surprise callers that mutate it expecting the buffer to update. The PIN_MEMORY flag is read at import time, so runtime changes to pinned-memory availability are not reflected. The CPU UvaBuffer now silently returns non-UVA slices, which could mask misconfiguration on platforms where UVA is expected.

**Key insights**  
The change correctly separates the UVA abstraction from its pinned-memory requirement by making uva() a method with implementation-specific semantics, but the differing return semantics (view vs copy) between UvaBuffer and NonUvaBuffer is a subtle contract that should be documented and tested. The fallback disables the uva_instead_of_gpu memory-saving optimization, which is a reasonable trade-off but worth noting for memory-constrained non-UVA environments. Tests covering the NonUvaBuffer path and the PIN_MEMORY=False branch would strengthen confidence in this portability fix.

### Summary

**What changed and why**  
Fixes a race in the NIXL KV connector where a request with multiple in-flight transfer handles (e.g. heterogeneous TP) could have its blocks invalidated and reported failed as soon as one handle hit ERR, while sibling handles were still posting RDMA writes into those same blocks. The fix defers failure reporting and block invalidation until all handles for a request are terminal, and reworks the failure bookkeeping into a `_recv_failures` set plus the existing `_failed_recv_reqs` queue. Supporting changes touch `_pop_done_transfers`, `_handle_failed_transfer`, `_try_release_xfer_handle`, and the push/pull workers.
