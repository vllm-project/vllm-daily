### Summary

**What changed and why**  
The PR extends the kernel-microbenchmark skill documentation to cover ROCm/HIP and adds a new platform-agnostic benchmark script (graph_replay_benchmark.py) that times kernels via HIP/CUDA graph replay over rotating weight buffers sized to exceed the last-level cache. It also adds guidance on tuning comparison arms and on a ROCm-specific NCCL watchdog workaround (TORCH_NCCL_BLOCKING_WAIT=1). The motivation is that FlashInfer CUPTI is unavailable on ROCm and Triton do_bench has launch overhead that distorts small/decode-size kernel measurements.

**Technical impact**  
Introduces a reusable timing pattern that captures one graph containing multiple calls cycling over rotating buffers, then measures replays with events and reports the median across rounds. This yields near-zero launch overhead and cold-HBM weight reads, and the script computes TFLOPS and GB/s for compute-bound and decode-GEMM cases. Documentation changes affect only the skill guidance, but the new script is executable code that others may copy as a reference pattern.

**Potential risks**  
The new script is untested per the empty Test Plan/Test Result sections, so correctness of the graph-capture logic, buffer rotation, and timing math is unverified. The NCCL watchdog workaround is a benchmark-only knob that could be misapplied in production. Correctness checks use loose tolerances (atol/rtol=1e-1) that may mask real errors, and the LLC_TARGET_BYTES constant is hardcoded for specific hardware (MI355X/B200).

**Key insights**  
The core insight is that graph replay with rotating buffers larger than LLC avoids both launch overhead and cache-warm bias, making it preferable to do_bench for small kernels on ROCm. The PR also emphasizes that untuned comparison arms produce unreliable conclusions, and documents a non-obvious ROCm constraint that HIP forbids querying events recorded in a capturing stream, tripping the NCCL watchdog. Because it adds behavior-bearing code and infra guidance rather than pure docs, it is classified as SUBSTANTIAL.

Adds a new `openai-responses` backend to `vllm bench serve` so the `/v1/responses` protocol can be benchmarked directly instead of routing workloads through `/v1/chat/completions`. This required a dedicated SSE parser (`_extract_sse_data`) because Responses streams prefix each message with an `event:` line, plus new TTFT/ITL accounting that treats reasoning and output-text deltas as token events while ignoring metadata and `.done` events. Supporting changes include registering the backend in `ASYNC_REQUEST_FUNCS` and `OPENAI_COMPATIBLE_BACKENDS`, rejecting `--min-p` in `serve.py`, fixing `sonnet` dataset prompt formatting, and adding docs and a 24-test suite.

**Technical impact**  
Introduces a new client-side request function with careful latency semantics: TTFT starts on the first token-bearing delta, E2EL stops at the last token event so `latency - ttft == sum(itl)`, and usage is read from the terminal event. The new backend is only validated against vLLM's Responses implementation and a mock server; other Responses-compatible servers may emit different terminal or error event shapes, though the code accepts spec-defined `response.incomplete`, `response.failed`, and `error`. Reasoning deltas counting toward TTFT/ITL is a deliberate but potentially surprising choice that differs from some user expectations and is documented with a warning about `include_reasoning: false`. The `--min-p` rejection is a behavioral restriction that could surprise users migrating from `openai-chat`. The `sonnet` dataset change alters prompt formatting for the new backend, which is correct but changes what the server receives.

**Key insights**

The reasoning-delta TTFT decision is empirically justified: on Qwen3-0.6B, excluding reasoning deltas would report TTFT as ~1.47 s instead of ~0.02 s. The `split("\n")` vs `splitlines()` distinction correctly handles U+2028/U+2029/U+0085 inside JSON strings, a subtle correctness detail. Scope is clearly bounded to single streamed text generation per prompt, with tools, MCP, and multi-turn state explicitly out of scope.

### Summary

**What changed and why**  
This PR optimizes the MRV2 model runner by reusing Mamba/GDN attention metadata across KV cache groups that share the same MambaSpec and builder type. Instead of rebuilding metadata for every group each step, it builds the first group's metadata and derives subsequent groups' state indices via a new update_block_table() method, which is also applied during CUDA graph capture so FULL graphs share batch-level buffers. This reduces CUDA API calls and step time, enabling more KV cache groups without the previous performance penalty.

**Technical impact**  
Adds update_block_table() to GDNAttentionMetadataBuilder and a supports_update_block_table flag gated on v2 model runner, CUDA, and exact builder type. The runner's build_attn_metadata now caches metadata by (KVCacheSpec, builder type) and reuses it for compatible Mamba groups. GDN build() is refactored to use helper methods _stage_spec_decode and _stage_decode, and to accept precomputed mamba_aligned_state_indices. A new spec_sequence_masks_cpu field is added to GDNAttentionMetadata. Tests cover the new path across cache modes and cudagraph settings.

**Potential risks**  
The reuse logic assumes groups with the same spec and builder type differ only in state indices; any future builder that adds per-group state would silently break. The supports_update_block_table check uses exact type equality to exclude KDA subclasses, which is fragile if new subclasses are introduced. FULL graph buffer sharing across groups could cause subtle correctness issues if buffer lifetimes or capture ordering change. The mamba_aligned_state_indices precompute is CUDA-only and MRV2-only, so behavior diverges across configurations.

**Key insights**  
The change delivers substantial measured gains: -40% step time and +57% output tok/s at c=1 versus main, and reduces CUDA API calls per step from 1032 to 424. It also makes the --min-kv-cache-group-layers tradeoff much cheaper, narrowing the 46-group vs 17-group gap from +39% to +15%. The design keeps GDN-specific logic out of the runner by relying on a generic supports_update_block_table capability flag and a builder-provided update_block_table() method.

The change is well-scoped to one backend and backed by unit tests, E2E benchmarks, accuracy evals, and profiler traces showing the sync is eliminated. The main long-term concern is the reliance on FlashInfer internals, which the PR acknowledges with a TODO and an upstream issue reference.

### Summary

**What changed and why**  
Adds a new ZenCPUSDPAMLAPrefillBackend that subclasses the generic CPU SDPA MLA prefill backend and routes per-request prefill attention through zentorch_sdpa on AMD Zen CPUs when the op is available, falling back to the reference matmul/softmax path otherwise. The selector now prefers the Zen backend on CPU when available, a new ZEN_CPU enum entry was registered, and tests were added/updated to cover selection and kernel correctness.

**Technical impact**  
On Zen CPUs with zentorch, the prefill attention op group (bmm, mul, masked_fill, softmax, triu) collapses into a single fused zentorch_sdpa call, reported as roughly 5x less CPU time for that stage (2.28s vs ~12.4s across 1728 calls). Requests needing LSE (context chunks, prefix/suffix merge) still delegate to the base fp32 implementation, and V is padded to the query head dim then sliced back, preserving MLA's asymmetric head dims.

**Potential risks**  
The fused path is only exercised when zentorch_sdpa is registered, so environments without it silently use the reference path; the new test is skipped in that case, leaving the kernel path untested in CI. The V-padding and output slicing logic is subtle and could break for other head-dim combinations. Accuracy deltas on gsm8k are small but present (0.7938 vs 0.7870 flexible-extract), so numerical differences from the fused kernel should be monitored. The selector now raises ValueError if no CPU backend is available, a behavior change from the previous unconditional return.

**Key insights**  
This is a performance-oriented backend addition gated by runtime availability rather than a config flag, keeping the generic CPU path as a safe fallback. The design cleanly separates the fused fast path from the LSE-requiring path by delegating to super()._ragged_sdpa, and the selector change generalizes CPU backend selection to allow accelerator-specific subclasses. The reported ~5x prefill attention speedup with comparable accuracy makes this a worthwhile optimization for AMD Zen deployments.
