## 1. [[Bugfix][Multimodal] Handle prefix-covered items in SHM worker cache](https://github.com/vllm-project/vllm/pull/54994)


### Base Information

- **PR Number:** #54994
- **Author:** [waizuichougou](https://github.com/waizuichougou)

- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/54994/files) (4):**
  - `tests/multimodal/test_cache.py`
  - `tests/v1/core/test_output.py`
  - `vllm/multimodal/cache.py`
  - `vllm/multimodal/utils.py`

### Summary

**What changed and why**  
This PR fixes a crash in vLLM's shared-memory (SHM) multimodal processor cache when prefix caching is enabled. The bug occurred because strip_covered_mm_data() stripped the tensor payload from fully prefix-covered items, but for SHM-cached items it also removed the small address descriptor needed by the worker's receiver cache to resolve the payload and acknowledge the sender's reference count. The fix preserves address-only SHM items during stripping and makes the SHM receiver skip items with data=None (which now only represent stripped uncached payloads).

**Technical impact**  
The change modifies the stripping logic in vllm/multimodal/utils.py to keep items containing an 'address' field, and adds an override in ShmObjectStoreReceiverCache.get_and_update_features() to filter out None-data features before calling the parent method. This restores the correct reference-counting protocol for SHM cache hits, preventing both the crash and potential memory leaks. Two regression tests were added to cover the SHM receiver path and the stripping behavior.

**Potential risks**  
The fix relies on the presence of an 'address' key to identify SHM items, which could be fragile if the internal representation changes. The filtering of None-data features in the SHM receiver assumes that None always indicates a stripped uncached payload; if other code paths pass None for different reasons, they might be silently ignored. The change does not alter the LRU receiver behavior, but the interaction between prefix caching and SHM cache eviction could still have edge cases not covered by the tests.

**Key insights**  
The bug was a subtle interaction between two caching optimizations: prefix caching can make multimodal payloads unnecessary, but SHM cache hits still require the address descriptor for reference counting. The fix preserves the address while still stripping heavy tensor payloads, maintaining the intended optimization without breaking the SHM protocol. The comprehensive test plan, including end-to-end A/B testing and a focused SHM probe, demonstrates that the fix resolves the crash and keeps reference counts balanced.

  - `rust/src/text/src/output/decoded.rs`

### Summary

**What changed and why**  
This PR modifies the Rust frontend's decoded text event stream to coalesce decoded chunks per engine update instead of per token. Previously, the code extracted and appended a decoded chunk after every token push, even when multiple tokens were generated in a single engine update (e.g., with MTP or speculative decoding). The change moves the chunk extraction outside the inner token loop, so at most one decoded chunk is appended per nonterminal engine update, while terminal updates still go through the existing flush path. The purpose is to reduce CPU time, allocations, and improve loop throughput during incremental detokenization.

**Technical impact**  
The change reduces the number of decoder.next_chunk() calls and append operations per engine update, leading to measurable performance improvements: CPU time reduced by up to ~21%, loop throughput increased by up to ~26%, and allocations reduced by ~18% for larger MTP batch sizes. The behavior of decoded text, token IDs, logprobs, stop handling, and streaming event boundaries remains unchanged, as verified by existing tests. The code change is minimal (7 additions, 4 deletions) and localized to the decoded.rs file.

**Potential risks**  
The main risk is that moving the chunk extraction outside the inner loop could alter the timing or granularity of decoded chunk generation, potentially affecting streaming latency or the order of events in edge cases. However, the PR ensures terminal updates still flush correctly, and tests pass. There is also a risk that the condition `finish_reason.is_none()` might not cover all terminal cases, but the existing flush path handles terminal updates. The performance gains are benchmarked only for the tokenizer used; end-to-end gains depend on the share of frontend CPU spent in incremental detokenization.

**Key insights**  
The PR addresses a known inefficiency (TODO comment) by coalescing chunk generation per engine update, which is a common optimization for speculative decoding scenarios. The benchmark results show significant improvements with larger MTP batch sizes, indicating the change scales well. The code change is simple and well-tested, with no behavioral changes expected. The use of AI assistance is disclosed, and the submitter reviewed all changes.
