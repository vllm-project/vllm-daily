## 3. [[Perf] Give a prefill-only batch the model state's number of logit rows](https://github.com/vllm-project/vllm/pull/57416)


### Base Information

- **PR Number:** #57416
- **Author:** [mmastrac](https://github.com/mmastrac)
- **Merged By:** [LucasWilkinson](https://github.com/LucasWilkinson)
- **Merged time:** 2026-09-19 21:58:31
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/57416/files) (1):**
  - `vllm/v1/worker/gpu/model_runner.py`

### Summary

**What changed and why**  
The PR optimizes the vLLM V1 GPU model runner for diffusion models by avoiding an unnecessary logits computation pass during prefill-only batches. Previously, every request in a prefill-only batch was allocated one logit row regardless of the model state's num_new_sampled_tokens_per_step, causing a full pass over the 262144-row vocabulary matrix (~8.8 ms on GB10). The fix gates the fast path on num_new_sampled_tokens_per_step == 1, routes non-1 cases through the general branch, and guards grammar bitmask application when logits has zero rows.

**Technical impact**  
Reduces prefill latency for DiffusionGemma from 116.5 ms to 106.9 ms median by skipping compute_logits on prefill steps. Decode steps and autoregressive models are unchanged, as they still take the one-row-per-request branch. The adaptive_verification condition is also tightened to only activate when draft tokens are actually scheduled, aligning with compact_batch's budget priming.

**Potential risks**  
The change alters control flow in prepare_inputs and sample, so regressions could appear for models with num_new_sampled_tokens_per_step != 1 or for structured output paths. The grammar bitmask guard assumes zero-row logits are safe to skip, which could mask a real bug if a non-diffusion path ever produces empty logits with a grammar output. Testing was limited to one DGX Spark and one model, so broader model coverage is not demonstrated.

**Key insights**  
The core insight is that prefill-only batches in diffusion models do not consume logit rows, so allocating them wastes a full vocabulary projection. The fix correctly distinguishes the fast path (no drafts and k==1) from the general path, and the adaptive_verification condition change is a necessary consequence of that split. The grammar bitmask guard is a defensive addition that prevents applying a bitmask to an empty tensor.

### Summary

**What changed and why**  
This PR refactors the Arm CPU paged attention implementation to improve performance. It introduces a ProbabilityTokenStore abstraction that lets attention implementations write softmax probabilities directly in a packed format, rewrites the BFMMLA GEMM kernels (cpu_attn_neon_bfmmla.hpp) with a new BfmmlaGemm class, prepacks Q during copy, and lowers BLOCK_SIZE_ALIGNMENT from 32 to 16 to enable NEON for block_size % 16. The Python backend selection logic in cpu_attn.py is reordered so Arm NEON is chosen before the block_size % 32 fallback. The stated goal is up to 25% faster paged attention while removing ~100 lines of code.

**Technical impact**  
Behavioral changes span the C++ attention kernels and the Python ISA-selection path. The new ProbabilityTokenStore template with a void_t specialization changes how probability buffers are laid out and indexed (probability_token_stride), which affects GEMM A-packing assumptions. The rewritten BFMMLA kernels replace macro-heavy code with a structured BfmmlaGemm class handling m<=2, m<=4, and 8x8 paths, and the NEON block-size alignment change means more block sizes now route to NEON, altering which kernels execute for a given configuration.

**Potential risks**  
The packed-probability layout and stride changes are subtle and could introduce correctness regressions if any consumer still assumes the old contiguous layout. The BLOCK_SIZE_ALIGNMENT reduction from 32 to 16 and the reordered ISA selection in cpu_attn.py could change kernel selection for existing workloads, potentially affecting accuracy or performance on non-Arm or mixed configurations. The large BFMMLA rewrite (360/-487) carries risk of edge-case bugs in tail handling, row-pair masking, and accumulate paths that may not be fully covered by CI alone.

**Key insights**  
This is a performance-focused refactor with real behavioral impact, not a cosmetic change, so it warrants careful review of numerical correctness and kernel-selection logic. The introduction of ProbabilityTokenStore as an extensible interface is a clean design improvement that decouples probability storage from the main loop. Reviewers should verify that the new packed-probability stride is consistently applied across all attention implementations and that the NEON block-size change does not regress other ISAs. The PR description claims CI-only testing, so additional targeted benchmarks and correctness checks on Arm hardware are advisable.

### Base Information

  - `vllm/models/deepseek_v41/amd/rocm.py`

### Summary

**What changed and why**  
The PR memoizes the decode topk ragged metadata (ragged indices, indptr, and lens) on the index-source layer, keyed by compress ratio, so that the layers between two index sources reuse the same packed result instead of rebuilding it. Previously each of the 38 compressed layers rebuilt the same pack per decode step even though only 8 distinct index sources exist, causing ~4.8x redundant GPU work. Consumers resolve their source once in __init__ via static_forward_context and raise NotImplementedError if a PP split lands inside an index-sharing group.

**Technical impact**  
Reduces _pack_global_topk_ragged_kernel and _compute_topk_lens_kernel launches from 380 to 80 per 10 decode steps (8 per step instead of 38), removing roughly 250 us of GPU work per step (~1.8% of decode GPU time on DeepSeek-V4.1-Flash). The change is confined to one file (vllm/models/deepseek_v41/amd/rocm.py) and is a pure memoization, with prefill untouched. Unit tests pass (68 passed) and GSM8K accuracy is identical (0.9025).

**Potential risks**  
Cache invalidation relies on structural ordering: the source clears its entry when it runs and always runs before consumers, so a step cannot read stale data. This assumption is implicit and could break if layer execution order changes or if a consumer runs before its source. The NotImplementedError for PP splits inside an index-sharing group is a new hard failure mode that could affect configurations not covered by the test plan. The end-to-end interactivity benefit is not demonstrated; the author notes the loop is host-bound with spec decode off, so the kernel-level saving may not translate to latency gains.

**Key insights**  
The optimization exploits the fact that the ragged pack is a pure function of shared topk_indices_buffer plus per-step metadata, with compress_ratio as the only per-layer term, making it safe to cache per ratio on the source. The PR is well-scoped, includes trace-based evidence of the redundancy, and honestly reports that end-to-end ITL improvements are not measurable at this scale. The main review focus should be on the correctness of the invalidation ordering assumption and the PP-split limitation.

The change is applied consistently to the native CUDA writer, the fused DeepSeek-V3.2 Triton writer, and the Kimi K3 CUDA writer, with tests updated to enforce bit-compatibility and exercise the real writer-to-reader path.

**Technical impact**  
The physical 656-byte cache entry layout is unchanged (512 FP8 NoPE, 4 FP32 scales, 128-byte BF16 RoPE tail), but the numeric scale values written change on all platforms. Tests now assert exact (rtol=0, atol=0) scale equality and bit-compatible output across native, Triton, and Kimi writers, and the sparse FlashMLA reader test now validates end-to-end correctness using fixed-width -1-padded indices compatible with both SM90 V3.2 and SM100. The 1e-4 lower bound maps an all-zero tile to 2^-13 after rounding, matching the FlashMLA UE8M0 reference margin.

**Potential risks**  
The unified contract intentionally changes SM90 quantization output, and the PR explicitly notes that an SM90 model evaluation is still outstanding and required before merge, with the H100 kernel-test result pending CI. Any downstream consumer or reference implementation that assumed arbitrary FP32 scales (rather than power-of-two) could break, though the PR updates the known writers and tests. The exp2f/ceilf/log2f computation adds a small amount of per-tile math in hot kernels, and the 1e-4 floor differs from the previous FLT_MIN floor, which could subtly affect edge-case tiles with very small amax.

**Key insights**  
The core insight is that the writer and reader must agree on the scale representation, and power-of-two scales are the only values that round-trip exactly through both BF16 (SM90) and E8M0 (SM100) conversions. The PR is well-scoped, applies the same rule to all three writers, and strengthens tests from loose tolerance to exact equality, which is the right way to lock in a bit-compatibility contract. The main open item is SM90 validation, which the author correctly flags as a merge blocker given the intentional behavior change on that platform.

The MTP loader's pending_qkv_proj buffering assumes weight and weight_scale_inv both arrive and are keyed by the same prefix; a checkpoint emitting only one of them would silently skip loading. Requantization introduces a small fp8 round-trip error (~2-3% relL2) on the non-exact-chunk path, which the tests bound but real-model accuracy impact is only indirectly validated via GSM8K.

**Key insights**  
The root cause is a subtle mismatch between the checkpoint's pre-shard count (num_key_value_heads) and the layer's actual KV-head count, which coincide for Pro and GA layers but diverge for SWA layers, masking the bug until V2.5 SWA was exercised. The fix correctly separates ckpt_tp from num_kv_heads and handles the three regimes (tp < ckpt_tp, tp == ckpt_tp, tp > num_kv_heads) explicitly. The new CPU-only unit test is well-designed: it builds synthetic GA/SWA/Pro checkpoints in the export's chunk layout, checks all TP sizes against an independent reference, verifies the exact-chunk fast path is byte-identical, and asserts the old reading is detectably wrong (relL2 1.05), giving strong regression coverage without GPU.
