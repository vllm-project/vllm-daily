### Summary

**What changed and why**  
Extends the Kimi-K3 prefill checkpoint optimization (#52789) to support speculative decoding/Eagle block rewind, partial prefix caching where prefix_match_unit is smaller than the Mamba block size, and checkpoint blocks restored via KV connectors like MooncakeStore. It introduces shared checkpoint-validity helpers (get_mamba_prefill_checkpoint_position, is_mamba_prefill_checkpoint_valid) and a prefill_checkpoint_alignment field on MambaSpec so the cache manager and FlashKDA worker agree on when a checkpoint block is allocated, hashed, and re-keyed from its provisional boundary to the state position actually exported by FlashKDA.

**Technical impact**  
Touches core scheduling and KV-cache paths: scheduler._mamba_block_aligned_split, MambaManager allocation/checkpoint bookkeeping (renaming _num_checkpoint_blocks to _checkpoint_positions), block_pool.cache_partial_block (new replace_existing_hashes flag), kv_cache_coordinator (Eagle checkpoint alignment), and Kimi-K3 KDA metadata. **Potential risks**  
The change alters checkpoint allocation, hashing, and re-keying semantics across scheduler, cache manager, and worker, so subtle mismatches could cause stale or aliased checkpoint state, null-block or assertion failures, or incorrect prefix-cache hits. The new validity rules and the replace_existing_hashes path remove previously cached hashes, which could regress non-partial or non-Eagle configurations if edge cases (e.g., hash-aligned query ends, multi-module MTP, multiple Mamba specs with differing alignments) are not fully covered; the code itself flags TODOs for these. Correctness depends on FlashKDA exporting state at the expected boundary, and the PR notes the bundled binary predates the current custom-op ABI, so deployment must rebuild _C_stable_libtorch.so.

**Key insights**  
The design centralizes checkpoint-validity logic in kv_cache_interface so the scheduler, cache manager, and worker share one source of truth, and re-keys a reserved request-owned checkpoint block from its provisional full-block hash to the actual exported state boundary. Tests cover Eagle rewind, partial-hash lifecycle, and hash-aligned query ends, and the benchmark plus OCR-Bench and MooncakeStore/NIXL E2E results provide strong empirical evidence. Remaining gaps are explicitly noted as TODOs (multi-module MTP, multiple Mamba specs with different alignments), and the change is behavior-affecting and non-trivial despite being well-tested.

Performance overhead of per-request validation is likely negligible but unmeasured.

**Key insights**  
This is a security-relevant hardening change that moves validation from the engine to the request boundary, converting a crash/500 into a clean early rejection. ### Summary

**What changed and why**  
The DP finish-sync all-reduce in DPEngineCoreProc._has_global_unfinished_reqs previously ran only every 32 steps, so pausing an idle MoE DP engine forced 32 dummy forwards per rank before pause consensus. This PR adds an unconditional sync on the first step of a wave (step_counter == 1) and makes the cadence configurable via a new ParallelConfig.dp_sync_interval / --dp-sync-interval flag with a default of 16, cutting idle-pause dummy steps from 32 to 1 and shortening mid-wave pause tails.

**Technical impact**  
Behavioral change in the DP engine control loop: an extra gloo all-reduce per wave at step 1, plus a lower default cadence (32 to 16) that adds one all-reduce per 16 steps of normal serving. The new config field is threaded through ParallelConfig, EngineArgs, and the CLI, and step_counter semantics are unchanged, so other consumers like SchedulerStats.step_counter and _should_throttle_prefills are unaffected. The change is control-plane only and does not alter model output.

**Potential risks**  
The cadence must match across all DP ranks; there is no runtime cross-rank validation, so a mismatched --dp-sync-interval can cause ranks to enter the blocking all-reduce with unequal forward-launch counts and deadlock. The default change from 32 to 16 alters steady-state all-reduce frequency for existing deployments, adding communication overhead. Correctness relies on step_counter being rank-synchronized (reset at wave-end consensus, restored by elastic-EP state sync), which the PR argues but does not verify at runtime.

**Key insights**  
The first-step sync is a pure function of lockstep state (step_counter), so it is immune to elastic EP divergence and requires no new protocol state. Benchmark data shows the two levers are complementary: first-step sync fixes idle pauses (332ms to 43ms, 7.7x) while a shorter interval cuts mid-wave tails, and the combined configuration is best in both columns. Unit tests script sync_dp_state to pin the cadence at steps {1, N, 2N} and the idle-pause consensus at step 1, but the distributed regression suite is the real guard against deadlock.

### Base Information

- **Author:** [peakcrosser7](https://github.com/peakcrosser7)
- **Merged By:** [jeejeelee](https://github.com/jeejeelee)
- **Merged time:** 2026-09-05 07:02:20
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/55375/files) (2):**
  - `tests/models/qwen4_exp/test_ple.py`
  - `vllm/models/qwen4_exp/nvidia/ops/ple.py`

### Summary

**What changed and why**  
Fixes a correctness bug in the fused PLE short-convolution kernels where state indices were loaded with an implicit unit stride. In Mamba align-cache mode, pure-prefill state indices come from column zero of the Mamba block table, producing a non-contiguous 1D tensor with stride equal to the block-table row width (e.g., 4 with MTP=3). The kernels now receive state_indices.stride(0) and load each request's slot via state_idx_ptr + r * state_idx_stride, preventing later requests from reading the wrong block-table row and writing convolution state to the wrong cache slot.

**Technical impact**  
Adds a state_idx_stride parameter to both _ple_conv_kernel and _ple_conv_writeback_kernel and threads it through ple_conv from state_indices.stride(0). This avoids materializing a contiguous index tensor, so there is no extra allocation or device copy. The change is confined to the fused PLE path and keeps fusion, CUDA graphs, and the device-resident PLE path enabled. Tests add a strided-state-index regression case with query lengths (16, 676), 10240 channels, and stride 4, covering both SD and DS state layouts.

**Potential risks**  
The fix assumes stride(0) correctly describes the logical request-to-slot mapping for all callers; if any caller passes a tensor whose stride(0) does not match the intended indexing (e.g., a transposed or otherwise reshaped view), the new arithmetic could misaddress. The added test only exercises stride 4 and a specific two-prefill shape, so other strides or batch compositions are not directly covered. The change is otherwise narrow and does not alter kernel launch configuration or fallback behavior.

**Key insights**  
The root cause is a classic non-contiguous view bug: slicing column zero of a block table yields a 1D tensor with a non-unit stride, which the kernels silently treated as contiguous. Passing the stride explicitly is a zero-cost fix that preserves the fused kernel design. The PR includes a clear end-to-end reproducer and A/B validation showing 90.3% element mismatch with unit-stride addressing, which strongly supports the diagnosis. The test additions are well targeted at the production-shaped multi-prefill scenario.

### Summary

**What changed and why**  
In vllm/models/deepseek_v4/common/ops/cache_utils.py, the caller-supplied output path of combine_topk_swa_indices now seeds the combined_indices workspace with -1 before the kernel writes the valid prefix. Previously only the out=None branch used torch.full(-1), so a rotating workspace buffer could reach the sparse attention kernel with uninitialized padding that the kernel interprets as KV indices. This one-line fill_(-1) matches the seeding already done by the ROCm and XPU variants and compressor_utils.py.

**Technical impact**  
Fixes a latent correctness and safety bug: uninitialized padding columns in the sparse index workspace were read as KV indices, causing out-of-range reads (idx_max ~2.1e9 vs kv_rows=2) and Triton CUDA illegal memory access aborts during prefill CUDA graph capture with many chunks. The change is confined to the out= path and replaces garbage reads with the -1 sentinel the kernel contract assumes; behavior is unchanged where the buffer was already fully rewritten. Reported A/B shows out-of-range reads dropping from 404,096 to 0 and warmup completing all 256 chunks, with no clear accuracy regression and a ~0.63% throughput difference that the author does not treat as a stable regression.

**Potential risks**  
The added fill_(-1) writes the entire workspace tensor on every call, adding a small memory-bandwidth cost that could matter in hot prefill paths, though the measured throughput delta is within noise. The fix relies on the kernel treating -1 as an invalid/sentinel index; if any downstream consumer does not honor that contract, padding could still be misinterpreted. The A/B validation used different nightly builds for accuracy and throughput and only one engine per configuration, so exact output equivalence and absence of a small accuracy change are not fully established.

**Key insights**  
This is a classic uninitialized-workspace bug that stayed latent because the prefill chunk plan normally reused a single chunk and rewrote the same slot, masking the missing sentinel until a many-chunk plan rotated through unwritten slots. The fix is minimal and consistent with three other code paths that already seed -1, which is strong evidence it is the correct contract. The PR is a workspace correctness fix rather than a performance optimization, and the author is appropriately cautious about the inconclusive throughput and accuracy measurements.
