  - `vllm/models/deepseek_v41/nvidia/ops/o_proj.py`

### Summary

**What changed and why**  
Adds a new CuTe-DSL FusedWoAKernel that collapses the DSv4.1 small-batch O-projection chain (inverse RoPE, per-32 FP8 quant, WO-A GEMM, MXFP8 output quant) into one kernel on SM100/SM103, plus a new dsv41_o_proj dispatcher that falls back to deep_gemm_fp8_o_proj for unsupported shapes or larger batches. The FlashMLA and FlashInfer sparse backends now route _o_proj through this dispatcher and register warmup, and _wo_b_proj accepts a pre-quantized QuantizedActivation to skip its own quantize. A new test validates the fused kernel against the unfused Triton + DeepGEMM + FlashInfer reference.

**Technical impact**  
Cuts the WO-A chain latency roughly 2x at decode batch sizes (e.g. 10.98 to 5.28 us at T=1) and improves serving ITL/TPOT by 5-6% at low concurrency, with dispatch limited to 1-96 tokens (32 for TP1/TP2 shapes) where the fusion is still a win. It introduces a new kernel, a new dispatch/warmup path, and a QuantizedActivation handoff into wo_b, so it touches kernel correctness, warmup coverage, and the GEMM-RS interaction in _wo_b_proj.

**Potential risks**  
The fused path is only exercised on SM100/SM103 with specific layouts (per-32 FP8 WO-A, FlashInfer CuTe-DSL MXFP8 WO-B, o_lora_rank multiple of 128, <=8 heads per group), so mis-gated dispatch could silently fall back or, worse, run the kernel on an unsupported shape. Warmup must compile every token count dispatch can hit, and the description notes a quack preprocessor interaction (TYPE_UNSTABLE_JOIN) that required binding amax/exponent/inv; missing that binding would break warmup in-server. Split-K accumulation order differs from the unfused path, producing small numerical differences (relative L2 up to ~7e-4), and the 96-token extension is only marginally faster (1.03x) at the top of its range, so the dispatch cutoff is a tuning-sensitive boundary. The _wo_b_proj change also alters GEMM-RS behavior for QuantizedActivation inputs, which should be verified for the reduce-scatter path.

**Key insights**  
This is a well-scoped, heavily validated performance fusion with strong microbenchmark and accuracy evidence (GSM8K parity, GPQA 91.92%, bit-identical scale checks, sanitizer clean). The main review focus should be the dispatch guard in _can_fuse_wo_a and _fused_wo_a_max_tokens, warmup coverage of all reachable token counts, and the _wo_b_proj QuantizedActivation/GEMM-RS interaction. The PR is large (+759/-55 across 6 files) and behavior-changing, so it warrants careful correctness and integration review rather than a trivial pass.

### Summary

**What changed and why**  
Fixes issue #43894 where InputBatch.condense() copied a moved request's allowed_token_ids_mask row into the freed index but never cleared the source row. Since add_request only writes that row when the new request sets allowed_token_ids, a later unrestricted request reusing the index would inherit the previous request's stale whitelist. The fix adds fill_(False) on the vacated row, mirroring remove_request, plus a regression test.

**Technical impact**  
Changes sampling behavior for requests that reuse a condensed index without allowed_token_ids, ensuring they are no longer incorrectly constrained by a stale mask. The change is a single line in the condense path and aligns the mask-clearing behavior with remove_request, improving correctness of the input batch bookkeeping.

**Potential risks**  
Low risk given the change is a targeted one-line clear plus a test. The main consideration is ensuring the mask tensor is always allocated when condense runs; the existing code already indexes it in the same block, so this is consistent. No performance concern since fill_ on a single row is negligible.

**Key insights**  
The bug is a classic stale-state issue in index reuse: copying data into a freed slot without clearing the source leaves latent state that only manifests when a subsequent request omits the field. The regression test carefully reproduces the exact sequence (constrained request on highest row, remove lower row, condense, reuse) and asserts both the cleared source row and the new request's unconstrained status.

### Summary

**What changed and why**  
This PR fixes a bug in the NIXL pull-mode connector where a prefiller restarting with a new engine ID at the same host/port left the decoder holding stale NIXL resources and cached metadata until TTL eviction. It adds an _engine_by_address map to track which engine currently serves each pull peer address, detects replacement after a successful handshake, and releases the old peer's state once in-flight requests and pending handshakes have drained. The re-handshake path in start_load_kv could add latency or fail if the engine is truly gone, and the new address map must stay consistent with _remote_agents across TTL eviction and shutdown.

**Key insights**  
The fix is narrowly scoped to pull mode and carefully avoids premature teardown by waiting for handshakes and active requests to drain before releasing old peer state. Test coverage is thorough, exercising confirmed replacement, address preservation, failed handshakes, in-flight read draining, queued notifications, concurrent handshakes, and re-handshake of released engines. The explicit TODO for push mode is an important known limitation to track.

## 6. [[Qwen3.8-Flash-Next] Avoid memory fragmentation in QSA indexer logits workspace](https://github.com/vllm-project/vllm/pull/57105)

  - `vllm/models/qwen4_exp/nvidia/ops/qsa_indexer.py`

### Summary

**What changed and why**  
The PR modifies the QSA indexer prefill path to avoid memory fragmentation by pre-allocating a worst-case logits workspace instead of calling torch.empty per chunk. The _prefill_logits function now accepts a logits_workspace tensor and slices/views it, and qsa_select_paged_prefill computes a budget based on max_logits_bytes and the full page_table width times k_cache head dim, allocating a single reusable buffer.

**Technical impact**  
Behavior changes in memory allocation strategy: a single larger workspace is allocated up front and reused across chunks, reducing repeated allocator churn and fragmentation. The new assertions enforce contiguity and sufficient size, and the view/slice approach preserves the same logits shape and dtype used by downstream kernels. This is a performance/memory-management refactor rather than a functional change to the indexer math.

**Potential risks**  
The worst-case budget uses page_table.shape[1] * k_cache.shape[1] * 4 bytes, which could be significantly larger than the previous per-chunk allocation and may increase peak memory usage for large page tables or head dims. If num_queries * logits_width ever exceeds the allocated workspace, the new assertion will fail rather than silently reallocating, so callers must guarantee the bound. The change assumes q.new_empty produces a contiguous float32 tensor, which is asserted but not otherwise validated.

**Key insights**  
The fix trades a small increase in peak memory for stable, fragmentation-free allocation across chunked prefill calls. The added assertions are a good guardrail, but the PR description lacks test plan and results, so the actual memory and performance impact is unverified. Reviewers should confirm the worst-case budget formula matches the maximum possible num_queries * logits_width used in practice.

**What changed and why**  
Bumps the FlashKDA dependency pin in cmake/external_projects/flashkda.cmake from commit b59532f to 17a037d, which merges FlashKDA PR #13. That upstream change keeps the KDA recurrent state in fp32 between 16-token tiles instead of bf16, adds missing TMA store waits, and fixes an sm_10x register-pressure regression. **Technical impact**

**Potential risks**  
The change pulls in new upstream kernel code that is only validated by the author's tests and benchmarks, so regressions on untested hardware, dtypes, or shapes remain possible. fp32 state increases memory and register pressure, which could affect occupancy or OOM margins on smaller GPUs even though sm_10x was specifically fixed. Because the pin is a moving dev-branch commit rather than a tagged release, reproducibility depends on that commit remaining reachable, and the AI-assisted kernel changes warrant independent review.

**Key insights**  
The fix targets a real correctness bug (bf16 recurrent-state rounding accumulating across tiles) rather than a pure performance tweak, and the reported accuracy gains on long-context tool calls are substantial. The change is low-risk from a build perspective since only the GIT_TAG moves and the external interface is identical, but it is not trivial because it changes numerical behavior and kernel performance. ### Summary

**What changed and why**  
This PR fixes a bug in Elastic EP where EPLB load statistics became stale after a reshuffle. When a reshuffle occurs, a different expert may occupy a physical location, but old load measurements persist. If Elastic EP triggers another reshuffle before a full window of new measurements arrives, EPLB attributes old load to the wrong expert. The fix adds a last_expert_load tensor to EplbModelState that stores global logical-expert totals from the last reshuffle, and a use_last_expert_load flag to rearrange() that uses these saved counts instead of potentially stale load history during Elastic EP-triggered reshuffles.

The rearrange() method now accepts a use_last_expert_load parameter that, when True, bypasses the normal physical-to-logical load mapping and instead uses the saved last_expert_load tensor. The saved load is distributed via the existing all-reduce mechanism (rank 0 provides the data, other ranks contribute zeros). After each non-profile rearrange, last_expert_load is updated with the new global_expert_load_window. The elastic_execute.py call site is simplified to always pass rank_mapping and use_last_expert_load=True, removing the conditional branching.

**Potential risks**  
The last_expert_load tensor is initialized to ones (equal demand) and only updated during non-profile rearranges, so the first Elastic EP reshuffle before any prior rearrange will use uniform load distribution. The all-reduce pattern assumes rank 0 always has the authoritative saved load, which could be problematic if rank 0's state diverges. The PR description explicitly notes that regular EPLB can still hit the same stale-history problem when step_interval is smaller than window_size, meaning this fix is incomplete for non-Elastic-EP scenarios. There may be edge cases around async reshuffles where last_expert_load is updated but the actual rearrangement hasn't completed.

**Key insights**  
The fix correctly identifies that load measurements are tied to physical locations but experts can move between locations during reshuffles, creating a temporal mismatch. Using the last known good expert-level load totals is a reasonable approach for Elastic EP where reshuffles can be triggered externally before measurement windows complete. The explicit acknowledgment that regular EPLB has the same underlying issue (when step_interval < window_size) suggests this is a known architectural limitation that needs a separate, more general fix. The design of storing last_expert_load per model state and updating it only on non-profile rearranges is clean and minimal.
