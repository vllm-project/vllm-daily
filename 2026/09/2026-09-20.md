  - `vllm/v1/worker/cpu_worker.py`
  - `vllm/v1/worker/gpu_worker.py`
  - `vllm/v1/worker/xpu_worker.py`

### Summary

**What changed and why**  
This PR unifies torch profiling across CPU, CUDA, and XPU workers by centralizing profiler construction into new create_worker_profiler and validate_worker_profiler_config helpers, adding a configurable torch_profiler_activities field with platform-specific defaults, and rebuilding the one-shot torch.profiler.profile object on every start() so multiple profiling rounds work correctly. It also skips worker annotation computation and the AsyncLLM frontend CPU trace when a CUDA-only torch profile cannot record CPU events, and removes duplicated profile() overrides from cpu_worker and xpu_worker.

**Technical impact**  
Behavior changes are significant: TorchProfilerWrapper now recreates the underlying torch.profiler.profile on each _start and resets warmup/version-metadata state, adds a should_annotate property used by GPUWorker.annotate_profile, and switches device-time dumping to self_device_time_total so XPU summaries work. ProfilerConfig gains validation for activities (non-empty, no duplicates, only with profiler='torch') and worker startup now validates profiler kind and activities against current_platform.device_type, raising ValueError for unsupported combinations. CPU and XPU workers now inherit the shared GPUWorker.profile path, which also means CPU profiling now honors profile_prefix.

**Potential risks**  
The new platform validation could break existing deployments that previously passed activities or profiler kinds that were silently accepted (e.g., cuda profiler on non-CUDA devices, or XPU activities on CUDA). Rebuilding the profiler each start changes lifecycle semantics and could interact poorly with schedules, warmup counters, or on_trace_ready handlers if any caller assumed a persistent profiler object. The should_annotate gate means CUDA-only profiles will no longer emit CPU annotations, which is intended but may surprise users relying on iteration context in traces. Tests rely on patching current_platform.device_type and torch.profiler internals, so coverage of real multi-round GPU/XPU behavior is limited to the manual test described.

**Key insights**  
The refactor consolidates two previously conflicting PRs (#45992 and #55751) and addresses #45987 by making the torch profiler reusable across rounds rather than one-shot. Centralizing construction in create_worker_profiler removes per-platform duplication and makes platform defaults explicit via _DEFAULT_TORCH_PROFILER_ACTIVITIES. The should_annotate abstraction cleanly separates 'profiler running' from 'annotations meaningful', enabling the CUDA-only optimization. The PR is well-tested at the unit level (122 + 2 passing tests) but the diff is truncated, so some worker changes could not be fully reviewed.

### Summary

**What changed and why**  
The PR widens two platform gates from is_cuda() to is_cuda_alike() in vllm/config/engram.py and vllm/config/vllm.py, and switches vllm/models/deepseek_v41/amd/model.py to import Engram from the NVIDIA implementation instead of the common base class. Tests in tests/kernels/test_engram.py and tests/test_config.py are updated to match the widened gates.

**Technical impact**  
On ROCm, Engram tables now live in pinned host memory and are read over UVA, freeing substantial device memory for KV cache. The offload path now depends on UVA coherence between host and device on ROCm, which the PR validates on gfx950 but not across all supported AMD hardware or ROCm versions. Pinned host memory usage is large (188.8 GiB at TP=4), requiring memlock limits to be raised in containers. The DP shared-memory path is only functionally smoke-tested, not performance-validated. The PR also notes a rebase dependency with three other PRs editing vllm/config/engram.py, and mypy/pre-commit were not run.

**Key insights**  
The change is small in diff size but behaviorally significant: it unlocks a large memory-capacity win on ROCm by removing an unintended platform restriction rather than writing new code. The test gate widening is essential because the offload path previously had zero ROCm coverage. The main open question is whether UVA coherence holds broadly enough on AMD hardware, which the PR acknowledges as the outstanding gate before upstreaming.

## 6. [[Bugfix][Spec Decode] Stop dummy draft decode steps from writing KV through stale block-table rows](https://github.com/vllm-project/vllm/pull/56734)


### Base Information

- **PR Number:** #56734
- **Author:** [ivanium](https://github.com/ivanium)
- **Merged By:** [ivanium](https://github.com/ivanium)
- **Merged time:** 2026-09-20 18:06:25
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/56734/files) (5):**
  - `tests/v1/worker/test_gpu_block_table.py`
  - `vllm/v1/worker/gpu/block_table.py`
  - `vllm/v1/worker/gpu/spec_decode/autoregressive/speculator.py`
  - `vllm/v1/worker/gpu/spec_decode/multi_module_mtp/speculator.py`
  - `vllm/v1/worker/gpu/spec_decode/speculator.py`

### Summary

**What changed and why**  
Fixes a KV-cache corruption in Model Runner V2 speculative decoding under data parallelism. An idle DP rank's dummy batch ran the drafter's multi-step decode, computing real slot mappings via persistent block tables with idx_mapping = arange(num_reqs), causing drafter K/V writes into stale blocks of previously-occupied request slots (often already in the prefix cache). The fix adds an is_real_req guard in _compute_slot_mappings_kernel so rows with idx_mapping < 0 emit PAD_SLOT_ID without dereferencing a negative block-table row, and marks all dummy rows with idx_mapping = -1 in AutoRegressiveSpeculator.propose(dummy_run=True).

**Technical impact**  
The kernel-level guard is necessary because the fused multi-step path re-runs compute_slot_mappings inside the captured CUDA graph between draft steps, so only the kernel can neutralize a replayed dummy run. Changes touch the Triton slot-mapping kernel, the shared speculator input-copy path, and both autoregressive and multi-module MTP speculators, plus a new GPU test. Behavior for real requests is unchanged; dummy/padding rows now consistently produce PAD slots.

**Potential risks**  
The fix relies on the convention that idx_mapping == -1 uniquely identifies dummy or CUDA-graph padding rows; any caller passing -1 for a legitimate request would now silently get PAD slots. The change is minimal and backportable but does not unify the read and write sides (a follow-up could compute slot mappings from per-batch gathered input_block_tables). End-to-end validation was on a specific GLM-5.2 NVFP4 DP=4 EP configuration, so other DP/spec-decode geometries are less exercised.

**Key insights**  
The bug was latent on main because written values happened to be finite, but on the production tree (f94666b60d) the poisoned rows were NaN (fp8 0x7F), producing exactly-zero MTP acceptance that latched onto a conversation and cleared only after POST /reset_prefix_cache. Prior protections (#49757 read-side zeroing, #55458 DP padding exclusion) covered the read side and attention metadata but not the persistent block_table_ptrs read by _compute_slot_mappings_kernel. The new test test_dummy_request_slot_mapping_is_pad directly asserts the PAD behavior for idx_mapping == -1 while confirming real rows still resolve correctly.

## 7. [[Perf][DSV4.1] Overlap mHC coefficients for small TP batches](https://github.com/vllm-project/vllm/pull/57603)


### Base Information

- **PR Number:** #57603
- **Author:** [WoosukKwon](https://github.com/WoosukKwon)

- **Merged time:** 2026-09-20 17:33:17
- **Type:** `SUBSTANTIAL`

  - `vllm/model_executor/kernels/mhc/tilelang_kernels.py`
  - `vllm/model_executor/kernels/mhc/warmup.py`
  - `vllm/models/deepseek_v41/nvidia/model.py`
  - `vllm/models/deepseek_v41/nvidia/ops/mega_mhc.py`
  - `vllm/models/deepseek_v41/nvidia/ops/mhc.py`

### Summary

**What changed and why**  
This PR introduces a new scheduling optimization for DeepSeek V4.1 mHC (multi-head coefficient) computation that overlaps coefficient generation with attention/FFN sublayers on small tensor-parallel batches. A new module vllm/models/deepseek_v41/nvidia/ops/mhc.py adds supports_mhc_overlap() gating (SM100/DeepGEMM, no ubatching, hidden_size%64==0, mix_size in {8,16,24,32}) and mhc_pre_delayed_overlap(), which splits the mHC pre-kernel epilogue into input-collapse on the caller stream and coefficient generation on a side stream. The decoder layer now conditionally uses this overlap path when token count is within MHC_OVERLAP_MAX_TOKENS=16 and not in a piecewise CUDA graph, joining the side stream before consuming coefficients. The TileLang kernel gains a split_mode parameter (fused/stats/input) to support the split epilogue, and warmup registers the new split modes. Tests were extended to cover overlap output parity, CUDA graph replay with changed inputs, and decoder dispatch across disabled/overlap/piecewise/large_batch modes.

**Technical impact**  
The change adds a new execution path that runs the mHC prenorm GEMM and coefficient epilogue on a side CUDA stream concurrently with the attention sublayer, then joins before the FFN consumes the coefficients. This requires careful stream synchronization (wait_stream calls before mhc_shifted_post_pre and after FFN) and record_stream on transient tensors (x, mix, sqr) to prevent premature allocator reuse. The kernel split_mode refactor preserves the fused path for existing callers while enabling the split epilogue. The overlap path is gated by supports_mhc_overlap() and a 16-token cutoff derived from TP4/GB200 measurements, with fallback to native execution for larger batches, draft layers, and breakable graphs. Reported gains are modest (~1.5% forward latency, ~0.4% TPOT) with some P99 ITL regression noted.

**Potential risks**  
The 16-token cutoff is generalized from TP4 measurements and the PR explicitly states it does not establish gains for every newly enabled configuration (other TP sizes, attention backends, LoRA configs). The P99 ITL increased from 5.228ms to 6.049ms in the serving measurement, which could affect tail latency SLOs. Stream synchronization correctness is critical: the caller must retain weights and coefficient outputs until the side stream joins, and any missed record_stream or wait_stream could cause silent data corruption or allocator races. The overlap path is disabled in piecewise CUDA graphs, but interaction with other graph modes (full graphs, ubatching) needs verification. Numerical parity is not bitwise across arms, and GSM8K showed 10 improve/5 regress, indicating rounding-sensitive behavior. The warmup caveat notes reliance on cached-tactic workarounds from another PR, so stock-stack behavior may differ.

**Key insights**  
The core insight is that mHC coefficient generation (a small GEMM plus epilogue) can be decoupled from input collapse and run concurrently with the attention sublayer, hiding its latency on small batches where the sublayer is short. The split_mode kernel parameter is a clean way to reuse the existing TileLang kernel for both fused and split execution without duplicating code. The gating logic is appropriately conservative (SM100-only, dimension constraints, token cutoff, no ubatching, no piecewise graphs), and the test coverage for CUDA graph replay with changed inputs is valuable for catching stream-synchronization bugs. However, the performance claims are narrow (TP4/GB200 only) and the P99 ITL regression warrants monitoring. The PR is well-documented about its limitations, which is commendable, but the modest and configuration-specific gains should be weighed against the added complexity and synchronization risk.

### Summary

**What changed and why**  
This PR switches ROCm GPU memory measurement in tests from amdsmi physical-device indices to HIP logical devices via torch.accelerator.get_memory_info, raises ROCm teardown headroom from 2 GiB to 4 GiB, and stops remapping HfRunner memory checks through get_physical_device_indices on ROCm paths. It also adds workspace-manager reset/init fixtures for compile-pass and MoE tests. The motivation is that on MI355 DPX/NPS2, amdsmi reports the parent MI350 card (~288 GiB) including sibling partition VRAM, causing false failures in _wait_for_gpu_memory_release, whereas HIP is partition-scoped (~144 GiB).

**Technical impact**  
ROCm memory accounting now reflects the actual memory partition visible to the process, aligning teardown waits and HfRunner thresholds with what the runtime can actually free. The removal of the amdsmi import and _nvml context manager simplifies tests/utils.py, but the new HIP path initializes HIP in the caller, which the docstring notes requires spawn-based multiprocessing for subsequent GPU workers. The added conftest fixtures ensure workspace tensors are released before allocator flushes on ROCm.

**Potential risks**  
HIP initialization side effects in the test process could affect multiprocessing behavior if any ROCm test path still uses fork instead of spawn. The 4 GiB headroom is a heuristic and may mask genuine leaks or, conversely, still be insufficient on some driver versions. Removing get_physical_device_indices remapping on ROCm changes threshold dictionary keys from physical to logical IDs, which could break callers that assumed physical indices. The new autouse fixture in tests/compile/passes/conftest.py depends on cleanup_fixture being available and correctly ordered.

**Key insights**

### Base Information

  - `tests/kernels/test_kpool_decode_update_batched.py`
  - `vllm/models/glm5next/nvidia/ops/kpool_compress.py`

### Summary

**What changed and why**  
The NVIDIA kpool prefill tail-seed Triton kernel addressed tail blocks with a dense stride (blk * 2 * KPOOL * HEAD_DIM), but the tail cache is an as_strided view aliased onto the indexer tensor with the indexer's padded block stride (19008 elements vs dense 1024). This caused the request's own tail block to go unseeded while 2048 B of raw bf16 K/gate rows were written into unrelated indexer blocks, silently corrupting the sparse top-k indexer cache for prefix-cached prompts. The fix passes TAIL_BLOCK_ELEMS=tail.stride(0) and KPOOL_HEAD=tail.stride(1) into the kernel (matching the AMD kernel and decode path), adds view-layout assertions in kpool_seed_tail_cache, and un-skips the regression test so it runs on all platforms.

**Technical impact**  
Corrects the byte addressing of the prefill tail seed so writes land in the request's own tail block at the padded stride, eliminating cross-request corruption of indexer fp8 key rows and fp32 scale regions. The change is confined to the NVIDIA seed kernel plus test enablement; the decode kernel and AMD seed kernel already used stride-based addressing, so behavior is now consistent across platforms. The added assertions document and enforce the expected 4-D strided view layout, catching future regressions where the tail view is constructed differently.

**Potential risks**  
The new assertions (ndim==4, shape[1]==2, stride(3)==1, stride(2)==head_dim) could fail on any future or alternate tail-cache layout that is otherwise valid, turning a silent misconfiguration into a hard error; this is intentional but should be verified against all supported GLM-5.3-Flash configurations. The fix relies on tail.stride(0)/stride(1) being the correct padded strides, so any change to how get_kv_cache_config_from_groups aliases the tail tensor must keep those strides meaningful. The PR is stated to compose with the open NUM_TAIL_BLOCKS guard PR (#56059), but that composition is not exercised by the tests here.

**Key insights**  
The bug was a silent, accumulating indexer-cache corruption that only manifested with prefix caching and a long-lived hot prompt, because only low block ids (roughly 5% of the pool) could be hit and those are handed out first; this explains why the same prompt with cache_salt stayed correct. The root cause was a dense-stride assumption in a Triton kernel that replaced a previously stride-correct torch fancy-index scatter, and the existing regression test was ROCm-only, so the NVIDIA path was never covered. The provided kernel-level and end-to-end evidence (0/38 pages modified vs 16-30/38 on main, 7/7 vs 1/7 correct lookups) is strong and directly ties the fix to the observed failure mode.
