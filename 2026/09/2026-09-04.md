### Summary

**What changed and why**  
This PR optimizes Qwen2.5-Omni's embed_input_ids to avoid duplicate text embedding. Previously, the method always embedded text first, then either called the parent implementation or the interleaved path, both of which embedded text again, discarding the first result. The change now checks for the interleaved audio-in-video path before embedding, so the regular and empty-multimodal paths delegate directly to the parent, and the interleaved path performs its custom merge with a single text embedding.

**Technical impact**  
Reduces text embedding calls from 2 to 1 for all multimodal inputs, yielding a 17-19% reduction in embedding-stage latency across various token lengths. No change in output tensors or placement behavior. The code path is restructured to avoid redundant computation, improving performance without altering functionality.

**Potential risks**  
The change relies on the condition checks (multimodal_embeddings is None or is_multimodal is None) and the length check to correctly delegate to the parent. If the parent implementation's behavior differs from the previous custom path for empty multimodal embeddings, there could be subtle output differences, though tests confirm no change. The benchmark is isolated to the embedding stage and may not reflect end-to-end performance, but the logic change is straightforward.

**Key insights**  
The optimization is achieved by moving the text embedding after determining the merge path, eliminating duplicate work. The PR includes call-count assertions in tests to verify the reduction. The benchmark shows consistent improvements across input sizes, indicating the duplicate embedding was a significant overhead in the embedding stage.

### Summary

**What changed and why**  
This PR improves prefill efficiency for the Qwen3.8-Flash-Next indexer by reducing the logits workspace size. Previously, the logits width was based on the full page table capacity, which overestimates the actual context length. Now it derives a tighter upper bound from max_seq_len, allowing more tokens per chunk and fewer chunks. It also removes the constant normalization factor (1/sqrt(HEAD_DIM)) from the indexer scoring since it doesn't affect topk ranking.

**Technical impact**  
The change reduces memory usage for the logits workspace and increases GPU efficiency during prefill. Microbenchmarks show significant speedups (up to 10x) for indexer scoring and up to 3.5x for full indexer+topk. E2E TTFT and TPOT improve by up to ~6% at low concurrency. The code changes include adding a max_seq_len field to metadata, passing it through the call chain, and adjusting kernel parameters to use a runtime page_table_width instead of a compile-time constant.

**Potential risks**  
The new logits_width calculation relies on max_seq_len being accurate; if max_seq_len is underestimated, it could cause out-of-bounds access. The code clamps to page_table capacity and rounds up to 64, but edge cases like spec-decode over-estimation are handled via tests. Removing the normalization factor is safe for topk but could affect any downstream use of raw scores (though likely none). The kernel now uses a runtime page_table_width, which may slightly reduce performance due to dynamic bounds, but tests cover various scenarios.

**Key insights**  
The PR demonstrates a common optimization: using actual runtime bounds instead of worst-case allocations to reduce memory and improve efficiency. The microbenchmarks show that chunking overhead was significant, and reducing chunks yields large speedups. The test changes add parametrization to cover edge cases like slack in max_seq_len and forced chunking, ensuring correctness under the new logic.
