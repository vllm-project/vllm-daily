- **[Changed Files](https://github.com/vllm-project/vllm/pull/57502/files) (1):**
  - `vllm/v1/worker/gpu_model_runner.py`

### Summary

**What changed and why**  
Fixes a crash in DeepEP low-latency profiling under DP+EP+DBO. The MoE padding mask (is_padding) was previously computed after num_tokens_padded was shrunk to a single microbatch, causing the DBO ubatch wrapper to slice an out-of-range empty mask for the trailing microbatch. The fix moves mask computation before the single-ubatch adjustment and sizes it against the full padded token count, and routes dummy tokens through experts during profile runs (num_tokens_unpadded = num_tokens_padded when is_profile) to mirror ModelRunner V2 behavior.

**Technical impact**  
Restores correct mask sizing per microbatch so DeepEP low-latency combine stays synchronized across microbatches, eliminating the AttributeError on recv_hook and the empty torch.cat. Also ensures MoE memory is properly measured and MoE kernels are exercised during profiling, improving memory profiling accuracy for MoE models.

**Potential risks**  
Behavior change in dummy-run profiling: dummy tokens now flow through experts during profile runs, which could alter measured memory/activation profiles and potentially affect other backends or configurations relying on the previous all-padding behavior. The change is localized to _dummy_run but touches a sensitive DBO/EP code path; regression risk exists for non-DeepEP MoE or non-DBO setups that were implicitly depending on the prior ordering.

**Key insights**  
The bug was an ordering issue: mask computation must precede the single-ubatch adjustment so the mask spans the full padded token count. The fix is small (+5/-2) but semantically meaningful, and was validated on MI300X with both deepep_low_latency and deepep_high_throughput variants. AI-assisted but human-reviewed; no test additions are included, so coverage relies on existing distributed tests.

### Summary

**What changed and why**  
The CohereASR RelPositionMultiHeadAttention forward path was refactored to fuse the content-score matmul, relative-position score addition, and scaling into a single torch.baddbmm call using alpha and beta. The regression test adds a reference implementation of the pre-change math and asserts numerical equivalence plus exactly one baddbmm invocation for square and non-square query/key lengths.

**Technical impact**  
Reduces the score-path op count from {bmm: 2, add: 1, mul: 1} to {bmm: 1, baddbmm: 1}, eliminating an intermediate content-score tensor and elementwise add/scale. Reported microbenchmark speedups are ~1.10x geometric mean (up to ~1.24x at T=1024) with 10-21% temporary peak-memory reduction, and real-model throughput improved ~1.07x with WER within the upstream threshold. The matrix_bd truncation now uses k.size(-2) instead of matrix_ac.size(-1), which is equivalent but relies on that invariant.

**Potential risks**  
Numerical behavior depends on baddbmm's alpha/beta semantics and dtype handling; FP16/BF16 accumulation order may differ slightly from the prior add-then-scale path, though tests and WER checks passed. The flatten(0,1)/view reshape assumes contiguous tensors and standard batch/head layout, so any future non-contiguous inputs or layout changes could break it. Performance and WER evidence comes from a single RTX 4090 run, so cross-platform and CI coverage remain unverified.

**Key insights**  
This is a clean, self-contained kernel-fusion optimization with no new dependencies, flags, or model gates, and it includes a targeted equivalence test that also verifies the fusion actually occurs. The change is low-risk given the reference-implementation test and matching token IDs, but reviewers should confirm the k.size(-2) truncation equivalence and baddbmm dtype/contiguity assumptions hold across supported backends.

**What changed and why**  
The PR optimizes build_attn_metadata() in vllm/v1/worker/gpu/attn_utils.py by sharing a single token-to-request mapping tensor across all KV cache groups within one call. Previously each group lazily launched its own identical mapping kernel, causing redundant launches (6 in target prep, 3 in draft prep per step). **Technical impact**

Test coverage includes one unrelated failure due to a gated HF repo, so full validation of the shared-mapping path depends on the passing tests and benchmark.

**Key insights**  
This is a small but behavior-affecting performance optimization that exploits redundancy across KV cache groups rather than changing the mapping algorithm itself. The per-call lifetime design avoids cross-step state and keeps CUDA-graph replay safe, which is the key correctness consideration. The reported ~11-12% host-time reduction in metadata building is meaningful for spec-decode workloads with many KV groups, though the absolute savings (~0.2 ms/step) is modest relative to overall step time.

### Summary

**What changed and why**  
The PR fixes a memory access fault (MAF) crash in GLM-5.3-Flash when serving very long (500k ISL) prompts. The root cause is that KpoolTailSpec inherits from the sliding-window spec and therefore was deemed to use the generic _compute_slot_mappings_kernel, which indexes block tables by pos // kernel_block_size (unbounded). Since the kpool tail buffer is a fixed-size ring buffer addressed by pos % kpool, this unbounded indexing ran off the end of the allocation. The fix adds a uses_slot_mapping property returning False on KpoolTailSpec so it relies solely on its tailored compute_kpool_tail_slot_mapping, plus two regression tests.

**Technical impact**  
Behaviorally, the kpool tail group now opts out of the generic slot mapping kernel and emits PAD_SLOT_ID for its slots, which is correct because the tail buffer is addressed via its own dedicated kernel. The MLA/main KV groups are unaffected and continue to use the generic kernel. This aligns KpoolTailSpec's semantics with CircularBufferSpec, which is the intended model for a one-block-per-request ring buffer. The change is small (4 lines of production code) but fixes a real out-of-bounds read that could corrupt neighboring requests' data or crash.

**Potential risks**  
The main risk is that any code path that implicitly relied on the generic slot mapping being populated for the tail group would now receive PAD_SLOT_ID; the PR asserts the tailored kernel covers this, but downstream consumers should be verified. The GPU regression test is skipped on non-CUDA/ROCm platforms, so CPU-only CI will not exercise the actual kernel behavior. The alternative approach mentioned (inheriting from CircularBufferSpec) was not taken, so the inheritance hierarchy still differs from the conceptual model, which could invite future regressions if other properties are added to the SW spec.

**Key insights**  
This is a good example of a latent bug introduced by a refactor (#53781) that changed how specs declare slot-mapping usage: KpoolTailSpec kept inheriting from the SW spec and thus silently retained the generic kernel despite being a ring buffer. The regression test is well-constructed, using poisoned block IDs and positions chosen to land in-row, in the next request's row, and past the whole allocation, which precisely demonstrates the out-of-bounds indexing. The fix is minimal and targeted, and the included GSM8k comparison shows no accuracy regression.

### Summary

**What changed and why**  
The PR fixes a startup stall on ROCm (8x MI308X, TP8, 500 GiB offload pool) where six ranks failed with cudaHostRegister code=1. The root cause is that _uses_shared_region() treated ROCm as CUDA-alike via is_cuda_alike(), causing every worker to register the entire shared mmap region. The fix changes the predicate to current_platform.is_cuda_alike() and not current_platform.is_rocm(), so ROCm falls back to the existing private per-rank pinned tensor allocator. **Technical impact**  
On ROCm, CPU KV offload now uses private per-rank pinned tensors instead of a shared mmap region, avoiding the failing cudaHostRegister call and allowing startup to complete. The CUDA path is unchanged and still uses shared-region replicated KV deduplication. ROCm loses shared-region replicated layout dedup, which is an intentional trade-off to restore functionality. The change is a one-line behavioral gate in vllm/v1/kv_offload/cpu/spec.py, with the rest being test coverage.

**Potential risks**  
ROCm deployments no longer benefit from shared-region replicated KV deduplication, so memory usage per rank may increase compared to the intended shared-region design. The fix relies on is_rocm() being accurate for all ROCm platforms; any ROCm variant not reporting is_rocm() correctly would still hit the original failure. The test matrix now encodes the assumption that ROCm never uses shared regions, which could become stale if ROCm shared-region support is fixed later. No performance or correctness regression is expected on CUDA, but ROCm behavior changes materially.

**Key insights**  
The bug was a platform-classification mismatch: is_cuda_alike() is too broad for a decision that depends on whether shared mmap registration actually works. The fix correctly narrows the predicate rather than special-casing the failure, and the updated tests explicitly model the three-way distinction (CUDA, ROCm, non-CUDA-alike) instead of a binary cuda_alike flag. The PR description notes this bypasses shared mmap allocation on ROCm, distinguishing it from prior chunked/coordinated registration approaches (#51081, #52296). Validation on two 8x MI308X hosts with TP8 and a 32K eviction/replay test provides reasonable confidence, though broader ROCm hardware coverage is not shown.
