### Summary

**What changed and why**  
This PR refactors the multimodal timing instrumentation introduced in #51922 by moving MM-specific span helpers (mm_request_span, mm_timing_layer) and the MM_STAGE_TARGET constant out of the generic vllm-tracing crate and into a new vllm-chat/src/multimodal/timing.rs module. The removal of the MultiModalTimingStats alias and mm_stage_span from vllm-tracing is a breaking API change for any external consumers, though the PR indicates these were recently added and likely internal. The switch from explicit .instrument(mm_stage_span(...)) calls to #[tracing::instrument] attributes changes span creation semantics slightly (e.g., attribute-based spans are created at function entry), which could subtly affect timing boundaries if any setup work previously occurred outside the span. Validation was limited to CPU preprocessing and Rust integration; no model/GPU evaluation was run, so runtime timing accuracy under real workloads is unverified.

**Key insights**  
The refactor cleanly separates generic tracing infrastructure from multimodal-specific instrumentation, which is a sound architectural direction. The added documentation on RequestTimingLayer's span contract and drain semantics is valuable for future maintainers. The new test asserting exact stage keys via expect_test provides good regression protection for the timing contract. Reviewers should confirm no external crates depend on the removed vllm-tracing exports and that the attribute-based instrumentation produces identical span lifetimes to the previous explicit instrumentation.

## 2. [[Kernel] Add opt-in load-time MXFP4 dequantization](https://github.com/vllm-project/vllm/pull/50814)


### Base Information

- **PR Number:** #50814

- **[Changed Files](https://github.com/vllm-project/vllm/pull/50814/files) (3):**
  - `tests/kernels/quantization/test_mxfp4_kernel_selection.py`
  - `vllm/envs.py`
  - `vllm/model_executor/kernels/linear/mxfp4/emulation.py`

### Summary

**What changed and why**  
Adds an opt-in, default-off environment flag VLLM_MXFP4_EMULATION_DEQUANT_AT_LOAD that dequantizes packed MXFP4 emulation weights to BF16 once during process_weights_after_loading, mirroring the existing MXFP8 emulation behavior. The goal is to eliminate repeated per-forward weight dequantization in EmulationMxfp4LinearKernel, which dominates latency for large models with many dense linears. Activation QDQ is intentionally left unchanged, and the change is implemented in the generic emulation backend so it applies to Quark, compressed-tensors, ModelOpt, and online quantization callers.

**Technical impact**  
process_weights_after_loading now conditionally replaces layer.weight with a contiguous BF16 Parameter when the flag is set, and apply_weights branches on layer.weight.element_size() >= 2 to decide between a plain F.linear on pre-dequantized weights and the existing per-call dequant path. This roughly doubles resident weight memory for emulated layers when enabled, and the element_size heuristic couples the runtime branch to the dtype of the stored weight. Tests cover both the enabled and disabled paths, including dtype/device/requires_grad assertions and call-count checks on dequant_mxfp4 and quant_dequant_func.

**Potential risks**  
The element_size() >= 2 check is an implicit contract: any future code path that stores MXFP4 weights in a wider container, or that mutates layer.weight after load, could silently take the wrong branch. Enabling the flag increases device memory (historical Kimi-K3 evidence cites ~+1.5 GiB resident weights and ~-3.43 GiB KV cache), which can cause OOM or reduced throughput on memory-constrained deployments. The PR description itself notes the performance and accuracy numbers are historical, from a different runtime/configuration, and were not rerun on the current default-off implementation, so the claimed speedup is not directly validated here. The removed AITER A16WFP4 backend is deferred, so any prior dependency on it is not covered by this PR.

**Key insights**  
The change is small (+112/-3 across 3 files) but behaviorally significant because it alters weight storage dtype and the hot-path linear computation under an env flag. Default-off is the right call given the memory trade-off, and the MXFP8 precedent provides a reasonable design template. Reviewers should focus on the element_size heuristic's robustness, whether weight_scale should be dropped or kept when dequantized, and whether the historical benchmarks need to be re-run on the current head before merging.

  - `vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py`

### Summary

**What changed and why**  
Reworks QwenGatedDeltaNetAttention._output_projection to norm per-head (N, H, D) tensors directly and flatten once for out_proj, eliminating an Inductor-generated reshape/copy kernel. The XPU and CPU forward paths are refactored to reuse this shared helper, and the ROCm AITER RMSNormGated+FP8 group-quant fusion pattern is extended to match both flattened (N*H, D) and 3D (N, H, D) layouts via a new remove_noop_reshapes graph utility. Tests were added/updated to cover the new shape contract and both fusion layouts.

**Technical impact**  
Reduces kernel launches per GDN layer per step, yielding modest serving gains (under 1% throughput/TPOT) as expected for a small launch-count reduction. The fusion pass now registers a second layout variant when the quant op is native, and the replacement reshapes operands to (M, D) as a view since both are contiguous. New unit tests lock in the (N, H, D) norm contract and 3D-vs-2D equivalence for RMSNormGated.

**Potential risks**  
The fusion pattern matches on op structure rather than rank, so correctness depends on the replacement's reshape being a true view; a non-contiguous input would silently copy or error. The new remove_noop_reshapes relies on meta['val'] shapes being present, and could drop reshapes that are semantically meaningful if meta is stale or absent. Relaxing the FP8 test tolerance to 2e-2 for the opaque quant path slightly weakens the numerical assertion. Behavior changes on XPU/CPU paths are only covered indirectly by the shared helper test.

**Key insights**  
The core insight is that RMSNormGated is last-dim RMS+gate, so it is rank-agnostic and can operate on (N, H, D) without a pre-flatten, letting the compiler avoid a redundant reshape/copy. The fusion matcher needed a companion remove_noop_reshapes to align make_fx tracing with the already-optimized compiled graph. Reported accuracy (GSM8K) is unchanged or slightly better, and the perf delta is intentionally small, consistent with removing only a few launches per layer.

## 6. [[Bugfix][Frontend] Validate mixed prompt embedding mask lengths](https://github.com/vllm-project/vllm/pull/57006)


### Base Information

- **PR Number:** #57006
- **Author:** [shaohuaxi](https://github.com/shaohuaxi)

  - `tests/test_request_input_bounds.py`
  - `vllm/v1/engine/input_processor.py`

### Summary

**What changed and why**  
Adds an admission-time validation in InputProcessor._validate_model_input that rejects a prompt_is_token_ids mask whose length does not match the number of prompt embedding rows, raising VLLMValidationError with parameter='prompt_is_token_ids'. Previously such mismatched masks passed input processing and caused a NumPy broadcast error (or silent broadcast) inside InputBatch.add_request(), which could kill the engine. Regression tests were added to tests/test_request_input_bounds.py covering empty, short, broadcastable, and long masks plus valid pure-embed, token-ids-without-mask, and aligned mixed prompts.

**Technical impact**  
Behavior change limited to malformed mixed-embedding prompts: requests with a mask length differing from prompt_len are now rejected early with a clear validation error instead of reaching the worker and triggering a broadcast failure. Valid inputs (no mask, correctly aligned mixed prompts, pure embeddings) are unaffected, and the check reuses the already-computed prompt_len so overhead is negligible. This improves robustness by preventing engine-dead states caused by malformed client input.

**Potential risks**  
The check assumes prompt_len derived from length_from_prompt_token_ids_or_embeds is the correct reference for mask length; if any code path legitimately allows a mask shorter than the embedding rows (e.g., partial masking semantics), this could reject previously accepted requests. The tests rely on Mock-based config/renderer setup, so they may not fully exercise real tokenizer or multimodal paths. No coverage is shown for multimodal prompts combined with is_token_ids, so interaction with the multimodal branch is unverified.

**Key insights**  
The fix targets a real crash vector where a client-supplied mask length mismatch could propagate to a NumPy broadcast error and take down the engine, as reproduced on A10/Qwen3.5-0.8B. Catching it at InputProcessor admission is the right layer since it is cheap, deterministic, and returns a structured VLLMValidationError. The PR description explicitly distinguishes this from related work (#54509 truncation alignment, #56656 prefix-cache keys, #51891 embedding replacement positions), indicating no overlap or duplicate fix.

## 7. [[Security] Reject min_tokens that exceeds the filled max_tokens default](https://github.com/vllm-project/vllm/pull/57731)

- **PR Number:** #57731
- **Author:** [jperezdealgaba](https://github.com/jperezdealgaba)
- **Merged By:** [DarkLight1337](https://github.com/DarkLight1337)
- **Merged time:** 2026-09-21 22:50:24
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/57731/files) (3):**
  - `tests/entrypoints/scale_out/token_in_token_out/test_serving_tokens.py`
  - `tests/test_request_input_bounds.py`
  - `vllm/v1/engine/input_processor.py`

### Summary

**What changed and why**  
The PR fixes a security/robustness bug where SamplingParams skips the min_tokens <= max_tokens check when max_tokens is unset. The input processor later fills max_tokens from max_model_len and forwards the request, so an explicit null max_tokens with an oversized min_tokens was only caught during EngineCore reconstruction, where the uncaught validation error wedged the engine. The change re-validates min_tokens immediately after filling the default and rejects the request with a VLLMValidationError.

**Technical impact**  
Adds a guard in vllm/v1/engine/input_processor.py right after max_tokens is defaulted, ensuring invalid min_tokens values are rejected at the input-processing boundary rather than deeper in EngineCore. This affects all paths that go through InputProcessor.process_inputs, including /inference/v1/generate, OpenAI /v1 routes, /invocations, offline LLMEngine/AsyncLLM, and streaming-input adds. Two unit tests and one generate-endpoint regression test were added to cover the reject and in-range cases.

**Potential risks**  
The generate-endpoint regression test was not run locally because it requires a GPU server, so its behavior is unverified in this PR. The new check only runs in the branch where max_tokens is unset; if other code paths fill max_tokens differently or bypass this branch, the same wedge could still occur. There is also a minor risk of rejecting previously accepted requests that relied on the old lenient behavior, though such requests were already invalid.

**Key insights**  
The root cause is a validation ordering gap: min_tokens is validated against max_tokens only when max_tokens is already set, but the default fill happens later in the input processor. Placing the check immediately after the fill closes the window before the request reaches EngineCore, preventing an uncaught exception on the input-socket thread from wedging the engine. The PR also documents duplicate-work checks against related Rust frontend and int32-overflow PRs, confirming this Python fill-then-forward path was previously uncovered.

**What changed and why**  
The PR optimizes sparse attention metadata preparation in two MLA backend files. **Key insights**  
This is a targeted micro-optimization of metadata preparation rather than a broad performance win, and the PR is honest that gains are marginal. The main value is removing redundant GPU work on the hot decode path without introducing new configuration surface. Reviewers should focus on verifying that compressed_seq_lens is truly prefill-only and that the in-place torch.ge write preserves the exact semantics of the prior copy-based validity computation.
