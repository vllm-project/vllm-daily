## 1. [[Bugfix][KV Offload] Submit CPU stores on no-forward steps](https://github.com/vllm-project/vllm/pull/56621)


### Base Information

- **PR Number:** #56621
- **Author:** [LucasWilkinson](https://github.com/LucasWilkinson)
- **Merged By:** [LucasWilkinson](https://github.com/LucasWilkinson)
- **Merged time:** 2026-09-12 22:56:15
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/56621/files) (2):**
  - `tests/v1/simple_kv_offload/test_worker.py`
  - `vllm/v1/simple_kv_offload/worker.py`

### Summary

**What changed and why**  
Fixes a bug in SimpleCPUOffload where finished requests could emit CPU stores on a no-forward step that skips wait_for_save(). Clearing connector metadata dropped the pending copy, and a later completion watermark could falsely acknowledge it. The fix calls wait_for_save() in clear_connector_metadata() and adds a _store_submitted guard so stores are submitted once per step, preserving deferred draft-forward timing.

**Technical impact**  
Adds a _store_submitted flag reset in bind_connector_metadata and set after launching the store copy, ensuring idempotent submission. clear_connector_metadata now drains pending stores before dropping metadata, so no-forward steps correctly complete CPU stores. Tests cover both legacy and V2 no-forward paths plus deferred draft finalization, verifying completed_store_events and data correctness.

**Potential risks**  
Calling wait_for_save() inside clear_connector_metadata changes the lifecycle ordering and could interact with other connector implementations or paths that clear metadata without expecting a store submission. The _store_submitted flag assumes one store per metadata binding; if metadata is reused or rebound unexpectedly, stores could be skipped. Validation is limited to SimpleCPUOffload and a 32-question sample, not a full accuracy benchmark.

**Key insights**  
The root cause is a lifecycle gap: no-forward steps bypass wait_for_save, so pending stores were silently dropped while completion watermarks could still advance. The fix is narrowly scoped to SimpleCPUOffload and separate from the Mooncake fix in #55142. The added tests directly reproduce the empty-step and deferred-draft scenarios, which is good regression coverage, but broader connector interaction testing would strengthen confidence.

The change is small (2 files, +2/-2) and relies on the requires_token_ids contract being accurate across all pooling tasks, which the PR's test sweep partially validates.

**Key insights**  
The fix correctly moves validation from a blanket precondition to a task-specific one, aligning MRV2 with MRV1 semantics for prompt embeddings. Reported accuracy checks show exact parity (max abs diff 0.0, cosine ~1.0) between token-ID and precomputed-embedding inputs across Qwen3, Gemma2, and Mistral pooling models, and the added test coverage plus reproducer give reasonable confidence in the fix.

## 3. [[Bugfix][Benchmark] Make streaming TTFT/E2E latency accounting consistent across endpoints](https://github.com/vllm-project/vllm/pull/55508)

  - `tests/benchmarks/test_endpoint_request_func_timing.py`
  - `vllm/benchmarks/lib/endpoint_request_func.py`

### Summary

**What changed and why**  
Fixes timing accounting in the streaming benchmark request functions so that TTFT is read from the same clock sample that seeds the ITL chain, and so the trailing choice-less usage chunk no longer advances the measured end of the request. The same two defects are corrected in both vllm/benchmarks/lib/endpoint_request_func.py and the legacy benchmarks/backend_request_func.py (plus a TTFT fix in async_request_tgi), and a new CPU-only test suite pins the identity (latency - ttft) == sum(itl) across completions, chat, and audio endpoints.

**Technical impact**  
Makes E2EL and TPOT comparable across openai, openai-chat, and audio endpoints, since serve.py derives TPOT directly from latency - ttft. It also changes behavior for streams that never deliver a token chunk: those are now marked as failures with an explicit error rather than reporting a zero-duration success. No engine, scheduler, or serving path is touched, so model outputs are unaffected.

**Potential risks**  
The magnitude of the fix is small in normal operation (tens of microseconds) but the usage-chunk gap is unbounded in principle, so any downstream consumer that implicitly relied on the old, slightly inflated E2EL/TPOT numbers will see a small downward shift. The new failure semantics for usage-only streams could surface previously silent client-side failures in existing benchmark runs. The legacy backend_request_func.py is still imported by benchmark_prefix_caching.py and benchmark_serving_structured_output.py, so those scripts inherit the behavior change.

**Key insights**  
The PR correctly identifies two independent root causes and fixes them in the direction that preserves the (latency - ttft) == sum(itl) invariant rather than the alternative that would break it on both endpoints. The scripted-clock test design is the strongest part: by making each clock read advance a fixed tick, a stray or misattributed read becomes a whole-tick drift instead of sub-microsecond jitter, yielding exact, non-flaky assertions. The author is also appropriately candid that this is a correctness and cross-endpoint-comparability fix, not a performance claim, and provides a mechanism probe (30 ms delayed usage chunk) that isolates the chat-side defect.

## 6. [[Kernel][Perf][Quantization] Fix odd-row performance cliff in per-token-group quantization](https://github.com/vllm-project/vllm/pull/56478)


### Base Information

- **PR Number:** #56478
- **Author:** [ayush1399](https://github.com/ayush1399)
- **Merged By:** [vllm-bot](https://github.com/vllm-bot)
- **Merged time:** 2026-09-12 20:27:09
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/56478/files) (2):**
  - `csrc/libtorch_stable/quantization/w8a8/fp8/per_token_group_quant.cu`
  - `tests/kernels/quantization/test_per_token_group_quant.py`

### Summary

**What changed and why**  
The per-token-group 8-bit quantization CUDA kernel previously selected one group per block when the total group count was odd, launching only 16 threads and causing a roughly 4x slowdown for odd row counts (e.g. Gemma TP8 down-projection width 2688). This PR changes the launch policy to compute block geometry from the next even row count, uses ceil-div for the block count, and adds a CHECK_BOUNDS template parameter with bounds checks so tail groups are handled without padding or copying tensors. Tests were extended to cover empty inputs, odd tails, FP16/BF16/FP32 dtypes, and group sizes 64/128 for both FP8 and INT8.

**Technical impact**  
Quantization arithmetic and scale layouts are unchanged, and the helper serves both FP8 and INT8 paths. The bounds check is compiled out for full blocks, and all threads still participate in block and PDL synchronization. Reported H100 kernel latency drops from ~339us to ~81us at the 13359x2688 shape, with geometric-mean reductions of ~39.5% hot and ~38.0% cold across 18 shapes; GB10 shows a smaller ~6.7% hot improvement. Outputs and scales were reported byte-identical to baseline across 18 H100 and 194 GB10 shapes.

**Potential risks**  
The new policy_num_groups computation assumes num_groups is divisible by groups_per_row and that input.size(-1) % group_size == 0, which is now enforced by STD_TORCH_CHECK but could surface as a new hard failure for previously tolerated inputs. The num_rows derivation from num_groups/groups_per_row may be incorrect for non-2D or flattened inputs, and the odd-row heuristic could regress shapes not covered by the benchmark matrix. H200, B200, B300, and ROCm were not tested, and end-to-end TP8 TPOT was not remeasured, so the claimed end-to-end benefit is unverified. The GB10 validation command ledger discrepancy (test_utils.py vs the test file) also needs reconciliation.

**Key insights**  
This is a targeted launch-geometry fix rather than a kernel rewrite, preserving the shared-memory kernel and even-row policy while adding a compile-time bounds-check specialization. The approach is complementary to the register-resident kernel in PR #55330 and mainly improves the shared-memory fallback path. The main review focus should be the correctness of the num_rows/policy_num_groups derivation for edge cases like empty inputs and non-standard shapes, and the new divisibility assertion's compatibility with existing callers.

### Summary

**What changed and why**  
This follow-up PR replaces the config-based quantization allowlist for the weight cache IPC loader with a runtime check that inspects the created model's quant_method.supports_pre_processed_weights flag. It adds a create_model hook to BaseModelLoader, introduces get_daemon_model in the daemon to run the quant check after model creation but before the slow weight load, and removes the now-unused is_ipc_quant_supported/allowlist machinery from protocol.py.

**Technical impact**  
The daemon and engine now share a single, model-driven verification path instead of a hardcoded registry, so newly supported quant methods are gated by their own supports_pre_processed_weights declaration rather than requiring allowlist edits. check_ipc_platform_support and check_ipc_quant_support lose their 'where' tag and config-only signatures, and the engine's _check_supported helper is removed in favor of an inline platform check plus a post-build quant check. The daemon now imports get_model_loader and process_weights_after_loading at module scope, which could introduce import cycles or ordering issues. Error messages no longer carry the daemon/engine tag, slightly reducing diagnosability.

**Key insights**  
This is a meaningful behavioral refactor, not a cosmetic cleanup, despite the 'Misc' title. The shift from a static allowlist to a per-method capability flag is a better long-term design, but it moves the safety guarantee onto each quant method's supports_pre_processed_weights implementation. Reviewers should confirm the removed kv-cache-dtype guard is intentionally obsolete and that the daemon's new explicit load sequence matches the previous get_model behavior, including eval() and finalize steps.
