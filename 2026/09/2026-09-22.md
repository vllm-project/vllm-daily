  - `tests/model_executor/layers/test_rocm_unquantized_gemm.py`
  - `vllm/model_executor/layers/utils.py`

### Summary

**What changed and why**  
The PR extends the ROCm unquantized GEMM dispatch condition in vllm/model_executor/layers/utils.py from 'm > 8 and 0 < n <= 5' to '(m == 1 or m > 8) and 0 < n <= 5', routing single-output GEMMs (weight.shape[0] == 1) to the wvSplitK kernel instead of the generic F.linear fallback. This targets the Qwen shared-expert gate shape used during batch-1 decode, where the existing wvSplitK kernel already supports M_in=1. Tests were updated to parametrize over m values and add a real-kernel single-output test.

**Technical impact**  
Single-output unquantized GEMMs on ROCm now use the specialized wvSplitK kernel with YTILE=1, yielding a reported 37.8x operator speedup for BF16 [1, 2048] and roughly +12.8% decode throughput / -11.3% per-token latency on gfx1151. The change is narrowly scoped to the ROCm path and preserves the existing n in [1,5] guard, so other shapes continue to fall back as before. Test coverage was expanded to exercise both m=1 and m=128 paths plus real-kernel correctness for fp16/bf16.

**Potential risks**  
The new branch relies on wvSplitK correctly handling M_in=1 across all supported ROCm architectures, but the benchmark and real-kernel test were only validated on gfx1151, so other GPUs (e.g., MI-series) could exhibit numerical or performance regressions. The m==1 condition is checked before the m>8 condition, which is logically fine but slightly obscures intent; also, correctness tolerances in the new test (atol/rtol 1e-2) are relatively loose. No fallback safety net is added if wvSplitK produces incorrect results for edge cases like non-contiguous or unusual dtypes.

**Key insights**  
This is a small but behavior-changing dispatch fix with meaningful performance impact for decode-time single-output GEMMs, so it is SUBSTANTIAL rather than trivial. The change is well-motivated by a specific model shape and backed by focused tests and A/B benchmarks, but cross-architecture validation is limited to one AMD GPU. Reviewers should confirm wvSplitK's M_in=1 support is guaranteed on all targeted ROCm devices and consider whether the condition should be expressed more clearly (e.g., m == 1 or m > 8 grouped explicitly).

The return_bias parameter defaults to True, but some call sites (e.g., gpt_oss) pass return_bias=False; the new _return helper must correctly handle both cases, and any missed call site that expects a tuple could break.

**Key insights**  
This is a broad refactor that unifies MoE gate implementations under GateLinear, enabling specialized router kernels across all MoE models. The key risk is ensuring that the new GateLinear path preserves the exact numerical behavior and dtype semantics of the replaced implementations, especially for models that previously used fp32 gates or custom forward logic. The PR description is empty, so the test plan and results are unknown; thorough validation across all affected models is essential before merging.

**Potential risks**

QUTLASS_DISABLE_PYBIND=1 could disable Python bindings that some workflows expect, though the PR implies they are not needed. The fix is validated only on PyTorch 2.13 with CUDA 13.0, so behavior on other PyTorch or CUDA versions is not demonstrated.

**Key insights**  
The root cause is a PyTorch header guard that rejects ATen inclusion when TORCH_TARGET_VERSION is defined, which conflicts with QuTLASS's direct ATen usage. The minimal one-line swap (remove version define, add pybind disable) resolves the build failure, but the PR provides limited detail on why QUTLASS_DISABLE_PYBIND is required and whether the removed define was needed for any other purpose.

### Summary

**What changed and why**  
This PR fuses DeepSeek-V4.1's MXFP8 wo_b row-parallel GEMM with its sequence-parallel TP reduce-scatter using the SM100 GEMM-RS kernel, eliminating one kernel launch and an HBM round trip per layer. It generalizes the previously Kimi-K3-specific GEMM-RS/AR kernel by relocating it to vllm/model_executor/kernels/linear/cute_dsl/gemm_rs_ar.py, adding MXFP8 (block-scaled tcgen05 MMA) support, and sharing one workspace, init gate, warmup, test, and benchmark across both models. The VLLM_KIMI_K3_GEMM_RS flag is replaced by a unified VLLM_ENABLE_GEMM_RS (default off) that gates both Kimi-K3 RS and V4.1 wo_b.

**Technical impact**  
Adds MXFP8 tcgen05 MMA and tcgen05_cp primitives to cute_utils/_tcgen05.py, extends the kernel with scale-factor TMA loads and tmem scale-factor handling, and binds wo_b to the fused path via a new _wo_b_proj wrapper that falls back to sp_reduce_scatter for small batches. The decoder layer skips its own sp_reduce_scatter when GEMM-RS is bound, and RS now zero-fills output rows beyond M for unpadded callers. Reported gains: ~28-37% lower operator latency for M>=2048, 7.1% lower GPU busy time on an 8192-token prefill, and up to +4.6% serving throughput, with GSM8K accuracy within one standard error.

**Potential risks**  
The fused path is only correct under strict preconditions (SM100, BF16 model dtype, sequence parallel, TP 2-16, FlashInfer CUTLASS/CuTe-DSL MXFP8 weights); anything else must fall back cleanly with a warning, and the collective NVLink multicast rendezvous requires all TP ranks to make the same decision. The flag rename is a breaking change for users relying on VLLM_KIMI_K3_GEMM_RS, and the new RS zero-fill semantics for padding rows must hold for all callers. Benchmark results show regressions below ~1024 tokens and the c32 serving improvement is at the edge of run-to-run drift, so the win is not fully resolved at low concurrency. Speculative decoding and TP8 were not measured, and the off arm used the same branch with the flag unset rather than a separate main checkout.

**Key insights**  
The change is a well-scoped kernel generalization plus a model integration, with a shared workspace and unified flag reducing duplication between Kimi-K3 and DeepSeek-V4.1. The eligibility check must run before online quantization re-layouts weights, which the code handles by binding in bind_gemm_rs before weight loading. The main review focus should be the MXFP8 scale-factor layout/TMA handling, the padding zero-fill contract, the fallback correctness when preconditions fail, and the flag rename migration.
