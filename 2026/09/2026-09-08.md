## 1. [[Bugfix] Fix Mooncake heterogeneous TP with replicated GQA heads](https://github.com/vllm-project/vllm/pull/52516)

  - `tests/v1/kv_connector/unit/test_mooncake_connector.py`
  - `vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py`

### Summary

**What changed and why**  
Fixes a silent KV-transfer corruption bug in the Mooncake connector's heterogeneous-TP planner when a standard GQA layout crosses the KV-head replication boundary (e.g. Prefill TP > num_kv_heads >= Decode TP, or the reverse). Previously the planner assumed producer_cache_replicated meant each rank held a full KV block, so only one head slice was transferred and Decode marked the request KV-ready despite incomplete data. The change maps paired producer/consumer ranks through global KV-head indices, selects one canonical producer per replicated head, applies correct source/destination head offsets in both directions, and adds a layout guard rejecting padded pages and NVFP4 KV cache for re-sharding.

**Technical impact**  
_compute_sender_transfer_plan and _validate_asymmetric_region_lengths gain an optional total_num_kv_heads parameter that activates a new replication-aware mapping path; when None (MLA, Mamba, or legacy callers) behavior is unchanged. A new _validate_head_resharding_layout method rejects unsupported layouts (padded pages, NVFP4) before transfer. Callers in send_kv_to_decode and _get_sender_transfer_plan now pass total_num_kv_heads unless MLA or Mamba layers are present. Unit tests cover TP8-to-smaller-TP fan-in, GQA-to-replicated-TP8 fan-out, and region-length validation.

**Potential risks**  
The new mapping path is only exercised when producer and consumer replication states differ; edge cases around divisibility of num_kv_heads by TP sizes and non-power-of-two head counts are not exhaustively covered by the added tests. The reverse fan-out direction is validated only by unit tests, not a multi-node Mooncake deployment, per the PR description. The layout guard could reject previously working configurations if padded pages or NVFP4 were silently tolerated before, though those cases were likely already broken. Interaction with the parallel PR #53078 for hybrid Mamba/GDN state transfer is unresolved and may require rebasing.

**Key insights**  
The bug was silent: Mooncake reported successful transfers and Decode marked KV-ready even though only 25% of the destination block was written, causing token corruption without API or transport errors. The fix correctly distinguishes 'rank holds a full copy' from 'rank holds one head slice that is replicated', which the old planner conflated. The PR includes a strong end-to-end reproduction on official vLLM with Qwen3-235B-A22B-FP8, demonstrating the issue is generic to the Mooncake planner rather than model- or quantization-specific. The 125-combination reference-mapping check and focused unit tests provide reasonable coverage, but the reverse direction lacks end-to-end validation.

### Summary

**What changed and why**  
The ECExampleConnector.start_load_caches method previously passed the bare device string from current_platform.device_type (e.g. 'cuda') to safetensors.torch.load_file, which resolves to cuda:0 regardless of the worker's actual rank. Under tensor_parallel_size > 1, non-rank-0 workers would load the encoder cache onto cuda:0 and later fail when combining it with tensors on their local device. The fix pins CUDA-like loads to the device selected by vLLM's platform abstraction by appending current_platform.current_device(), while non-CUDA platforms keep the unchanged device_type. Two regression tests were added to cover both the CUDA-like (cuda:2) and non-CUDA (cpu) paths.

**Technical impact**  
This is a targeted bug fix in the example EC connector that corrects device placement for tensor-parallel workers, ensuring encoder caches are loaded onto the correct local GPU. The change is minimal and localized to the load path, using the existing platform abstraction so it remains compatible with CUDA-like backends and leaves non-CUDA platforms unaffected. The added tests use mocking to simulate multi-GPU rank placement without requiring a multi-GPU host, improving coverage of the TP>1 scenario.

**Potential risks**  
The fix relies on current_platform.current_device() returning the correct rank-local device index, which should hold under vLLM's platform abstraction but is not independently verified in this PR. The regression tests mock safetensors.torch.load_file and the platform, so they validate the device string passed rather than actual end-to-end loading behavior on real GPUs. Full CI (Buildkite #82780) was still running at PR submission, and the focused pytest could not be rerun locally on macOS ARM, so real-hardware validation is pending.

**Key insights**  
The root cause is a subtle safetensors behavior where a bare 'cuda' device string defaults to cuda:0, which is a common pitfall in tensor-parallel code paths. The fix correctly leverages vLLM's platform abstraction to derive the rank-local device, and the tests thoughtfully cover both CUDA-like and non-CUDA branches. Reviewers should confirm that current_device() semantics match the intended rank-local device and that CI passes on Linux/GPU before merging.

### Summary

**What changed and why**  
This PR fixes a NIXL EC consumer fault-isolation bug where a failed remote encoding transfer could trigger an assertion and terminate EngineCore instead of failing only the affected request. It introduces a per-request/per-embedding 60-second remote wait budget that survives retries, adds a take_unavailable_requests() API so the scheduler can abort requests lacking local model input, preserves local fallback when actual input (pixels/embeds/shm) exists, converts ACK timeouts from tombstone to retryable, and raises the default ACK timeout from 2s to 30s. It also adds a fault-injection integration test and substantially expands unit test coverage.

**Technical impact**  
The scheduler delegate now tracks per-request deferral clocks and an unrecoverable-request set, changing admission semantics: previously many failure paths silently fell back to local compute, now they either fall back only when local input is present or surface the request for abort. ACK timeouts become retryable rather than terminal, and the default ACK timeout increases 15x, which affects latency behavior for slow producers. The connector exposes a new take_unavailable_requests() method that the scheduler must drain to avoid double-abort.

**Potential risks**  
The 60s wait budget and 30s ACK timeout could increase request latency and resource holding under producer slowness, and the retryable ACK path may cause repeated re-requests. The new _unrecoverable set must be reliably drained or requests could leak or be aborted twice. The PR notes the historical crash was not reproduced on latest main and that a deterministic fault-injection E2E has not yet been run for this revision, so the fix is validated primarily by unit tests and a new integration test that requires two GPUs and NIXL. Behavior changes in fallback conditions (e.g., orphan not-ready entries now defer instead of falling back) could alter scheduling under edge cases.

**Key insights**  
The core insight is that a remote encoding miss should fail the request, not the engine, and that local fallback is only safe when the request still carries actual model input (pixels, embeds, or shared memory) rather than metadata alone. The change cleanly separates 'no remote source' (local encode) from 'remote source failed' (abort or fallback), and makes retry budgets per-request so shared hashes have independent clocks. Test coverage is notably thorough, parametrizing payload types, retry scenarios, invalid sizes, and per-request budget isolation, though end-to-end fault-injection validation remains outstanding.
