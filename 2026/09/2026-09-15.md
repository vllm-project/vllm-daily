## 1. [[Bugfix][Rust Frontend] Tolerate NaN-corrupted logprobs in engine-core](https://github.com/vllm-project/vllm/pull/51026)


### Base Information

- **PR Number:** #51026
- **Author:** [almersawi](https://github.com/almersawi)
- **Merged By:** [BugenZhao](https://github.com/BugenZhao)
- **Merged time:** 2026-09-15 20:10:58
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/51026/files) (3):**
  - `rust/src/engine-core-client/src/protocol/logprobs.rs`
  - `rust/src/engine-core-client/src/protocol/logprobs/tests.rs`
  - `rust/src/server/src/routes/openai/utils/logprobs.rs`

### Summary

**What changed and why**  
The Rust engine-core client previously rejected any decoded logprobs payload containing a sampled rank of 0, which occurs when the engine's sampled logprob is NaN (since NaN comparisons make the rank count zero). Because decode failures are frame-scoped and recorded as sticky health errors, a single NaN-producing request permanently broke the client, causing /health 503 and failures for all subsequent requests. The fix removes the rank-zero bail in PositionLogprobs::from_decoded_row, preserving rank 0 and the engine's raw NaN/infinity values, and adds regression tests for both the decode path and the existing HTTP -9999.0 clamping.

**Technical impact**  
Decoding now tolerates rank-0 sampled entries and non-finite logprob values, so one anomalous request no longer poisons the shared output-reader path or the sticky health state. Healthy payloads are unaffected, and the OpenAI serving layer already converts NaN and negative infinity to -9999.0 for JSON responses, so downstream HTTP consumers see the same sanitized values as before. The change is confined to the Rust frontend decode tolerance and does not alter engine numerical output.

**Potential risks**  
Relaxing the rank validation means malformed or unexpected rank-0 payloads from other causes will now be silently accepted rather than surfaced as decode errors, potentially masking genuine engine bugs. Consumers that assume rank >= 1 (e.g. top-k ordering or ranking logic) could behave unexpectedly if they encounter rank 0, though the PR indicates the HTTP helper handles non-finite values. The tests rely on expect-test snapshots and do not exercise a full end-to-end engine run, so integration behavior under real NaN logits is inferred rather than directly verified.

**Key insights**  
The root cause is a validation invariant (rank >= 1) that conflicts with a legitimate engine state (rank 0 from NaN sampled logprobs), turning a per-request data anomaly into a server-wide outage via frame-scoped decode failure and sticky health errors. The fix correctly targets the decode boundary while relying on the existing serving-layer clamping to keep HTTP output valid. The PR description clearly distinguishes this from related Python-frontend and stop-string PRs, and the added tests cover both the decode tolerance and the JSON clamping behavior.

**Potential risks**  
The PR is still a draft pending ROCm validation, so the fix has not been confirmed on actual hardware. The new test relies on exact equality (torch.equal) against the reference, which could be brittle if future reference implementations diverge slightly. The ceil-based scale formula may produce slightly different rounding than the previous floor-based approach in edge cases, though this is intentional to match the reference.

**Key insights**  
This is a targeted bug fix that aligns an omitted fused kernel with an already-established reference behavior, following a prior fix (#53110) for the generic quantizer.
