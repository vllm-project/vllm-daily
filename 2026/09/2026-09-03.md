  - `vllm/models/deepseek_v4/nvidia/ops/dequant_gather_k_cutedsl.py`

### Summary

**What changed and why**  
The launch grid for the dequantize_and_gather_k_cache_cutedsl kernel is changed from a fixed grid.y of 1024 to a dynamic value computed per call. The new grid.y is max(1, min(ceil(max_rows/4), ceil(8192/num_reqs))), where max_rows is the caller's upper bound on rows per request and num_reqs is the number of requests. This addresses severe underutilization in batch-invariant decode scenarios where many requests have few rows each, causing the old fixed grid to launch far more CTAs than needed, leading to low effective bandwidth and high latency.

**Technical impact**  
The kernel's launch configuration now adapts to the actual workload shape, improving performance dramatically for many-request, few-rows cases (e.g., 32-request SWA decode improves from 18.66 µs to 3.06 µs, a 6.1x speedup) while maintaining or slightly improving performance for single-request large-row cases. The change is a small code modification (+6/-1 lines) but has significant performance implications for the batch-invariant DSv4 decode path, reducing gather time per decode step from 1.66 ms to 0.51 ms. The public API is unchanged; only the internal grid computation is altered.

**Potential risks**  
The dynamic grid computation relies on heuristics (ceil(max_rows/4) and ceil(8192/num_reqs)) that were tuned based on measurements on GB200. These heuristics may not be optimal on other hardware or for unusual shapes not covered in the tests. There is a risk of performance regression for shapes where the chosen grid.y is suboptimal, though the PR includes extensive benchmarking showing no regressions in the tested shape set. The change also introduces a dependency on cutlass.min/max and cute.ceil_div, which must be available in the execution context. Since the kernel's per-row work is unchanged, numerical results are bitwise identical, so correctness risk is low.

**Key insights**  
The PR demonstrates that launch grid sizing is critical for kernel performance, especially for kernels with variable per-request work. A fixed grid can cause massive over-subscription or under-subscription depending on the workload. The solution uses a two-term heuristic: one term limits CTAs per request based on rows (one row per warp), and another caps total CTAs near a measured plateau (8192) to balance parallelism across requests. This approach is generalizable to other kernels with similar launch shape sensitivity. The PR also highlights the importance of profiling real deployment scenarios (batch-invariant decode) rather than only synthetic benchmarks, as the original grid was tuned for prefill shapes.

### Summary

**What changed and why**  
This PR fixes a bug in the scheduler where a synchronously resumed speculative-decode request (via a KV connector) on a data-parallel rank with no already-running requests was not padded to the uniform verifier shape. The padding condition previously required scheduled_running_reqs, causing a rank to schedule only one token while peers ran the full 1+num_spec_tokens shape, preventing full CUDA graph utilization. The change relaxes the condition to also allow padding when num_computed_tokens > 0 (indicating a resumed request) and no prefill is scheduled, while preserving behavior for ordinary prefills and diffusion speculative decoding.

**Technical impact**  
The scheduler now pads resumed speculative-decode requests to 1+num_spec_tokens even when no running requests exist on that rank, as long as the request has resolved computed tokens (num_computed_tokens > 0) and no prefill is scheduled. This ensures uniform verifier shape across DP ranks, enabling full decode CUDA graph usage. The change is minimal (one condition modification) and adds a regression test using a synchronous mock KV connector with 32 matched tokens.

**Potential risks**  
The change could affect scheduling behavior for any request with num_computed_tokens > 0 and no prefill, potentially padding requests that were previously not padded. However, the condition still requires num_new_tokens == 1 and no prefill, and the padding uses existing reject-only placeholder semantics, so model outputs are unchanged. There is a slight risk of increased padding in edge cases, but tests and serving validation show no regressions in accuracy or throughput at high QPS.

**Key insights**  
The root cause is a race between local num_computed_tokens and request.num_computed_tokens during synchronous KV connector resolution. The fix leverages the existing num_computed_tokens variable to identify resumed requests without needing scheduled_running_reqs. Serving benchmarks show significant P99 ITL improvements (up to -83%) at low QPS, confirming the benefit of uniform graph shapes.
