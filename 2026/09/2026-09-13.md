## 1. [[Bugfix] Fix --lora-modules name=path parsing when path contains '='](https://github.com/vllm-project/vllm/pull/53353)


### Base Information

- **PR Number:** #53353
- **Author:** [hungnnvidia](https://github.com/hungnnvidia)
- **Merged By:** [vllm-bot](https://github.com/vllm-bot)
- **Merged time:** 2026-09-13 23:55:22
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/53353/files) (1):**
  - `vllm/entrypoints/launchers/cli_args.py`

### Summary

**What changed and why**  
The PR fixes a bug in LoRAParserAction where the old 'name=path' format for --lora-modules was parsed using str.split('=') without a maxsplit. When the adapter path itself contained an '=' (e.g. a directory like run=3/adapter), unpacking into name and path raised ValueError and crashed vllm serve at argument parsing. The fix changes the split to item.split('=', 1) so only the first '=' is treated as the name/path separator.

**Technical impact**  
This is a one-line behavioral fix in CLI argument parsing for the OpenAI-compatible server entrypoint. It correctly preserves the documented name=path semantics and allows paths containing '=' characters, which is common in checkpoint directory naming conventions. No model inference, serving logic, or output behavior is affected; only argument parsing robustness improves.

**Potential risks**  
The change is minimal and low risk, but it assumes the first '=' always separates name from path, which matches the documented format. Edge cases such as an empty name or empty path before/after the first '=' are not explicitly validated here and would still be accepted, potentially producing an invalid LoRAModulePath. The PR notes the file path as vllm/entrypoints/launchers/cli_args.py while the description references vllm/entrypoints/openai/cli_args.py, a minor inconsistency worth confirming.

**Key insights**  
Using split with maxsplit=1 is the correct idiom for parsing key=value style CLI arguments where the value may legitimately contain the delimiter. The fix is well-scoped, includes a reproduction and verification, and is backed by existing CLI tests plus lint/type checks. The only notable gap is the file path discrepancy between the description and the diff, which should be reconciled for clarity.

### Summary

**What changed and why**  
The weight cache fast-start daemon previously identified its socket by the physical GPU id derived from CUDA_VISIBLE_DEVICES, which is fragile when that variable contains UUIDs or is otherwise non-integer. This PR switches the socket folder/file identifier to the GPU UUID via a new get_current_device_uuid() helper, updates the socket name template, and adjusts the test to glob for socket files. **Potential risks**

The test's glob-based readiness check could pass on stale or unrelated socket files matching the pattern, and it no longer verifies the exact expected paths. UUID-based socket names are longer and may hit filesystem path length limits on some systems, and existing socket files named by the old gpu_id scheme will not be cleaned up or matched.

**Key insights**  
The core improvement is replacing an environment-dependent integer mapping with a direct UUID lookup, which is more robust but shifts the failure mode from a clear 'cannot infer physical GPU id' error to whatever get_device_uuid raises. The import hoisting is a secondary cleanup that deserves scrutiny for circular-import risk since it touches engine and distributed modules. The test change trades precision for flexibility, so reviewers should confirm it still detects partial daemon startup failures.

### Summary

**What changed and why**  
This PR adds FULL CUDA graph capture and replay for microbatched (DBO) steps in the V2 model runner, building on the eager-mode DBO support from PR #50945. It introduces microbatched capture candidates, dispatches microbatched steps through the CUDA graph manager, captures graphs on the microbatch threads' stream, and replays them without per-microbatch Python overhead. The config gate is relaxed so DBO is only unsupported with PIECEWISE graphs, not all CUDA graphs.

**Technical impact**  
Microbatched decode steps can now run as captured FULL CUDA graphs, eliminating the CPU launch path and thread handoffs that dominate eager decode. Perf validation is deferred, so the actual benefit is not yet measured.

**Key insights**  
The design mirrors V1's gpu_ubatch_wrapper capture approach, with two critical fixes: capturing on the microbatch threads' stream and initializing CUDA/cuBLAS state before capture opens. Candidate generation must include the uniform-decode branch because MLA backends downgrade to FULL_AND_PIECEWISE and their FULL graphs are the uniform-decode ones. The gate uses UBatchRunner.wants_ubatch so captured shapes cannot drift from dispatchable ones, and dispatch falls back to eager when no graph matches. ## 9. [[Bugfix][Multimodal] Validate base64 video payloads, matching image and audio](https://github.com/vllm-project/vllm/pull/54323)


### Base Information

- **[Changed Files](https://github.com/vllm-project/vllm/pull/54323/files) (1):**
  - `vllm/multimodal/media/video.py`

### Summary

**What changed and why**  
The PR adds validate=True to pybase64.b64decode in VideoMediaIO.load_base64 (vllm/multimodal/media/video.py), making video base64 decoding strict like the image and audio loaders. The stated motivation is consistency and input validation: without validate=True, pybase64 silently strips invalid characters and re-packs the remaining bytes, so a corrupted payload is passed to the video decoder instead of being rejected. The PR description explicitly retracts an earlier claim that this path returns HTTP 500 under the default opencv backend, noting that opencv already raises ValueError mapped to 400.

**Technical impact**  
Behavior changes for malformed base64 video payloads: pybase64 now raises binascii.Error (a ValueError subclass) before the decoder is invoked, which maps to HTTP 400 through the existing handler. This aligns VideoMediaIO with ImageMediaIO, AudioMediaIO, and VideoEmbeddingMediaIO, and prevents shifted/derived byte streams from reaching C/C++ media parsers. A new test uses a sentinel backend to assert the decoder is never reached, making the check backend-independent. The change also rejects base64 containing line breaks or whitespace, which RFC 2045 permits, so some previously accepted line-wrapped payloads (e.g., from base64 CLI or Java MIME encoders) will now fail with 400.

**Potential risks**  
The main risk is a backward-compatibility break for clients that send line-wrapped or whitespace-containing base64 video payloads, which currently decode successfully and will now be rejected with 400. The PR acknowledges this and notes image and audio are already strict, but video clients may not have been tested against that constraint. The behavior of the torchcodec and pynvvideocodec backends on shifted input is explicitly unverified, so the claim that no 500 occurs is limited to the default opencv backend. The change is a one-line diff with no new exception types or handlers, so implementation risk is low, but the user-visible contract change is real.

**Key insights**  
The PR is a small, well-scoped consistency fix rather than a status-code bug fix, and the author transparently retracted the original 500 claim after verifying the default backend. The strongest argument is that two loaders in the same module now behave differently, which is a maintenance and security-relevant inconsistency. The test design using a sentinel backend is a good pattern because it asserts the decoder is not entered, not merely that an exception is raised. The open question for maintainers is whether strict rejection of RFC 2045 whitespace is acceptable or whether stripping should be applied uniformly across all three loaders as a follow-up.
