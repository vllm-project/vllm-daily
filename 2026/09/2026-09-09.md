### Summary

**What changed and why**  
Centralizes MRV2 DCP-local sequence length initialization into a single helper, maybe_prepare_dcp_local_seq_lens, which now returns a padded view of caller-owned storage or None when DCP is disabled. Previously several call sites (model_runner, pcp_manager, cudagraph_utils, dflash, speculator) prepared dcp_local_seq_lens independently at different points, causing stale or unset metadata after PCP partitioning, padding, or dummy/cudagraph batch construction. The PR also fixes a flashinfer DCP config attribute name (dcp_kv_cache_interleave_size to cp_kv_cache_interleave_size), moves page-count derivation after DCP seq_len conversion, adds dcp_query_start_loc for decode masking, and makes ubatch slicing recompute DCP lengths per microbatch.

**Technical impact**  
Behavioral change across eager, CUDA Graph, DFlash, PCP, and DBO/ubatch execution paths. DCP metadata is now derived from the final runtime InputBatch after partitioning and padding, ensuring padded rows are covered and CUDA graph replay sees recomputed values in persistent buffers. The helper returns None for dcp_size==1, clearing stale metadata, and ubatch slicing now allocates per-microbatch DCP buffers so truncated seq_lens produce correct local lengths. The flashinfer attribute rename and reordered num_blocks computation also affect attention metadata construction.

**Potential risks**  
The helper now returns a view sliced to num_reqs_padded; callers that previously used num_reqs or the full buffer may see shape changes, and any missed call site could still leave dcp_local_seq_lens unset. The flashinfer attribute rename assumes parallel_config exposes cp_kv_cache_interleave_size, which could break if the config field differs. Ubatch DCP buffer allocation adds memory and assumes dcp_size/dcp_rank are stable at construction. Tests are largely CUDA-gated and were not run locally, so CI coverage is essential before merge.

**Key insights**  
This is a genuine bug fix consolidating duplicated DCP setup that caused NoneType subscript errors and stale metadata. The design correctly defers DCP derivation until after PCP partitioning and padding, and the new tests target padded DCP, non-DCP clearing, per-microbatch recomputation, and buffer aliasing. Reviewers should verify all former prepare_dcp_local_seq_lens call sites are migrated and that the flashinfer config rename matches the actual ParallelConfig field.

  - `tests/multimodal/test_audio.py`
  - `vllm/multimodal/audio.py`
  - `vllm/multimodal/parse.py`

### Summary

**What changed and why**  
Adds a torchaudio backend to AudioResampler via a new resample_audio_torchaudio function using torchaudio.transforms.Resample, and flips the default resampling method from pyav to torchaudio in both AudioResampler and MultiModalDataParser. The rationale is that torchaudio is already a required dependency (unlike optional soxr), is faster than the current pyav default, needs no padding for short inputs, and resamples along the last axis so multi-channel audio avoids a per-channel loop. Kernel instances are cached per (orig_sr, target_sr) with lru_cache, and method validation is moved to construction time.

**Technical impact**  
Changes default audio resampling numerics for all audio models using the default path (except Phi-4-MM, which pins scipy), which is a deliberate behavior change. Adds a new public-ish function and a cached factory, extends the method Literal and validation, and wraps the torchaudio call in set_default_torch_num_threads(1) plus mkldnn disabled to avoid poisoning forked engine-core processes. Tests cover correctness, non-divisible rates, multichannel, short inputs, kernel caching, eager validation, and the new default.

**Potential risks**  
The default-path numeric change could subtly affect model outputs beyond the tested whisper-large-v3 case, so broader model validation may be warranted. The lru_cache(maxsize=32) holds torchaudio resampler instances (and their kernels) globally, which could retain memory and is not thread-safe under concurrent first-calls, though duplicate builds are benign. The thread/mkldnn context manager is a non-obvious workaround whose correctness depends on set_default_torch_num_threads semantics. torchaudio is imported via a PlaceholderModule fallback, but since it is now the default backend, environments lacking it would fail at runtime rather than import time.

**Key insights**  
The PR is well-justified: choosing torchaudio over the faster soxr avoids making an optional dependency load-bearing for the default path, and benchmarks show torchaudio beats pyav across tested cases with negligible cold-start cost. The eager method validation and kernel caching are sensible improvements. The main review focus should be the intentional default behavior change, the global cache's memory/thread implications, and confirming the thread-state workaround is necessary and correct.

### Summary

**What changed and why**  
Adds a new dispatch path in vllm/v1/attention/ops/rocm_aiter_mla_sparse.py that routes large DeepSeek V4 sparse-MLA prefill calls (>=1024 queries) on gfx950 to AITER's pa_sparse_prefill_opus kernel, gated by a new _can_use_aiter_sparse_prefill_opus eligibility check and a cached _get_aiter_sparse_prefill_opus loader, with the existing Triton dense/ragged paths retained as fallback. The PR also adds 211 lines of tests covering selection logic, routing, fallback preservation, and a gfx950 correctness check against a reference. The motivation is measured end-to-end throughput gains of roughly 0.3% to 8.4% depending on concurrency.

**Technical impact**  
Introduces a new kernel dispatch branch in the hot prefill path, including conversion of dense indices to ragged form via build_ragged_indices_from_dense when needed, and passes empty placeholder tensors for unused OPUS arguments. The gate is explicitly a performance crossover threshold rather than a correctness bound, and the AITER import is lazy and cached so environments without the OPUS kernel silently fall back to Triton. Behavior is unchanged on non-gfx950 hardware or below the query threshold.

**Potential risks**  
The 1024-query threshold is a measured heuristic and may not generalize across shapes, head counts, or future AITER versions, potentially causing regressions on workloads near the crossover. The eligibility check relies on many shape/stride/dtype/device conditions and could silently reject valid inputs or, conversely, admit inputs the OPUS kernel does not actually support. The OPUS call passes kv[:1] and empty indices/indptr placeholders whose semantics depend on the AITER kernel contract, which is not validated here. Correctness is only verified by a targeted gfx950 test and a gsm8k eval, so broader numerical parity across models and sequence lengths is not fully established.

**Key insights**  
The change is well-scoped: lazy import, cached lookup, explicit fallback, and a conservative perf gate keep the blast radius small. Test coverage is notably thorough for a dispatch change, including negative selection cases, fallback preservation, and a reference-comparison correctness test. The main review focus should be on whether the 1024-query threshold and the placeholder-argument contract with pa_sparse_prefill_opus are robust across the intended deployment matrix.

**What changed and why**

It introduces a new capture_axes mechanism in EncoderCudaGraphConfig, a reserved ENCODER_CUDAGRAPH_AXIS_KEYS_KWARG for models to report resolved axis keys, and a large MiniCPM-V mixin implementing SupportsEncoderCudaGraph. It also rewrites Idefics2VisionTransformer position-id computation and attention masking to be CUDA-graph-safe (device-side ops, async H2D copies) and adds tests, docs, and example entries.

**Technical impact**  
The encoder CUDA graph manager now captures one graph per token budget per cartesian product of capture-axis keys, with a warning threshold at 64 graphs. **Key insights**  
The core design is a clean generalization: token_budget still drives packing and buffer sizing, while an orthogonal capture axis handles shape-dependent patch-grid tiers, avoiding forced padding. The Idefics2 refactor to fully device-side position ids and unconditional additive masking is the riskiest part and deserves focused review and regression testing beyond MiniCPM-V. The PR is well-tested with unit tests (36 passed), functional image/video checks, and benchmarks showing no regression, but the benchmark numbers are within run-to-run variance so the performance claim is weak. Reviewers should verify the axis_keys contract, graph-count/memory scaling, and that the Idefics2 changes preserve outputs for existing models.
