  - `vllm/multimodal/media/audio.py`

### Summary

**What changed and why**  
This PR restores the automatic audio decoding order to soundfile -> TorchCodec -> PyAV, reverting a regression introduced by PR #51826 which made TorchCodec the preferred auto decoder. The regression caused test_long_audio_request failures on AMD MI300/MI355 because TorchCodec 0.10 with FFmpeg 4.4.2 adds 192 padding samples to the Mary Vorbis fixture at 16 kHz, altering repeated-audio boundaries and reducing recognized phrase repetitions from ten to seven. Documentation and a regression test were updated accordingly.

**Technical impact**  
The load_audio auto path in vllm/multimodal/media/audio.py now attempts soundfile first, preserving the previous waveform length and encoder padding behavior for soundfile-supported formats, then falls back to TorchCodec and finally PyAV. This restores prior decoding semantics for speech workloads while retaining TorchCodec availability for formats soundfile cannot read (e.g., video containers) and for users who explicitly select it for concurrent decoding. A new test asserts the default path matches soundfile output shape and sample rate.

**Potential risks**  
Users relying on the TorchCodec-first auto behavior for concurrency benefits will now get soundfile by default, potentially reducing throughput for concurrent audio decoding workloads unless they explicitly set backend='torchcodec'. The fallback chain still depends on ImportError or soundfile unsupported-format errors to advance, so any change in those error semantics could alter behavior. The regression test only covers Vorbis padding via the dummy fixture, so other format-specific padding differences may not be caught.

**Key insights**  
Decoder priority is a behavioral contract, not just a performance knob: swapping TorchCodec ahead of soundfile silently changed waveform lengths due to encoder padding, breaking downstream speech recognition. The fix correctly separates the default correctness-preserving path from the explicit concurrency-optimized path, and documents that TorchCodec should be selected explicitly for concurrent decoding. The added test guards against future priority regressions for soundfile-supported formats.

### Summary

**What changed and why**  
Adds a new XPU custom op (xpu_fused_input_norm) wrapping torch.ops._xpu_C.fused_input_norm, with a fake impl for tracing, and dispatches FusedInputNorm.forward to it on XPU when input is uint8 and weight is fp32. **Technical impact**  
Introduces a new registered custom op and a platform-conditional fast path in the vision model. **Potential risks**  
The new path depends on an external kernel (vllm-xpu-kernels) being present; missing or mismatched versions could cause import/runtime failures on XPU. The dispatch condition checks weight.dtype but not bias dtype, so a non-fp32 bias could silently take the fused path. Numerical equivalence is asserted but not verified by tests in this diff, and the fake impl assumes a 2D shape, which could break if input rank changes.

**Key insights**  
This is a targeted XPU performance optimization gated behind platform and dtype checks, with a safe fallback for other cases. Reviewers should confirm the external kernel dependency is properly declared, that bias dtype is validated, and that tests cover both the fused and fallback paths for numerical parity.

### Summary

**What changed and why**  
This PR removes torch.compile support from the NVIDIA Qwen4Exp implementation (model, MTP, and related modules) and eliminates the custom ops (qwen4_exp_compute_ple_ngram_ids, qwen4_exp_ple_short_conv, qwen4_exp_qsa_with_output) that were used to bypass compilation inspection. It replaces them with direct eager calls guarded by eager_break_during_capture decorators at state-routing and attention-core boundaries, and updates model_state buffers to keep fixed shapes/addresses across replays. The stated motivation is fixing issue #54688 and enabling FP8 checkpoint loading on a single GB300 by avoiding a ~50GB ngram table activation peak caused by torch.compile autotuning.

**Technical impact**  
Behavior changes are significant: Qwen4Exp architectures are added to default_breakable_cudagraph_architectures, the PLE ngram ID computation and short-conv now run eagerly inside captured regions, and QSA index projection is moved outside the eager break so only cache/selection logic is broken out. Model state buffers (ngram_context, ple_query_start_loc) are now full-size and reused in place, with unused capacity represented as trailing zero-length requests, which is required for stable CUDA graph addresses. Tests were updated to assert pointer stability and padded-row inertness, and the compilation splitting-ops list drops qwen4_exp_compute_ple_ngram_ids while retaining the AMD-only ops.

**Potential risks**  
Removing torch.compile may regress performance at low concurrency (reported -4.83% BF16 and -3.14% FP8 at concurrency 1), though gains appear at higher concurrency. The eager-break boundaries and fixed-shape buffer reuse are subtle: incorrect handling of num_reqs_after_padding or query_start_loc trailing values could cause stale data or incorrect ngram context in captured replays. The QSA refactor changes the forward signature to accept pre-projected Q/K, so any caller or test still passing hidden states will break; the updated tests cover this but external integrations may not. The FP8 single-GB300 memory benefit is asserted but not directly benchmarked in the provided results.

**Key insights**  
The core trade-off is replacing compiler-driven fusion with explicit eager breaks and manual buffer management, trading some low-concurrency throughput for memory savings and simpler FP8 deployment. The pointer-stability assertions in tests are a good guard against silent reallocation bugs in CUDA graph capture. The PR is well-tested with GSM8K/MMMU-Pro accuracy and E2E perf tables, but the perf deltas are noisy and the author acknowledges future manual fusion is needed to recover losses. Reviewers should focus on the eager_break_during_capture placement and the query_start_loc padding semantics.

**Technical impact**

The in-place copy_ into a reshaped view of the preallocated scale tensor relies on the interleaved output having exactly the same number of elements as the scratch buffer, so a mismatch would raise or corrupt data. The dtype handling changed from explicit .view(torch.float8_e4m3fn).reshape(...) to empty_like of the original scale tensors, so the returned scale tensors must already carry the expected fp8 dtype and shape. No tests are included in the PR description, so correctness of the new indexing path is not demonstrated.

**Key insights**  
This is a memory-optimization refactor of a weight-conversion utility rather than a pure bug fix, and it changes allocation behavior and tensor construction semantics, so it warrants careful numerical verification against the previous implementation. Reviewers should confirm that permute indices are truly expert-invariant, that the preallocated output shapes/dtypes match the old stacked results exactly, and that the scale interleave copy_ length always matches. Fixes a KV-offload scheduler bug where chunked prefill used the current step's SWA chunk count as the store-reachability horizon, causing it to submit SWA chunks the load path could never request (152 vs expected 150 chunks). The fix uses the prompt's final offloadable length while prefill is active, and on abort reconsiders the computed frontier as the final segment to submit newly reachable SWA tail chunks exactly once. A new final_segment_end_block parameter is threaded through reachable_block_mask in the sliding-window manager.

**Technical impact**  
Changes which SWA chunks are written to the offload tier during chunked prefill and abort, without altering load decisions, model execution, or output. Adds a new optional parameter to reachable_block_mask (default None preserves existing behavior) and refactors _build_store_jobs to compute per-group store ranges and a prompt-horizon mask for deduplication. Includes substantial new regression tests covering completed, aborted-sync, aborted-async, active-decode, and DCP-expanded abort lifecycles.

**Potential risks**  
The abort-path logic that reconsiders the final SWA tail and deduplicates already-stored chunks is intricate, with multiple interacting conditions (retention_interval, is_eagle_group, alignment divisibility, DCP scaling); subtle edge cases could still cause missing or duplicate stores. The new final_segment_end_block handling only applies to non-EAGLE SWA groups, so EAGLE paths rely on existing behavior. Tests were run CPU-only with accelerator cache-cleanup disabled, so GPU-specific behavior is not directly validated.

**Key insights**  
The core insight is that an intermediate prefill frontier is not the request's final segment, so reachability must be computed against the prompt's final offloadable length rather than the current step. On abort, the frontier becomes final and previously unreachable tail chunks must be submitted exactly once, requiring a prompt-horizon mask to avoid resubmitting chunks already stored. The added unit test on reachable_block_mask cleanly isolates the final-partial-segment semantics from the scheduler integration.

**Technical impact**

**Key insights**  
The change is small in line count but touches a core attention computation, so it should be validated against the original implementation for numerical parity across supported dtypes and devices.
