## 1. [[Perf][GDN] Slice pure spec-decode rows instead of a host-mask gather](https://github.com/vllm-project/vllm/pull/58763)


### Base Information

- **PR Number:** #58763
- **Author:** [lucamotz](https://github.com/lucamotz)
- **Merged By:** [vadiklyutiy](https://github.com/vadiklyutiy)
- **Merged time:** 2026-09-30 23:53:07
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/58763/files) (2):**
  - `tests/v1/attention/test_gdn_metadata_builder.py`
  - `vllm/v1/attention/backends/gdn_attn.py`

### Summary

**What changed and why**  
In the GDN attention metadata builder, pure spec-decode batches previously indexed the block table and num_accepted_tokens with a host boolean mask (spec_sequence_masks_cpu), which forced an H2D copy of the index plus a gather kernel. Since padded CUDA-graph rows always trail the spec rows, the code now slices the leading num_spec_decodes rows instead, and applies the same slicing in update_block_table(). A new test case covers pure spec-decode with trailing padding, and the test helper now explicitly sets cudagraph_mode to NONE when full_cuda_graph is false.

**Technical impact**  
Removes two host-mask gathers and their H2D index copies per GDN build and one per update_block_table() in pure spec-decode batches, cutting CUDA API calls per step roughly in half (424 to 197) and H2D copies from 36 to 4 in the reported nsys capture. Reported throughput gains on B300 are +1.4% to +4.1% across concurrency levels with unchanged acceptance length, while GB10 results are directionally positive but within noise. The change relies on the invariant that padded rows are always at the back of the batch.

**Potential risks**  
The optimization is only correct if padded sequences strictly trail spec decodes in every code path that reaches these branches; any future reordering of the batch (e.g. mixed prefill/decode interleaving or a different padding strategy) would silently produce wrong state indices. The num_accepted_tokens slicing is guarded by num_prefills == 0 and num_decodes == 0, but the block-table slicing in build() and update_block_table() is not similarly guarded, so the invariant must hold there too. Test coverage is CPU-only for the new case, and the performance claims are noisy on some hardware, so regressions could be hard to detect.

**Key insights**  
This is a targeted micro-optimization that trades a general mask-based gather for a positional slice, exploiting a layout invariant of pure spec-decode batches to eliminate host-to-device synchronization overhead. The measured gains are modest and hardware-dependent, but the reduction in CUDA API calls and H2D copies is substantial and could matter more on faster GPUs or with larger batch metadata. The added test and the explicit cudagraph_mode assignment improve coverage of the padded pure-spec-decode path, though the correctness argument rests entirely on the trailing-padding invariant being maintained elsewhere.

The test strategy of comparing against the exact unfused kernels (fused_qk_rmsnorm_rope_gate + reshape_and_cache_flash) with FP8 ULP tolerance is appropriate for validating numerical equivalence.

  - `tests/tokenizers_/test_hf.py`
  - `vllm/tokenizers/hf.py`

### Summary

**What changed and why**  
Fixes an off-by-one bug in get_cached_tokenizer in vllm/tokenizers/hf.py where max_token_id was computed as max(max(get_vocab().values()), tokenizer.vocab_size). Since vocab_size is a count, the largest valid id is vocab_size - 1, so the code could return an id one past the last valid token. This was reported as GHSA-q97c-p368-75c4 and could cause a CUDA device-side assert at TP=1 when a prompt contained the out-of-range id. A regression test was added in tests/tokenizers_/test_hf.py.

**Technical impact**  
max_token_id is now consistent with other tokenizer implementations (MistralTokenizer, KimiAudioTokenizer) and with downstream consumers like InputProcessor._validate_model_input and SamplingParams, which treat it as the inclusive largest valid id. Tokenizers whose added tokens exceed vocab_size (e.g. Qwen2.5) are unaffected because max(get_vocab().values()) remains the primary source. The change is a one-line semantic correction with a targeted test.

**Potential risks**  
Any code that implicitly relied on the previous off-by-one value (e.g. allocating buffers sized max_token_id + 1) could see a one-element reduction, though this aligns with the documented inclusive semantics. Tokenizers with unusual vocab_size properties that raise NotImplementedError are still guarded by contextlib.suppress. The test only covers gpt2, so broader tokenizer families are validated indirectly via the existing test suite.

**Key insights**  
The fix correctly distinguishes between a count (vocab_size) and a maximum index (vocab_size - 1), which is a common source of off-by-one errors in tokenizer and embedding code. Keeping max(get_vocab().values()) as the primary source preserves behavior for tokenizers with added tokens above vocab_size. The PR includes a focused regression test that fails on main and passes with the fix, and the author reports broad test coverage across tokenizer, sampling, and prompt-validation suites.

### Summary

**What changed and why**  
The Rust incremental decoder's DecodeStream now tracks the joint decode of pending tokens in a new pending_string field and, on the next push, checks whether the released chunk equals that pending text followed by the new token's isolated decode. When provably independent, the older pending tokens keep the shared anchor and the new token is anchored at its own first byte, fixing wrong attribution for cases like a stray incomplete UTF-8 byte followed by a special or ASCII token. Decoded text is unchanged; only anchor placement changes.

**Technical impact**  
Modifies core token attribution logic in rust/src/tokenizer/src/incremental.rs, adding a pending_group_split helper and restructuring push_token's pending/zero-width handling. This affects consumers that map spans to tokens, including the token-aware marker parsing stacked on top of this decoder. The normal path only pays an Option::take, and the extra single-token decode runs only when older tokens are pending and their lossy text survived verbatim.

**Potential risks**  
The split relies on an equality check between the joint decode and pending plus isolated decode, which is intentionally conservative because isolated single-token decodes are not context-free for all backends (e.g. SentencePiece leading-space stripping); when isolation is not provably consistent the shared anchor is kept, so some cases may remain mis-anchored. Edge cases around zero-width tokens, filtered special tokens, and flush/reset paths are covered by new tests but the change touches subtle incremental state, so regressions in other tokenizer backends are possible if their decode behavior differs.

**Key insights**  
The fix correctly distinguishes tokens that merge (byte-fallback completing a character) from tokens that are merely adjacent, using a provable equality rather than a suffix match to avoid backend-specific isolation pitfalls. The pending_string is cleared on both resolution and flush, preventing stale joint decodes from leaking into later pushes. Test coverage includes special tokens, ASCII, byte-fallback completion, and filtered special tokens, which is appropriate for the behavioral surface changed.

  - `vllm/multimodal/cache/base.py`
  - `vllm/multimodal/cache/shm.py`

### Summary

**What changed and why**  
This PR fixes a security vulnerability in the shared-memory multimodal processor cache (--mm-processor-cache-type shm) where the worker trusted client-supplied shared-memory addresses and IDs, allowing a client to make the worker deserialize attacker-chosen data. It introduces a random 32-byte HMAC secret stored at the start of the SHM segment, signs each handle over (key, address, monotonic_id), and rejects unsigned, mis-signed, or stale handles before shared memory is read. It also adds validate_input_item to the cache base class and calls it on client-supplied multimodal items in the scale-out serving path, and changes clear() to keep monotonic IDs increasing so pre-clear handles cannot alias new data.

**Technical impact**  
The SHM ring buffer layout changes to reserve a 32-byte auth-secret prefix, shifting all data offsets by DATA_OFFSET and requiring the shared memory allocation to grow accordingly; existing SHM segments are incompatible and must be recreated. Handles now carry a signature field that must survive msgpack serialization between sender and receiver, and readers verify signatures in get/touch while writers additionally check the key index. The default LRU cache is unaffected since validate_input_item is a no-op there, and the scale-out path now returns an ErrorResponse before engine handoff when validation fails.

**Potential risks**  
The layout change is a breaking change for any code or persisted state assuming the old SHM buffer size/offsets, and the assertion on attached segment size could fail against older segments. Signature verification adds per-access HMAC computation and validation overhead on the hot path, and the strict type checks (e.g. rejecting bool for address, bounds on address/monotonic_id) could reject previously accepted but unusual handles. The clear() behavior change means IDs no longer reset, which could affect any code relying on ID reuse semantics, and correctness depends on the secret never leaking to clients.

**Key insights**  
The fix correctly uses HMAC with constant-time comparison (hmac.compare_digest) and binds the signature to the cache key, address, and ID, preventing both forgery and cross-key/address replay. Keeping monotonic IDs increasing across clear() is a subtle but important detail that lets in-flight requests still read their own data while ensuring stale handles fail once slots are reused. Test coverage is thorough, spanning missing/altered/wrong-key signatures, out-of-range fields, pre-clear handles, msgpack round-trips, and the scale-out validation path, which gives good confidence in the security fix.
