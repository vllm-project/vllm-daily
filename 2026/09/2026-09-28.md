  - `vllm/model_executor/models/mistral3.py`
  - `vllm/model_executor/models/pixtral.py`

### Summary

**What changed and why**  
This PR optimizes image preprocessing for HF-format Mistral 3 models by (1) skipping dummy [IMG] text tokenization on Transformers >= 5.15 where PixtralProcessor supports image-only calls, and (2) moving rescaling/normalization from the CPU renderer to the GPU executor via vLLM's fused mm input norm. It also adds a new pixtral_patch_embed helper that normalizes and projects all CHW images in a single matrix multiplication, plus supporting config plumbing in mm_input_norm.py and a LightOnOCR opt-out flag.

**Technical impact**  
Renderer latency drops ~8% by avoiding placeholder tokenization and CPU normalization; raw uint8 pixels are transferred H2D and normalized on device, shortening the renderer critical path. The new pixtral_patch_embed path replaces per-image Conv2d calls with a packed F.linear projection, and Mistral3ForConditionalGeneration now declares supports_mm_device_do_normalize=True. A fallback path preserves prior behavior when input_norm is None or Transformers < 5.15.

**Potential risks**  
The packed patch-embed path relies on correct stride/order handling and dtype casting; subtle mismatches versus the reference Conv2d could degrade vision quality despite passing tolerance-based tests. The version gate on Transformers 5.15.0 is a hard cutoff that may break if the upstream image-only API changes. The mm_input_norm config fallback to hf_image_processor_config could pick up unexpected values for models with unusual processor configs, and LightOnOCR must remain opted out to avoid incorrect normalization.

**Key insights**  
The optimization is well-scoped with explicit before/after benchmarks and targeted tests covering FusedInputNorm equivalence, uint8 vs normalized outputs, and patch-embed ordering/strides. The dual-path design (fused vs legacy) limits blast radius, but correctness of the new packed projection and the version-gated processor behavior are the main review focus areas. The added LightOnOCR opt-out and config fallback show awareness of cross-model regressions.

## 2. [[Bugfix][GLM-5.3-Flash] Take video placeholder timestamps from the pixel path's frame sampler](https://github.com/vllm-project/vllm/pull/55647)

  - `tests/models/multimodal/processing/test_glm5next.py`
  - `vllm/models/glm5next/common/multimodal.py`

### Summary

**What changed and why**  
Fixes a bug where GLM-5.3-Flash video prompts were expanded by one frame sampler (GLM-4.6V constants) while pixels were encoded by another (the checkpoint's Glm5NextVideoProcessor), causing placeholder/encoder-row count mismatches outside 30-300s durations that crashed the engine core. The PR overrides _get_video_second_idx_glm46v in Glm5NextProcessingInfo to derive timestamps from the pixel path's own sampler (glm_sample_frame_indices), making placeholder count structurally equal to grid_t, and converts a too-short-clip IndexError into a descriptive ValueError. A new CPU-only test file verifies the arithmetic across several clip durations.

**Technical impact**  
Placeholder counts now match video_grid_thw for all clip durations, eliminating the shape mismatch in _merge_multimodal_embeddings that previously killed the engine core on malformed requests. The do_sample_frames=False branch is handled separately using delivered frames and frames_indices, and the 30-300s window (where samplers already agreed) is preserved as a regression guard. Behavior change is confined to timestamp computation; pixel processing is untouched.

**Potential risks**  
The override relies on internal attributes (fps_interval, max_frame_count_dynamic, temporal_patch_size) of the video processor and on glm_sample_frame_indices semantics; if those change, the invariant could silently break. The ValueError for too-short clips changes error type from IndexError to ValueError, which could affect callers catching specific exceptions. mypy and other pre-commit hooks were not run locally, so static type issues may remain. The PR explicitly leaves related issues (max_pixels propagation, supported-limit clamp, 400-vs-engine-death) unaddressed.

**Key insights**  
The root cause was a split-brain design where two independent samplers governed placeholder count and encoder rows, agreeing only coincidentally in a narrow duration window. Deriving timestamps from the same sampler as pixels makes the count structural rather than coincidental. The test suite is well-designed: it recomputes the pixel path's grid independently and includes a regression guard for the previously-agreeing window, plus coverage of the pre-sampled branch and the error path.

### Summary

**What changed and why**  
This PR modifies the shared schema-aware tool-argument conversion in rust/src/parser/src/tool/parameters.rs to make typed value parsing more forgiving and composite type handling stricter. It adds whitespace trimming for non-string types, support for Python-style digit separators (1_000), handling of the OpenAPI 'nullable' flag, and type-matched JSON decoding for object/array parameters. The goal is to unify argument-typing rules across Rust tool parsers (Qwen3-Coder, GLM, MiniMax, DeepSeek DSML, Hy) and support the hf response-template parser above it.

**Technical impact**  
Behavior changes affect all Rust tool parsers sharing this conversion: integer/number/boolean/object/array values now ignore surrounding whitespace, integers and numbers accept single underscores between digits, nullable schemas accept null, and object/array parameters only accept JSON that decodes to the matching type instead of coercing arbitrary JSON. **Potential risks**  
The stricter composite decoding is a behavior change that could break existing callers relying on the previous permissive coercion (e.g., a string '5' for an object parameter previously became number 5). The digit-separator logic only validates underscores between ASCII digits, so edge cases like underscores adjacent to signs, decimals, or exponents may behave unexpectedly. The nullable handling assumes the OpenAPI 'nullable' spelling and may not cover other optionality conventions. Test coverage is limited to unit tests in one module; broader integration impact across all tool parsers is asserted but not exhaustively demonstrated.

**Key insights**  
This is the bottom of a stack that centralizes argument-typing rules for all Rust tool parsers, so changes here have wide blast radius despite the small diff. The PR is well-tested at the unit level with 1887 workspace tests and 20 roundtrip tests passing, and clippy/fmt are clean. The exclusion of vllm-tool-parser-py is noted as an unrelated host issue. Reviewers should focus on whether the stricter composite decoding and whitespace trimming align with expected model output and downstream parser expectations.

There is also a minor merge conflict risk with PR #58439, which modifies the same expression and will require a one-line rebase. No model evaluation was performed, though the change only selects a storage path and should not alter lookup results.

**Key insights**  
The root cause was an ordering/validation gap: use_thp was only validated against dp_shared_memory at construction time when the field was still unset, so the DP default from #57651 could later resolve sharing on and bypass THP. The fix is minimal and aligns runtime resolution with the documented contract.
