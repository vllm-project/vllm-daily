## 1. [[Bugfix][Examples] Launch prefill and decode concurrently in NixlPushConnector demo](https://github.com/vllm-project/vllm/pull/55088)


### Base Information

- **PR Number:** #55088
- **Author:** [junuxyz](https://github.com/junuxyz)
- **Merged By:** [NickLucche](https://github.com/NickLucche)
- **Merged time:** 2026-09-11 23:22:35
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/55088/files) (1):**
  - `examples/disaggregated/disaggregated_serving/disagg_proxy_pushconnector_demo.py`

### Summary

**What changed and why**  
The NixlPushConnector demo proxy previously awaited the full prefill response before issuing the decode request, forcing the two upstream calls to run sequentially. This PR wraps the prefill drain in an asyncio background task and starts the decode stream immediately, so prefill and decode execute concurrently. The change is a behavior fix in an example script, motivated by measured latency improvements (decode start moved from ~144ms to ~0.9ms).

**Technical impact**  
Decode requests now begin almost immediately after prefill is dispatched rather than waiting for prefill completion, reducing end-to-end latency in the disaggregated serving demo. The prefill task is still awaited in the decode generator's finally block, preserving the requirement to drain the prefill connection so the upstream server can free its slot. Only one example file is touched, so production code paths are unaffected.

**Potential risks**  
If the decode stream is cancelled or errors before completion, the finally block awaits prefill_task, which could delay cleanup or propagate a prefill exception into the decode response. Exceptions raised inside drain_prefill are only surfaced when awaited, so failures may be reported later or attributed to the decode path. Concurrency assumptions between prefill and decode engines (KV transfer readiness, request ordering) are not explicitly validated in the diff, though the test plan exercises the intended flow.

**Key insights**  
The fix correctly identifies that an async-for drain loop blocks subsequent code, and uses asyncio.create_task to overlap the two upstream requests while still guaranteeing prefill completion via the finally await. The included reproduction script and before/after timeline provide concrete evidence of the latency win. Reviewers should confirm error handling and cancellation semantics for the background prefill task, since those edge cases are not covered by the single-request benchmark.

  - `vllm/v1/worker/gpu/spec_decode/eagle/utils.py`
  - `vllm/v1/worker/gpu/spec_decode/utils.py`

### Summary

**What changed and why**  
Adds a helper get_pp_safe_draft_load_config that, when PP world size > 1 and load_format is fastsafetensors, returns a copied LoadConfig with load_format set to auto, and wires it into the EAGLE/EAGLE3, DFlash, and DSpark draft model loaders. This avoids a deadlock where fastsafetensors uses WORLD-group collectives but the external draft model only exists on the last PP stage, so other ranks never join the broadcast. The target model keeps fastsafetensors, and PP=1 or other load formats are unchanged.

**Technical impact**  
Behavior changes only for speculative-decoding draft model loading under pipeline parallelism with fastsafetensors: the draft falls back to the standard safetensors loader while the target retains the fast path. EAGLE uses replace(vllm_config, load_config=...) to avoid mutating the shared config, while DFlash/DSpark pass the derived load_config directly to get_model. Existing tests were updated to supply a LoadConfig and mock get_pp_group, and new unit tests cover the helper.

**Potential risks**  
The fallback is silent apart from a warning_once, so users may not notice the draft loader changed; performance of draft load could regress slightly, though the draft checkpoint is small. The helper calls get_pp_group() at load time, which assumes the distributed group is initialized, and the EAGLE path relies on replace() semantics to avoid side effects on the target config. The fix is a workaround for a fastsafetensors adapter bug (subgroup-local ranks passed as global ranks) rather than a true fix, so it may need revisiting once upstream fastsafetensors supports subgroup collectives.

**Key insights**  
The root cause is a mismatch between fastsafetensors' WORLD-group collectives and the fact that external draft models are only instantiated on the last PP stage, causing ranks to wait on peers that never enter the loader. Using the stage TP subgroup is not viable because the installed fastsafetensors PyTorch adapter passes subgroup-local source ranks as global ranks, failing with 'Global rank 0 is not part of group'. The chosen mitigation is pragmatic and well-scoped: keep the fast target load, use the collective-free loader only for the much smaller draft checkpoint, and preserve PP=1 and other load formats. The PR includes targeted unit tests and an end-to-end Kimi-K3 DSpark validation on 2x8 B200 GPUs showing successful startup, generation, and 59.1% speculative acceptance.

  - `rust/src/chat/src/renderer/hf/mod.rs`
  - `rust/src/chat/src/renderer/hf/template.rs`

### Summary

**What changed and why**  
Adds a new generation.rs module that rewrites Hugging Face `{% generation %}...{% endgeneration %}` blocks into MiniJinja `{% call __hf_generation() %}...{% endcall %}` blocks, since MiniJinja rejects the `generation` tag. The rewrite uses MiniJinja's lexer to locate statement keyword spans, preserving whitespace controls, literals, comments, and raw blocks, and validates original generation/call pairing. It is wired into template compilation and the environment registers the `__hf_generation` callback, applying to both configured templates and per-request overrides.

**Technical impact**  
Enables the Rust HF renderer to compile and render public chat templates (e.g., SmolLM3-3B, TRL Qwen3 training) that use generation blocks, which previously failed with `unknown statement generation`. The scoped call-block approach preserves local scope and whitespace-trimming semantics, matching Transformers' AssistantTracker behavior, and the rewrite runs before content-format detection so detection sees the rewritten template.

**Potential risks**  
The lexer-based span replacement is sensitive to MiniJinja tokenizer behavior and could break if tokenization changes or if unusual constructs (nested generation blocks, generation inside macros/raw) are not fully covered. Validation only covers template rendering; GPU model-generation evaluation and assistant-token-mask correctness are not verified, so downstream training/inference semantics are assumed rather than proven. Edge cases like generation blocks spanning control structures are tested for rejection but real-world template diversity may exceed test coverage.

**Key insights**  
Using scoped call blocks rather than regex/literal removal (as Mistral.rs, TGI, and Dynamo do) preserves rendering semantics including whitespace trimming and in-block assignments, which is a meaningful correctness improvement. The implementation carefully validates original generation/call pairing before rewriting, and tests cover whitespace, literals, raw, comments, scope, and nested calls. The change is well-scoped to the Rust HF renderer with no apparent impact on other frontends.

### Summary

**What changed and why**  
This PR introduces HiSparse, a host-resident sparse-MLA decode hot-buffering tier for vLLM, adding a scheduler-side coordinator, a KV connector, worker-side pinned host pools, fused CUDA kernels for residency resolution and host-row gathering, and extensive wiring through config, KV cache layout, attention backends, and NIXL/offloading connectors. It also refactors shared infrastructure: KVConnectorTransferResults replaces get_finished, bind_kv_cache_manager replaces bind_gpu_block_pool, block pools gain unpin_blocks/reuse watchers, and NIXL/Mooncake gain per-region group mapping. The change is large (124 files, ~14k insertions) and spans kernel, scheduler, worker, and connector layers.

**Technical impact**  
Adds a new execution path where sparse-MLA decode resolves top-k positions across resident GPU pages, a per-request GPU hot buffer with LRU, and a pinned host pool, all inside CUDA-graph-compatible kernels. **Potential risks**  
High blast radius: core KV cache manager, block pool, scheduler, and multiple connectors are modified, so regressions could affect non-HiSparse workloads. The new CUDA kernels use raw PTX and pinned host memory with manual registration/unregistration, risking memory-safety or teardown issues. Failure-reporting semantics changed (failed_recving, deferred split-read reporting), and NIXL region/group mapping changes could break P/D layouts. Host pool sizing is topology-dependent and validated only by preliminary B300 results; ROCm and DeepSeek V4 are explicitly unsupported.

**Key insights**  
The design keeps the indexer as a normal prefix-cacheable GPU group and only owns sparse-MLA residency, which limits coupling but requires careful prefix-boundary handling with OffloadingConnector. Spill correctness depends on enqueue vs completion acknowledgements and on publishing host hashes only after durability. The PR is explicitly staged with prerequisite PRs (#53779, #53780) and follow-ups (#53782, #53592), and AI assistance was used, so reviewers should scrutinize the kernel addressing, LRU/eviction invariants, and the broad interface refactors for unintended behavior changes.

### Summary

**What changed and why**  
This PR migrates the DeepSeek V4 NVIDIA CuTeDSL attention and sparse-attention kernels (indexer-Q, dequantize-and-gather, and the sparse-attention compression family) onto a shared warmup contract. It moves the generic kernel_launcher decorator from the Triton helper into jit_warmup.py, unifies the CuTeDSL launch spec to support optional outputs and a post-launch finalizer, and converts free functions into VllmCuTeDSLJitKernel subclasses with kernel-owned CompileKeys and AST-traced warmup spaces. Call sites in attention.py, cache_utils.py, fused_indexer_q.py, and compressor.py are updated to invoke the new kernel objects with keyword arguments.

**Technical impact**  
The launcher abstraction is now backend-agnostic: kernel_launcher delegates to self.launch, with CuTeDSL setting bind_launch_inputs=False and Triton keeping named-input binding. CuTeDSL launch specs gain a 3-tuple (outputs) and 4-tuple (finalizer) form, and the Triton launch signature changes to accept a LaunchSpec plus inputs, so all Triton kernels must be updated consistently. New compile-only CuTeDSL paths using fake tensor descriptors enable warmup without real tensors, and torch_to_cute_dtype centralizes dtype mapping. Warmup registration is now gated on enable_jit_warmup and platform/CuTeDSL availability, changing when kernels are precompiled.

**Potential risks**  
The Triton launch signature change is a breaking API change for any out-of-tree or unmodified callers, and the test diff shows the expected call shape changed. The CuTeDSL launch spec union is loosely typed (Any for outputs/finalizer), so incorrect tuple lengths could silently misroute results. The 4-tuple finalizer path returns the finalizer result rather than the executor result, which is subtle and only lightly tested. Warmup registration now depends on current_platform.is_cuda() and has_cutedsl() checks in model constructors, so misconfiguration could skip warmup or trigger CUDA driver init in tests. Large mechanical rewrites of kernel bodies (e.g. +1945/-1606 in sparse_attn_compress_cutedsl.py) risk subtle behavioral drift despite the claim of preserved kernel bodies.

**Key insights**  
The core design goal is a single shared warmup/launch contract across Triton and CuTeDSL, achieved by hoisting kernel_launcher into jit_warmup and letting each backend implement launch. CuTeDSL kernels are restructured from stateful classes with __init__ parameters into static kernel(compile_key) factories plus frozen CompileKey dataclasses, which makes compile keys explicit and warmup spaces traceable. The added tests verify executor reuse and the new post-launch finalizer behavior, but coverage of the new 3-tuple output and finalizer semantics and of the migrated CuTeDSL kernels themselves appears limited relative to the size of the change.
