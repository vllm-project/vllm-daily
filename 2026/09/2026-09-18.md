  - `vllm/triton_utils/importing.py`
  - `vllm/v1/worker/gpu/sample/gumbel.py`

### Summary

**What changed and why**  
The PR fixes a bug where DeepSeek V4.1 fails to import when Triton is unavailable. The TritonLanguagePlaceholder previously set constexpr to None, causing tl.constexpr(...) calls at import time in sparse_mqa_logits.py to crash. The fix changes the placeholder's constexpr to an identity lambda, allowing modules to define constants without Triton, and simplifies gumbel.py by removing the HAS_TRITON conditional since the placeholder now supports constexpr.

**Technical impact**  
This changes the behavior of the Triton fallback path so that tl.constexpr(value) returns value instead of raising a TypeError. It unblocks model import and inspection on CPU-only environments, and removes the need for model-specific guards like the HAS_TRITON conditional in gumbel.py. The real Triton implementation is untouched, so GPU behavior is unaffected.

**Potential risks**  
The identity lambda silently accepts any value, so if a module relies on constexpr for actual compile-time semantics under real Triton, the placeholder path may mask type or usage errors that would surface on GPU. The change is narrow and well-tested, but the full Triton utility suite still has two pre-existing failures on the CPU wheel related to backend detection, which are unrelated to this patch.

**Key insights**  
The root cause was an overly strict placeholder that set constexpr to None rather than providing a no-op implementation. Making the placeholder behave like a pass-through for constexpr is a minimal, targeted fix that restores importability without touching the real Triton path. The updated tests now cover integer and float constexpr values, and the removal of the HAS_TRITON guard in gumbel.py demonstrates the fix's broader benefit.

## 2. [[Bugfix][Multimodal] Frame the multi-modal hash digest input](https://github.com/vllm-project/vllm/pull/54283)

- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/54283/files) (3):**
  - `tests/multimodal/test_hasher.py`
  - `tests/multimodal/test_processing.py`
  - `vllm/multimodal/hasher.py`

### Summary

**What changed and why**  
The PR fixes a hash-collision defect in MultiModalHasher where the digest input stream was not uniquely decodable, allowing distinct processor kwargs (key/value boundary shifts, nested vs flattened keys, sequence vs mapping, None vs empty, empty container vs omitted key) to produce identical mm hashes. It introduces length-prefixed framing for every byte chunk and container tags (NONE, SEQUENCE, MAPPING, LEAF) in vllm/multimodal/hasher.py, replacing the dotted-key flattening, and adds regression tests in test_hasher.py and test_processing.py.

**Technical impact**  
The mm hash is used as the identity for the multi-modal processor cache and is mixed into prefix-cache block keys, so collisions could silently serve one request another's processed features and KV blocks. The new framing makes the digest input uniquely decodable, eliminating the collision class. All digests change, but mm hashes are process-local (in-memory caches), so the only upgrade effect is a cold cache, not incorrect reuse. Measured hashing overhead is roughly 2% of the hashing stage, with negligible end-to-end impact.

**Potential risks**  
All existing mm hashes change, causing a one-time cold cache after upgrade; this is expected and documented but could surprise operators monitoring cache hit rates. The framing adds 8 bytes per chunk, a small but non-zero cost. Primitive leaves remain untyped (str vs its UTF-8 bytes still collide) and nested mapping key order still affects the digest, both explicitly out of scope. The change touches a security-adjacent hashing path, so any subtle framing bug could reintroduce collisions or cause spurious cache misses.

**Key insights**  
This is the same defect class as GHSA-c65p-x677-fgj6 and is correctly handled as a public LOW-severity fix per SECURITY.md. The test plan is thorough: six of seven new cases fail on main with literally equal digests, and the full multimodal suite shows a byte-identical failure set with seven extra passes. The performance analysis is honest about measurement limits, noting the ~2% hashing overhead sits at the edge of harness resolution. The decision to keep primitive leaves untyped to preserve the 'same image, same hash' property across PIL decoders is a reasonable trade-off worth a follow-up.

### Summary

**What changed and why**  
This PR fixes issue #55679 by allowing KV-event publishers to bind to port 0 (tcp://*:0), letting the OS assign an ephemeral port at bind time, and then exposing the resolved endpoints. Previously, a launcher had to pre-allocate a free port block, which could be stolen by other processes during the long engine startup window. **Potential risks**

The change only supports exactly tcp://*:0 and leaves other port-0 spellings (e.g., 0.0.0.0:0, [::]:0) untouched, which could surprise users. The Rust implementation reads ready responses and filters out engines without kv_events_config, which is consistent with Python but relies on the ready handshake completing before the route is queried.

**Key insights**  
The PR reuses the existing shm_broadcast.py pattern for ephemeral binding, minimizing new surface area and keeping explicit endpoints untouched. The design deliberately limits support to tcp://*:0 to avoid growing the bind path for various address-family spellings, as documented in the adversarial review. The route returns the same map in both Python and Rust frontends, ensuring parity. The test plan is thorough, covering DP across nodes, hybrid LB, IPv6, and in-process usage, with a control showing the unpatched wheel fails. Reported throughput gains (18 to 45 tok/s, and a separate 13 to 61 tok/s with FULL cudagraphs) come from removing per-launch overhead and cross-rank skew.

**Potential risks**  
The causal flatten is explicitly unsupported under DCP (asserted, not handled), so any future DCP causal multi-token path would fail rather than degrade. The merge() change from any() to strict agreement could reject previously accepted layer groupings, potentially breaking configurations that relied on the looser OR semantics. The unconditional UNIFORM_BATCH declaration removes the previous per-spec conditional, so any group that does not actually satisfy the uniform-batch contract now silently claims it. The new tests use a mocked kernel and cannot catch real kernel-level indexing errors, and the PR itself notes there is no same-flags unpatched baseline for the headline throughput numbers.

**Key insights**  
The root cause is a coupling between the reorder threshold and query_len_support: the non-causal DSpark route raises the threshold after the base __init__ asserted SINGLE_ONLY implies threshold 1, letting a causal batch be split with a raised threshold while forward_mqa only expanded tables under 'if not causal'. The fix is elegant in reusing decode_attention_fwd's per-row seq_lens as the causality mechanism instead of adding a causal flag to the kernel. The PR is well documented with overlapping prior work (#47310, #51171, #51705, #52218) and independent corroboration, though several cited benchmarks are integration evidence rather than isolated measurements of this change.

  - `tests/kernels/quantization/test_block_fp8.py`

### Summary

**What changed and why**  
This PR fixes a performance regression in the SM100 FP8 blockwise GEMM path for misaligned M values. The SM100 blockwise scale-factor copy requires the SFA M extent to be a multiple of 4 (4-row copy atom), so the code now pads only the per-token activation scales (column-major (m, k/128), 1/64 the size of the bf16 activation) on the non-swapAB path and builds layout_SFA from the padded extent. The swapAB heuristic was also changed from (m < 16) \\|\\| (m % 4 != 0) to (m <= 64), since misaligned M >= 65 is faster on the non-swapAB path with padded scales, as shown by the GB300 microbenchmark.

**Technical impact**  
The change affects the CUTLASS SM100 FP8 blockwise GEMM dispatch in csrc/libtorch_stable/quantization/w8a8/cutlass/c3x/scaled_mm_blockwise_sm100_fp8_dispatch.cuh. It introduces a temporary padded activation-scale tensor allocated via torch::stable::new_empty and filled with cudaMemcpy2DAsync on the current CUDA stream, then uses that padded buffer for the SFA layout and pointer. The swapAB threshold change alters which kernel path is selected for M in (16, 64] and for misaligned M > 64, which should improve performance for those shapes. The CI config and unit test were updated to cover the new M residue classes and the new code path.

**Potential risks**  
The padding path uses cudaMemcpy2DAsync with the current CUDA stream and assumes the activation scales are contiguous column-major with num_groups = a_scales.numel() / m; if the input layout or dtype assumptions are violated, the copy could be incorrect or out of bounds. The temporary tensor lifetime is tied to the optional a_scales_pad, which must remain alive until the kernel launch completes; this appears handled but is a subtle lifetime dependency. The swapAB threshold change is based on GB300 measurements and may not be optimal on other SM100 variants or for all N/K combinations, potentially causing regressions on untested shapes. The test only covers a small set of M values and a single N/K/block_size configuration, so broader coverage is limited.

**Key insights**  
The fix targets a specific hardware constraint (4-row SF copy atom) by padding only the small activation-scale tensor rather than the full activation, keeping overhead low. The microbenchmark shows substantial speedups for misaligned M (e.g., M=129 from 140.5 to 68.0 us at N=34816, K=5120) and for large M, while aligned small M remains on the swapAB path. The alternative of fusing padding into the quantization kernel was rejected due to broader file impact. The PR is classified as SUBSTANTIAL because it changes kernel dispatch behavior and adds a new memory-copy path, not just documentation or formatting.

The wire format mirrors vLLM's sparse list[list[int]] contract with optional CSR offsets, and packed bitmap transport is explicitly deferred. Test coverage spans engine-core decoding (including multipart aux frames), LLM collection, text decoding with mid-chunk stop truncation, and server proto conversion, which is reasonably thorough for the new behavior.
