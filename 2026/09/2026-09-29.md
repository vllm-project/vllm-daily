**Potential risks**  
The unverified Rust changes (new metrics module, route response changes, middleware exclusion removal) carry regression risk since Cargo/rustfmt were unavailable and no live-server E2E was run on the current revision. The wake_up bool contract could silently break external EngineClient implementations that return None, causing them to be reported as 'sleeping'. The in-flight gauge uses multiprocess_mode='livesum' and relies on context-manager cleanup on cancellation; correctness under abrupt process termination or multiprocess edge cases is not fully demonstrated. Removing the sleep handlers from EXCLUDED_HANDLERS changes existing metric cardinality/behavior for those routes.

**Key insights**  
The PR is well-scoped and explicitly documents the breaking wake_up interface change and the deferred follow-ups (resource dimensions, memory byte metrics, HTTP in-progress middleware redesign). ## 3. [[Core] Bound UniProc EngineCore startup threads to available CPUs](https://github.com/vllm-project/vllm/pull/58946)


### Base Information

- **PR Number:** #58946
- **Author:** [AndreasKaratzas](https://github.com/AndreasKaratzas)
- **Merged By:** [njhill](https://github.com/njhill)
- **Merged time:** 2026-09-29 23:02:56
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/58946/files) (2):**
  - `tests/v1/engine/test_startup_watch_processes.py`
  - `vllm/v1/engine/utils.py`

### Summary

**What changed and why**  
Adds a launch-scoped context manager in vllm/v1/engine/utils.py that caps UniProc EngineCore startup threads to the smaller of the current PyTorch per-process thread count and the available-CPU budget divided by local EngineCore processes, setting OMP_NUM_THREADS and the vLLM ownership marker only during subprocess start and restoring the parent afterward. This addresses a CI timeout where a 12-CPU cgroup quota process loaded weights with 192 PyTorch threads, taking 38 minutes, because the quota-aware budget from #49919 did not cover UniProc workers running in EngineCore. A new parametrized test in tests/v1/engine/test_startup_watch_processes.py verifies thread capping, user-override precedence, failure restoration, and non-UniProc exclusion.

**Technical impact**  
UniProc EngineCore subprocesses now start with a CPU-affinity-aware thread budget, reducing oversubscription and weight-load time under cgroup quotas while leaving MultiprocExecutor and explicit user OMP_NUM_THREADS settings untouched. The context manager wraps the existing per-process launch loop, so fork inherits the reduced PyTorch thread count and spawn reads the temporary OMP_NUM_THREADS value. Parent environment and torch thread state are restored in a finally block even when process start raises, preventing a later launch from misreading vLLM's generated OMP value as a user override.

**Potential risks**  
The cap is computed from available_cpu_count divided by local_engine_count, so unusual cgroup or affinity configurations could yield a very small or unexpected thread count; the min() with the current PyTorch count mitigates but does not eliminate this. The launch-only scope relies on fork/spawn semantics, and any future change to process start ordering or environment handling could break the intended inheritance. The test monkeypatches several internals (torch, engine_utils, numa_utils), so it may be brittle to refactors. Evaluation data in the description is preliminary and does not directly exercise the new automatic startup cap, so real-world benefit is inferred rather than fully measured.

**Key insights**  
The fix correctly scopes the thread budget to the subprocess launch window and restores parent state, which is essential because fork and spawn consume the setting differently and a leaked vLLM-generated OMP value would suppress future CPU budgeting. Explicit user OMP_NUM_THREADS remains authoritative, preserving user control. The accompanying test covers the key edge cases including start failure and non-UniProc executors, which is good coverage for a subtle environment-mutation change.

  - `tests/quantization/test_cpu_wna16.py`
  - `vllm/_custom_ops.py`
  - `vllm/model_executor/models/whisper.py`

### Summary

**What changed and why**  
This PR adds W4A16 quantized Whisper support on the CPU WNA16 kernel. It modifies cpu_gemm_wna16 to flatten >2-D activations to [M, K] and reshape outputs back (matching int4_scaled_mm_cpu), extends _create_fake_bias_for_k_proj to handle compressed-tensors .k_proj.weight_packed checkpoints and size the fake bias from config.d_model, and defers fake bias emission until after the input iterator is exhausted. Tests were added for 3-D kernel shapes and fake k_proj bias injection.

**Technical impact**  
The kernel wrapper now transparently supports 3-D inputs like the Whisper encoder's [B, T, D] tensors, and the weight loader correctly synthesizes k_proj biases for packed AWQ/Marlin checkpoints where weight.size(0) is not the true out_features. Deferring fake bias yields makes the helper robust to ordering and avoids emitting a fake bias when a real one exists, while AutoWeightsLoader resolves by name so fused qkv/kv shard loads remain order-independent. The change is scoped to CPU WNA16 and Whisper/GLM-ASR/Moss-Transcribe shared loading paths.

**Potential risks**  
The deferred-yield behavior changes iteration semantics for all callers of the shared helper, so any caller relying on immediate fake-bias emission could be affected, though the PR argues name-based resolution makes this safe. The new out_features parameter defaults to weight.size(0) when omitted, preserving old behavior but potentially masking incorrect sizing for packed weights if callers forget to pass it. The 3-D reshape assumes the last dimension is K and that leading dims can be flattened, which is valid for contiguous inputs but could misbehave for non-contiguous or unusual layouts.

**Key insights**  
The core bug was a shape mismatch: the C++ kernel reads K from input.size(1), so 3-D Whisper activations produced garbage output (100% WER) until flattened. The k_proj bias fix is equally critical, since without it the quantized model also produced 100% WER, and the LMMS-eval results show W4A16 now matches BF16 quality. The use of config.d_model instead of weight.size(0) is the key correctness detail for packed weights, and the tests directly cover both the shape and bias-injection behaviors.

### Base Information

- **Author:** [fjosw](https://github.com/fjosw)

- **Merged time:** 2026-09-29 22:34:27

- **[Changed Files](https://github.com/vllm-project/vllm/pull/51994/files) (3):**
  - `vllm/model_executor/models/diffusion_gemma.py`
  - `vllm/v1/attention/backends/flash_attn.py`
  - `vllm/v1/attention/ops/triton_unified_attention.py`

### Summary

**What changed and why**  
Fixes a silent correctness bug where DiffusionGemmaModelState._causal_buf was allocated as bool, causing FlashAttentionMetadataBuilder.build() to allocate a new int32 tensor via .to(torch.int32) on every call. Under FULL CUDA graph replay, the captured graph kept reading the orphaned capture-time tensor, freezing per-request causal/bidirectional attention flags for the graph's lifetime. The fix allocates _causal_buf as int32 and updates it in place with .copy_()/direct assignment, and replaces the silent cast in flash_attn.py with a hard ValueError to prevent recurrence.

**Technical impact**  
Changes the dtype contract for per-request causal tensors in the FlashAttention metadata builder from implicit-cast-tolerant to strictly int32, which is a breaking API change for any other caller passing non-int32 causal tensors. DiffusionGemma now takes the dtype-matched fast path, so no per-build allocation occurs and FULL graph replay reads live values. The triton_unified_attention comment update reflects the new int32 expectation for per_seq_causal_ptr.

**Potential risks**  
The new ValueError in flash_attn.py could break other models or backends that pass bool or other-dtype causal tensors, since it converts a previously working (if inefficient) path into a hard failure; those callers must be audited. The triton kernel change is comment-only, but if any caller still passes bool pointers, the kernel's semantics for per_seq_causal_ptr may now be inconsistent with the documented int32 contract. The PR author notes E2E output impact was inconclusive, so the actual quality improvement is unverified beyond the capture/replay regression test.

**Key insights**  
The root cause is a subtle interaction between out-of-place dtype casts and CUDA graph address binding: any allocation inside a captured region silently detaches the graph from the intended buffer. The fix correctly enforces dtype at construction and adds a fail-fast guard rather than silently casting, which is the right pattern for graph-captured code paths. The regression test directly exercises the capture/replay mechanism, which is more reliable than E2E comparison given DiffusionGemma's inherent denoising variance.

### Summary

**What changed and why**  
This PR adds MI355 (AMD CDNA 4) CI coverage for large-model GSM8K evaluations that previously only ran on NVIDIA H200. It introduces six new eval config YAMLs (DeepSeek R1 TP/DP, DeepSeek V3.2 TP/DP, Nemotron Super BF16/FP8) plus config-list files, wires them into .buildkite/test-amd.yaml and .buildkite/test_areas/lm_eval.yaml as four-GPU mirrors, and relaxes the ROCm skip in test_gsm8k_correctness.py so DeepSeek models run on CDNA 4+ while still skipping older ROCm pools.

**Technical impact**  
Extends CI to validate DeepSeek and Nemotron large-model inference on MI355 using AITER MLA/MoE for DeepSeek and Triton Mamba/MoE for Nemotron, with TP4/DP4 and EP4. The test logic change gates the previous unconditional ROCm skip on get_cdna_version() < 4, enabling execution on newer hardware without affecting older pools. NVIDIA configurations and evaluation parameters (checkpoints, precision, MTP draft counts, 1319 questions, 5 shots, tolerance) are preserved.

**Potential risks**  
The new jobs are marked optional: true, so failures may not block merges and could mask regressions. The CDNA version gate relies on get_cdna_version() correctly reporting hardware; misdetection could either skip valid runs or attempt unsupported ones. Four-GPU coverage does not replace eight-rank continuous coverage, and the added jobs increase MI355 CI load and runtime (65-minute timeouts each).

**Key insights**  
All twelve reported runs (six configs on four and eight MI355s) passed with accuracies 93.03-95.75%, comfortably above the 87%/85% floors after the eight-point tolerance. The change is primarily CI/config plus a targeted test-skip refinement, with no core vLLM runtime code modified. Reviewers should confirm the optional flag and mirror hardware lists match intended gating policy.
