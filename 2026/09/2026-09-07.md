## 2. [[Bugfix][ROCm] Mask paged attention V cache padding](https://github.com/vllm-project/vllm/pull/53856)


### Base Information

- **PR Number:** #53856
- **Author:** [aoshen02](https://github.com/aoshen02)
- **Merged By:** [tjtanaa](https://github.com/tjtanaa)
- **Merged time:** 2026-09-07 23:39:24
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/53856/files) (2):**
  - `csrc/rocm/attention.cu`
  - `tests/kernels/attention/test_attention.py`

### Summary

**What changed and why**  
This PR fixes a NaN-propagation bug in the ROCm paged-attention kernel (csrc/rocm/attention.cu) where vectorized V-cache loads could consume unwritten padding slots in the final block; if those slots contained NaN, the subsequent 0 * NaN accumulation corrupted the output. It adds mask_v_cache_padding, mask_16b_v_cache_boundary, and mask_8b_v_cache_boundary helpers and applies them at V-consumption points across gfx9 MFMA16, gfx9 MFMA4, gfx11, and gfx12 paths, while also lowering the MFMA16 launch bound from 5 to 4 waves to avoid scratch spilling. The test (tests/kernels/attention/test_attention.py) is updated to give each sequence a private final physical block, poison padding slots with NaN (or the architecture-correct FP8 NaN), and use distinct non-default K/V scales.

**Technical impact**  
The change alters kernel behavior by sanitizing V padding before matrix accumulation, which is necessary because score masking alone cannot prevent 0 * NaN from producing NaN. It restructures the MFMA16 softmax-V loop into compile-time-separated auto and FP8 paths, introduces tail-only masking in MFMA4 outside the full-warp hot path, and changes register/scratch resource usage (96 VGPR/16B scratch to 104 VGPR/0 scratch for the scratch-sensitive MFMA16 auto head-128 case). The test now directly exercises the kernel with poisoned padding and non-default scales, improving coverage of the actual failure mode.

**Potential risks**  
The PR reports a stable 2-3.5% direct-kernel performance cost concentrated in partial-tail handling, so it is not performance-neutral. Runtime validation was performed on gfx950 and gfx1100, but gfx942 and gfx1200 received compile validation only, leaving some architecture-specific risk. The masking helpers rely on caller guarantees about valid_bytes ranges and use reinterpret_cast on vector types, which could be fragile if assumptions change. The test changes also alter block-table allocation and scale values, which could affect other test expectations if not carefully reviewed.

**Key insights**  
The core insight is that V must be sanitized before accumulation because 0 * NaN is NaN, whereas K does not need the same treatment since invalid K values are removed before softmax. The fix is deliberately scoped to partial-tail vectors, preserving vectorized loads and the full-warp hot path, and the launch-bound reduction is a targeted response to scratch spilling from added boundary state. The test design is notably strong: it isolates padding per sequence, uses architecture-correct FP8 NaN representations, and retains distinct K/V scales to avoid masking the bug through default-scale behavior.

- **[Changed Files](https://github.com/vllm-project/vllm/pull/54756/files) (3):**
  - `tests/v1/attention/utils.py`
  - `tests/v1/simple_kv_offload/test_worker.py`
  - `vllm/v1/simple_kv_offload/worker.py`

### Summary

**What changed and why**  
Fixes a startup crash in SimpleCPUOffloadConnector.register_kv_caches on sparse-MLA (DSA) models like DeepSeek-V3.2 and GLM-5.2, where mixed page sizes within one cache group made the old single-block-size reinterpretation (raw[:size].view(-1, num_blocks, block_bytes)) raise a RuntimeError. Registration now derives each region from KVCacheTensor placement metadata (layers, layer_stride, block_stride, offset) instead of reinterpreting the whole allocation with one layer's block size, splitting layer-outermost tensors into one region per layer and keeping block-outermost tensors as a single region. It also fixes a latent misregistration in mixed groups where the division happened to succeed (e.g. Gemma-4 with --disable-hybrid-kv-cache-manager), where dedup keyed on backing storage caused only the first layer's block stride to be used for the whole allocation.

**Technical impact**  
Changes the region derivation logic in vllm/v1/simple_kv_offload/worker.py to be placement-metadata driven, with dedup now keyed on region address rather than backing storage, and adds a helper dense_kv_cache_tensor in tests plus new regression tests covering mixed-page DSA specs, odd block counts, and DCP invariance. Behavior for uniform-page and block-outermost allocations is preserved, while mixed-page layer-outermost allocations now register one correctly aligned region per layer-cache instead of crashing or misaligning. This is a correctness fix on a path introduced by #51718 that currently only exists in the v0.28.1rc0 prerelease.

**Potential risks**  
The new logic relies on KVCacheTensor placement metadata (layer_stride, block_stride, offset) being correct and consistently populated by upstream allocation code; any producer that omits or miscomputes these fields could cause incorrect region boundaries or assertion failures. The layer_outermost heuristic (layer_stride >= num_blocks * block_stride) and the groups_per_layer division assume specific layout semantics, so unusual layouts or future layout changes could break the assumption. Test coverage requires CUDA and a full smoke suite against the fixed build was not collected, and the real-model validation was limited to GLM-5.2-FP8 on 8x B300 plus an RTX 4090 repro.

**Key insights**  
The root cause is that a single layer's block size cannot describe an allocation whose layers have different page sizes, which is exactly what DSA models produce when MLA latent and indexer key caches land in one UniformTypeKVCacheSpecs group. Existing tests only built uniform-page allocations and no eval entry paired mixed page sizes with a layer-outermost layout, so the bug escaped coverage. The fix is well-targeted and the PR includes strong evidence: a minimal repro, a real-model startup and prefix-cache reuse check, and assertions that registered regions alias the model's own KV bytes via data_ptr and stride(0) equality.

### Summary

**What changed and why**  
This PR enables Programmatic Dependent Launch (PDL) for the fusedQKNormRopeKernel and fusedQKNormRopeKernelNTokenHeads CUDA kernels. It adds cudaGridDependencySynchronize() and cudaTriggerProgrammaticLaunchCompletion() calls guarded by __CUDA_ARCH__ >= 900, introduces a launchWithPDL helper that uses cudaLaunchKernelEx with the programmaticStreamSerializationAllowed attribute, and gates PDL on num_tokens <= 16 (kPDLEnableTokens). The goal is to overlap this kernel with the predecessor QKV projection for small batches where the kernel is launch-bound.

**Technical impact**  
Behavior changes for SM90+ (Hopper) GPUs: kernels can begin execution before the predecessor finishes, with explicit synchronization before global memory access. The launch path is refactored from <<<>>> syntax to cudaLaunchKernelEx, and a ROCm fallback preserves standard launch semantics. PDL is only enabled for num_tokens <= 16, so larger batches retain prior behavior.

**Potential risks**  
Correctness depends on cudaGridDependencySynchronize() being placed before any global memory read; the NTokenHeads variant relies on it preceding the first cp.async commit group, which is subtle. The hardcoded kPDLEnableTokens=16 threshold is empirical and may not generalize across hardware or workloads. cudaLaunchKernelEx error handling is not checked, and the ROCm path ignores enable_pdl. No test plan or results were provided in the PR description, so validation evidence is missing.

**Key insights**  
The change is well-scoped with architecture guards and a ROCm fallback, and the comments explain the PDL synchronization ordering rationale. However, the PR description is essentially empty (no purpose, test plan, or results), which is a notable gap for a kernel-level concurrency change. ### Summary

**What changed and why**  
The PR adds a conditional pytest.skip in tests/models/test_initialization.py that skips initialization tests for HYV4ForCausalLM and HYV4MTPModel when running on ROCm. This is needed because HY-V4's CUDA-only implementation raises NotImplementedError on ROCm, breaking AMD CI builds 12635 and 12653, and the skip is intended as a temporary guard until ROCm enablement lands in PRs #54405 and #54404.

**Technical impact**  
Behavior of the test suite changes on ROCm only: two model architectures are no longer exercised in test_can_initialize_large_subset on that platform, unblocking AMD CI. No production code, model implementation, or non-ROCm test behavior is affected, and the guard is explicitly marked for removal once ROCm support is implemented.

**Potential risks**  
The skip could mask genuine ROCm regressions or be forgotten, leaving HY-V4 initialization untested on ROCm indefinitely; it also reduces coverage on AMD CI for these architectures. There is a minor risk that the platform check or architecture name strings drift from the actual model registry entries, causing the skip to silently not apply or apply too broadly.

**Key insights**  
This is a narrowly scoped CI-unblocking change with a clear removal condition tied to follow-up PRs #54405 and #54404, and it is isolated to a single test file with only six added lines. Reviewers should verify the architecture names match the registry and consider tracking the temporary skip so it is removed alongside ROCm enablement.
