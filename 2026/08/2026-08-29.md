  - `vllm/entrypoints/openai/responses/protocol.py`
  - `vllm/entrypoints/pooling/base/protocol.py`
  - `vllm/entrypoints/scale_out/token_in_token_out/protocol.py`

### Summary

**What changed and why**  
This PR adds a maximum length constraint of 1024 characters to the cache_salt field across six API protocol models to mitigate a denial-of-service vulnerability where an attacker could send arbitrarily large salt strings, causing CPU exhaustion on the scheduler. It also adds a missing min_length=1 constraint on the pooling endpoint for consistency.

**Technical impact**  
The change introduces input validation that rejects cache_salt values longer than 1024 characters with an HTTP 422 error before they reach the scheduler. This prevents resource exhaustion attacks without affecting legitimate use cases, as typical salts are around 43 characters. The change is minimal and localized to Pydantic field definitions.

**Potential risks**  
There is a low risk that some legitimate users might have salts longer than 1024 characters, though this is unlikely given the documented expected length. The change does not alter any existing behavior for valid inputs, and no other code paths are affected. The addition of min_length=1 on the pooling endpoint could reject previously accepted empty strings, but that is likely a bug fix.

**Key insights**  
The vulnerability stems from unbounded input being processed by expensive operations (pickle.dumps and sha256) on a single-threaded scheduler. Adding a max_length is a simple and effective mitigation. The PR also highlights the importance of consistent validation across all API endpoints to prevent similar issues.

The microbenchmark was run on eager mode; under CUDA graphs the launch-overhead savings may be smaller, though kernel work savings remain.
