### Summary

**What changed and why**  
This PR fixes a bug where the default max_cudagraph_capture_size was computed in tokens but the widest uniform decode batch under speculative decoding is max_num_seqs * (1 + num_speculative_tokens) tokens, causing the largest decode steps to fall back to eager execution. The fix appends decode sizes based on a request-count grid scaled by the uniform decode query length, capped at 512 requests, and also handles dynamic speculative schedules by generating capture sizes per tier. It also updates related tests and documentation.

**Technical impact**  
The change modifies the default cudagraph capture size computation in VllmConfig._set_cudagraph_sizes to include uniform decode sizes when speculation is enabled, ensuring the widest uniform decode batch is captured. It also refactors the dynamic speculative schedule handling in cudagraph_utils to use a dense schedule lookup, and updates tests to cover the new behavior. The change affects both V1 and V2 runners as it is a VllmConfig default.

**Potential risks**  
The change could increase the number of captured cudagraph sizes, potentially increasing startup time and memory usage, though the request-count grid is capped to mitigate this. There is a risk of regression for non-speculative configurations, but tests assert bit-identical behavior for those. The dynamic schedule handling relies on a new utility function and could introduce edge cases if schedules are invalid, though the code falls back to a single-tier default on ValueError.

**Key insights**  
The fix correctly identifies that the historical formula min(max_num_seqs * 2, 512) was token-based and insufficient for speculative decoding where each request has multiple tokens. By scaling a request-count grid by the query length, it keeps the number of capture sizes comparable to the non-speculative case while ensuring coverage. The use of a dense schedule lookup for dynamic speculative decoding ensures consistency between the scheduler and the capture size generation.

### Summary

**What changed and why**  
This PR fixes a memory leak in in-process engine shutdown (VLLM_ENABLE_V1_MULTIPROCESSING=0) where the model and its KV cache were not released. Two module-level strong references kept the model alive: a dict cache in interfaces.py and a weakref.finalize argument in LLMEngine. There is a slight risk that some code path expects the strong cache behavior, but tests cover the main usage.

**Key insights**  
The PR identifies two independent holders that both must be fixed together; fixing only one does not free memory. It also clarifies that the issue is not a missed teardown call but a reference cycle preventing garbage collection. The measurements show that unpinning the model is more effective than severing KV cache aliases alone, and the PR explains the relationship to prior art and concurrent PRs.

**What changed and why**

**Technical impact**  
On ROCm, when the profiling measurement is negative (free memory grew), the KV cache is now sized from the increase in torch reserved memory instead of failing an assertion. **Potential risks**

The change modifies the profile result object in place, which could affect downstream logic if not carefully handled.

**Key insights**  
The root cause is that the profiling measurement is not isolated to the current process; other processes can release memory during the profiling window, causing a negative drop. The fix leverages process-local torch memory reservation as a more reliable signal on ROCm. The PR includes a comprehensive test plan with a helper process to reproduce the failure and unit tests for all branches, ensuring the fix is validated.
