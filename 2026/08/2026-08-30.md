## 1. [[Bugfix][Multimodal] Honor modality-scoped mm_processor_kwargs](https://github.com/vllm-project/vllm/pull/53808)


### Base Information

- **PR Number:** #53808
- **Author:** [Prudhvivuda](https://github.com/Prudhvivuda)
- **Merged By:** [DarkLight1337](https://github.com/DarkLight1337)

- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/53808/files) (5):**
  - `tests/models/multimodal/processing/test_qwen3_vl.py`
  - `tests/multimodal/test_processing.py`
  - `vllm/model_executor/models/qwen2_vl.py`
  - `vllm/model_executor/models/qwen3_vl.py`
  - `vllm/multimodal/processing/context.py`

### Summary

**What changed and why**  
This PR fixes a bug where modality-scoped mm_processor_kwargs (e.g., videos_kwargs) were ignored by vLLM's token-budget and dummy-input reads, causing under-reservation for video-heavy models like Qwen3-VL. It adds a helper function overlay_modality_mm_kwargs that overlays nested modality-specific kwargs (images_kwargs, videos_kwargs, audio_kwargs) onto the flat namespace only when the requested modality matches, and updates get_merged_mm_kwargs to accept an optional modality parameter. Call sites in Qwen2/3-VL that read size or other processor kwargs now pass the appropriate modality (image or video) to prevent cross-modality leakage.

**Technical impact**  
The change introduces a new public helper function and modifies the signature of get_merged_mm_kwargs to accept an optional modality keyword argument. Existing callers that do not pass modality retain previous behavior (no overlay). The Qwen2/3-VL models now correctly apply modality-specific overrides when computing token budgets and dummy inputs, aligning vLLM's internal reads with HuggingFace processor behavior. This is a behavior change for users who use nested mm_processor_kwargs, but it does not alter generation output.

**Potential risks**  
Potential risks include: (1) If a caller passes a modality that does not match the actual processor type (e.g., passing 'image' for a video processor), the overlay may not apply as intended, but the code attempts to infer modality from processor type in Qwen3-VL when not explicitly provided. (2) The overlay function only handles top-level nested keys; if nested dicts contain non-mapping values, they are ignored gracefully. (3) There is a slight risk of double-overlay if a caller already merges nested kwargs manually, but the function is designed to be idempotent. (4) The change touches core multimodal processing code, so any missed call site that should pass modality could lead to inconsistent token budgets, but tests cover the main paths.

**Key insights**  
The PR correctly identifies that HuggingFace processors accept nested modality-specific kwargs, and vLLM's internal reads must respect that scoping to avoid cross-modality contamination. The solution is clean and minimal, adding a helper that overlays only the relevant modality's nested dict. The tests are well-targeted, covering both scoped and flat overrides, and the regression test for Qwen3-VL verifies the exact issue scenario. The PR also notes that full GPU evals are not required since generation output is unchanged, which is a reasonable assessment.

  - `tests/renderers/test_token_offsets.py`
  - `vllm/renderers/params.py`

### Summary

**What changed and why**  
This PR fixes a bug where prompt_token_offsets were not truncated along with prompt_token_ids when truncation is applied in apply_post_tokenization. The fix factors out the truncation logic into a new _truncation_slice method that returns a slice, and applies that same slice to both the token ids and the offsets to keep them aligned. Tests were added to verify the offsets are truncated correctly for both left and right truncation sides.

**Technical impact**  
The change modifies the tokenization post-processing in vllm/renderers/params.py to ensure that prompt_token_offsets are truncated consistently with prompt_token_ids. This prevents a mismatch where the offsets array could be longer than the token ids array, which would cause incorrect character span mapping for consumers. The refactoring introduces a helper method that centralizes the truncation decision, making the logic reusable and reducing duplication.

**Potential risks**  
The change assumes that the length of prompt_token_offsets always matches the length of prompt_token_ids before truncation. If there is any case where they are already misaligned, applying the same slice could still result in incorrect offsets. Additionally, the code uses a cast and type ignore for the offsets assignment, which could hide type issues. The new tests cover the main scenarios but may not cover edge cases like when truncate_prompt_tokens is negative or when tokenizer is None.

**Key insights**  
The bug was reachable only when truncation_side is explicitly set, because that disables tokenizer-level truncation. The fix ensures that any parallel arrays (like offsets) are truncated with the same slice as the tokens, maintaining the documented invariant that their lengths are equal. The test plan includes both unit tests and an end-to-end test to verify the fix works over HTTP.

### Summary

**What changed and why**  
Fixed a bug in the pooling frontend where token padding was applied before truncation, causing left-side truncation to discard the actual prompt and leave only pad tokens. The fix reorders validation in TokenizeParams._validate_tokens to truncate before padding, matching Transformers semantics. Also updated the parallel token_type_ids handling in ScoringIOProcessor to apply truncation before padding to keep the arrays aligned, and added tests covering the regression and the padding-only case.

**Technical impact**  
Changes the order of token post-processing operations in the pooling path. For requests that set both padding and truncate_prompt_tokens with truncation_side='left', the resulting prompt_token_ids now contain real content followed by pad tokens instead of all pad tokens. This affects the actual token sequences sent to models, potentially changing embedding outputs for such requests. The change also ensures token_type_ids remain aligned with prompt_token_ids for cross-encoder scoring, fixing a potential misidentification of the query/document boundary.

**Potential risks**  
The reordering could affect any code that relies on the previous (incorrect) order, though no such dependencies are known. The change to token_type_ids handling in ScoringIOProcessor is more invasive and could introduce regressions if the logic diverges from TokenizeParams in edge cases (e.g., when truncate_prompt_tokens is 0 or None). The tests added cover the main scenarios but may not cover all combinations of padding, truncation, and side settings. There is also a known unaddressed issue: _token_padding uses tokenizer.pad_token_id unguarded, which could cause issues if a tokenizer has no pad token.

**Key insights**  
The bug was subtle because it only manifested with left-side truncation; right-side truncation coincidentally matched expected behavior. The fix aligns with the documented Transformers pipeline semantics. The follow-up commit highlights the importance of keeping parallel token arrays (like token_type_ids) in sync when applying post-tokenization transforms. The tests use a sentinel pad_token_id outside the range of real token ids to clearly detect all-pad sequences.
