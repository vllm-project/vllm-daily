The change enables the fused kernel path for deployments using VLLM_SSM_CONV_STATE_LAYOUT=DS, which is required for NIXL point-to-point state transfer in P/D-disaggregated serving, avoiding the slower multi-op Triton fallback. The kernel now dispatches to separate SD- and DS-specialized instantiations using compile-time stride template parameters to maintain performance.

**Technical impact**  
The kernel template now includes two integer strides (channel and tap) as non-type template parameters, allowing the address calculations to be compile-time constants for each layout. The ROCm kernel changes are not covered by the reported performance tests, so there is some uncertainty about ROCm-specific behavior. The removal of the is_conv_state_dim_first() check means the fused kernel will now be used for DS layout, which could expose previously untested code paths in production.

**Key insights**  
The PR demonstrates a careful approach to supporting multiple memory layouts without runtime overhead by using compile-time specialization. ### Summary

**What changed and why**  
This PR overlaps the multimodal renderer warmup with engine-core initialization by launching the warmup as a background task on the single-worker _mm_executor. Previously, warmup ran sequentially after engine-core init, adding ~30s to startup. Now, the MM warmup runs concurrently with model loading, and is joined by warmup(), reset_mm_cache(), or shutdown() to ensure no concurrent access to the mm_processor_cache or numba parallel regions.

**Technical impact**  
Adds new methods (warmup_mm, start_mm_warmup_in_background, _join_mm_warmup) and state (_mm_warmup_future, _mm_warmup_done) to BaseRenderer. The warmup() method now joins any background warmup and calls warmup_mm() which is idempotent. Engine initialization in async_llm.py and llm_engine.py now calls start_mm_warmup_in_background() after InputProcessor creation. reset_mm_cache() in both engines joins the background warmup before clearing caches. This reduces startup wall time by overlapping MM warmup with engine-core init, but introduces concurrency management complexity.

**Potential risks**  
The background warmup runs on the same single-worker executor as serving, so it may delay serving requests if they arrive during warmup, though this is intended to avoid numba concurrency issues. There is a risk of deadlock if _join_mm_warmup is called from within the executor worker, but the code comments indicate it is only called from main/event-loop threads. The _mm_warmup_done flag must be correctly maintained across reset_mm_cache and warmup to avoid double-running or skipping warmup. The change relies on the executor being single-worker; if that changes, concurrency issues could reappear. The tests cover many scenarios but may not cover all edge cases like exceptions in the background task.

**Key insights**  
The PR cleverly reuses the existing single-worker _mm_executor to serialize warmup with serving requests, preventing numba's 'Concurrent access has been detected' abort. The idempotent warmup_mm() with a persistent _mm_warmup_done flag ensures warmup() does not re-run MM warmup even after reset_mm_cache joins the background task. The placement after InputProcessor is critical to avoid concurrent numba execution during synchronous MM processing. The test suite is comprehensive, covering fault isolation, idempotency, and join behavior.
