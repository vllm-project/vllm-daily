## 3. [Count store offers, not lookups, for CPU offload store_threshold](https://github.com/vllm-project/vllm/pull/52227)


### Base Information

- **PR Number:** #52227
- **Author:** [okorzh-amd](https://github.com/okorzh-amd)

- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/52227/files) (3):**
  - `tests/v1/kv_offload/cpu/test_manager.py`
  - `vllm/v1/kv_offload/cpu/manager.py`
  - `vllm/v1/kv_offload/cpu/spec.py`

### Summary

**What changed and why**  
The PR changes the counting mechanism for CPU offload store admission from counting lookups to counting store offers. Previously, the counter was incremented in lookup(), which was ineffective because callers often break on the first miss or return early when the GPU cache covers the request, preventing repeated lookups for cold prefixes and never counting resident repeated prompts. The fix moves the counting to prepare_store(), which receives the entire offerable key set, so a block becomes eligible after a number of repetitions equal to store_threshold, independent of prefix length and unaffected by early returns.

**Technical impact**  
The change modifies the behavior of the CPUOffloadingManager's admission control: blocks are now admitted based on how many times they are offered for storage rather than how many times they are looked up. This makes the store_threshold feature actually warm up the CPU offload tier as intended, reducing the number of repetitions needed to fully populate a prefix from O(2N+1) to O(N) (where N is the number of chunks). The code refactors the counting logic into a helper method _record_access and updates the test to reflect the new semantics.

**Potential risks**  
The change may alter the admission timing for blocks that are looked up but never offered for storage (e.g., blocks that are already in the GPU cache and not part of a store offer). Such blocks will no longer be counted, which could delay or prevent their offloading if they are later evicted from GPU cache. However, this is likely acceptable because the purpose is to offload blocks that are actually being stored. The test changes are comprehensive but limited to unit tests; integration with real workloads may reveal edge cases where store offers are not made for blocks that should be offloaded.

**Key insights**  
The original design incorrectly assumed that lookup frequency correlates with store eligibility, but the actual access pattern in the scheduler breaks that assumption. Counting store offers aligns the admission metric with the actual storage operation, making the feature effective. The refactoring into _record_access improves code clarity and centralizes the LRU eviction logic.

### Summary

**What changed and why**  
Fixed a silent performance bug in fused_q_kv_rmsnorm where outputs were allocated with torch.empty_like, which preserves the strides of size-1 dims. When inputs are column slices of a fused buffer and num_tokens==1, the output tensors had non-packed row strides, causing downstream low-latency GEMM dispatchers to reject them and fall back to slower cuBLAS kernels on every decode step. The fix allocates packed row-major outputs explicitly using torch.empty, ensuring the intended fast GEMM path is used.

**Technical impact**  
This change improves decode performance for models like Kimi-K3 that use fused_q_kv_rmsnorm with column-sliced inputs. The A/B test shows a 1.9% reduction in decode step wall time (9.251 ms to 9.075 ms) and a reduction of ~148.5 µs per step in GEMM-group exclusive time. The fix also adds a regression test to ensure outputs are packed for both num_tokens=1 and num_tokens=16.

**Potential risks**  
The change is low risk because packed row-major outputs are strictly better for downstream consumers and the numerical correctness is preserved. However, there is a slight possibility that some downstream code relied on the non-packed strides (unlikely but not explicitly checked). The new test covers the main scenarios, but edge cases like num_tokens=0 or unusual input strides are not explicitly tested, though the code handles num_tokens==0 early return.

**Key insights**  
The bug was subtle because it only manifested at num_tokens==1 (decode) and was machine-dependent due to cuBLAS heuristics, making it easy to miss in benchmarks. The root cause is PyTorch's behavior of preserving strides for size-1 dimensions in empty_like, which is a common pitfall when slicing tensors. The fix is simple and general: explicitly allocate with torch.empty to guarantee packed layout.
