  - `vllm/v1/worker/gpu/model_states/mm_pruning.py`
  - `vllm/v1/worker/gpu/pp_utils.py`

### Summary

**What changed and why**  
Fixes a correctness bug where, with EVS video pruning and pipeline parallelism > 1, only the first PP stage recomputes M-RoPE positions from pruned encoder outputs while later stages use stale unpruned positions, producing wrong outputs (empty answers). The PR adds a ModelState.positions_depend_on_encoder flag, relays the first stage's positions to later stages via IntermediateTensors (send_positions/receive_positions), adds a persistent pp_positions buffer for transport compatibility, and adds a 2-GPU regression test plus a CI dependency entry.

**Technical impact**  
Touches the GPU model runner PP path, model state interface, and mm_pruning helpers. Positions are sent as a token-major [num_tokens, 3] int64 tensor only when PP > 1 and the model state reports encoder-dependent positions, and are copied into the persistent positions buffer before forward so CUDA graphs see them. No host sync is added; overhead is 3 x num_tokens int64 per step only under EVS+PP. Behavior is claimed bitwise identical for PP=1 eager.

**Potential risks**  
Only Qwen2.5-VL was validated; other M-RoPE pruning models (Qwen3-VL family, Cohere Compass) and PP > 2 are untested, and the test was not run on ROCm. The relay depends on the new flag being set correctly on every stage (evaluated from config since later stages lack encoder cache), so a mis-set flag would silently reintroduce the bug. The positions buffer must match transport expectations in keys, dtypes, and per-token shapes, and the copy assumes only real tokens are copied to avoid padding dependence.

**Key insights**  
The root cause is a stage asymmetry: encoder-dependent positions are computed only where the encoder runs, so any encoder-derived state must be explicitly relayed across PP stages. Reusing the existing IntermediateTensors relay mechanism and gating on a model-state capability flag keeps the change scoped and avoids overhead when pruning or PP is off. The regression test comparing PP=2 vs PP=1 prompt logprobs and decode tokens is a meaningful guard, though broader model and PP-depth coverage would strengthen confidence.

The test hardcodes 196 tokens per frame (14x14 pooling), which is checkpoint-specific and could become brittle if the processor changes.

**Key insights**  
The root cause is a shape-contract mismatch: converting a list to a tuple preserved 3D elements instead of the required 2D per-video embeddings. The fix is minimal and localized, with a clear before/after GPU reproduction (baseline assertion failure vs. passing run). The regression is well-targeted but relies on a single model and environment, so broader coverage would strengthen confidence.

## 4. [[Bugfix][Distributed] Order packed NCCL loads after the caller stream](https://github.com/vllm-project/vllm/pull/65487)


### Base Information

- **PR Number:** #65487
- **Author:** [hao-aaron](https://github.com/hao-aaron)
- **Merged By:** [aoshen02](https://github.com/aoshen02)
- **Merged time:** 2026-11-15 23:05:03
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/65487/files) (2):**
  - `tests/distributed/test_packed_tensor.py`
  - `vllm/distributed/weight_transfer/packed_tensor.py`

### Summary

**What changed and why**  
Fixes a stream-ordering race in packed_nccl_broadcast_consumer where per-slot streams never waited on the caller's stream, allowing caller-queued work (e.g. the zero-fill of padded MoE params from begin_direct_reload) to run after the loads and overwrite them with zeros. The fix adds a one-time stream.wait_stream(caller_stream) for each slot stream before the first receive, with no host sync. The test file is refactored to a shared roundtrip helper that reproduces the direct-reload pattern (caller zero-fill behind a GPU sleep) and asserts the fill was still pending at first load.

**Technical impact**  
Adds a single stream dependency per slot stream at consumer setup, ensuring all work queued on the caller stream before the call is ordered ahead of the broadcast/load on slot streams. This is a low-overhead, host-sync-free change that aligns the packed path with the unpacked NCCL and IPC paths, which already load on the caller's stream. Test refactor consolidates four duplicated produce/consume/verify blocks into one helper and strengthens validation with byte-for-byte checks and shape/dtype assertions.

**Potential risks**  
The wait_stream is only issued once before the first receive; if the caller queues conflicting work on its stream after the consumer starts, ordering is not guaranteed, though that matches the documented contract. The test relies on a ~1s GPU sleep and an assertion that the fill was still pending, which could become flaky on very slow hosts or unusual hardware, though the assertion is designed to fail loudly rather than silently pass. The PR description notes a separate misaligned packed-entry copy fix was intentionally dropped, so that issue remains unaddressed here.

**Key insights**  
The root cause is a missing cross-stream dependency rather than a logic error, and the fix is minimal and targeted. The test design is notable: it verifies the race window was actually open (fill pending at first load) rather than just checking final correctness, which prevents the test from passing vacuously. Validation evidence (7/7 cases failing without fix, passing with fix, plus end-to-end gpt-oss-20b bit-identical results) is strong.

  - `vllm/model_executor/layers/mamba/ops/ssd_chunk_scan.py`
  - `vllm/model_executor/layers/mamba/ops/ssd_chunk_state.py`
  - `vllm/triton_utils/__init__.py`
  - `vllm/triton_utils/tensor_descriptor.py`

### Summary

**What changed and why**  
Adds an opt-in tensor-descriptor (TD) code path to the Mamba2 SSD prefill kernels _chunk_scan_fwd_kernel and _chunk_state_fwd_kernel, gated by a USE_TD constexpr that is auto-enabled on Intel XPU and opt-in elsewhere via VLLM_TRITON_USE_TD. A new tensor_descriptor_compatible guard falls back to the pointer path when operands cannot back a descriptor, and USE_TD is added to both autotune keys. Tests and an Intel CI step are added to validate the TD path against the pointer path and the torch reference.

**Technical impact**  
On XPU this replaces masked pointer loads/stores with 2D block IO descriptors and skips the prev_states dot for sequences without initial state, yielding large kernel-level speedups (up to ~2x scan, ~1.8x state) and measurable end-to-end prefill/TTFT gains. With TD off (CUDA default) the generated TTGIR/PTX and autotune config lists are reported unchanged, so non-XPU behavior is preserved. The guard adds a per-launch compatibility check and a per-launch set_triton_allocator call on the TD path.

**Potential risks**  
The TD path is only validated by unit tests on CUDA sm90/sm100 and is untested on ROCm, with no accuracy or end-to-end measurements there. Correctness depends on the compatibility guard correctly rejecting operands (alignment, stride, width, pitch) that descriptors cannot cover; a missed case could produce wrong results or aborts (e.g. head_dim=8 under TRITON_INTEL_2DBLOCK_ASSERT). Results are reported to depend on a separate PR (#60800) for stable autotune picks, and the change overlaps another PR (#58592) touching the same CI/test files. The per-launch allocator setup and descriptor creation add overhead that is a net loss at very short sequences (128 tokens on B70).

**Key insights**  
The change is well-scoped behind a constexpr with a pointer-path fallback and explicit guard, and the authors provide strong evidence that the non-TD path is byte-identical on NVIDIA hardware. The main scan win comes largely from skipping the prev_states dot rather than TD alone, and state gains are shape-dependent (slower on some small models). Reviewers should focus on the correctness of tensor_descriptor_compatible edge cases, the per-launch allocator/guard overhead, and the lack of ROCm validation.

### Summary

**What changed and why**  
Adds daemon-to-daemon weight seeding so a second replica's daemons can fill their shards from an already-loaded replica instead of re-reading the checkpoint. Introduces a new internal peer_cache load format and PeerModelLoader, a new --weight-cache-seed CLI flag, a weights Seedable (WeightShardSeed) served over the existing D2D transport, and two movers (peer_ipc via CUDA IPC for same-host, Mooncake RDMA for cross-host). It also refactors shared model-build/export logic out of ipc_loader and daemon into reusable helpers, renames seed.py to transport.py, and adds a ROCm device-UUID fix plus a has_mooncake helper.

**Technical impact**  
Touches core model-loading paths: get_model loader registry, LoadConfig, model_loader/utils.py (new build_model_from_processed_weights and _register_processed_tensors), ipc_loader (refactored to share the build pipeline), and the weight cache daemon (new device_index, state lock, lease/acknowledgement protocol for safe release). The control plane is split into a local owner-verified Unix socket (pickle, required for CUDA IPC) and a token-authenticated JSON-only remote TCP listener that refuses node-local movers. Fingerprints (WeightCacheKey) are validated before any bytes move, and same-host mirror GPU placement is inferred from source GPU UUIDs. This is a large behavioral change with new cross-host networking, memory-registration, and lifecycle semantics.

**Potential risks**  
Cross-host RDMA path depends on optional Mooncake and an unencrypted token-authenticated channel, so misconfiguration or token leakage is a security/operability concern. The lease/acknowledgement and release logic is concurrency-sensitive (state lock, retained copies on failed Mooncake transfers) and could deadlock or leak GPU/NIC memory if a mirror dies mid-copy. Same-host mirroring requires all GPUs visible and correct UUID-based placement; CUDA_VISIBLE_DEVICES remapping is rejected. The refactor of ipc_loader and shared build helpers risks regressions in the existing ipc_cache path, and the new peer_cache format is not yet supported for standalone reload. DSv4.1-class models cannot reach READY due to a separate quant-kernel gap, and multi-source fan-in, throttling, and pipelined copy are explicitly deferred.

**Key insights**  
The design reuses the ordinary daemon lifecycle (world group, config finalization, warmup, autotune adoption) rather than a special mirror state, which keeps chained seeding and future warmup kinds working without mirror-specific code. The data plane moves whole storages described by a manifest so shared allocations (e.g. MLA W_UV/W_UK_T) are copied once and keep aliasing and footprint. Validation is credible: Qwen3-30B shows a 2.3x startup improvement with byte-identical outputs, and DSv4.1 demonstrates ~54 GiB/s aggregate RDMA throughput, though the DSv4.1 mirror cannot yet reach READY. The PR is well-scoped but large (25 files, +2123/-391) and would benefit from splitting the data plane from the mirror lifecycle for reviewability.

### Summary

**What changed and why**

To satisfy PP transport's expectation of full-token tensors replicated across TP ranks, each non-last stage now concatenates hidden_states and residual, all-gathers once, trims padding, and splits them back; non-first stages also shard the received residual instead of asserting it is None.

**Technical impact**

**Key insights**  
The PR is well-validated with GSM8K, prompt-logprob, throughput, and MTP acceptance comparisons against PP1 and PP2 main, showing accuracy within noise and modest throughput trade-offs. The core correctness argument is that PP transport requires full-token, TP-replicated stage outputs, which the added all-gather restores. ### Summary

**What changed and why**  
The PR rewrites vllm/models/muse_spark/__init__.py to resolve the three Muse Spark model classes lazily via a module-level __getattr__ instead of eagerly importing the platform-specific (nvidia/amd) model modules at package import. The motivation is that the eager NVIDIA imports pull in FlashInfer, whose jit/env.py calls torch.cuda.get_device_capability() at import, initializing CUDA in any process that merely imports a muse_spark submodule and causing 'Cannot re-initialize CUDA in forked subprocess' failures in distributed tests.

**Technical impact**  
Importing vllm.models.muse_spark or its submodules (e.g. common.vision) no longer touches CUDA; model classes are imported on first attribute access, with platform selection (amd on ROCm, nvidia otherwise) evaluated at access time rather than import time. The registry and 'from vllm.models.muse_spark import X' still resolve the same classes, and TYPE_CHECKING imports preserve static typing. This mirrors the existing vllm/models/inkling pattern and is a small, contained change to a single file.

**Potential risks**  
Lazy resolution means platform detection and module import errors surface at first attribute access rather than at package import, which could shift where failures appear. Any code relying on dir()/hasattr introspection or on the classes being present as real module attributes at import time may behave differently, though __all__ and __getattr__ cover normal access. Loading an actual model still imports FlashInfer and initializes CUDA, so the underlying constraint remains; no automated regression test was added, relying instead on manual GPU-process validation.

**Key insights**  
The root cause is a transitive import chain (muse_spark __init__ -> nvidia model -> FlashInfer -> CUDA init) that made a test-collection import poison forked subprocesses, and the intermittency came from the runtime-shard plugin only importing files assigned to its shard. Making the package __init__ lazy is a broader and cleaner fix than making each FlashInfer import lazy, and the PR's before/after CUDA-trace evidence is convincing. The main residual gap is the absence of a CI test guarding against future eager imports reintroducing CUDA initialization.
