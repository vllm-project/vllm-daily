  - `vllm/distributed/pp_transport/copy_engine.py`
  - `vllm/distributed/pp_transport/rocm_sdma.py`
  - `vllm/envs.py`

### Summary

**What changed and why**  
Adds an opt-in ROCm SDMA copy-engine path for pipeline-parallel stage hand-off (VLLM_PP_TRANSPORT=copy_engine on gfx950), refactoring the existing CUDA copy-engine transport into a pluggable _CudaCopyEngines backend plus a new rocm_sdma.SdmaCopyEngines backend that drives ROCr hsa_amd_memory_async_copy_on_engine over ctypes. The motivation is that HIP/NCCL peer copies run as blit kernels on the sender's CUs, slowing adjacent compute by ~5x, while explicit SDMA engines avoid CU contention. Also updates env docs, the auto-mode behavior on ROCm (stays NCCL), and extends the distributed transport test to ROCm.

**Technical impact**  
Touches the PP transport layer used by every PP deployment, but the new path is gated behind VLLM_PP_TRANSPORT=copy_engine and further restricted to gfx950, TP1, PP2, eager mode, and single-node xGMI connectivity, raising at init otherwise. The refactor of copy_engine.py into a backend abstraction changes shared code paths (flag ops, peer copy, buffer layout with a new _ENGINE_OFFSET region), so CUDA copy-engine behavior must remain identical. The ROCm backend relies on ctypes bindings to libhsa-runtime64 and libamdhip64, hardcoded engine masks (2 and 4), and /dev/shm counters, which is fragile to runtime/library changes.

**Potential risks**  
Heavy reliance on undocumented/version-specific ROCr and HIP behavior (engine selection, signal semantics, uncached shared buffers) that could break on driver or HIP updates; hardcoded engine IDs and gfx950-only support limit portability. The ctypes layer bypasses normal error handling and could crash or silently misbehave if HSA calls fail. The refactor of the CUDA path introduces regression risk for existing copy-engine users. Eager-only and PP2-only constraints are enforced but the failure modes (e.g., CUDA graph replay, middle-stage relaying) are subtle. Test coverage is limited to 2 GPUs and specific hardware, so CI coverage on ROCm gfx950 may be sparse.

**Key insights**  
The PR is well-scoped and opt-in with clear guardrails and measured evidence (+3.6% throughput, byte-exact copies, unchanged gsm8k). The main review focus should be on the CUDA-path refactor preserving behavior, the robustness of the ctypes/HSA bindings and hardcoded engine masks, and ensuring the init-time validation reliably rejects unsupported configurations before any collective. The /dev/shm counter synchronization and gloo isend reaping are non-trivial concurrency logic worth careful scrutiny.

  - `tests/v1/kv_offload/tiering/test_fs_tier.py`
  - `tests/v1/kv_offload/tiering/test_tiering_offloading.py`
  - `vllm/v1/kv_offload/tiering/fs/io.py`
  - `vllm/v1/kv_offload/tiering/fs/manager.py`

### Summary

**What changed and why**  
The fs tier store path now reports only blocks it actually wrote in transfer_bytes, instead of the full batch. Python _store_block returns a bool (False when the target already exists), fs_io_C.batch_store_block returns the number written via a new kAlreadyPresent sentinel, and FileSystemTierManager.submit_store wraps the store in a closure that records the written count into _job_block_counts. This prevents skipped, hash-deduplicated writes from feeding large instant samples into the backpressure EMA.

**Technical impact**  
Changes the return type of batch_store_block in both the C extension and pure Python paths (None -> int), and changes _store_block's return contract. get_finished_jobs now distinguishes a missing count (None) from a zero count, so a store that wrote nothing reports transfer_bytes=0 rather than None. BackpressureDetector.update already ignores num_bytes <= 0, so zero-write jobs no longer contribute latency samples. On-disk bytes, job success, lookup verdicts, and KV events are unchanged; Prometheus WRITE_BYTES/WRITE_TIME counters are intentionally left alone.

**Potential risks**  
The C extension and Python paths must stay in sync on the return contract; any other caller of batch_store_block or _store_block expecting None would break, though the PR indicates these are internal. The EEXIST rename race is counted as written (bytes were written before the rename lost), which is a deliberate accounting choice that could be debated. The closure captures paths/offsets/view, and the count is written by the pool worker relying on GIL ordering similar to _load_progress; correctness depends on that ordering assumption holding. Test coverage is strong (both store paths, cascade integration, detector behavior), but the change touches a C extension, so build/ABI consistency across environments is a residual risk.

**Key insights**  
The root cause is a warm-filesystem cascade pattern: CPU tier eviction causes recompute and re-store to fs, where hash-named files already exist, so writes are skipped but still reported as full-batch instant transfers, dragging the EMA down and keeping the fast path engaged when the filesystem may be slow. The fix correctly attributes counts to the writers themselves rather than the job's key list, and the None-vs-zero distinction in get_finished_jobs is the subtle but important detail that makes zero-write jobs invisible to the detector. Tests pinning both the detector behavior and the race conditions (post-filter publish, EEXIST) are well targeted.

CI jobs now export PYTHONPATH=/opt/quantization-deps and list the lock in source_file_dependencies, and the tethering allowlist entries for the affected tests are removed.

**Potential risks**  
The ROCm image build and the rendered test-amd.yaml jobs have not been validated yet (pending /ci run and a scoped AMD build), so the new stage, the COPY --link, and the PYTHONPATH wiring are unproven in CI. The PYTHONPATH export approach is a temporary workaround that will be simplified after ci-infra#825, and the ROCm lock is not in the run-all list, so a torchao bump relies on per-step source dependencies to trigger jobs. MI300 also moves from torchao 0.17.0 to 0.18.0, which could surface version-specific test behavior.

**Key insights**  
The design cleanly isolates torchao/conch from other jobs by keeping them off site-packages and gating visibility behind PYTHONPATH, which addresses the fork/import-init root cause rather than skipping tests. Placing the stage below the per-commit marker and excluding the lock from the cache key is a sensible cache-efficiency tradeoff. The main outstanding gap is end-to-end CI validation of the ROCm image and AMD pipeline jobs.

  - `vllm/models/minimax_m3/amd/ops/nvfp4_sparse_decode/kernel.py`

### Summary

**What changed and why**  
This PR rebalances MiniMax-M3 decode attention work across XCDs on ROCm (gfx942/950) and removes a redundant page read in the context-parallel indexer. The sparse-decode host logic replaces the old _xcd_splits table with a new _xcd_plan that returns (splits, row placement, waves_per_eu), adds a PLACE_BAL row-placement mode in the kernel, and introduces a two-workgroups-per-CU occupancy hint for 33-48 requests. The CP push indexer kernel is generalized to accept query_len 4 or 8 and a configurable run length ch, so 8-row (DSpark 7) requests are scored directly with each index-K page read and dequantized once instead of twice. Tests are updated and extended to cover the new plans, placements, and 8-row push path.

**Technical impact**  
Behavior changes in kernel selection and row-to-workgroup mapping for the XCD-aware sparse decode grid, plus a new compiled kernel variant for the CP push scorer. The PLACE_BAL mapping is a bijection onto the padded grid and is asserted bitwise-equal to PLACE_REQ and the plain grid at the same split count, so numerics are preserved. Reported speedups are substantial (e.g. 17-24 req 29.6-31.1 to 22.1-22.8 us/layer, indexer push 24x250K 45.9 to 29.4 us) with eval parity on GSM8K and GPQA. The metadata field cp_requests is removed, simplifying the forward path.

**Potential risks**  
The plan is hand-tuned for specific shapes (top-k 16, DSpark 7 8-row requests, one KV head per rank, 8-XCD devices) and falls back to the cost model otherwise, so regressions on untuned configs are possible but bounded. The waves_per_eu hint is not a kernel argument and only keys the compile cache, which is subtle and could cause confusion or stale-cache issues if the launcher mapping is wrong. The new PLACE_BAL index math and the generalized CP push kernel (ch in 4/8/16, ql in 4/8) add complexity and rely on the added bitwise tests for correctness; coverage is limited to the tested shapes and one-GPU CP emulation. The 8-row direct path changes the CP scorer's inputs, so any downstream consumer expecting the split 4-row form must be verified.

**Key insights**  
The core win is recognizing that a second round of workgroups on an XCD costs a full latency chain (~7 us) that outweighs the few blocks saved, so the plan maximizes splits subject to one round per XCD, and uses a 2-waves-per-CU build when rows exceed CUs. The indexer improvement comes from scoring both 4-row column groups of an 8-row request against each dequantized key tile, halving page reads. The PR is well-validated with bitwise-equivalence tests across placements and split counts plus benchmark and eval numbers, though the tuning is shape-specific and the cache-keying of waves_per_eu deserves scrutiny.
