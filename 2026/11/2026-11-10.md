## 1. [[torch.compile] Only flag `_buffers.update` in the cudagraph buffer assignment check](https://github.com/vllm-project/vllm/pull/65446)


### Base Information

- **PR Number:** #65446
- **Author:** [hmellor](https://github.com/hmellor)
- **Merged By:** [hmellor](https://github.com/hmellor)
- **Merged time:** 2026-11-10 23:41:18
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/65446/files) (2):**
  - `tests/compile/test_wrapper.py`
  - `vllm/compilation/wrapper.py`

### Summary

**What changed and why**  
The cudagraph buffer-assignment guard in vllm/compilation/wrapper.py previously rejected any residual bytecode containing an 'update' name, which falsely flagged unrelated dict updates such as Transformers' kwargs.update({'is_causal': ...}). The check now inspects disassembled instructions and only rejects when '_buffers' is immediately followed by 'update', matching Dynamo's emission for buffers assigned during forward. A parametrized test in tests/compile/test_wrapper.py covers both the rejected buffer-assignment case and the allowed kwargs-update case.

**Technical impact**  
Narrows a compile-time safety check to the specific bytecode pattern Dynamo emits for in-forward buffer mutation, restoring cudagraph compilation for Transformers backend models that use kwargs.update (e.g. is_causal handling in Ettin/ModernBERT decoders). The change is localized to the bytecode hook and adds a dis-based scan of new_code, which is cheap and only runs during tracing. Buffer assignment during forward remains rejected, preserving the original correctness guarantee.

**Potential risks**  
The pairwise instruction scan assumes the '_buffers' load is immediately followed by the 'update' attribute load; if Dynamo emits a different instruction sequence (e.g. via LOAD_ATTR variants or intervening instructions), the guard could miss a real buffer mutation or still false-positive. The test relies on monkeypatching depyf.decompile and VLLM_USE_BYTECODE_HOOK, so it may be sensitive to environment or Dynamo version changes. Coverage is CPU-focused, though the PR reports B200 validation.

**Key insights**  
The fix correctly trades a coarse name-based heuristic for a precise bytecode-pattern match, which is the right approach for a guard that must distinguish buffer mutation from benign dict updates. The added test meaningfully exercises both branches of the new logic. Reviewers should confirm the instruction-pair assumption holds across supported Python/Dynamo versions and that the guard still catches all real buffer-assignment patterns.

  - `tests/kernels/test_engram.py`
  - `vllm/models/deepseek_v41/common/engram.py`

### Summary

**What changed and why**  
Adds support for DeepSeek-V4.1 checkpoints whose Engram embedding tables are stored as packed MXFP4 (two E2M1 values per byte with UE8M0 block-32 scales) instead of FP8. EngramLayout now reads quantization_config metadata to select and validate the format, the Triton lookup kernel decodes packed nibbles, and all allocation/storage paths (GPU, peer HBM, pinned host, huge pages, DP-shared cuMem/shm) use the packed row width. Tests and docs are extended, and the DSpark TP4 GSM8K CI revision pin is removed.

**Technical impact**  
Halves Engram table storage (264 to 136 bytes per 256-element row, ~48.5% reduction), enabling the published MXFP4 checkpoint to load and run. The lookup kernel gains a PACKED_FP4 constexpr branch with bit-exact E2M1 decode, peer-buffer scale offsets and shared-memory sizing switch to row_bytes, and unsupported metadata (bad block size, scale dtype, layer list, or packed FP8 output) fails fast before allocation or kernel launch. DP exchange falls back to BF16 for packed tables.

**Potential risks**  
Packed lookup measured 42.3% slower in an isolated cold-L2 microbenchmark, so per-lookup latency increases even though memory drops. Mixed per-layer formats and packed-table FP8 batched exchange are unsupported and must be rejected correctly. Validation was on NVIDIA GB300 only; ROCm eligibility is enabled but unmeasured. Accuracy deltas are single-run (GSM8K +0.83pp, MMLU -0.18pp) with output-limit caveats, and the CI unpin now depends on the published checkpoint revision remaining stable.

**Key insights**  
The change is well-scoped: format resolution is centralized in EngramLayout, the kernel reuses existing scale handling, and tests parametrize both formats across storage modes with targeted reversion checks. The main review focus should be the E2M1 decode correctness, the packed-output guard, and consistent use of row_bytes in every allocation and peer-offset path. The performance tradeoff (memory savings vs. slower lookups) is documented and should be weighed against the deployment's memory constraints.

Adds a new CuTe DSL kernel (mhc_boundary.py, ~1200 lines) implementing the DeepSeek-V4.1 shifted mHC boundary for decode batches up to 336 tokens, adapted from TensorRT-LLM. It uses 16-CTA clusters, distributed shared memory for partial mixes/sums of squares, L2-streamed mixer weight fragments with 4-step prefetch, and a TF32-exact BF16 hi/lo weight split. The decoder layer registers non-persistent buffers for the laid-out mixer weights, fills them in process_weights_after_loading, and passes them through mhc_shifted_post_pre, which dispatches to the new kernel for small batches and falls back to Mega mHC otherwise. Tests are refactored to share input generation and a new correctness test is added.

**Technical impact**  
Replaces ~79 sm100_mega_mhc_impl launches per decode step with the new kernel for batches up to 336 tokens, cutting boundary op time 1.13-2.04x and step time 1.5-5.8% at 48-336 tokens per rank. Results are deterministic and the updated residual is claimed bitwise identical to Mega mHC; behavior above 336 tokens is unchanged. The change touches model weight-loading paths, CUDA-graph capture (in-place buffer fill), and the mHC dispatch logic, so it affects core decode behavior for the target model.

**Potential risks**  
The kernel relies on low-level inline PTX (ldmatrix, mma, st.async, mbarrier, bulk copies) and hand-tuned tile configs, which are fragile across architectures and driver/toolchain versions. Correctness depends on the TF32 hi/lo weight split being exact and on fixed reduction order; an adversarial case shows comb error up to 3.3e-3 relative at 10 Sinkhorn iterations (passes at 20). The in-place buffer fill assumes every load/reload path calls process_weights_after_loading and that captured graphs observe updates; a missed path or shape mismatch could silently use stale or uninitialized weights. The dispatch also assumes each tile is compiled before graph capture via the eager run, which could break if that assumption changes. Fallback and None-weight paths add branching complexity.

**Key insights**  
This is a well-validated performance PR with extensive benchmarking (every token count 1-336, bitwise residual equality, memcheck, graph-vs-eager, GSM8K) and a clean fallback to Mega mHC above 336 tokens. The main review focus should be on the weight-buffer lifecycle (registration, in-place fill, reload correctness), the correctness of the TF32 hi/lo split and reduction ordering, and the robustness of the inline-PTX kernel and tile-config table across environments. The adversarial Sinkhorn case is a known limitation worth documenting.
