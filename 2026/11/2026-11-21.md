## 1. [[Bugfix][KV Offload] Store the chunks that fit when a request exceeds the CPU tier](https://github.com/vllm-project/vllm/pull/66719)


### Base Information

- **PR Number:** #66719
- **Author:** [lnvitesace](https://github.com/lnvitesace)

  - `vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py`
  - `vllm/distributed/kv_transfer/kv_connector/v1/offloading/store_triggers/base.py`
  - `vllm/distributed/kv_transfer/kv_connector/v1/offloading/store_triggers/candidates.py`
  - `vllm/distributed/kv_transfer/kv_connector/v1/offloading/store_triggers/on_compute.py`
  - `vllm/distributed/kv_transfer/kv_connector/v1/offloading/store_triggers/on_handoff.py`
  - `vllm/v1/kv_offload/base.py`
  - `vllm/v1/kv_offload/cpu/manager.py`
  - `vllm/v1/kv_offload/tiering/manager.py`

### Summary

**What changed and why**  
Fixes issue #66696 where a request with more unstored chunks than the CPU offload tier can hold was never offloaded at all, because CPUOffloadingManager.prepare_store() returned None and the ON_COMPUTE handler retried the same oversized offer every step. The manager now trims the offer, storing the lowest token positions that fit and reporting the remainder via a new PrepareStoreOutput.keys_to_retry field; the store handlers end each group's range at the first retried chunk so the cursor advances and the rest is offered on later steps. Finished requests and hand-offs with leftover keys are counted as allocation failures since they are not offered again.

**Technical impact**  
Adds a keys_to_retry field to PrepareStoreOutput (default empty, so other managers are unaffected) and a record_allocation_failure() hook on the store handler interface. StoreCandidates gains a key_chunks list mapping each key to its config group and chunk index, used by OnComputeStoreHandler to trim group ranges and assert the retry constraints. CPUOffloadingManager._prepare_store gains an allow_partial flag (true only for prepare_store, false for prepare_write promotions), and TieringOffloadingManager defers cascading of retried keys so resident keys after the cut are cascaded exactly once. The CPU allocation-size metric now records the post-trim size.

**Potential risks**  
Behavioral change: prepare_store() no longer returns None for oversized offers, so any caller relying on that rejection now gets a trimmed result; in-tree callers are the store handlers and tiering manager, but out-of-tree managers/callers could be affected. Without a secondary tier, oversized requests now cycle through the CPU tier and can evict their own prefix, and a request finishing before all chunks are consumed stores only the leading part. The trimming logic relies on get_offload_key_position and group-index invariants, guarded by asserts that could fire if a manager returns inconsistent keys_to_retry. Validation notes 10 test failures attributed to environment (missing GPUs, stale precompiled fs_io_C), which limits CI confidence.

**Key insights**  
The fix is well-scoped: capacity awareness stays in the manager while the connector only sees keys_to_retry, keeping the abstraction clean. The PR provides strong evidence (byte-identical fs-tier files between trimmed and untrimmed stores, load-back verification, and a production report of warnings dropping to zero). The main review focus should be the retry/cascade interaction in the tiering manager and the new assert invariants in OnComputeStoreHandler, plus confirming no external callers depend on the old None-on-full behavior.

  - `vllm/transformers_utils/processors/nano_nemotron_vl.py`
  - `vllm/transformers_utils/processors/ovis2_5.py`

### Summary

**What changed and why**  
Adds a two-line torch.Tensor to .cpu().numpy() conversion at the start of the video paths in three vLLM-owned HF processors (internvl.py, nano_nemotron_vl.py, ovis2_5.py). Since #53675 the parser passes tensor videos through unchanged, but these processors only accepted NumPy, so tensor videos failed with AttributeError, AssertionError, and TypeError respectively. The fix restores tensor support while keeping the NumPy path unchanged.

**Technical impact**  
Behavioral fix limited to the video preprocessing paths of three multimodal processors. NumPy inputs follow the identical code path as before, so existing behavior is preserved; tensor inputs (CPU or CUDA) are now normalized to NumPy before the existing frame-handling logic runs. The change is small and localized, with no API or config surface changes.

**Potential risks**  
The .cpu().numpy() conversion forces a device-to-host copy, which may add latency and memory traffic for CUDA-resident videos (e.g. NVDEC-decoded frames) that #53675 intended to keep on-device; this is a correctness fix but a potential performance regression for GPU pipelines. The Nemotron Nano VL device_resize/CV-CUDA path is explicitly not covered and still fails on CUDA tensors, leaving an inconsistent behavior gap. Grayscale and RGBA frames remain unsupported. The author removed the added test after review, so there is no CI regression coverage for this fix.

**Key insights**  
The root cause is a mismatch between the parser change in #53675 (pass tensors through) and vLLM-owned processors that were never updated to accept tensors. The fix is minimal and well-validated at both processor and end-to-end levels (CPU and CUDA tensors, matching NumPy outputs), but the lack of a committed test and the unaddressed CV-CUDA path are notable follow-ups. The author transparently flags the device_resize question and grayscale/RGBA limitation for separate work.

  - `vllm/models/inkling2/nvidia/ops/ll_gemm_sm120.py`
  - `vllm/models/inkling2/nvidia/sconv.py`

### Summary

**What changed and why**  
This PR renames and substantially extends the SM12x low-M BF16 GEMM kernel (gemv.py becomes ll_gemm_sm120.py) with three decode-time optimizations: deterministic split-K for narrow outputs, batched GEMM for the loop blend, and a fused q/k/v projection. It also wires these into attention, loop, model, linear, and sconv call sites, and updates the corresponding test import. The goal is faster small-M (M<=16) decode on RTX 5090 (SM120), with reported 6.5-7.5% end-to-end decode speedups.

**Technical impact**  
Adds a new Triton kernel with split-K partials, an acq_rel tile counter for deterministic reduction, PDL launch, and per-shape cached configs. Introduces a grouped qkv_bmm kernel that handles tiles spanning segment boundaries, plus a batched path for the loop blend replacing two torch.bmm calls. Dispatch is gated on SM12x device capability and bf16/stride/shape checks, so non-matching paths fall back to existing implementations. The old gemv module is removed and all callers migrated.

**Potential risks**  
Split-K correctness depends on the atomic counter protocol and partial-buffer reuse across launches; a bug could cause nondeterminism or stale partials, though the counter is reset after each launch. The counter is cached per CUDA stream, which may be fragile with multiple streams or CUDA graph capture. The PR explicitly states it is not tuned or validated on DGX Spark (SM121) despite dispatching there, and CI runs on B200 (SM100) so these SM12x paths are not exercised in CI. The qkv_bmm boundary-tile logic and the assertion that only one boundary falls per tile add correctness constraints that must hold for all model shapes.

**Key insights**  
Performance gains are well-documented with kernel-level and end-to-end benchmarks plus GSM8K accuracy parity, which is strong evidence. The main review focus should be the split-K synchronization and counter lifecycle, the SM121 dispatch without validation, and the lack of CI coverage for these code paths. The fallback gating appears conservative, limiting blast radius to SM12x bf16 low-M cases.

### Summary

**What changed and why**  
The Rubin prerelease build moves from PyTorch's cu134 nightly and cuda13.4 builders to the cu135 nightly (torch 2.16.0.dev20261116+cu135) and cuda13.5 builders, since PyTorch now publishes both. The source-built Triton path (two scripts, Dockerfile stages, build args) is removed in favor of the triton==3.9.0+gitb7ddcf86 wheel that torch's own requirement pulls in, which also resolves the torch/Triton requirement conflict. Because ptxas 13.5.37 silently miscompiles some sm_107a code, the Rubin build docs now warn about it and document a TRITON_PTXAS_BLACKWELL_PATH docker run option that keeps Triton on the wheel's bundled ptxas-blackwell 13.4.59.

**Technical impact**  
Rubin images now ship torch built against CUDA 13.5 with matching runtime wheels (cuda-toolkit 13.5.0, nvidia-cuda-runtime 13.5.37), while torchvision and torchaudio stay on cu134 nightlies via a second extra index and CUDA minor-version compatibility. Triton 3.9.0 comes from PyTorch's index instead of a multi-minute source build, shrinking the Dockerfile by ~85 lines and making uv pip check pass (245 packages compatible). The ptxas workaround is documentation-only: no image sets the variable, so default behavior is unchanged and users must opt in via --env.

**Potential risks**  
The miscompile is only mitigated by a documented runtime flag, so users who don't pass it still get garbled output on VR200/R100 with GLM-5.3-class models; the fix depends on NVIDIA shipping a corrected ptxas. The documented path hardcodes Python 3.14 site-packages, so it breaks if PYTHON_VERSION changes. Triton 3.9 removes block pointers, so MiniMax-M3's Hopper sparse prefill kernel won't compile on SM90 until #66099 lands. The cuda13.5 builder tags float, and Rubin CI steps only run in nightly builds, so PR CI doesn't exercise them; x86_64 was not built or run. The PR also overlaps with open #68088 on the same Dockerfile/versions.json, requiring a rebase.

**Key insights**  
The root cause is ptxas 13.5.37 miscompiling a negated floor-division ceiling in i64 index math, which Inductor emits for ceil-div and which corrupts the last partial 128-row block of per_block_cast_to_fp8. FlashInfer 0.7.4 sets TRITON_PTXAS_BLACKWELL_PATH to the PATH ptxas when unset, so a plain import silently reintroduces the bad assembler; the validation correctly imports vLLM and FlashInfer first to reproduce server behavior. The PR deliberately avoids Rubin-only Dockerfile stages and a global ENV (which would break Triton 3.8 in other images), choosing documentation over baking in a workaround, and the requirements file notes to recheck Triton's bundled ptxas before future torch bumps.

### Summary

**What changed and why**  
Fixes Whisper prompt conditioning by replacing the invalid `<\\|prev\\|>` token with the real `<\\|startofprev\\|>` token and encoding the prompt as `<\\|startofprev\\|> {prompt.strip()}` to match HF transformers and openai-whisper token IDs. It also introduces a per-prompt `should_skip_decoder_start_token` predicate so `build_enc_dec_input` only omits the decoder start token when the prompt actually opens with `<\\|startofprev\\|>`, preserving existing behavior for empty and SOT-less prompts. Tests and example docs are updated accordingly.

**Technical impact**  
Changes the decoder input layout for prompted Whisper transcription requests, aligning them with the reference implementation and fixing silent truncation of 30s windows. The `build_enc_dec_input` signature now accepts a bool or a predicate, and `EncDecMultiModalProcessor` gains an overridable method, which is a backward-compatible extension for other enc-dec models like Canary and Cohere ASR. Adds renderer-level CPU tests and an LLM-level GPU test covering prompted, empty, and SOT-less decoder prompts.

**Potential risks**  
Behavior change for existing Whisper prompt users: previously malformed prompts now produce different (correct) decoder inputs, which could shift outputs for anyone relying on the old layout. The predicate path relies on tokenizer availability; with `skip_tokenizer_init=True` it falls back to the default, which is documented but worth verifying. Prompt tokenization still parses special-token text inside prompts and does not truncate to 223 tokens as openai-whisper does, so edge cases remain. The GPU test is marked `core_model` and may add CI runtime.

**Key insights**  
The root cause was a nonexistent `<\\|prev\\|>` token that tokenized into six text tokens, combined with unconditional prepending of `<\\|startoftranscript\\|>`, causing dropped transcript segments. The per-prompt predicate is a cleaner design than a global `skip_decoder_start_token` flag, which an earlier revision showed breaks empty and SOT-less prompts. Validation is strong, with renderer tests, an LLM-level test, and real serving evidence showing improved transcription quality.

**Technical impact**

**Key insights**  
The core design is sound: a ContextVar-backed request scope plus explicit propagation into executor threads correctly addresses the thread-context gap.
