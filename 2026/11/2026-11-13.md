  - `vllm/multimodal/media/audio.py`

### Summary

**What changed and why**  
This PR fixes a regression introduced by #58364, which made torchcodec the first backend in the auto chain and treated any torchcodec decode error as final. MP3s with occasional undecodable frames that previously decoded via soundfile now returned 400 errors. The change introduces a private _CorruptAudioError (a ValueError subclass) raised on torchcodec open/decode failures, and in auto mode falls back to soundfile only when this error occurs, re-raising the original torchcodec error if soundfile also fails and skipping PyAV.

**Technical impact**  
Behavior of load_audio(backend='auto') changes: torchcodec decode failures now trigger a soundfile retry before failing. Duration and memory-limit ValueErrors remain non-falling-back since they are not _CorruptAudioError. The public error message and 400 API response are preserved via the ValueError subclass. Only one file (vllm/multimodal/media/audio.py) is modified with +30/-12 lines, keeping the change localized.

**Potential risks**  
For genuinely corrupt inputs, auto now incurs an extra soundfile decode attempt after torchcodec fails, adding latency (bounded by soundfile's own duration/memory limits). The fallback logic relies on exception type discrimination, so future changes to torchcodec error handling could silently break the fallback. No regression test is added because it requires an MP3 with a corrupted frame, leaving the fix unguarded against future regressions. The re-raise uses 'from torchcodec_error.__cause__' which preserves the original chain but could be fragile if __cause__ is None.

**Key insights**  
The root cause is that soundfile's mpg123 decoder resyncs past bad frames that FFmpeg-based decoders (torchcodec and PyAV) abort on, so the previous assumption that all decode errors are equivalent across backends was incorrect. The fix correctly distinguishes torchcodec decode failures from guard failures via a dedicated exception subclass, and correctly skips PyAV since it shares FFmpeg's failure mode. The PR is well-validated with a concrete reproducer, backend comparison table, and end-to-end API test, though the absence of an automated regression test is a notable gap.

  - `rust/src/managed-engine/src/process.rs`

### Summary

**What changed and why**  
The Rust frontend's ManagedEngineHandle::shutdown previously sent SIGTERM to the managed engine's whole process group, which caused GPU worker processes to exit immediately and fail in-flight requests instead of draining. This PR changes shutdown to SIGTERM only the Python launcher pid, keeping the process-group SIGKILL as a timeout fallback and adding a post-exit group SIGKILL to reap stragglers. It also reorders vllm-rs serve shutdown so the API server drains first while the engine keeps serving, then stops the engine with the remaining timeout budget, matching vllm serve behavior.

**Technical impact**  
Behavioral change in shutdown semantics for the managed engine: launcher-only SIGTERM lets the launcher drain requests and stop workers in order, and the API-server-first ordering prevents data-parallel rank exits from prematurely failing requests on other ranks. Signal helper is refactored to support both single-pid and process-group targets with ESRCH treated as success. Two new integration-style unit tests using shell-script launchers validate launcher-only signaling and the SIGKILL fallback path.

**Potential risks**  
A launcher that exits without stopping its children now relies on the final group SIGKILL rather than the initial SIGTERM, so any child that ignores SIGKILL or escapes the process group could linger. The reordered shutdown in main.rs changes timing assumptions and could interact with edge cases where the serve task errors or the shutdown reason is Server. Tests depend on /proc and shell trap behavior, so they are Linux-specific and may be flaky under load or in constrained CI environments.

**Key insights**  
The root cause is a signal-scope mismatch: process-group SIGTERM hit both the launcher and the workers, so workers died mid-drain. Scoping SIGTERM to the launcher aligns the Rust frontend with vllm serve --headless semantics. The shutdown-order change is a necessary companion fix because data-parallel ranks drain independently and the first rank exit fails requests on others, so draining the API server first preserves the full drain window. The PR includes a concrete end-to-end reproducer showing requests completing instead of failing, which is strong evidence for the fix.

The extensible KV cache sizing now measures how far each sizing step grows torch's caching-allocator reservation (net of memory the step leaves allocated) and keeps the larger of that growth and the allocated transient peak free, instead of relying on the allocated peak plus a fixed margin. This addresses OOMs caused by large per-call workspaces (CUTLASS MoE, AITER MLA verify buffer) whose fragmentation is invisible to the allocated peak. The sizing decode step now also verifies a full set of draft tokens (with fixed draft counts, matching warmup_kernels), and the peak-less-current bookkeeping is consolidated into ExtensibleKVCache.record_transient_peak(), removing Worker.kv_cache_transient_bytes_before_tuning.

**Technical impact**  
Adds torch_reserve_growth_bytes to ExtensibleKVCache and a torch_reserve_growth_bytes parameter to measure_kv_cache_bytes, where the kept-free amount becomes max(transient_peak, reserve_growth). A new _measure_sizing_step context manager wraps the full-budget mixed step, prompt-logprobs step, and MLA context-prefill step, emptying the cache and resetting peak stats before each and recording reservation growth after. run_mixed_prefill_decode_warmup now schedules 1 + num_spec tokens with scheduled_spec_decode_tokens and uses a shared _fixed_draft_counts helper. Behavior changes: models that fragment during warmup get less KV cache (about 6.3 GiB/GPU, -4.8% for Kimi-K3 DSpark on MI350X), and JIT warmups reusing the mixed step now run a verifying decode.

**Potential risks**  
The measurement only captures fragmentation reproduced by the sizing steps; lazily allocated buffers or shapes not exercised still rely on the margin. The 0.75*T margin still stacks on top of measured growth, so fragmentation can be double-covered, reducing KV cache more than strictly necessary. The new decode-verify path changes warmup behavior for all spec-decode configs and could surface backend-specific issues in JIT warmups (attention, FlashInfer sparse MLA, Step5 DSA). The CUDA-only test for reserve growth is hardware-sensitive (segment sizes, allocator behavior) and may be flaky across drivers. The Qwen3.5 reproducer was not rerun after the decode-verify change.

**Key insights**  
The root cause is well diagnosed: torch's cap is set from reservation, so reserved-but-unallocated fragmentation from large per-call workspaces is the real failure mode, and measuring reservation growth directly is more principled than a fixed floor. Validation is strong, with before/after GSM8K runs on MI350X and GB200 plus targeted unit tests that fail without the change. The PR is transparent about tradeoffs (KV cache reduction, margin stacking, deferred workspace reuse in #60570 and AITER). The consolidation of peak bookkeeping into record_transient_peak simplifies the Worker/kernel_warmup interaction.
