## 1. [[CI] Pass --models=llama3.2 so Rust Frontend Tool Use gets a shard plan](https://github.com/vllm-project/vllm/pull/65750)

- **[Changed Files](https://github.com/vllm-project/vllm/pull/65750/files) (1):**
  - `.buildkite/test_areas/rust_frontend.yaml`

### Summary

**What changed and why**  
A single CI YAML line in .buildkite/test_areas/rust_frontend.yaml changes the Rust Frontend Tool Use command from '--models llama3.2' to '--models=llama3.2'. The automatic_shard planner only understands pytest's own value-taking options, so it treated 'llama3.2' as a test path, failed to find it, and fell back to a single unplanned job. The '=' form lets the planner parse the command and produce a shard plan.

**Technical impact**  
Behavior of the CI shard planner changes for the NVIDIA job and its AMD mirror: both now get a real plan (one shard today) instead of a 'no plan' fallback, and will shard automatically once tests exceed the 20-minute target. Test execution is unchanged because pytest's conftest option with nargs='+' parses '--models=llama3.2' identically to the space-separated form. The fix is confined to CI config and does not touch the planner or vLLM test code.

**Potential risks**  
The '=' form can only pass a single model value; a command needing multiple models would require changing the conftest option from nargs='+' to action='append', which no CI command does today. Validation is well documented (build 100042 vs main 100025 showing identical 630 node IDs and outcomes), so regression risk is low, but the change relies on the planner's parsing behavior remaining consistent.

**Key insights**  
The root cause was a mismatch between conftest-defined options and the planner's knowledge of pytest options, correctly fixed in YAML rather than by coupling ci-infra to vLLM's tests. The PR includes strong evidence: planner output before/after, pytest argument-parsing equivalence, and a full CI build comparison confirming no test drift. The noted multi-model limitation is a reasonable, explicitly scoped trade-off.

The PR enables existing native 8/16/32-head BF16 FlashMLA sparse kernels on SM90 for sufficiently large query batches, avoiding the previous requirement to pad heads to 64. It adds a heuristic (_should_use_bf16_small_head_kernel) gated on SM90, head count in (8,16,32), and token count exceeding SM count (or 2x SM count for 32 heads), slicing queries and optional output buffers to the actual head count before calling FlashMLA. Only SM90 is covered; behavior on other architectures is unchanged but untested here.

**Key insights**  
The change is a targeted performance optimization that reuses existing native kernels rather than adding new ones, keeping the padded path as a safe fallback. The new test is thorough across head counts, head sizes, and query waves, but its assertions are tied to the heuristic thresholds, so future tuning will require test updates.
