## 1. [[Bugfix][Kernel] Fix cooperative top-k dispatch on SM110](https://github.com/vllm-project/vllm/pull/56102)


### Base Information

- **PR Number:** #56102
- **Author:** [kbenkhaled](https://github.com/kbenkhaled)
- **Merged By:** [gau-nernst](https://github.com/gau-nernst)
- **Merged time:** 2026-11-02 23:46:40
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/56102/files) (2):**
  - `vllm/model_executor/layers/indexer_topk.py`
  - `vllm/models/qwen4_exp/nvidia/ops/qsa_indexer.py`

### Summary

**What changed and why**  
The PR fixes a bug where the QSA top-k dispatcher selected cooperative_topk on Jetson AGX Thor (SM110) because SM110 satisfies has_device_capability(90). The cooperative kernel requests a 16-block cluster but Thor supports a maximum cluster dimension of eight, causing model warmup to fail. The fix excludes SM110 from the cooperative path in both indexer_topk.py and qsa_indexer.py so it falls back to persistent_topk, and updates the error message accordingly.

**Technical impact**  
Behavior changes only for SM110 devices, which now route to the persistent_topk fallback instead of cooperative_topk. SM90 and other non-SM11x/SM12x devices retain the cooperative path, and SM12x exclusion is preserved. The change is small and localized to capability gating logic in two files.

**Potential risks**  
The fix relies on is_device_capability_family(110) correctly identifying all affected Thor/SM110 variants; if other architectures share the same cluster-size limitation they would still hit the failure. There is no automated test added, only manual verification on Qwen3.8 Next Flash, so regression coverage is limited. The persistent_topk fallback path should be validated for performance parity on SM110.

**Key insights**  
The root cause is a capability check that treats SM110 as SM90-compatible for cooperative launch, ignoring the smaller maximum cluster dimension on Thor. Gating on capability family rather than a simple >=90 check is the right approach, and the same pattern was already used for SM12x. Adding a unit test that asserts dispatch selection per capability family would prevent similar regressions.

## 6. [[Perf][Model Loader] Fault in mmap'd weight pages before host-to-device copies on integrated GPUs](https://github.com/vllm-project/vllm/pull/58868)


### Base Information

- **PR Number:** #58868
- **Author:** [Willian-Zhang](https://github.com/Willian-Zhang)
- **Merged By:** [arpera](https://github.com/arpera)
- **Merged time:** 2026-11-02 23:14:20
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/58868/files) (7):**
  - `tests/model_executor/test_utils.py`
  - `vllm/model_executor/layers/fused_moe/routed_experts.py`
  - `vllm/model_executor/layers/linear.py`
  - `vllm/model_executor/layers/vocab_parallel_embedding.py`
  - `vllm/model_executor/model_loader/weight_utils.py`
  - `vllm/model_executor/parameter.py`
  - `vllm/model_executor/utils.py`

### Summary

**What changed and why**  
Adds a copy_weight_ helper in vllm/model_executor/utils.py that, on integrated GPUs, touches one byte per page of a contiguous same-dtype CPU source before dst.copy_(src), so mmap page faults happen on the CPU rather than inside the driver's host-to-device copy. The 26 copy sites in linear.py, parameter.py, routed_experts.py, vocab_parallel_embedding.py and default_weight_loader are switched to the helper, gated by a cached current_platform.is_integrated_gpu() check. Motivation is issue #58726, where GB10 weight loads took 450+ s due to faults taken during the copy.

**Technical impact**  
Behavior is unchanged on discrete GPUs and non-CUDA destinations; on integrated GPUs the source pages are prefaulted via a strided uint8 sum before the copy. Reported gains are large: main weight load on Qwen3.8-Flash-Next NVFP4 dropped from ~452-660 s to ~26-71 s, and DeepSeek-V4.1 TP4 improved 18-27%. The gate is cached per device, and the extra checks cost ~0.46 us per call when off. Only contiguous, same-dtype, multi-element CPU sources are touched, since PyTorch already stages other copies through a CPU temporary.

**Potential risks**  
The touch path is only measured on GB10; other integrated devices (Jetson Orin/Thor, possibly GH200) will take it untested, and the gate's behavior on those platforms is unverified. The prefault reads the full source, so it could add I/O or memory pressure in cases where the copy would not have read all pages, though the PR argues the copy reads them anyway. Model-specific loaders that call .copy_() or .to(device) directly (e.g. the Qwen4Exp PLE shard copy) are not covered, so gains are partial until follow-ups land. The strided sum allocates a small temporary and relies on view(torch.uint8) semantics, which the tests cover but only with the gate monkeypatched on CPU.

**Key insights**  
Placing the prefault at the copy site rather than in the safetensors iterator avoids reading whole tensors per TP rank and avoids touching tensors served directly from the mapping. The helper is a low-risk, opt-in-by-default shim that preserves copy semantics exactly (byte-identical weights verified by tests and greedy-output comparisons). The PR is well-validated with multi-machine A/B boots, but the untested integrated-GPU variants and the uncovered in-tree loader are the main gaps to track.

**Technical impact**  
Fixes startup failures where the granule-aligned block count rounded to zero, and recovers up to ~11.6 GB of lost capacity for the stride in the issue. Padding is worker-local so engine/scheduler configs keep unpadded placements, and shrink_kv_cache_configs scales size by block count. ExtensibleKVCache now validates segment tiling with gaps allowed and derives bytes_per_block from summed segment strides, which is a meaningful change to allocation/commit bookkeeping. **Potential risks**  
registers_kv_cache_memory() is a name-based allowlist, so out-of-tree connectors loaded via kv_connector_module_path that register device memory silently lose one-chunk-per-segment behavior and may hit RDMA registration failures. Padding increases reserved address space, and correctness depends on commits mapping whole granules per segment (physical_bytes_for), which is asserted but not exhaustively tested across all layouts. **Key insights**  
The root cause was conflating a connector-specific requirement (one physical chunk per RDMA-registered segment) with a global block-count constraint, forcing every connector to pay the rounding cost. Moving the fix to worker-local segment padding and gating on connector capability is a cleaner separation of concerns. Validation is strong: a concrete startup reproducer, NIXL P/D accuracy runs, and targeted unit tests for padding, defragmenting commits, and connector gating. ### Base Information

  - `rust/src/engine-core-client/src/tests/client.rs`

### Summary

**What changed and why**  
Moves the utility call fan-out from EngineCoreClient into ClientInner, which owns the ZMQ socket, and changes cancellation semantics: once requests are prepared, the call runs to completion in a spawned task on the client runtime instead of being abandoned when the caller's future is dropped. The UtilityCallGuard is removed and replaced by explicit unregistration on preparation failure and after the spawned task collects replies. This is needed so callers (e.g. a /pause handler) can tie state to actual engine completion even if the HTTP/gRPC client disconnects.

**Technical impact**  
Utility calls now spawn a single task rather than one per engine via send_to_engine, and the caller awaits that task and decodes replies, so arguments and result types no longer need 'static. ClientInner now stores engine_ids and client_index, and the constructor signature gains a client_index parameter. Dropping the returned future only stops waiting; a runtime shutdown during a call surfaces as a ClientClosed error, and panics are resumed via resume_unwind.

**Potential risks**  
Behavior change is intentional but subtle: callers that relied on cancellation aborting work will now see requests still sent and executed, which could surprise code assuming drop means no side effects. The spawned task holds a cloned Arc<ClientInner>, so client teardown may be delayed until in-flight utility calls finish, and a hung engine reply could keep the task alive. The test only covers the happy-path reply-after-abort case; send-failure unregistration and runtime-shutdown paths are not directly exercised in the diff.

**Key insights**  
The refactor correctly separates preparation (fallible, unregisters on error) from execution (non-cancellable, unregisters after collection), which is the right shape for tying state to engine completion. The test rename and rewrite from cancelled_utility_call_unregisters_waiter to cancelled_utility_call_still_collects_the_reply directly encodes the new contract and would fail on main, giving good regression coverage. Worth confirming that holding the Arc in the spawned task does not deadlock shutdown ordering and that the ClientClosed path is tested elsewhere.
