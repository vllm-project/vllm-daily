## 3. [[Bugfix] Use max_split_size_mb:21 so freed 1-10 MiB tensors are reused](https://github.com/vllm-project/vllm/pull/66561)


### Base Information

- **PR Number:** #66561
- **Author:** [viktorkou](https://github.com/viktorkou)
- **Merged By:** [MatthewBonanni](https://github.com/MatthewBonanni)
- **Merged time:** 2026-11-11 23:04:26
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/66561/files) (3):**
  - `tests/kernels/quantization/test_k3_gfx942_int4_requant.py`
  - `tests/v1/worker/test_gpu_worker.py`
  - `vllm/v1/worker/gpu_worker.py`

### Summary

**What changed and why**  
Raises the scoped caching-allocator max_split_size_mb from 20 to 21 in Worker.load_model and profile_run via a new _MAX_SPLIT_SIZE_MB constant, and updates the gfx942 requant test to reference that constant instead of hardcoding 20. The root cause is that PyTorch serves 1-10 MiB requests from a 20 MiB segment, and at a limit of exactly 20 those freed segments become oversize and are never split, so loaders freeing small tensors one at a time strand 20 MiB per tensor and eventually thrash through allocator OOM retries.

**Technical impact**  
Behavior change in the allocator configuration used during model loading and memory profiling: freed 1-10 MiB segments are now reusable, while blocks of 21 MiB and above remain unsplittable, preserving the large-block releasability that #41268 and #58430 depend on. Reported end-to-end impact is large (Kimi-K3-REAP load 690-703 s to 96.8 s, ~964,000 OOM retries to 0) with identical output. A new worker unit test pins the regression, and the gfx942 test now tracks the real setting rather than a duplicated literal.

**Potential risks**  
The change is a single-MiB tuning constant with subtle allocator semantics, so it is sensitive to PyTorch internals (kLargeBuffer) and could regress if those change. The gfx942 requant test was not run locally (no MI300), so its coverage relies on the AMD CI job. Other code paths still hardcoding max_split_size_mb=20 (e.g. open PR #59893) would diverge from the new constant. The new test depends on native allocator backend and spawn isolation, and its 20 MiB growth bound could be brittle across platforms.

**Key insights**  
The fix is a minimal, well-justified off-by-one correction to a compile-time allocator boundary rather than a new mechanism. The PR provides strong evidence: root-cause explanation, before/after benchmarks, a targeted regression test that fails at 20 and passes at 21, and confirmation that the Inkling workaround is no longer needed. The main follow-up is consolidating remaining hardcoded 20 MiB scopes onto _MAX_SPLIT_SIZE_MB and confirming the AMD-only test in CI.

### Summary

**What changed and why**  
The PR adds explicit token budgets to the MiniMax-M3-MXFP8 wide-EP CI cells in .buildkite/amd-disagg/models.yaml: --max-num-batched-tokens 2048 for prefill and 64 for decode. The AITER MXFP8 MoE kernel pads its buffer to max-num-batched-tokens (131072 by default), so every step paid for the full buffer; shrinking it cuts the GSM8K eval from ~1h37 to ~118s (EP16) and ~1h to ~84s (EP8).

**Technical impact**  
Only the ep: flag strings for the MiniMax-M3-MXFP8 model change; TP cells and all other models are untouched. The launcher dry run over 168 cases reportedly differs only for the MiniMax wide-EP cells. Accuracy remains above the 0.90 gate (0.9098 and 0.9030), so the change is a CI runtime optimization with no production code impact.

**Potential risks**  
The 64-token decode budget is very small and could interact poorly with --max-num-seqs or concurrency 64, potentially capping effective batch size and affecting throughput or accuracy on other workloads. Accuracy margins are thin (0.9098 vs 0.90 gate), so small variance could cause flakiness. The change is validated only on the two named cells, so other topologies or future model variants may need separate tuning.

**Key insights**  
The root cause is a padded MoE buffer sized by max-num-batched-tokens, making token budget the dominant cost driver for wide-EP MXFP8 cells. The ~50x eval speedup is a strong CI win, but the narrow accuracy margin and tiny decode budget warrant monitoring for flakiness. The change is well-scoped to a single config file with a broad dry-run diff check.

### Summary

**What changed and why**

It adds a new 'GPU Memory Utilization' docs section explaining when to leave it unset versus when to set it (shared GPUs, unified memory, weight-transfer buffers, KV connectors), updates docstrings and cross-links, and adjusts two runtime messages plus the auto_tune.sh search logic and VllmRunner XPU None handling.

**Technical impact**

Most of the diff is documentation, recipe YAML, and test config cleanup that shifts those runs to the default 1.0 utilization, which should increase KV cache size where the extensible cache is active.

**Potential risks**  
Removing explicit values from tests, eval configs, and recipes that were compensating for estimate-based sizing or transient memory (CUDA graph profiling, FlashInfer autotuning, spec-decode, multimodal) could surface as OOMs in CI since the PR author did not run the edited tests. On vLLM versions before v0.33.0, recipe commands without the flag fall back to older defaults (0.92/0.9), changing behavior for users on older releases. Some kept values (e.g., diffusiongemma, ERNIE 1M prefills, 810e/m890 overrides) are left on judgment calls that may need re-measurement.

**Key insights**  
The change is largely a documentation and configuration hygiene pass aligned with the extensible KV cache, but it does touch runtime messaging and benchmark tooling, so it is not trivial. The main validation gap is that edited tests and examples were not executed; the author flags unexplained 0.85-0.9 test values as the highest-risk removals. Reviewers should confirm the auto_tune.sh GPU branch and the XPU None handling behave as intended, and that kept values genuinely need headroom.
