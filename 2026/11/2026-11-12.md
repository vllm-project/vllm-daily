  - `vllm/entrypoints/serve/fault_tolerance/api_router.py`
  - `vllm/v1/fault_tolerance/engine_core_sentinel.py`

### Summary

**What changed and why**  
Adds a new FaultToleranceConfig.request_failure_policy option ("fail" default, "recompute") that controls whether unfinished requests are aborted or preempted and resumed after fault recovery. The engine sentinel now evicts potentially contaminated KV blocks, preempts running requests and clears stale output counters under "recompute", and supports a per-retry params.abort override. Docs and the E2E test are updated to cover the new resumption behavior.

**Technical impact**  
Changes fault-handling behavior in the engine core sentinel: KV block eviction on fault, scheduler preemption via _preempt_request, and resetting num_in_flight_tokens/num_stale_output_tokens for all queued requests. The API router now validates that params.abort is a boolean. Default behavior is preserved via the "fail" policy, but the new code path touches scheduler internals and KV cache manager block bookkeeping, so correctness depends on accurate num_computed_tokens/num_in_flight_tokens accounting.

**Potential risks**  
The _clear_contaminated_blocks logic computes block ranges from num_computed_tokens and num_in_flight_tokens; off-by-one or stale counter values could evict valid blocks or miss contaminated ones, causing silent corruption. Directly manipulating scheduler.running and private fields (_preempt_request, num_stale_output_tokens) couples to scheduler internals and may break with refactors. Resumption correctness relies on retained token history and recomputation; the test only covers a single injected fault scenario on 2 GPUs, so edge cases like multiple concurrent faults or scale-down are less validated.

**Key insights**  
The PR is well-scoped and preserves backward-compatible default behavior while adding an opt-in resumption mode with a clear naming convention aligned to kv_load_failure_policy. The E2E test meaningfully verifies stream stalling, exact token count, finish_reason, and post-recovery accuracy, which is strong coverage. Main review focus should be on the KV eviction boundary math and reliance on scheduler private APIs, plus ensuring the abort override is consistently honored across recovery paths.

### Summary

**What changed and why**  
Adds a _replay_exceeds_capture guard in encoder_cudagraph.py that detects when replay tensors exceed the fixed leading dimension of captured CUDA-graph buffers, and falls back to eager encoder execution instead of asserting/crashing the shared engine. Includes unit tests for the capacity check and a GPU regression test verifying oversized replay falls back to eager.

**Technical impact**  
Changes the encoder CUDA-graph execute path so that oversize multimodal batches (e.g., legal video batches exceeding capture capacity) degrade gracefully to eager execution rather than terminating the engine. The guard sits on the shared _execute_local -> _run_budget_graph sink, so it covers DP sharding and multi-path budgets; graph_misses is incremented on fallback, preserving counter semantics.

**Potential risks**  
The check only compares the leading dimension (shape[0]) of each buffer, so tensors that overflow on non-leading dimensions or via dtype/shape mismatches could still raise in the padded copy path. The fallback path calls encoder_eager_forward inside inference_mode, which may differ subtly from the graph path's context; also, repeated oversize batches will silently incur eager cost without visibility beyond graph_misses. Test coverage relies on a monkeypatched prepare function, so real-world trigger conditions are only indirectly validated.

**Key insights**  
This is a targeted robustness fix that converts a hard failure into a graceful degradation, which is the right tradeoff for a shared engine. The model-agnostic shape comparison is a reasonable sink-level guard, but reviewers should confirm that non-leading-dimension overflows and the eager fallback's context/return contract are handled, and that the new graph_misses accounting is consistent with existing metrics expectations.

### Summary

**What changed and why**  
The zmq_socket_ctx context manager in vllm/utils/network_utils.py previously caught KeyboardInterrupt, logged it at DEBUG, and returned normally; the fix re-raises it after the log. This lets a SIGTERM delivered during engine startup (converted to KeyboardInterrupt by _interrupt_init in run_server) propagate out of launch_core_engines and actually stop the API server instead of silently completing startup. A unit test was added to verify the interrupt escapes and the socket is closed.

**Technical impact**  
Behavioral change in a shared utility: any KeyboardInterrupt raised inside zmq_socket_ctx now propagates rather than being swallowed. The only in-tree caller is launch_core_engines, which has no reason to suppress it, and the finally block still destroys the ZMQ context with linger=0. **Potential risks**  
The change is small but touches a general-purpose context manager, so any future or out-of-tree caller relying on the old swallow behavior would see new exceptions. Exit-code semantics shift (Kubernetes pods deleted mid-boot now end as Failed rather than Succeeded), which could affect orchestration or alerting expectations. The end-to-end validation was done on a fork and no RemoteOpenAIServer regression test was added, so CI coverage of the real SIGTERM-during-startup scenario is limited to the unit test.

**Key insights**  
The root cause is a narrow but high-impact bug: a swallowed KeyboardInterrupt in a context manager defeated the API server's startup signal handling, leaving pods holding GPUs and serving until SIGKILL. Re-raising is the minimal correct fix and composes with the related PR #44751, whose re-raised cleanup exception would otherwise still be swallowed here. The added unit test is a reasonable, non-flaky proxy for the production scenario.

### Summary

**What changed and why**  
Removes the TeleChat2 and TeleChat3 model architectures, which are reported to have very low usage. Deletes the telechat2.py implementation, drops both entries from the model registry, test registry, and supported_models docs, and removes the telechat3-yarn RoPE normalization branch in _patch_legacy_rope_type along with its test. Both architectures are added to _PREVIOUSLY_SUPPORTED_MODELS with version 0.34.0 so loading them now raises the deprecation error.

**Technical impact**  
Behavioral change: users loading TeleChat2ForCausalLM or TeleChat3ForCausalLM will now get a 'supported in vLLM until v0.34.0' error instead of a working model. The removal of the telechat3-yarn branch in _patch_legacy_rope_type means configs declaring that rope_type will no longer be normalized to plain yarn with a precomputed attention_factor, though this is acceptable since only TeleChat3 used it. Registry and docs are consistently updated, and the remaining yarn test case is preserved.

**Potential risks**  
Any downstream users or forks still relying on these architectures will break on upgrade, mitigated only by the version-gated error message. If any other model configs in the wild declare rope_type 'telechat3-yarn', they will now fail or behave differently since the normalization is gone. The change is otherwise low-risk given the small diff and passing validation tests.

**Key insights**  
This is a clean deprecation/removal following vLLM's established _PREVIOUSLY_SUPPORTED_MODELS pattern, with registry, tests, and docs updated in lockstep. The RoPE patch removal is tightly coupled to TeleChat3 and is safe to drop alongside the model. Validation covers registry and rope/max_len config tests, which is appropriate for the scope of the change.
