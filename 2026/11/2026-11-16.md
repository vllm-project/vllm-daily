  - `vllm/models/muse_spark/amd/muse_moe_runner.py`

### Summary

**What changed and why**  
Adds a ROCm-only Muse Spark optimization that shards the residual stream by token across TP ranks for large forwards (gated by new env var VLLM_ROCM_MUSE_SP_MIN_TOKENS, default 1024, 0 disables). All-reduces after o_proj and the MoE output become reduce-scatters plus all-gathers, and per-token work (norm, squeeze, expand) runs only on each rank's owned tokens. Includes a TokenShard helper, a token_sharded_moe_output context manager, deferred-reduce plumbing in attention/MoE layers, a new distributed test, and expanded MoE/loading tests.

**Technical impact**  
Changes collective patterns and layer construction (o_proj and MoE built with reduce_results=False when sharding is possible) in the Muse Spark ROCm path, with fallback all-reduce when a forward is not sharded. Requires TP>1, EP or bf16 MoE reduction, and DP=PP=PCP=DCP=1; disabled for DSpark configs. Reported gains are ~2-16% throughput and ~15-26% lower TTFT with unchanged GSM8K accuracy, but the path is gated and off for decode/CUDA-graph batches below the token threshold.

**Potential risks**  
Correctness depends on consistent row ownership (ceil(T/tp) padding) across TokenShard, the MoE finalize, and the reduce-scatter; mismatches could silently corrupt tokens. The global _token_sharded_output flag is process-global state, which is fragile under concurrency or nested calls. The optimization is ROCm/Muse-Spark-specific and only lightly covered by CI (2-GPU distributed test plus mocked unit tests), so edge cases like non-divisible token counts, EP vs TP-sharded MoE, and speculative decoding hidden-state gathering may be under-tested. Benchmark claims are from a single hardware/config.

**Key insights**  
The design trades extra collective launches for eliminating redundant per-token work, with a token threshold to avoid launch-latency regressions on small/decode batches. The skip_final_all_reduce validation relaxation (now only rejected when tp_size>1) and the new EP test are important guardrails. Reviewers should focus on row-ownership invariants, the global flag's safety, and whether the threshold and fallback paths are exercised in CI.

## 2. [[Core][Bugfix] Honor prefill_schedule_interval for prefix replay](https://github.com/vllm-project/vllm/pull/67879)

  - `tests/v1/core/test_prefix_replay.py`
  - `vllm/v1/core/sched/scheduler.py`

### Summary

**What changed and why**  
Fixes a scheduler bug where prefill_schedule_interval throttling was bypassed for requests whose prefix-cache hit requires a sliding-window replay. The prefill-deferral gate previously compared raw num_computed_tokens against the prompt length, so a request with a one-token cache-hit tail appeared to need only one token and was admitted, then the replay rewind inflated scheduled work beyond the throttle. The fix reuses the replay-adjusted count (renamed ec_computed_tokens to effective_computed_tokens) for the deferral check, and adds regression tests covering local and connector-based cache hits plus DecodeBench fill behavior.

**Technical impact**  
Changes admission behavior in the v1 core scheduler's prefill gate so that replay-adjusted progress, not raw computed tokens, determines deferral. The renamed effective_computed_tokens now serves both encoder-input transfer checks and prefill admission, keeping the calculation consistent with _mark_prefix_replay. Requests whose transferred KV already includes window state remain eligible for one-token scheduling, and the change is localized to the scheduling loop with no new data structures.

**Potential risks**  
The correctness of the gate now depends on effective_computed_tokens staying in sync with the rewind logic in _mark_prefix_replay; divergence between the two calculations could cause either over-deferral (starvation) or under-deferral (throttle bypass). The change touches a hot scheduling path and interacts with DP prefill balancing, external KV connectors, and encoder-input transfers, so edge cases around async loads and window_loaded flags warrant scrutiny. Test coverage is focused on unit-level replay scenarios with limited GPU integration coverage.

**Key insights**  
The root cause is an ordering issue: the prefill gate evaluated progress before replay adjusted it, so a 97-token prompt with a 96-token hit looked like one token of work but became 33 after a 32-token rewind. Reusing the already-computed replay-adjusted count is a minimal, low-complexity fix that avoids duplicating replay math. The added parametrized tests for throttle and connector paths, including repeated deferral and subsequent admission, meaningfully validate the fix's intent.

- **Author:** [MatthewBonanni](https://github.com/MatthewBonanni)

  - `tests/v1/attention/test_sparse_mla_backends.py`
  - `vllm/v1/attention/backends/mla/flashmla_sparse.py`

### Summary

**What changed and why**  
Fixes a CUDA illegal memory access in the HiSparse FP8 sparse decode path. The hot cache was passed to FlashMLA as 64-token pages, but HiSparse resolves top-k to flat-row indices over a strided cache (e.g. 271-row stride with fp8_ds_mla), so FlashMLA's page*64+offset decoding addressed wrong rows and ran past the cache end. The fix passes the hot cache as a flat row view ([rows, 1, row_bytes]) via flat_kv_row_view, matching the BF16 HiSparse path and other sparse MLA backends, and the test is updated to use an interleaved hot cache and verify each index reaches the resolved row.

**Technical impact**  
Changes the kv_c_and_k_pe_cache layout handed to the FP8 FlashMLA sparse decode kernel from 64-row pages to single-row pages, so topk_indices are interpreted as flat row indices consistent with HiSparse's block*block_stride_rows+offset resolution. This aligns the FP8 path with the existing BF16 and other sparse MLA backends. Reported kernel timing is essentially unchanged (72.4 vs 72.8 us) and outputs match bit for bit.

**Potential risks**  
The fix relies on the V32 layout where each row carries its own scales, so correctness depends on that layout assumption holding for all HiSparse FP8 configurations. SM90 was not exercised in testing, only SM100/B200, so behavior on Hopper is unverified. The unit test uses a stub kernel and CPU tensors, so it validates index-to-row mapping but not real kernel behavior. Performance impact of page size 1 on other shapes is not broadly benchmarked.

**Key insights**  
The root cause was a layout contract mismatch between HiSparse's flat-row index resolution and FlashMLA's page-based addressing, which only surfaced with interleaved strided caches. The updated test now encodes the interleaving and asserts the exact resolved rows, which would have caught the bug (fails on main with IndexError). End-to-end GSM8K results show the crash is resolved and accuracy matches the non-HiSparse reference, including under forced host offload.

  - `vllm/multimodal/video_decoders/deepstream.py`
  - `vllm/multimodal/video_decoders/opencv.py`
  - `vllm/multimodal/video_decoders/pynvvideocodec.py`
  - `vllm/multimodal/video_decoders/torchcodec.py`

### Summary

**What changed and why**  
This PR fixes a security/DoS gap in the per-request decoded-media budget (VLLM_MAX_MEDIA_REQUEST_DECODE_BYTES). Previously video frames were only charged after the loader fully decoded the sampled clip into memory, so an oversized sample could allocate gigabytes before being rejected. The change introduces a SampledFramesCharge context variable installed by VideoMediaIO during loader execution, and each decoder (OpenCV, TorchCodec, PyNvVideoCodec, DeepStream) now calls charge_sampled_frames after computing frame indices but before decoding. Loaders that duplicate frames (EmbeddingGemma2, GLM, Clef Omni) call charge_frame_copies before allocating copies, and VideoMediaIO charges any residual amount after the loader returns to cover custom loaders.

**Technical impact**  
Behavior changes: oversized video samples are now rejected before frame allocation, dramatically reducing peak RSS (e.g. 6840 MiB to 117 MiB in the reported reproducer) and latency. The public loader interface and backend kwargs validation are unchanged thanks to the context variable. Videos within budget decode as before and are charged exactly once, including repeated frames. The docs security table is updated to reflect the new charging semantics. New tests cover rejection-before-decode, single-charge accounting, and repeated-frame rejection.

**Potential risks**  
The PyNvVideoCodec and DeepStream paths require GPU decoders and were not exercised in the author's environment, so their one-line changes are unverified. The context-variable approach relies on all decoders calling the helper; custom loaders that bypass decode_video fall back to post-hoc charging, which still bounds retained memory but not peak. Charging is computed as RGB uint8 from container dimensions, so clips with partially failing frames are now charged for requested frames rather than decoded ones, a slight over-charge. The 18 pre-existing test failures in the author's environment (missing av, old GPU driver, no network) mean full CI validation of the video paths is not demonstrated here.

**Key insights**  
The root cause was a check-after-decode ordering bug: the budget bounded what was kept, not what was allocated, leaving peak memory unbounded up to tens of GB per request. Using a ContextVar to thread the charge callback avoids invasive interface changes and keeps backend kwargs validation intact. The repeated-frames case (fps above clip frame rate causing many copies of few decoded frames) is a subtle secondary amplification vector that the charge_frame_copies hook correctly addresses. The tracemalloc-based tests are a good pattern for asserting pre-allocation rejection rather than just post-hoc accounting.

## 10. [[ROCm][CI] Install the AITER nightly's own requirements in the test image](https://github.com/vllm-project/vllm/pull/67986)


### Base Information

- **PR Number:** #67986
- **Author:** [josh-schell-amd](https://github.com/josh-schell-amd)

- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/67986/files) (1):**
  - `docker/Dockerfile.rocm`

### Summary

**What changed and why**  
The ROCm test image installs the AITER nightly wheel with --no-deps, so requirements the nightly raised past the stack's AITER release (e.g. flydsl 0.5.0 vs 0.4.2) are never installed, causing import aiter to fail and nearly all AITER tests to fail. This PR adds a step in Dockerfile.rocm that reads the installed wheel's requirements via importlib.metadata, installs them constrained by /etc/rocm-constraints.txt, logs which stack packages changed, and fails the build if pip check still reports an unmet amd-aiter requirement.

**Technical impact**  
Changes the AITER nightly test image build path only; builds without an AITER nightly ($spec empty) are unaffected. Stack-owned packages (torch, triton, torchaudio, torchvision, pybind11) are pinned by the constraints file so they cannot move, while non-pinned transitive requirements like flydsl follow the nightly's pin. The build now fails fast on incompatible nightly requirements instead of producing an image where every AITER test fails at runtime.

**Potential risks**  
If a future nightly requires a torch/triton version outside the stack constraints, the image build will fail rather than degrade at runtime, which could block the nightly pipeline until the stack is bumped. The pip check grep pattern '^amd[-_]aiter ' is somewhat brittle and depends on pip check output formatting. Installing requirements could still pull in unexpected transitive dependencies not covered by constraints, and the diff-based change logging relies on pip list output stability. Validation is limited to CI build links; no unit tests cover the shell logic.

**Key insights**  
The fix correctly separates stack-owned dependencies (constrained) from AITER-owned ones (allowed to move), which is the right ownership model for a nightly that answers whether vLLM can bump AITER. Reading requirements from the installed wheel avoids re-downloading the 712 MB wheel and preserves AITER_SPEC overrides. Logging changed stack packages improves traceability of FlyDSL-related failures. The change is small and localized but behaviorally significant, so it is SUBSTANTIAL.
