## 1. [[Bugfix][Multimodal] Fill the Qwen2-VL video budget up to the context length](https://github.com/vllm-project/vllm/pull/66432)


### Base Information

- **PR Number:** #66432
- **Author:** [subhashpolisetti](https://github.com/subhashpolisetti)
- **Merged By:** [DarkLight1337](https://github.com/DarkLight1337)
- **Merged time:** 2026-11-08 23:38:04
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/66432/files) (4):**
  - `docs/configuration/conserving_memory.md`
  - `tests/models/multimodal/generation/test_qwen2_5_vl.py`
  - `tests/models/multimodal/processing/test_qwen2_vl.py`
  - `vllm/model_executor/models/qwen2_vl.py`

### Summary

**What changed and why**  
Fixes a Qwen2-VL-family bug where the video token budget only grew in whole full-size frame steps (e.g. 16,384 tokens), causing videos that fit max_model_len to be rejected with 'exceeds the pre-allocated encoder cache size'. Adds get_video_size_and_frames_with_most_features, which spreads the budget across multiple temporal steps with a smaller per-step image size, and uses that shape for both get_max_video_tokens and the profiling dummy so the budget matches the profiled dummy. Includes regression tests and a docs note.

**Technical impact**  
Changes memory profiling behavior for Qwen2-VL, Qwen2.5-VL, EXAONE 4.5 and OpenPangu-VL: at contexts where the budget grows, the profiled dummy video is larger, increasing peak activation memory and reducing KV cache (e.g. 182,272 to 135,168 tokens at max_model_len=40000 on A10). Videos that previously failed validation are now served. Size-hinted and pruning configurations intentionally keep main's shape and budget, and Qwen3-VL / encoder CUDA graph frame sizing are unchanged.

**Potential risks**  
The KV cache reduction at affected contexts is a real capacity regression for users who do not need large videos, mitigated only by limit_mm_per_prompt video hints. The new shape-selection logic is intricate (step counting, min/max pixel bounds, hint clipping, pruning bypass) and could have edge cases not covered by the 549+132 setting sweep, especially with unusual min_pixels/max_pixels combinations or num_frames-only hints. OpenPangu-VL was not actually run due to transformers version constraints, and the new LLM test is skipped on CPU, so CI coverage depends on GPU runners.

**Key insights**  
The core insight is that the budget must equal the profiled dummy's token count, otherwise admitted videos can exceed profiled encoder memory; this is why the PR rejects the simpler budget=seq_len approach used for Qwen2.5-Omni (whose 768-token steps make the gap small). Pruning and size hints deliberately fall back to main's shape because placeholders and hint clipping make a larger budget unsafe. The tradeoff between admitting larger videos and preserving KV cache is explicit and documented, with hints as the escape hatch.

  - `vllm/v1/attention/backends/rocm_aiter_unified_attn.py`

### Summary

**What changed and why**  
Opts the ROCM_AITER_UNIFIED_ATTN metadata builder into the fused multi-step draft decode path by setting supports_draft_decode_metadata_update = True and adding a no-op update_draft_decode_metadata, mirroring the Triton and FlashInfer trtllm-gen backends. This lets EAGLE/MTP drafters run all draft decode steps in one CUDA graph instead of rebuilding metadata and replaying a graph per step. Tests in test_triton_attn_metadata_builder.py are extended to cover the ROCm builder when running on ROCm.

**Technical impact**  
Changes runtime behavior for ROCM_AITER_UNIFIED_ATTN speculative decoding: draft decode now uses the fused loop, eliminating per-step metadata rebuilds and inter-step idle gaps. The builder's metadata only holds views of persistent buffers (seq_lens, block_table, slot_mapping, query_start_loc) plus step-invariant scalars, so the no-op update is claimed safe. Measured draft loop time drops 16-19% at k=3 and 6-8% at k=7, with no end-to-end throughput or accuracy regression claimed.

**Potential risks**  
Correctness hinges on the audit that build() writes no builder-owned tensor read by a captured graph and that all step-dependent fields alias persistent buffers; if any future change stages data in a builder-owned tensor, the no-op update would silently produce stale metadata. ROCM_ATTN shares build() but is deliberately excluded, so the opt-in is backend-specific. The shared test file has not been run on ROCm outside CI, and the concurrency-32 serving numbers are confounded by instance-to-instance variation, so the small negative delta is not fully explained.

**Key insights**  
The change is small and well-scoped, gated behind a single backend flag, and backed by detailed profiling, accuracy, and sync-check evidence. The main residual risk is the implicit contract that the builder never writes builder-owned tensors during build(), which the added tests attempt to enforce. Reviewers should confirm the test parametrization correctly skips ROCm imports on non-ROCm builds and that the no-op update remains valid as the builder evolves.

  - `tests/v1/kv_connector/nixl_integration/run_accuracy_test.sh`

### Summary

**What changed and why**  
The PR shards the NixlConnector PD accuracy core CI step across 3 Buildkite parallel jobs (parallelism: 3, timeout 90->45 min) and round-robins configs by BUILDKITE_PARALLEL_JOB in config_sweep_accuracy_core_test.sh, falling back to running all configs when the Buildkite vars are absent. It also introduces a DECODER_CUDAGRAPH knob (default 0 in run_accuracy_test.sh, set to 1 in the core sweep) that swaps --enforce-eager for VLLM_USE_BREAKABLE_CUDAGRAPH=1 plus -cc.cudagraph_mode=FULL_DECODE_ONLY on decoders, while prefillers stay eager. The goal is to cut the ~65 min per-PR step wall time.

**Technical impact**  
Behavior changes in CI config and test harness only, not in core vLLM code. Sharding reduces per-job runtime to roughly 20-25 min and lowers the timeout accordingly, while the round-robin logic preserves full coverage across shards and degrades to a single full run locally. Decoder execution mode changes for this sweep only, since other callers keep DECODER_CUDAGRAPH=0 and thus retain --enforce-eager; the eager-arg construction was refactored into DECODER_EAGER_ARG/DECODER_CUDAGRAPH_ENV variables.

**Potential risks**  
Decode-only CUDA graphs may surface issues under DP-EP decode (deepseek-vl2-tiny at DP2), sleep/wake, or when two engines share a GPU at 0.35 utilization, and graph memory could cause OOM in those configs. Accuracy may drift slightly versus eager, though the 0.05 threshold provides margin. The sharding assumes BUILDKITE_PARALLEL_JOB_COUNT matches the YAML parallelism: 3; a mismatch would silently skip or duplicate configs. The 45 min timeout is tighter and could flake if a shard runs long.

**Key insights**  
The PR's own analysis shows decode graphs barely reduce total time because the GSM8K eval is bound by NIXL KV transfer on L4 (no P2P, ~6 MB/s median, ~20 s per transfer), so sharding is the real lever. The design correctly limits graphs to decoders (uniform query length 1 after full KV load) and keeps prefillers eager since their multi-thousand-token batches exceed the 512-token capture limit. Per-shard timings are still pending from the next CI run, so the timeout reduction is not yet fully validated.

  - `vllm/config/kv_transfer.py`
  - `vllm/config/vllm.py`
  - `vllm/utils/vmm_driver.py`

### Summary

**What changed and why**  
Fixes a silent performance regression where same-host NIXL P/D transfers moved KV over TCP instead of NVLink after the extensible KV cache became default. The fix makes CudaVmmDriver request a CU_MEM_HANDLE_TYPE_FABRIC handle when the device supports it and an IMEX channel opens, with a fallback to non-FABRIC allocation on NOT_PERMITTED/NOT_SUPPORTED, and makes _resolve_extensible_kv_cache keep the feature off by default for NIXL on device memory without an IMEX channel. Adds tests, docs, and a refactor of kv_transfer connector helpers.

**Technical impact**  
Driver-mapped KV cache memory can now be exported via UCX cuda_ipc, restoring NVLink transport for same-host NIXL (claimed 9.9 s to ~24 ms per transfer). Behavior changes for users: extensible KV cache is now disabled by default when NIXL uses device memory and no IMEX channel is present, with an explicit opt-in honored via warning. The kv_transfer refactor introduces uses_nixl_on_device_memory and _connector_children helpers, preserving registers_kv_cache_memory semantics.

**Potential risks**  
The root-cause analysis is inferred from UCX protocol tables and library strings rather than UCX source, so the mechanism could be incomplete. The IMEX channel detection relies on opening /dev/nvidia-caps-imex-channels/channel* which may behave differently under container device cgroups or unusual permissions. The FABRIC fallback only triggers on specific error codes (800/801); other failures could still surface. Changing the default for extensible KV cache with NIXL could surprise users who relied on prior default behavior, though a warning is logged.

**Key insights**  
The regression was silent because accuracy was unaffected, so the existing NIXL accuracy check would not catch it; transport-level validation (UCX_PROTO_INFO) was needed. The fix correctly notes that the FABRIC device attribute alone is insufficient and requires an actual openable IMEX channel. The fallback path prevents devices that reject FABRIC from being unable to allocate the cache at all, which is a good defensive design.

### Summary

**What changed and why**  
Migrates Gemma (v1) and StableLM from native vLLM implementations to the Transformers modeling backend by deleting gemma.py and stablelm.py, updating registry.py to route both to TransformersForCausalLM, and moving them to the Transformers-backend section of supported_models.md. It also adjusts paligemma.py to call the language model directly and changes base.py's encoder-attention detection to use model_config.is_multimodal_model instead of comparing text configs, so PaliGemma's bidirectional Gemma text config still works.

**Technical impact**  
Behavior now depends on the Transformers backend for these two architectures, including weight loading, quantization hooks, and attention selection. The base.py change affects attention class selection for all Transformers-backend models with non-causal layers, not just PaliGemma, so it is a shared-code path. The paligemma.py forward change alters how the language model is invoked, which must match the new backend's module structure.

**Potential risks**  
The base.py heuristic change could misclassify other multimodal or encoder-like models that previously relied on the text-config comparison, potentially selecting EncoderOnlyAttention incorrectly or failing to select it. Removing native implementations drops any native-only features or quant paths not covered by the Transformers backend. The deleted Gemma test for checkpoint LM head override removes coverage of tied-embedding untying behavior. Validation is limited to B200 and a specific Transformers version, so other hardware, quantization configs, and PaliGemma variants carry residual risk.

**Key insights**
