### Summary

**What changed and why**  
Moved the atomic_writer context manager out of model_loader/weight_utils.py into a new lightweight vllm/utils/file_utils.py, and updated models/registry.py to import it directly instead of lazily importing weight_utils inside _save_modelinfo_to_cache. This avoids pulling the model-loader/quantization/distributed stack (~943 modules, ~1s) into the API-server process on a model-info cache miss. weight_utils re-exports atomic_writer for backward compatibility, and new tests cover the atomic replace/error paths plus an import-boundary check in a clean subprocess.

**Technical impact**  
Reduces cold-start import cost and module count in the parent/API-server process when the model-info cache is empty, which is the common Docker case. The atomic_writer implementation is byte-for-byte equivalent (same tempfile-in-same-dir + os.replace + cleanup semantics), so behavior is preserved. The re-export keeps existing callers of weight_utils.atomic_writer working, and the new subprocess-based test enforces the import boundary going forward.

**Potential risks**  
The import-boundary test relies on a hardcoded FORBIDDEN module list and a fresh interpreter, so it could become brittle if registry internals or module paths change; it also depends on VLLM_CACHE_ROOT being empty and on subprocess behavior. The re-export via 'import ... as atomic_writer' is fine but any future refactor must keep it. Minor: file_utils still imports vllm.logger, so it is not strictly stdlib-only, though that is far lighter than the model loader.

**Key insights**  
The fix is a targeted dependency-inversion: extracting a stdlib-only helper to break an accidental heavy import chain triggered on a hot startup path. The added tests are well-designed, using a clean subprocess to genuinely verify the import boundary rather than relying on the test process's already-loaded modules, and covering the previously untested atomic-writer success and error paths.

**What changed and why**  
Removes the legacy EAGLE/EAGLE3/MTP trailing-block drop and the disable_eagle_block_drop / disable_lookahead_block_hashes options, making lookahead block hashes the only behavior. The drop's compensating logic (proof margins, convergence guards, Mamba checkpoint backoff, extra SWA retention, draft-group tagging, per-connector copies) is replaced by a single get_reusable_prefix_length(N, L, alignment) helper, and num_hash_lookahead_tokens is now derived from a new SpeculatorConfig.draft_kv_depends_on_lookahead flag. Connectors that match external hits by token IDs (Example, HF3FS, LMCache, FlexKV) now report supports_lookahead_block_hashes() == False, which only logs a warning instead of disabling lookahead.

**Technical impact**  
Touches 68 files across config, KV cache core/coordinator, scheduler, planning, Mamba checkpointing, and five KV connectors, deleting roughly 3000 lines of drop-aware compensation. Prefix hits now keep one more block per question for EAGLE/MTP, and the shared helper centralizes hit-bound arithmetic so core and connectors cannot drift. Several behavior changes are user-visible: removed options fail config validation, Gemma4 MTP uses plain hashes (L=0), the multi-module MTP scheduler_block_size >= k check is gone, UMBP no longer rejects non-prefix-cacheable draft groups, and chunked local attention with target-hidden-state speculation now follows the VLLM_ALLOW_CHUNKED_LOCAL_ATTN_WITH_HYBRID_KV_CACHE opt-in.

**Potential risks**  
The change is a cross-cutting semantic shift in what a cache-hit length means, so any missed drop-aware compensation could silently corrupt reused draft KV or reduce acceptance; the PR mitigates this with extensive accuracy/acceptance and prefix-hit correctness validation, but the surface is large. External KV stores and consumers of KV cache events must be on the same lookahead setting, and connectors reporting False now only warn, so operators may miss degraded spec-decode acceptance. The replay-boundary change (keeping both resend and continuation positions) and the removed MTP block-size check are behavioral changes beyond strictly removing the drop. The seven commits only build as a complete series, which complicates bisection and partial reverts.

**Key insights**  
Lookahead hashes make a matched block self-proving because the hash covers the next L tokens the drafter reads, so the trailing-block drop and all its compensations become unnecessary. The design cleanly separates the drafter's prefill lookahead from its hash lookahead via draft_kv_depends_on_lookahead, letting Gemma4 MTP and DFlash/DSpark opt out. The validation methodology is strong: LongBench-v2 for the changed hit path, short-output acceptance to isolate post-hit draft KV reuse, and a positive control that catches trailing-block reuse without lookahead. The main review focus should be the new get_reusable_prefix_length call sites and the connector warning path.

  - `vllm/v1/executor/abstract.py`
  - `vllm/v1/worker/worker_base.py`

### Summary

**What changed and why**  
Fixes a pipeline-parallel bug in hybrid Mamba/attention models where stages without attention layers kept the default Mamba block size (64) while other stages used the aligned attention block size, causing prefix-cache failures and CPU offload startup errors. The engine core now resolves a single Mamba block size from all workers' KV cache specs via resolve_mamba_block_size, stores it in its cache config, and pushes it to every worker through a new set_mamba_block_size RPC before re-collecting specs. A regression test exercises a Mamba-only first stage at PP=2.

**Technical impact**  
Adds a new collective RPC (set_mamba_block_size) to Executor and WorkerBase, plus a second get_kv_cache_layer_configs round-trip when a mismatch is detected. The resolved size is the GCD of all prefix-cacheable attention block sizes, matching PP=1 behavior. When specs already agree (PP=1, no Mamba layers, or all stages with attention), behavior is unchanged and no extra RPC round-trip occurs. Out-of-tree workers inheriting WorkerBase pick up the new method automatically.

**Potential risks**  
The extra spec-collection round-trip only triggers on mismatch, but any out-of-tree worker that overrides get_kv_cache_layer_configs or bypasses WorkerBase could miss the new RPC. The GCD computation assumes attention block sizes are multiples of the desired Mamba size; unusual backend block sizes could yield a smaller-than-expected value. The Mamba page on attention-less stages remains unpadded, which is intentional but relies on the engine core taking the smallest block count across workers. Validation is thorough (PP=1/2/4/8, offloading, GSM8K, existing tests) but limited to a few hybrid models and B300 hardware.

**Key insights**  
The root cause is a scope mismatch: Mamba block size is a whole-model property aligned by the scheduler, but was being derived per-worker from locally-held attention layers. Resolving it in the engine core where all specs converge is the architecturally correct fix and is narrower than the alternative in #51764, which would have overwritten all cache config fields from one stage. The regression test's assertion on identical cached-token counts across PP sizes is a strong, deterministic check of prefix-hash granularity.
