## 1. [[Perf][DSv4] Process 4 heads per program in fused_inv_rope_fp8_quant](https://github.com/vllm-project/vllm/pull/63540)


### Base Information

- **PR Number:** #63540
- **Author:** [guanzheh](https://github.com/guanzheh)
- **Merged By:** [zyongye](https://github.com/zyongye)
- **Merged time:** 2026-11-06 23:45:58
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/63540/files) (2):**
  - `tests/kernels/test_fused_inv_rope_fp8_quant.py`
  - `vllm/models/deepseek_v4/common/ops/fused_inv_rope_fp8_quant.py`

### Summary

**What changed and why**  
Optimizes the fused_inv_rope_fp8_quant Triton kernel by having each program process 4 heads of one output group instead of one (token, head), swapping RoPE pairs in registers via tl.split/tl.join instead of re-loading partners, and selecting num_warps from grid size (4 below 2048 programs, else 1). The goal is to raise bytes in flight per program and fix the latency-bound behavior that capped throughput at ~1.5 TB/s on B200. A new H24_G4 test case exercises the gcd fallback to 2 heads per program.

**Technical impact**  
Kernel-level change to a DeepSeek-V4 op with no interface change; callers are unaffected. Reported speedups are large for prefill (3.53x on B200 at 16k tokens, 2.15x H100, 3.04x H200) and model forward prefill/mixed batches improve ~6%, while decode is essentially unchanged (up to 0.3 us slower per call). Outputs are claimed bitwise identical to main, and num_warps is added to CompileKey and warmed with WarmupChoices(1, 4) so both variants compile at startup.

**Potential risks**  
num_warps now depends on batch size, which could interact with batch-invariance guarantees, though the author argues each program handles one token and outputs are bitwise identical across configs. Validation is B200-centric: forward, serving and gsm8k were only run on B200, and V4.1 (quant group 32) and XPU paths were not timed. Hopper is not covered in CI, and the 5 test_einsum_end_to_end failures on H100/H200 are pre-existing but still reduce confidence there. The register-based RoPE rewrite is subtle and relies on tl.split/tl.join semantics matching the prior load-based math exactly.

**Key insights**  
The root cause is well diagnosed: one warp per (token, head) moves only 1.5 KiB, leaving HBM underutilized and making the kernel latency-bound (same time on H100 and H200 despite more H200 bandwidth). The PR is thorough in benchmarking (full BLOCK_H x num_warps sweeps across three GPUs, bitwise comparisons, gsm8k, forward and serving), and the gcd-based BLOCK_H keeps generality for other head/group configs. Main residual gaps are lack of XPU/V4.1 timing and Hopper CI coverage, which reviewers should weigh against the strong B200 evidence.

**What changed and why**  
Rewrites the CPU kernel fused_sigmoid_gating_delta_rule_update_spec_kernel_impl to parallelize over (sequence, value head, 64-column block) instead of (sequence, value head), keeping each state block in fp32 registers/scratch across all draft tokens so the cache slot is read once per step. **Technical impact**  
Changes the numerical summation order and keeps the running state in fp32 between draft tokens within a step, so outputs are not bit-identical to the previous kernel. The diff is truncated, so the full store path and edge handling for the value-dim tail could not be fully reviewed.

**Key insights**  
The main win comes from restructuring the loop to load each state block once and reuse it across draft tokens, eliminating redundant reads, combined with non-temporal stores to avoid read-for-ownership on write-only intermediate states. The PR is well-instrumented with a dedicated benchmark that models cold state via a large rotating footprint, and the test suite covers the tricky cases (zero accepted tokens, empty rows, value-dim tails, unaligned state). ### Summary

**What changed and why**  
Level-2 sleep previously discarded the entire weights pool, forcing non-parameter state (buffers, closures, pointer tables, LoRA/model state) to be rescued site-by-site. This PR changes the rule so level 2 discards only allocations whose live blocks all start at the storage addresses of parameters the weight update rewrites, keeping everything else at the same address. It adds a `discardable` argument to `CuMemAllocator.sleep`/`XpuMemAllocator.sleep` and replaces `SleepModeBackend.suspend(level)` with `suspend(discardable)`, and removes the now-redundant runtime-pool workarounds and CPU buffer/parameter backups.

**Technical impact**  
The allocator gains a shared `discardable_allocations` helper that inspects pool snapshots and only discards a weights allocation when every live block address is in the discardable set, so a mismatch costs host memory rather than lost state. `Worker.sleep(level=2)` computes discardable storage from `_discardable_parameters`, which subtracts `sleep_preserve_parameter_names` matches, and preserved parameters now flow through the allocator backup (pinned when PIN_MEMORY is on) instead of a separate CPU save/restore. This is a plugin interface change: out-of-tree sleep-mode backends must adopt the new `suspend(discardable)` signature.

**Potential risks**  
The change alters a public-ish backend interface and sleep semantics, so external backends and callers relying on level-2 discarding all weights will break or behave differently. Host memory usage rises notably (e.g. DeepSeek-V4.1-Flash 0.97 to 2.35 GiB per rank), and allocations mixing parameters with other tensors are backed up whole. Weight-derived tensors not refreshed by post-load processing now retain stale values instead of garbage, a separate bug class. XPU, full Kimi-K3, Inkling, and MiniMax-M3 verifier-level runs were not executed, and the Beam hang cause is undiagnosed.

**Key insights**  
The PR replaces fragile per-site fixes with a single allocator-level invariant, which is a cleaner design and is backed by extensive validation (NCCL verifier, disk reload, LoRA, ROCm) showing main's failures (GSM8K to 0, illegal address, hang) are resolved. The negative control (discarding the whole weights pool) differing in 4 of 4 cases confirms the test actually exercises the new behavior.
