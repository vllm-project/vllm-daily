  - `tests/models/multimodal/test_mimo_v2_omni.py`
  - `vllm/model_executor/models/mimo_v2_omni.py`

### Summary

**What changed and why**  
Fixes a correctness bug in MiMo-V2.6 vision attention when using --mm-encoder-tp-mode data. Under data parallel the encoder runs fully on every rank, but the code collapsed tp_size to 1 while retaining the process's tensor-parallel rank, so on ranks > 0 the per-head sink slice started past the end of the head range and sinks were silently dropped. The fix collapses tp_rank to 0 alongside the size and advertises supports_encoder_tp_data so the config accepts the data mode.

**Technical impact**  
Changes MiMoVisionAttention rank handling so data-parallel encoders keep all sinks on every rank, while weights mode continues to shard sinks per rank. Adds a model capability flag enabling the data TP mode, plus new unit tests covering data-parallel ranks, weights-mode slicing, and the advertised flag, and wires the test file into the AMD CI pipeline.

**Potential risks**  
The fix relies on the assumption that data-parallel encoders always run the full head set on every rank; if any future path partially shards heads under data mode, collapsing the rank could mask issues. Tests stub parallel_state and multimodal config, so they validate logic but not real multi-rank execution; end-to-end validation was done manually at TP4. CI addition to AMD yaml could increase pipeline runtime.

**Key insights**  
The root cause is a mismatch between collapsing the world size and not collapsing the rank, a subtle bug that silently degraded output rather than crashing. The tests are well-targeted, using a real MultiModalConfig with only the rank stubbed, and explicitly asserting weights mode still slices correctly to guard against over-correction. The PR is honest that it is a correctness fix with no performance claim.

**What changed and why**  
Adds a new Triton kernel (ops/norm_mxfp8.py) that fuses Gemma RMSNorm (optionally with residual add) and MXFP8 quantization into a single pass, emitting E4M3 data plus UE8M0 scales in the 128x4 swizzled layout, or plain BF16 output. **Technical impact**  
Changes the numerical path for MiniMax-M3 NVIDIA input/final/MTP norms and the QKV-projection activation quantization, replacing a norm-then-quantize chain with a single fused kernel. Introduces PDL usage (gdc_wait/gdc_launch_dependents), a do_not_specialize token count to limit to two compiled variants, and a swizzled scale buffer with zeroed padding rows. Behavior is gated on kernel type and quant key, so unsupported consumers fall back to BF16.

**Potential risks**

The hand-rolled UE8M0 exponent bump and E4M3 saturation logic is subtle and correctness depends on the claimed exhaustive BF16 validation, which is not fully reproduced in the added tests. PDL correctness relies on every CTA calling gdc_wait before any global access, including padding-row stores, which is easy to break in future edits. The kernel asserts 2-D row-contiguous inputs and only supports H divisible by 32 for scale grouping; edge cases like M=0 and non-power-of-two H are handled but lightly tested. GSM8K shows a small 0.002 accuracy delta attributed to noise.

**Key insights**  
This is a well-scoped, model-local optimization with strong microbenchmark and E2E evidence, and the test suite meaningfully checks bitwise residual/scale parity and bounded code distance rather than just tolerance. The main review focus should be the dispatch helper's robustness to wrapper/kernel changes and the correctness of the UE8M0/E4M3 conversion under adversarial inputs. ## 11. [[Bugfix][ROCm] Use 64-bit row offsets in the RDNA hybrid W4A16 GEMM](https://github.com/vllm-project/vllm/pull/64614)

  - `vllm/model_executor/kernels/linear/mixed_precision/rdna_hybrid_w4a16.py`

### Summary

**What changed and why**  
The RDNA hybrid W4A16 skinny GEMM kernel (_triton_w4a16_skinny_fmt_kernel) previously computed row offsets with int32 arithmetic, which overflowed once M*K or M*N exceeded 2^31, causing memory faults, hangs, and NaN rows. The fix casts pid_m to int64 so that offs_m and its derived strides (offs_m * stride_am, offs_m * N) are computed in 64-bit. A new parametrized test is added to cover both the output-offset and activation-offset overflow cases.

**Technical impact**  
Widening pid_m to int64 propagates through offs_m and all downstream offset computations, correctly addressing large-M cases without changing the kernel's numerical behavior for normal sizes. The change is minimal and localized to the skinny-format kernel, mirroring the earlier CDNA fix (#63054). The added test is gated on on_gfx1x() since no CI pool covers gfx11/gfx12, so it will not run in standard MI300/MI355 CI.

**Potential risks**
