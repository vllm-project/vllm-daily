## 1. [[Security] Widen int32 pointer arithmetic to int64 in CUDA kernels](https://github.com/vllm-project/vllm/pull/53131)


### Base Information

- **PR Number:** #53131
- **Author:** [jperezdealgaba](https://github.com/jperezdealgaba)
- **Merged By:** [jperezdealgaba](https://github.com/jperezdealgaba)
- **Merged time:** 2026-11-20 23:52:25
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/53131/files) (3):**
  - `csrc/layernorm_kernels.cu`
  - `csrc/layernorm_quant_kernels.cu`
  - `csrc/moe/topk_softmax_kernels.cu`

### Summary

**What changed and why**  
Widens 32-bit pointer offset arithmetic to 64-bit in CUDA kernels (rms_norm_kernel, rms_norm_static_fp8_quant_kernel, both fused_add_rms_norm_static_fp8_quant_kernel specializations, and MoE topk_softmax kernels) by casting blockIdx.x to int64_t before multiplying by stride/hidden_size, and widens host-side input_stride from int to int64_t. This prevents integer overflow at 2^32 that could cause cross-user data disclosure when num_tokens * stride exceeds 32 bits.

**Technical impact**  
Changes kernel signatures (input_stride type) and internal offset types, affecting ABI of these kernels and requiring recompilation. The fix is behavior-preserving for normal sizes but corrects silent overflow for very large token counts. The MoE kernels also change output_row_offset and thread_read_offset from int to int64_t, which is a correctness improvement but touches more code paths than strictly necessary.

**Potential risks**  
The PR description claims coverage of AllSpark W8A16 GEMM kernels but the diff only shows 3 files (layernorm_kernels.cu, layernorm_quant_kernels.cu, topk_softmax_kernels.cu) — allspark_qgemm_w8a16.cu is not in the diff, suggesting incomplete coverage or a mismatch between description and changes. Test plan items for existing LayerNorm/MoE tests and CI CUDA build are unchecked, so correctness is unverified. Widening input_stride to int64_t changes kernel ABI and could affect any external callers or other translation units that declare these kernels.

**Key insights**  
The fix follows an established pattern and is directionally correct, but the diff does not match the stated scope (AllSpark kernels missing). The unchecked test plan is a significant gap for a security fix. Reviewers should verify all claimed kernels are actually patched, confirm no other 32-bit blockIdx.x multiplications remain in these files, and ensure CI CUDA builds and kernel tests pass before merge.

## 2. [[Bugfix][Multimodal] Convert PIL video frames to RGB like PIL images](https://github.com/vllm-project/vllm/pull/69089)


### Base Information

- **PR Number:** #69089
- **Author:** [yarikama](https://github.com/yarikama)
- **Merged By:** [Isotr0py](https://github.com/Isotr0py)
- **Merged time:** 2026-11-20 22:49:12
- **Type:** `SUBSTANTIAL`
- **[Changed Files](https://github.com/vllm-project/vllm/pull/69089/files) (2):**
  - `tests/multimodal/test_parse.py`
  - `vllm/multimodal/parse.py`

### Summary

**What changed and why**  
The PR fixes a bug where videos supplied as a list of PIL frames kept each frame's original mode (L, LA, RGBA, P), causing failures in HF processors for models like Qwen3-VL, InternVL3, LLaVA-OneVision and Ovis2.5. It adds a _convert_pil_frames helper in vllm/multimodal/parse.py that applies convert_image_mode(frame, 'RGB') to PIL frames in both the plain list branch and the (frames, metadata) tuple branch of _get_video_with_metadata, mirroring the existing PIL image handling. A parametrized test in tests/multimodal/test_parse.py verifies the conversion across modes and with/without metadata.

**Technical impact**  
Non-RGB PIL video frames are now normalized to RGB before reaching the processor, matching the behavior already applied to PIL images. NumPy and tensor frames pass through untouched, and RGB PIL frames are returned unchanged by convert_image_mode, so existing RGB, NumPy and tensor paths keep identical output and timing. The change is localized to the parser and adds no new dependencies.

**Potential risks**  
Non-RGB PIL frame lists now incur an RGB conversion cost (e.g. ~73 ms vs ~12 ms for 32 L frames at 720p), which is the same work callers previously had to do manually, so it is a latency increase for previously-failing inputs rather than a regression for working ones. EXIF transpose (normalize_image) is intentionally not applied to video frames, which is a deliberate divergence from the image path and could matter if future frame sources carry EXIF. Ovis2.5 behavior changes for RGBA (alpha now composited over white) and P (palette colors now used), which is a correctness improvement but a behavior change for that model.

**Key insights**  
The root cause is a gap left by an earlier PR that added RGB conversion for PIL images but not for PIL video frames, and the resulting errors (e.g. torchcodec ImportError on Qwen) misleadingly point away from the frame mode. The fix reuses the existing convert_image_mode helper, keeping the change minimal and consistent with the image path. Validation is thorough: unit tests, processor-level checks across six models, an end-to-end LLM.generate reproducer, and timing comparisons confirming no regression for RGB/NumPy/tensor inputs.

  - `tests/models/test_vision.py`
  - `vllm/model_executor/models/vision.py`

### Summary

**What changed and why**  
Fixes a bug in run_dp_sharded_mrope_vision_model where data-parallel (mm-encoder-tp-mode data) vision outputs were sized incorrectly for rope_2d encoders like Kimi-K2.5/K2.6. Such encoders temporally pool frames in the patch merger, so each item yields h*w/factor embeddings rather than (t*h*w)/factor; the old code over-allocated rows and shifted every later item's slice. The fix computes per-item output sizes from the spatial grid for rope_2d, uses them for padding, slicing and reordering, and adds unit tests comparing DP output against direct execution.

**Technical impact**  
Changes output sizing, padding length (max_len_per_rank now derived from per-rank output lengths rather than grouped input lengths), and per-rank slicing in the DP sharded vision path. Behavior for mrope encoders (e.g. Qwen-VL) is preserved since patches_per_output_image falls back to the original formula. Only host-side sizes are used, so no added CPU/GPU sync. Tests cover single-process and 2-GPU paths.

**Potential risks**  
The new max_len_per_rank computation relies on image_to_tp_rank and cum_gpu_sample_counts being consistent with the actual sharding; any mismatch could cause incorrect padding or slicing. The rope_2d branch assumes all rope_2d encoders pool frames identically (h*w/factor), which may not hold for future rope_2d variants. Test file overlap with PR #68737 requires a trivial rebase. Validation is limited to Kimi and a synthetic model, so other rope_2d encoders are not explicitly exercised.

**Key insights**  
The root cause is a mismatch between input-patch-based sizing and the actual output size for temporally pooling encoders; the fix aligns DP sizing with the encoder CUDA-graph path. The added tests directly compare DP vs non-DP outputs, which is the right validation strategy for sharding bugs. Reviewers should confirm the rope_2d assumption generalizes and that the per-rank length bookkeeping is robust to empty ranks.

### Summary

**What changed and why**  
Adds an early VLLM_BATCH_INVARIANT rejection to the shared _can_use_flashinfer predicate in fused_allreduce_gemma_rms_norm.py, which also gates the standard RMSNorm helper since it imports this predicate. This prevents a batch-size-dependent switch between fused FlashInfer arithmetic and explicit all-reduce + norm, which produced non-bitwise-identical results and broke batch invariance. A two-GPU regression test and an optional B200 nightly CI step are added.

**Technical impact**  
Behavioral change: when VLLM_BATCH_INVARIANT=1, both manual FlashInfer all-reduce + RMSNorm paths (standard and Gemma-style) now fall back to explicit all-reduce + norm, guaranteeing deterministic results across batch sizes. The guard is centralized in one predicate, so both callers are covered while preserving their distinct norm implementations. BI mode loses the fusion performance benefit, which the PR explicitly does not measure.

**Potential risks**  
Performance regression for BI users on these norm paths is unquantified. The new test requires two CUDA GPUs and is only wired into an optional nightly CI step, so it may not run in presubmit and could rot. Validation used a non-repository-pinned environment (FlashInfer 0.7.2.post1/0.7.3, custom PyTorch/CUDA), and the GLM/Qwen reproductions were not rerun on the final split commit, so coverage of other dtypes, topologies, and quantized norm helpers remains unverified.

**Key insights**  
The root cause is that direct eager calls to the manual fused helpers bypass the existing compilation-pass and communicator BI exclusions, so a single early guard in the shared eligibility predicate is the minimal correct fix. The regression test is well-designed: it checks exact equality against an explicit reference and compares a target row alone versus at both ends of a large batch that crosses the workspace limit. The split from #66088 with temporary duplication is a reasonable review strategy, but the duplicate norm changes should be removed promptly after merge.
