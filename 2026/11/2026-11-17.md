### Summary

**What changed and why**  
The PR changes CPU KV offload region allocation so that, in the non-replicated layout, each rank gets its own private CPU region keyed by logical worker rank instead of sharing one replicated region. It adds local_world_size to OffloadingParallelConfig, sizes per-rank page padding against the full CPU budget, and performs aggregate /dev/shm and cgroup headroom checks before any rank allocates. Capacity failures still release workers waiting at the readiness barrier, and replicated/tiered layouts keep their shared behavior.

**Technical impact**  
Behavior changes in CPU offload memory layout and startup: per-rank regions are unlinked immediately after mapping (private=True), no barrier is used for private regions, and num_chunks is reduced to account for per-rank page alignment. The new local_world_size field is threaded through config construction and tests, and check_shm_free_space is invoked once per rank with the aggregate local allocation size. This should reduce startup and pinning time and avoid cross-rank interference in /dev/shm.

**Potential risks**  
The new required local_world_size field is a breaking change for any external constructors of OffloadingParallelConfig not updated here. The aggregate headroom check multiplies by local_world_size, so incorrect local_world_size values could over- or under-estimate memory and cause spurious failures or OOMs. The private-region unlink path and barrier release on capacity failure are subtle concurrency areas; the added tests cover them but multi-node and async_init paths deserve scrutiny. Reduced num_chunks from per-rank padding lowers effective cache capacity, which is logged but may surprise users.

**Key insights**  
The change is well-tested, including regression tests for the readiness barrier on capacity failure and for private region unlink semantics. Historical 4x H200 validation shows large startup and pinning improvements. The design cleanly separates replicated (shared, barriered) from per-rank (private, unlinked) regions via the private flag and SHARED_REGION_PER_RANK class attribute, with tiering opting out.

### Summary

**What changed and why**  
The FS offload tier previously reported a short write(2) (partial block write, typically caused by a full filesystem) as EIO on the C store path and as a bare 'Short write' message on the Python path. This PR introduces a kShortWrite sentinel in csrc/fs_io.cpp and updates both the C and Python store paths to raise a consistent OSError that names the short write and the likely cause (hardware error or full filesystem/ENOSPC). A new parametrized test uses RLIMIT_FSIZE to force a real short write and verifies the message and cleanup on both paths.

**Technical impact**  
Behavioral change limited to the error path: short writes now surface as a descriptive OSError with errno None instead of EIO, while genuine write(2) errors retain their original errno. The success path, single-write-per-block semantics, and on-disk format are unchanged. The C and Python error messages must be kept in sync manually, as noted in code comments.

**Potential risks**  
The duplicated error string across C and Python is a maintenance hazard if one side is edited without the other. Callers that previously inspected errno==EIO to classify failures may need updating, since short writes now have errno None. The test relies on RLIMIT_FSIZE and SIGXFSZ handling, which may behave differently across platforms or CI environments, though it is skipped when the C extension is absent.

**Key insights**  
The fix correctly distinguishes a short write (no errno) from a real write error, improving diagnosability of full-disk conditions on tmpfs-backed tiers. The end-to-end data showing EIO failures dropping from 329 to 0 with 319 short-write messages is strong evidence the change addresses the reported issue. The test's use of RLIMIT_FSIZE to deterministically produce a short write is a clean, portable technique worth reusing.

### Summary

**What changed and why**  
The gfx942 top-512 extension build previously passed the installed topk512_gfx942.cu directly to torch.utils.cpp_extension.load, which hipifies in place and writes a .hip file next to the source. On read-only installs (non-root, arbitrary UID) that write fails, the build fails, and the sparse indexer silently falls back to vLLM ops. The PR copies the source into the extension build directory (via _get_build_directory, honoring TORCH_EXTENSIONS_DIR) using a pid-suffixed temp file plus os.replace, then builds from that copy. A new test asserts the build succeeds and writes nothing beside the installed source.

**Technical impact**  
Restores the gfx942 top-512 kernels for non-root/read-only-install servers, with reported TPOT and interactivity gains and no measurable accuracy change. The atomic os.replace makes concurrent TP-rank builds into a shared cache safe, and since hipify only rewrites on content change, warm-cache rebuilds stay fast. Root servers and the existing fallback-on-failed-build behavior are unchanged.

**Potential risks**  
Relies on the private torch API _get_build_directory, which could change across torch versions. The new test only meaningfully exercises the read-only scenario when run as non-root; CI runs as root, so it mainly guards against regressions in the copy logic rather than the original permission failure. Concurrent-copy correctness depends on os.replace semantics on the target filesystem (e.g., network or overlay mounts).

**Key insights**  
The root cause is that hipify writes beside its input, so the fix is to relocate the build input into a writable build directory rather than to change permissions or fallback logic. The atomic copy pattern mirrors AITER's JIT approach and is validated with a TP8-style concurrent build test. The change is small and well-scoped to the DeepSeek-V4.1 monokernel gfx942 path.

**Key insights**

The PR is well-scoped to ROCm and includes explicit applicability conditions and fallbacks. However, the implicit attribute-based dataflow and the reliance on exact bit-parity of a hand-written Triton quant kernel are the main maintainability and correctness concerns worth scrutinizing in review.

**What changed and why**  
The PR modifies vllm/models/muse_spark/amd/muse_moe_runner.py so that, under TP with the bf16 reduce dtype (where the reduce-dtype copy is a no-op), the MoE finalize processes the whole batch in a single reduce-scatter/all-gather instead of 1024-token chunks. It also adds an in-place all_gather_into_tensor path when no padding is required, and handles non-TP-divisible oversized chunks by routing the small tail through the existing all-reduce + fused finalize path.

**Technical impact**  
Reduces collective launch overhead per MoE layer (62 layers) by collapsing up to eight reduce-scatter/all-gather pairs into one, yielding 14-29% faster finalize above 1024 tokens and 7-8% TTFT improvements plus 2-7% throughput gains at c16/c32. **Potential risks**  
Above 1024 tokens with bf16 reduce dtype, outputs are no longer bitwise identical to the base due to RCCL reduction order (error vs fp32 reference is equivalent, GSM8K shows no significant difference). The in-place all_gather_into_tensor relies on RCCL/NCCL supporting the in-place layout and on out being contiguous; correctness depends on that assumption. The tail-handling logic for non-TP-divisible oversized chunks adds branching complexity that is validated mainly by real-collective tests rather than unit tests, so regressions in edge cases (e.g., 1031, 8191 tokens) would rely on integration coverage.

**Key insights**  
The chunking existed only to bound the fp32 reduce-dtype copy; recognizing that the copy is a no-op under bf16 unlocks a clean single-collective optimization. The PR is well-scoped to one file with no new flags, and the validation is unusually thorough (A/B TTFT, concurrency sweep, isolated finalize benchmarks, GSM8K McNemar, bitwise checks, sync-check). The main trade-off is a deliberate, documented loss of bitwise determinism above 1024 tokens in exchange for measurable performance gains.

  - `tests/v1/attention/test_mla_backends.py`
  - `vllm/v1/attention/backends/mla/flashattn_mla.py`

### Summary

**What changed and why**  
Fixes an OOM in FA3 MLA decode-path batches larger than the largest captured CUDA graph size. Previously _build_decode passed num_splits=0, which FA3 interprets as 'choose', causing it to allocate a large fp32 split-KV accumulator (up to ~6.5 GiB) that was unused at 16 heads. The fix defaults max_num_splits to 1 for eager decode batches beyond captured sizes, while preserving max_num_splits within graphs and 0 when no graphs are captured. A new unit test asserts the transient allocation stays below one split's accumulator size for FULL_AND_PIECEWISE and PIECEWISE modes.

**Technical impact**  
Changes the num_splits selection logic in FlashAttnMLAMetadataBuilder._build_decode. Batches within captured CUDA graph sizes behave as before; larger eager decode batches now use num_splits=1 instead of letting FA3 plan splits. KV cache sizing is unchanged (26766 blocks). Output is bitwise equal at 16 heads per rank; minor bf16 ulp differences at 4 heads where FA3 previously split. Adds a regression test in tests/v1/attention/test_mla_backends.py.

**Potential risks**  
Performance regression for 4-head-per-rank configurations (e.g., TP4) with few requests and long queries over long KV, where FA3 would have split: reported 1.5x-2.7x slower per layer call. The enforce_eager / cudagraph_mode=NONE path still OOMs on the same load and is not addressed. Prefill graphs captured up to 8192 tokens still OOM both before and after. DCP (decode_context_parallel_size > 1) was not tested. The analogous block in flash_attn.py (GQA) is left unchanged.

**Key insights**  
The root cause is a semantic mismatch: num_splits=0 means 'FA3 decides' rather than 'no split', and FA3's varlen planning overestimates splits by assuming one request holds all queries. The extensible KV cache's tight transient-activation reservation exposed this latent waste that gpu_memory_utilization headroom previously masked. A constant KV cache margin was rejected because the buffer scales with batch shape. The fix is minimal and well-validated on the reported config, but the 4-head-per-rank slowdown and the unaddressed eager-mode OOM are notable trade-offs worth tracking.
